# Go 代码设计规范

遵循 Go 极简哲学：高内聚、低耦合、可商用、可测试。拒绝过度设计。

## 核心原则

1. **简洁优先** — 清晰大于巧妙，杜绝复杂封装
2. **单一职责** — 一个类型/函数只做一件事，功能正交
3. **最小导出** — 只暴露必要 API；导出接口，隐藏结构体
4. **组合复用** — 结构体嵌入 + 接口组合，禁止 OO 继承
5. **接口解耦** — 包内定义依赖接口，不绑定实现，支持 Mock
6. **零值可用** — 类型零值应可直接使用；否则隐藏类型 + 导出构造函数
7. **Context 传参** — 所有 IO/阻塞 API 首参数必须是 `context.Context`，禁止将 ctx 存 struct
8. **并发安全契约** — 禁止持锁执行阻塞 IO


- 简单配置用值类型；复杂配置用 Option 模式
- 尽量不要使用全局变量/全局客户端，依赖显式注入
- 进行模块设计审查时，需要梳理代码，对模块设计进行评价。然后发现潜在问题，排查隐患，整理代码，给出优化方案。
- 从 职责过载、过度抽象、重复设计、不合理设计、并发隐患 方面去思考优化方案
- 要求目录设计、文件名称、类型名称、属性名称应该符合行业最佳推荐，方法排序符合阅读习惯，避免出现魔法字符。
- 单一职责的工具包尽量将错误返回给上层，由上层决定是否打印日志。返回错误尽量使用英文。
- 模块new方法叫NewXXX(),不要叫New()
- 注释应该简洁，只描述提供什么功能，不要描述不提供什么功能
- 修改工具模块时，不要引入特异化的改造，保留工具的通用性
