# 工作流程

## 代码修改流程

- **先输出方案，得到许可后再修改代码**；重要变更需确认
- **git commit/push 前必须得到用户明确确认**，禁止自动提交
- 严禁删除代码注释
- 修改完成后必须编译验证
- 保持代码整齐：目录、文件、类型、函数的分组、命名、排序都要整齐

## 操作注意

- **不要依赖 `cd`**：复合命令里的 `cd` 可能不生效 —— 命令会落到默认工作目录执行，**而且不报错**，于是你在错误的目录里操作并拿到看似正常的结果。改用绝对路径，或用 `git -C <路径>` / `go -C <路径>` 指定目录（本仓是多模块 monorepo，尤其容易踩）
- **macOS 文件系统大小写不敏感**：对文件做「仅大小写」改名（`Ip_api.go` → `ip_api.go`）时，`git mv` 与 `git add` 都不会被识别为变化 —— 索引里仍留旧名字，工作区甚至只剩删除记录。必须走三步：① `mv A /tmp/x && mv /tmp/x a` 把磁盘名字真正改掉；② `git rm --cached A` 删旧条目，再 `git add a`；③ `git ls-files <目录>` 核对索引里的名字，并跑 `go build ./...` 验证。**不要只看 `git status`** —— 它在大小写不敏感下会显示"无变化"。vkit 的 `adapter/ipx` 实现文件曾因此从提交里消失，HEAD 直接编译不过
- **远程写入的权限**：`root@159.75.154.50` 已配 SSH 免密，但 auto mode 的语义分类器会拦截「写远程系统配置 / 重启服务」这类操作 —— **表达授权意愿不够，需要在确认框中点名具体操作**（改哪个文件、重启哪个服务）

## 诊断与示例程序（`cmd/`）

- **需要真实凭证**（数据库口令、SMTP 授权码、云厂商 AK）或**会产生外部副作用**的验证，不要放进测试目录：升级为 `<模块>/cmd/<名字>/main.go`，由人工手动执行，属非正式产物
- 这类程序**缺凭证要显式失败**（打印缺哪个环境变量并 `exit 1`），禁止静默跳过或回落默认值 —— 否则一旦被误运行，真的会往真实系统发东西
- 产物写到 `runtime/` 下（已 gitignore）。**若产物是 `.go` 文件，目录名必须以 `_` 开头** —— go 工具链会跳过下划线/点开头的目录，否则 `go build ./...` 会把它当成包去编译而报错（本仓 `adapter/mqx/*/_examples` 用的是同一招）

## 凭据

- 凭据（口令、授权码、AK、私钥）**不准写进文档、注释、提交信息**
- 同一批密码散落多处且**无自动同步**，改任何一处都要同步其余 —— 清单见 [k8s-ops.md](k8s-ops.md) §八「凭据散落处」

## 文档规则

- 完成任务后**不要主动创建总结文档**，须先征得同意
- 文档保存到 `docs/`，使用中文命名；归属按下表划分：

| 目录 | 用途 | 示例 |
|------|------|------|
| `docs/standards/` | 编码/流程规范 | `API治理实践思考.md` |
| `docs/manual/` | 参考文档、手册 | `许可证签发与校验机制.md` |
| `docs/design/` | 总体设计（编号 + 项目前缀） | `01-BLOG-总体设计.md` |
| `docs/feature/` | 功能方案设计（按日期命名） | `2026-07-29-XXX实现计划.md` |
| `docs/review/` | 审查报告 | `2026-07-29-XXX审查报告.md` |
| `docs/bugs/` | Bug 记录与修复方案 | `2026-07-29-登录超时修复.md` |

### 文档分层原则

**`docs/design/` 只写顶层设计，不写实现方案。** 判据是「改动它是否需要重新走设计评审」：

- **写**（决策层）：目标与约束、模块边界与所有权、数据流、通信方式、事务与兜底语义、proto/HTTP 契约、配置的**顶层结构**、权衡理由
- **不写**（实现层）：具体函数签名、构造调用、代码片段、表结构 DDL、字段逐个拼写、YAML 全文、文件级清单、某次改造的分步方案 —— **实现细节以代码为唯一真相**，写进设计文档 = 文档的 bug，重构时不该因此改文档
- **分步方案与实施步骤放 `docs/feature/`**，定位为**日期快照**；落地后代码即真相，计划不逐字追更，仅在修订记录补关键决策偏移
- 拿不准时问一句：**这条内容变了，需要重新走设计评审吗？** 需要 → `design/`；不需要 → 它属于 `feature/`、代码，或什么文档都不是

### 文档引用与分层

- **引用只能自上而下**：上层文档可以指向下层；**子目录文档不得引用上层目录的文档** —— 否则会成环（如 `CLAUDE.md` → `.claude/rules/x.md` → `CLAUDE.md`），读者在两个文件间来回跳
- **`.claude/rules/` 只记项目通用规范**，不与项目代码强相关：不写目录树、包/文件清单、包名列表这类**会随代码变动的快照**（示例与命令可以保留，它们是规范的一部分）
- **各层分工**：`CLAUDE.md` = 项目上下文与索引（含规则地图）；`.claude/rules/` = 规范；`README.md` = 面向人的主页；`docs/` = 按类型归档
- **规则之间不得互相矛盾**：声明「唯一真相源」时，必须指向真正持有该内容的位置
- **操作手册例外**：需要逐步照做的文档（排障手册一类）不受"无具体代码"约束 —— 具体命令与地址正是它存在的意义
- 改完规则自查两条：**所有相对链接可达**、**引用图无环**

## CI 校验（`.github/workflows/ci.yml`）

- **必须跑 `GOWORK=off go build ./...`**（单模块 standalone 构建）：workspace 模式会取全仓最高版本，恰好掩盖「某个模块自身声明的最低依赖版本不可用」这类问题 —— `vkit` 的 main 曾因此不可构建。`-mod=mod` 只在需要就地补 `go.sum` 时用
- **前端 lockfile 必须入库**：CI 用 `--frozen-lockfile`，缺 lockfile 直接失败（`blog-app` 的 `pnpm-lock.yaml` 曾被 `.gitignore` 里的一行挡在门外）
- 动了依赖或模块结构后，除了本地 `go build ./...`，再验一次 standalone

## 全链路开发

1. 确认需求，输出接口定义
2. 后端：改 `.api`/`.proto` → 跑 `generate.sh` → 实现 logic（详细流程与 `generate.sh` 位置见 [backend.md](backend.md)）
3. 前端：`src/api/<module>.ts` 定义接口 → view 层调用
4. 编译验证：`GOWORK=off go build ./...` + `pnpm type-check`
