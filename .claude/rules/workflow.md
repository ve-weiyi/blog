# 工作流程

## 代码修改流程

- 先输出方案，得到许可后修改代码
- **git commit/push 前必须得到用户明确确认**，禁止自动提交
- 严禁删除代码注释
- 修改完成后必须编译验证

## 沟通原则

- 先方案后实施，重要变更需确认
- 保持代码整齐：目录、文件、类型、函数的分组、命名、排序都要整齐

## 文档规则

- 完成任务后**不要主动创建总结文档**，须先征得同意
- 文档保存到 `docs/`，使用中文命名
- **设计文档分层原则**：设计文档（`docs/design/`）只写"改动它需要重新走设计评审"的内容（决策层）——
  - **写**：目标与约束、模块边界/所有权、数据流、通信方式、事务与兜底语义、proto/HTTP 契约、配置的**顶层结构**、权衡理由
  - **不写**：具体函数签名、构造调用、配置字段拼写、YAML 全貌、文件级清单——实现细节以**代码为唯一真相**，出现在设计文档 = 文档的 bug，重构时不该因此改文档
  - **实现计划**（`docs/feature/`）可写具体细节，但定位为**日期快照**；落地后代码即真相，计划不逐字追更，仅在修订记录补关键决策偏移

文档归属按以下目录划分：

| 目录              | 用途                       | 示例                         |
|-------------------|----------------------------|------------------------------|
| `docs/manual/`    | 参考文档、规范、手册       | `许可证签发与校验机制.md`    |
| `docs/review/`    | 审查报告                   | `2026-07-29-XXX审查报告.md`  |
| `docs/feature/`   | 功能方案设计（按日期命名） | `2026-07-29-设计方案.md`     |
| `docs/bugs/`      | Bug 记录与修复方案         | `2026-07-29-登录超时修复.md` |


## 全链路开发

1. 确认需求，输出接口定义
2. 后端：修改 `.api`/`.proto` → 运行 `generate.sh` → 实现 logic（详见 [backend.md](backend.md#api-修改流程)）
3. 前端：`src/api/<module>.ts` 定义接口 → view 层调用
4. 编译验证：`GOWORK=off go build ./...` + `pnpm type-check`
