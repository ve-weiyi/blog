# 架构总览

本文件只写**不随代码变动的分层规则**。仓库有哪些模块、模块内部目录怎么分，**以代码为准** —— 规则里不复制这类清单，否则代码一改规则就成错的。

## 后端分层

```
┌──────────────────────────────────────────────────────┐
│  HTTP 网关层（api）                                     │
│  handler → logic → svc                                │
│  handler: 路由注册 + 参数校验 + 响应封装                  │
│  logic:   业务编排（经 RPC client 调用下游服务）           │
├──────────────────────────────────────────────────────┤
│  RPC 服务层（rpc）                                      │
│  handler → logic → svc                                │
│  handler: gRPC server 方法实现                         │
│  logic:   业务逻辑                                     │
├──────────────────────────────────────────────────────┤
│  应用基础设施（infra）                                   │
│  中间件、拦截器、限流、响应封装、认证 token（应用级）         │
├──────────────────────────────────────────────────────┤
│  公共库（vkit）                                          │
│  adapter / infra / x 三层，判据见下                      │
└──────────────────────────────────────────────────────┘
```

层间约束：

- `handler` 不承载业务逻辑；`logic` 不依赖 HTTP / DB 类型（框架语义不侵入业务层）
- 依赖单向：上层可依赖下层，**下层不得反向依赖上层**

## 公共库（vkit）三层

判据是**面向什么**，不是"用不用标准库"：

| 层 | 面向什么 |
|---|---|
| `adapter/` | **具体外部系统** —— 有地址、凭证、连接 |
| `infra/` | **具体第三方框架** —— 有配置、生命周期 |
| `x/` | 与具体系统无关的**通用能力**（可依赖轻量单一用途的库） |

- 新包先问两句：面向具体外部系统吗？面向具体框架吗？都不是 → `x/`
- 纯本地文件/格式读写（无外部依赖、无状态）→ `x/`
- 依赖单向：`adapter/`、`infra/` 可以依赖 `x/`，**`x/` 不得反向依赖它们**
- 应用基础设施（`blog-cloud/infra`）与公共库的框架封装层（`vkit/infra`）**同名不同物** —— 前者是应用级中间件，后者是库级框架封装
