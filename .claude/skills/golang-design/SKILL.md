# Go 模块设计指导

从五个维度指导 Go 代码的设计与实现。遵循 Go 极简哲学：高内聚、低耦合、可商用、可测试。拒绝过度设计。

## 核心原则

1. **简洁优先** — 清晰大于巧妙，杜绝复杂封装
2. **单一职责** — 一个类型/函数只做一件事，功能正交
3. **最小导出** — 只暴露必要 API，导出接口隐藏结构体
4. **组合复用** — 结构体嵌入 + 接口组合，禁止 OO 继承
5. **接口解耦** — 包内定义依赖接口，不绑定实现，支持 Mock
6. **零值可用** — 类型零值应可直接使用，否则隐藏类型 + 导出构造函数
7. **Context 传参** — 所有 IO/阻塞 API 首参数必须是 `context.Context`，禁止将 ctx 存 struct
8. **并发安全** — 默认不保证并发安全，若安全须在方法注释中显式声明；禁止持锁执行阻塞 IO
9. **依赖注入** — 禁止全局变量/全局客户端，依赖显式注入
10. **分层清晰** — handler 不承载业务逻辑，logic 不依赖 HTTP/DB 类型，框架是细节

## 维度一：包与职责

包的内聚性、类型和函数的职责划分、分层边界。

### 规则

| # | 规则 |
|---|------|
| 1.1 | 包名用一句话说清目的。避开 `util`、`helper`、`common`、`misc` 等无意义名称 |
| 1.2 | 包内文件应共享未导出符号。若不共享，可能是两个包硬塞在一起，应拆分 |
| 1.3 | 一个类型只做一件事。struct 有 5+ 字段且分属不同关注点 → 拆分 |
| 1.4 | 一个函数只做一件事。超过 ~40 行或混合 IO + 业务逻辑 → 拆分。文件内方法排序：构造 → 导出 → 未导出 → 工具函数 |
| 1.5 | 只导出必要 API。不必要的符号一律 `unexported` |
| 1.6 | 分层清晰：handler 不承载业务逻辑；logic 不依赖 HTTP 类型（`*gin.Context`、`*http.Request`）或 DB 类型（`*sql.DB`、`*gorm.DB`） |
| 1.7 | 目录名、类型名、属性名符合行业惯例，避免魔法字符串 |

### 反模式

| 反模式 | 问题 | 做法 |
|--------|------|------|
| "上帝 struct" 承载所有配置 + 连接 + 缓存 | 职责不清，测试困难 | 拆分为独立类型 |
| handler 里写 SQL / 调用 ORM | 越层，换框架全废 | 下沉到 repository 层 |
| 一个包 30+ 文件 | 难导航，编译慢 | 按职责拆包 |
| 导出所有字段和方法 | 实现细节被锁定 | 只导出必要 API |
| logic 层操作 `*gin.Context` / `*http.Request` | HTTP 语义侵入业务层 | logic 只接收 `context.Context` + 普通参数 |

## 维度二：接口与耦合

接口的归属和粒度、依赖方向、抽象层级。

### 规则

| # | 规则 |
|---|------|
| 2.1 | **接口定义在消费方包内**，而非实现方包内。消费方声明自己需要什么 |
| 2.2 | **先有具体类型，再有接口。** 等第二个实现或测试 mock 出现时再抽接口 |
| 2.3 | 构造函数返回**具体类型**，而非接口。例外：隐藏唯一未导出实现时可返回接口 |
| 2.4 | 接口方法数 ≤ 3。更大接口通过组合小接口构成（`type ReadWriteCloser interface { Reader; Writer; Closer }`） |
| 2.5 | 类型嵌入是**组合**，不是继承。导出 struct 嵌入具体类型 → 内部方法全泄漏 |
| 2.6 | 依赖通过接口注入。**禁止全局变量 / 全局客户端** |
| 2.7 | 一个类型所有方法统一用指针 receiver 或值 receiver，禁止混用 |
| 2.8 | 编译期验证接口满足：对非平凡接口使用 `var _ I = (*T)(nil)`，接口签名变更时编译失败立即发现 |

### 反模式

| 反模式 | 问题 | 做法 |
|--------|------|------|
| 只有一个实现却定义了接口 | 无意义的间接层 | 直接用具体类型 |
| 具体类型硬编码在业务逻辑中，无法 mock | 测试被迫启 DB/外部服务 | 定义消费方接口，注入依赖 |
| 实现方定义并返回自己的接口 | 强耦合消费者到实现方包 | 实现方返回具体类型，消费方定义接口 |
| `var DB *sql.DB` 包级全局 | 测试不可并行 | 注入到 Service struct |
| 5+ 方法的接口 | 难以实现和 mock | 拆成小接口并组合 |
| 指针和值 receiver 混用 | 方法集不同，易出错 | 统一 receiver |
| 导出 struct 嵌入具体类型 | 内部方法变公开 API | 用未导出的命名字段 |
| 把 Java/C# 继承模式搬过来 | 强行模拟写出怪物 | 用组合 + 接口 |

## 维度三：并发安全

goroutine 生命周期、锁的使用、channel 设计。

### 原语选择

需要并发或同步时，按场景选对原语：

| 场景 | 原语 | 为什么 |
|------|------|--------|
| 生产者→消费者传值 | Channel | 转移所有权，显式 |
| N 个 goroutine 跑完即忘 | `sync.WaitGroup` | 无需收集错误 |
| 并发 + 收集首个错误 + 取消其余 | `errgroup.WithContext` | 结构化失败处理 |
| 限制并发数 | `errgroup.SetLimit(n)` | 替代手写 worker pool |
| 保护共享字段（短临界区） | `sync.Mutex` / `sync.RWMutex` | 锁内不调 IO |
| 高频读的计数器/标志位 | `sync/atomic`（`atomic.Int64` 等） | 无锁，类型安全 |
| 读多写少的并发 map | `sync.Map` | 裸 map 并发读写直接 crash |
| 一次性初始化 | `sync.Once` | 幂等 setup |
| 去重并发调用（防缓存击穿） | `x/sync/singleflight` | 合并重复请求 |

### 规则

| # | 规则 |
|---|------|
| 3.1 | **每开一个 goroutine 必须知道它怎么退出。** 无法退出 = 泄漏 |
| 3.2 | `context.Context` 是 IO/阻塞 API 的第一个参数，**禁止存 struct 字段** |
| 3.3 | **禁止持锁执行阻塞 IO。** 锁内调 RPC/DB/文件 → 串行化整个服务 |
| 3.4 | 调用方必须能等待 goroutine 完成。首选 `errgroup.WithContext`（自动取消 + 错误收集），其次 `sync.WaitGroup` |
| 3.5 | 长生命周期 `select` 必须包含 `<-ctx.Done()` case |
| 3.6 | 只由发送方关闭 channel；接收方用 `v, ok := <-ch` 或 `for v := range ch` |
| 3.7 | channel 方向标注在签名上：`chan<-` / `<-chan` |
| 3.8 | `wg.Add(1)` 写在 `go` 之前，否则 `Wait` 可能提前返回 |
| 3.9 | 若类型并发安全，必须在方法注释中显式声明 |

### 反模式

| 反模式 | 问题 | 做法 |
|--------|------|------|
| `go func() { for { flush(); time.Sleep(d) } }()` | 无退出信号 | 传 ctx，用 ticker + `select` |
| `time.After` 在热循环中 | 每次分配新 timer | `time.NewTimer` + `Reset` |
| 锁后调 RPC / 写文件 | 串行化服务 | 锁内取数据，释放后调 IO |
| buffer channel 随意给数字 | 掩盖背压 | 默认 0 或 1，更大须注释 |
| `wg.Add(1)` 在 goroutine 里 | Wait 可能提前返回 | Add 在 go 前 |
| 并发读写裸 `map` | 直接 crash | `sync.Map` 或 RWMutex + map |

## 维度四：错误与边界

错误处理模式、API 边界防护、零值设计。

### 规则

| # | 规则 |
|---|------|
| 4.1 | 错误最先判断，成功路径不缩进：`if err != nil { return err }` 后直接继续 |
| 4.2 | 需调用方检查时用 `%w` 包装；故意隐藏内部错误用 `%v`。错误字符串小写开头，不加标点 |
| 4.3 | 每个错误只处理一次：log 或 return，不同时做 |
| 4.4 | **禁止吞错误。** `_ = f()` 必须注释说明理由 |
| 4.5 | API 边界拷贝：存调用方 slice → `make` + `copy`；返回内部 map → 返回快照 |
| 4.6 | 类型零值应可直接使用；否则隐藏类型 + 导出 `New...` 构造函数 |
| 4.7 | 枚举零值明确有意义，否则 `iota + 1`（`StatusUnknown = iota` 或 `StatusRunning = iota + 1`） |
| 4.8 | 时间用 `time.Time` / `time.Duration`，禁止裸 int。业务逻辑注入 `now func() time.Time` |
| 4.9 | 密钥/令牌用 `crypto/rand`，禁止 `math/rand` |
| 4.10 | `defer` 紧跟资源获取后。`defer` 在循环内会累积到函数返回 |
| 4.11 | `os.Exit` / `log.Fatal` 只在 `main` 中；库代码只 return error；`panic` 不跨包边界 |
| 4.12 | 禁止 `init()` 做 IO。若必须用，保持确定性且无副作用 |

### 反模式

| 反模式 | 问题 | 做法 |
|--------|------|------|
| `if err != nil { log.Error(err); return err }` | 同层 log + return，日志风暴 | 只 return，最外层统一 log |
| `_ = doSomething()` 无注释 | 不知是忽略还是疏忽 | 加注释说明 |
| 返回内部 map 引用 | 外部可修改内部状态 | 返回快照 |
| `type Config struct { Timeout int }` | 单位不明确 | `time.Duration` |
| 枚举 `const ( Running = iota; Stopped )` | 零值易被误用 | 零值 = `Unknown` |
| `math/rand` 生成密钥 | 种子可预测 | `crypto/rand` |
| `log.Fatal(err)` 在库代码中 | 跳过 defer，不可测试 | `return err` |
| `init()` 读配置文件 | 导入即副作用 | 显式 `LoadConfig()` |

## 维度五：一致性与简洁

DRY、命名风格、模式统一、简洁优先。

### 规则

| # | 规则 |
|---|------|
| 5.1 | **相同逻辑出现两次 → 抽取。** 但如果抽取会引入耦合，保留独立副本 |
| 5.2 | 同类 DTO / 配置 / 错误处理 → 统一风格。一旦选定就保持一致 |
| 5.3 | 硬编码数字提取为命名常量或配置项（`30`、`1024`、`5*time.Second`） |
| 5.4 | 代码符号命名遵循 Go 惯例：`MixedCaps`、缩写统一大写（`URL`/`ID`/`HTTP`）、包名不口吃（`http.Server` 非 `http.HTTPServer`）、receiver 名 1-2 字母且一致 |
| 5.5 | 目录组织、类型声明顺序、方法排序保持一致 |
| 5.6 | 简洁优先：清晰 > 巧妙。能用标准库就不引入第三方依赖；已引入的依赖应充分利用，无用的及时移除 |

### 反模式

| 反模式 | 问题 | 做法 |
|--------|------|------|
| 相同逻辑多份拷贝 | 改一处漏多处 | 抽取公共函数 |
| DTO 命名不统一 | 前端对接混乱 | 统一命名规则 |
| 一种业务多种写法 | 排查困难 | 选定一种模式 |
| 为"简洁"引入晦涩 trick | 可读性比行数重要 | 写直白代码 |
| 为单一场景封装通用工具 | 工具退化无人敢改 | 等第二个场景再抽 |
| 引入依赖只用了 5% 的功能 | 增加构建体积和安全攻击面 | 评估收益，考虑标准库替代 |
