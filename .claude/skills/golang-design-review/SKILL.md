# Go 模块设计审查

从五个维度系统审查 Go 代码的设计质量。每个检查项附规则摘要，自包含可独立使用。

## 审查流程

1. **定位范围** — 确认要审查的模块/包/文件
2. **工具先行** — 执行 `gofmt`、`go vet`、`golangci-lint`，工具能发现的问题不在审查中重复
3. **逐维度审查** — 按五个维度依次检查 diff，每个 finding 标注 `file:line` + 规则编号
4. **读测试** — 测试是设计意图最诚实的表达，必须作为审查内容的一部分阅读
5. **自检** — 重读标记项，删除无法充分论证的 finding
6. **分级汇总** — 按严重程度分组输出

## 维度一：包与职责

包内聚、类型/函数职责划分、分层边界。

| # | 检查项 | 规则摘要 |
|---|--------|---------|
| 1.1 | 包名是否清晰？有无 `util`/`helper`/`common`/`misc`？ | 包名用一句话说清目的 |
| 1.2 | 包内文件是否共享未导出符号？ | 不共享 = 两个包硬塞在一起 |
| 1.3 | 类型是否职责单一？struct 是否字段过多或跨关注点？ | 5+ 字段且不同关注点 → 拆分 |
| 1.4 | 函数是否只做一件事？是否混合 IO + 业务逻辑？ | 超 40 行或混 IO+业务 → 拆分 |
| 1.5 | 导出符号是否都是必要的？ | 不必要的一律 unexported |
| 1.6 | 分层是否清晰？handler 有无业务逻辑？logic 有无 HTTP/DB 类型？ | handler 不承载逻辑，logic 不依赖框架 |
| 1.7 | 目录名、类型名、属性名是否符合行业惯例？有无魔法字符串？ | 目录名、类型名、属性名符合行业惯例，无魔法字符串 |

## 维度二：接口与耦合

接口归属和粒度、依赖方向、抽象层级。

| # | 检查项 | 规则摘要 |
|---|--------|---------|
| 2.1 | 接口是否定义在消费方？ | 消费方声明自己需要什么 |
| 2.2 | 是否存在只有单个实现的接口？ | 等第二个实现出现再抽 |
| 2.3 | 构造函数是否返回具体类型？ | 返回具体类型，非接口 |
| 2.4 | 接口是否 ≤ 3 个方法？大接口是否由小接口组合？ | 大接口 = 组合小接口 |
| 2.5 | 嵌入是否用于组合而非继承模拟？导出 struct 是否泄漏了内嵌 API？ | 组合非继承，用未导出字段 |
| 2.6 | 是否有全局变量或全局客户端？依赖是否通过接口注入？ | 禁止全局变量，显式注入 |
| 2.7 | 同一类型的 receiver 是否一致？ | 统一指针或值 receiver |
| 2.8 | 非平凡接口是否有编译期满足检查（`var _ I = (*T)(nil)`）？ | 接口变更时编译失败立即发现 |

## 维度三：并发安全

goroutine 生命周期、锁安全、channel 设计。

| # | 检查项 | 规则摘要 |
|---|--------|---------|
| 3.1 | 每个 goroutine 是否都有明确的退出路径？ | 无法退出 = 泄漏 |
| 3.2 | IO/阻塞 API 的首参数是否是 `context.Context`？ctx 是否被存入了 struct？ | ctx 第一参数，不存 struct |
| 3.3 | 是否存在持锁执行阻塞 IO？ | 锁内调 IO → 串行化服务 |
| 3.4 | 调用方能否等待 goroutine 完成（`errgroup`/`WaitGroup`）？ | 首选 errgroup.WithContext |
| 3.5 | 长生命周期 `select` 是否有 `<-ctx.Done()` case？ | 无 ctx 监听 = 无法取消 |
| 3.6 | 是否只有发送方关闭 channel？ | 接收方关 → panic |
| 3.7 | channel 参数是否标注了方向？ | `chan<-` / `<-chan` |
| 3.8 | `wg.Add` 是否在 `go` 之前调用？ | Add 在 go 前 |
| 3.9 | 并发安全类型是否在文档中显式声明？ | 默认不安全，安全须声明 |

### 验证命令

```bash
go test -race ./... -short
go test ./... -run TestMain   # 需引入 go.uber.org/goleak
```

## 维度四：错误与边界

错误处理一致性、API 边界防护、零值设计。

| # | 检查项 | 规则摘要 |
|---|--------|---------|
| 4.1 | 是否错误优先判断？成功路径是否保持不缩进？ | early return，成功路径不缩进 |
| 4.2 | 错误包装是否正确（`%w` vs `%v`）？错误信息是否小写、无标点？ | 需检查用 %w，隐藏用 %v |
| 4.3 | 每个错误是否只处理一次（未同时 log + return）？ | log 或 return，不同时做 |
| 4.4 | 有无无故吞错误（`_ = f()` 无注释）？ | 吞错误必须注释理由 |
| 4.5 | API 边界是否拷贝了 slices/maps？ | 存调用方数据 → copy，返回内部数据 → 快照 |
| 4.6 | 类型零值是否直接可用？否则是否隐藏并提供了构造函数？ | 零值可用，否则隐藏类型 + New |
| 4.7 | 枚举零值是否安全（要么显式定义，要么 `iota+1` 跳过）？ | 零值 = Unknown 或 iota+1 |
| 4.8 | 时间是否用了 `time.Time`/`time.Duration`？ | 禁止裸 int |
| 4.9 | 密钥/随机数是否用了 `crypto/rand` 而非 `math/rand`？ | math/rand 种子可预测 |
| 4.10 | `defer` 是否紧随资源获取？是否误写在循环内？ | 紧跟获取，循环内会累积 |
| 4.11 | `os.Exit`/`log.Fatal` 是否仅在 `main` 中？库代码有无 panic？ | 库代码只 return error |
| 4.12 | `init()` 是否无 IO/环境依赖？ | init 不 IO，不读配置 |

## 维度五：一致性与简洁

DRY、命名风格、模式统一、简洁度。

| # | 检查项 | 规则摘要 |
|---|--------|---------|
| 5.1 | 是否有重复两次以上的逻辑？是否该抽而未抽，或不该抽而抽了？ | 两次 → 抽取；抽取若引入耦合则保留副本 |
| 5.2 | 同类代码是否风格统一（DTO、配置、错误处理）？ | 选定一种方式就保持一致 |
| 5.3 | 是否有散落的魔法数字？ | 提取为命名常量或配置项 |
| 5.4 | 代码符号命名是否符合 Go 惯例（`MixedCaps`、缩写大小写、包名不口吃、receiver 1-2 字母）？ | Go 命名惯例 |
| 5.5 | 目录组织、类型声明顺序、方法排序是否一致？ | 同类文件结构一致 |
| 5.6 | 是否有不必要的复杂设计？是否有未充分利用或可被标准库替代的第三方依赖？ | 简洁 > 巧妙，无用依赖移除 |

## 严重程度分级

| 级别 | 含义 | 示例 |
|------|------|------|
| **Must Fix** | 正确性/安全/数据丢失，阻塞合并 | goroutine 泄漏、竞态、吞错误、`math/rand` 生成密钥 |
| **Should Fix** | 设计缺陷/技术债，建议修 | 接口在实现方定义、handler 含业务逻辑、包职责过载 |
| **Nit** | 风格/命名偏好，可选修 | 变量名可更短、方法排序可调整 |
| **Praise** | 值得肯定的设计亮点 | 名称精准、职责清晰、并发处理优雅 |

## 输出格式

```markdown
## 审查：[模块/包名]

### 一、包与职责
- **[Must/Should/Nit]** `file:line` — 问题描述（规则 X.X）
- ...

### 二、接口与耦合
- ...

### 三、并发安全
- ...

### 四、错误与边界
- ...

### 五、一致性与简洁
- ...

### 汇总
| 级别 | 数量 |
|------|------|
| Must Fix | N |
| Should Fix | N |
| Nit | N |
| Praise | N |

### 优化建议
1. 优先级最高的 3 个问题及修改方向
```

- 每个 finding 必须标注 `file:line` + 规则编号
- 无规则依据的纯主观意见不写入
- 同类型问题合并（标注 "× N similar"）
- 非平凡的设计亮点必须给出 Praise

## 审查者反模式

审查者自身应避免的坏习惯：

| 反模式 | 问题 | 做法 |
|--------|------|------|
| "我会写成另一种方式" | 纯主观偏好，无规则支撑 | 要么引用具体规则，要么不提 |
| 罗列所有 nit 而不合并 | 噪音淹没关键问题 | 同类问题合并（"× N similar"） |
| 审查人而非代码 | 触发防御心理 | 只写关于代码变更的事实 |
| 在 review 里重写代码 | 剥夺作者的修改权 | 引用规则编号 + file:line，让作者自己修改 |
| 不读测试就 Approve | 测试可能是事后补的，覆盖不全 | 读测试是审查的必做环节 |
| finding 无 file:line | 作者找不到问题位置 | 每条必标注路径和行号 |
| 无严重程度标签 | 作者不知该先修哪个 | Must Fix / Should Fix / Nit 必标 |

## 审查自检清单

提交审查报告前确认：

- [ ] 每条 finding 有 `file:line` + 规则编号，无纯主观意见
- [ ] 同类 finding 已合并（"× N similar"），无重复条目
- [ ] 测试已被阅读，不只是被计数
- [ ] 至少给出 1 条 Praise（如果 diff 中有值得肯定的设计）
- [ ] 严重程度标签经得起质疑（把 Must Fix 降级为 Nit 重新审视一遍）
- [ ] 工具（gofmt/vet/lint）结果干净，审查中未重复工具能发现的问题

## 审查守则

- **审查的是代码，不是作者** — 只谈设计，不针对人
- **不确定的不标** — 无把握的 finding 宁可不提
- **工具先行，再读测试** — 先执行 gofmt/vet/lint 消除机械问题；再把测试作为审查内容阅读，验证设计意图
- **规则是尺子，不是教条** — 某些场景打破规则反而是更好的设计。例如：50 行 CLI 脚本不需要分层架构；单文件工具不需要拆包。破例时必须有充分理由
