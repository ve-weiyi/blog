# 11 模块与数据所有权

> **本文回答**：系统分成哪些模块，谁拥有哪份数据，跨模块怎么说话、事务边界在哪。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、划分判据

模块划分按优先级使用三条判据：

| 判据 | 内容 | 拒绝的形态 |
|---|---|---|
| **聚合聚类** | 总是被一起修改的资源，构成一个模块 | 把同一聚合拆成多个模块，迫使每次修改跨模块 |
| **耦合验收** | 两个候选模块若会共享数据表，或互相伸手进内部，则不拆 | 公共耦合、内容耦合 |
| **反模式规避** | 不为单张表造薄 CRUD 模块；也不把多个同构资源拆成多个模块 | 「实体模块」反模式 |

判据的输出是**数据所有权**，不是代码目录。目录可以随生成工具变化，所有权不能。

## 二、模块与数据所有权

**每个资源有且只有一个拥有模块，每张表只属于一个模块。** 其他模块只持有引用。

| 模块 | 代码名 | 拥有的资源 | 主要数据表 | 边界说明 |
|---|---|---|---|---|
| 用户 | `user` | 用户、个人资料、第三方绑定、账号生命周期 | `t_user`、`t_user_oauth` | 不拥有角色授权关系 |
| 访客 | `guest` | 访客身份 | `t_guest` | 以服务端签发的设备令牌标识；设备指纹只作记录字段 |
| 认证 | `auth` | 登录、注册、登出、第三方授权、密码重置 | 无业务表 | 技术能力；会话与令牌状态写入会话存储，不写入业务表 |
| 访问控制 | `access` | 角色、菜单、接口资源、授权关系 | `t_role`、`t_menu`、`t_api`、`t_role_api`、`t_role_menu`、`t_user_role` | 判定可在网关中间件执行，但**数据**归本模块 |
| 内容 | `content` | 文章、分类、标签、修订版本 | `t_article`、`t_category`、`t_tag`、`t_article_tag` | 修订与正文同聚合；分类层级只存 `parent`，不维护 `children` |
| 媒体 | `media` | 相册、照片 | `t_album`、`t_photo` | 二进制存对象存储，表只存引用与派生信息 |
| 讨论 | `discussion` | 评论、留言、说说 | `t_comment`、`t_message`、`t_talk` | 三者是同一项能力：面向页面、需审核的用户发言 |
| 聊天 | `chat` | 聊天消息 | `t_chat` | 冗余发送者快照；经 STOMP 实时通道 |
| 站点 | `site` | 站点配置、自定义页面、友链、分发出口 | `t_config`、`t_page`、`t_friend` | feed / sitemap / robots 是出口，不是独立存储 |
| 通知 | `notification` | 场景、通知事件、公告内容、收件箱条目、渠道投递、偏好、验证码发送 | `t_notification_event`、`t_notification`、`t_notification_delivery`、`t_notification_preference`、`t_announcement` | 事件 / 条目 / 投递三层；文案在代码，不建模板表；验证码权威状态存会话存储，不产生事件与条目 |
| 日志 | `syslog` | 登录、操作、上传、访问日志 | `t_login_log`、`t_operation_log`、`t_upload_log`、`t_visit_log` | 四类同构同用途；名称沿用仓库既有叫法 |
| 统计 | `stats` | 统计数据与物化表 | `t_daily_stats` | 拥有物化数据，不是纯只读投影；不参与业务判定 |

**模型构造器集中在同一个包，不代表所有权共享。** 包是代码组织，所有权是设计事实；判断归属看「这张表由谁写入、谁对它的事务负责」。

### 2.1 归并的取舍

| 情形 | 结论 | 理由 |
|---|---|---|
| 评论、留言、说说 | 合为 `discussion` | 拆开等于三个围绕单表的薄 CRUD 模块，且三者承载同一项能力 |
| 聊天与讨论 | 分开 | 聊天有冗余用户快照、无主题引用、经实时通道；生命周期与讨论不同 |
| 用户、访客 | 分开 | 身份主体不同：一个有凭据，一个只有设备令牌；合并会引入一个宽泛上位词 |
| 统计 | 独立 | 拥有物化数据，与其他模块无公共耦合 |
| 订阅者 | **当前不存在** | 见 §七；若引入，按独立身份主体与独立模块处理，不与用户合并 |

### 2.2 命名

模块名表达**它拥有什么**，不表达「它跟什么有关」。

| 原则 | 说明 | 实例 |
|---|---|---|
| 名实相符 | 名字指向实际拥有的资源 | 只装角色、菜单、接口资源的模块叫「访问控制」，不叫「权限」 |
| 层级一致 | 并列概念用同一层级的名词 | 「用户」与「访客」并列，不引入同时罩住两者的上位词 |
| 具体优于宽泛 | 具体名词优于通用抽象 | 用户产出、需审核的发言叫「讨论」，不叫「互动」 |
| 一致性优先 | 仓库内已一致的术语，即使与行业惯例有出入也不改名 | 「日志」沿用既有叫法 |

**唯一被记录的例外是 `syslog`**：它与系统日志协议同名，实际拥有的是四类业务日志。边界本身无歧义，改名会触动全部引用，收益不抵改动面，故保留。这是已决定的例外，不再作为改名建议提出。

## 三、跨模块规则

1. **只经契约调用**。模块之间不得直接引用对方的模型、表或内部函数；调用形态见《契约与演进》。
2. **不共享表**。关联关系归拥有聚合的一方：修订随正文、照片随相册、投递记录随内容、用户-角色关系随访问控制。
3. **不做跨模块 join**。需要另一模块的数据时，由调用方分别取回后在内存组合；组合逻辑属于调用方的用例，不写进任一模块的查询。
4. **事务只在一个模块内**。模块内保持强一致；跨模块操作由编排方组织为「本地事务 → 远程调用 → 失败补偿/重试」，**不引入分布式事务**。
5. **跨模块异步只经消息**。消息的生产者拥有消息形状，消费者按至少一次语义处理，见《异步消息与投递可靠性》。
6. **视图裁剪在拥有方**。字段集由拥有数据的模块决定，调用方不通过「取全量再删」实现最小暴露。
7. **唯一例外：统计是只读报表投影**。统计模块可以只读其他模块的表与 Redis 计数，用于生成报表；它不得写其他模块的表、不得参与对方事务，其他模块也不得反向依赖统计。该例外只适用于统计，不得被其他模块模仿。

**编排方通常是网关**：一个页面动作需要多个模块的数据时，由网关分别调用并在响应中组合。网关只做编排，不落库。

## 四、关键决策

| 决策 | 内容 | 备选 | 代价 | 重审触发 |
|---|---|---|---|---|
| **D1 一表一主** | 每张表只属于一个模块；关联关系归拥有聚合的一方 | 按代码目录划分所有权 | 跨模块查询需要组合 | 出现两个模块必须共享表的强需求 |
| **D2 跨模块只经契约** | 不直接引用对方的模型、表或内部函数 | 允许直接引用模型 | 多一次调用与序列化 | 模块拆到独立数据库，远程调用成本不可接受 |
| **D3 不共享表、不做跨模块 join** | 组合在调用方内存完成 | 允许只读 join | 调用方需要理解多个模块的数据 | 出现第二类稳定的跨域只读场景 |
| **D4 事务只在一个模块内** | 跨模块用补偿与重试，不引入分布式事务 | 引入分布式事务 | 需要设计可重入的补偿 | 出现无法用补偿表达的一致性要求 |
| **D5 编排在网关** | 网关按用例组合多个模块的调用 | 由某个模块统一编排 | 网关需要了解多个契约 | 网关编排复杂到成为业务层 |
| **D6 统计只读投影** | 统计可只读跨域表；不写、不参与事务、不被反向依赖 | 通过各模块契约逐项取数 | 报表与业务表结构耦合 | 模块拆库，或统计查询影响业务库性能 |

## 五、不变量

- [ ] 每张表有且只有一个拥有模块；所有权矩阵是唯一真相源。
- [ ] 模块之间不存在共享表、跨模块 join、跨模块事务（统计的只读报表投影是唯一例外）。
- [ ] 每个模块的写入只由自己的逻辑执行；其他模块只能通过契约请求。
- [ ] 模块内事务失败即整体回滚；跨模块操作不返回「部分成功」。
- [ ] 聚合关系与表归属一致：修订随正文、照片随相册、投递记录随内容。
- [ ] 模块边界不依赖进程边界；拆进程只改变调用方式。
- [ ] 新增模块必须同时声明它拥有的资源与表，并更新本矩阵。

## 六、失败与降级

| 情形 | 行为 | 约束 |
|---|---|---|
| 跨模块同步调用失败 | 调用方明确失败，返回错误；不回传半成品 | 写操作需具备幂等键或可安全重试 |
| 拥有方不可用 | 依赖它的功能不可用 | 禁止直接读对方的表绕过；禁止缓存未授权的副本 |
| 跨模块异步投递失败 | 按投递语义重试；超过上限进入失败终态 | 消费者必须幂等，重复投递不得产生第二条记录 |
| 编排到一半失败 | 已完成的写操作由补偿或状态机收敛 | 不引入分布式事务；补偿必须可重入 |

## 七、边界与重新审视

**当前没有订阅者模块**：邮件订阅在当前实现中不存在。若恢复，订阅者按独立身份主体处理，拥有自己的订阅状态、退订凭据与同意记录，**不与用户合并**；不得先在用户表上加字段作为临时方案。

出现下列信号时重新评审模块边界：

- 某模块的资源不再总是被一起修改（聚合瓦解）。
- 两个模块开始共享同一张表（公共耦合）。
- 讨论域中评论、留言、说说之一演化出独立的数据模型与生命周期。
- 访客长出独立能力（如行为归因），或职责萎缩到不值得单独成模块。
- 统计开始参与业务判定 —— 这违反「统计不参与判定」，应修正用法而不是扩大统计模块。
