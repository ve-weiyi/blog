# 00 设计宪法

> **本文回答**：这个系统在什么约束下做设计，做取舍时依据什么。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、定位

本文是整个设计体系的根。**与本文约束或原则冲突的设计，必须先改本文，再改设计** —— 不允许绕过去，也不允许在别处另立一套判据。

本文只回答三件事：目标是什么、约束是什么、冲突时按什么排序。具体机制由各专题篇定义。

## 二、目标与成功标准

系统服务两类使用者：**读者**浏览内容并参与互动，**管理员**维护内容、审核互动、配置站点。

设计是否成立，看四条：

| 维度 | 成功标准 |
|---|---|
| 读者体验 | 内容读取在缓存命中时不触达后端；订阅与检索入口稳定可用 |
| 作者效率 | 发布、修订、定时、撤回、审核都是低成本动作，不需要运维介入 |
| 可运维性 | 单机故障后能恢复；故障可定位；配置变更不需要重新构建镜像 |
| 可演进性 | 新增一个业务域，不改其他域的代码；拆分部署形态不改契约与模块边界 |

**成功标准不是功能清单**。功能可以增删，这四条是判断架构是否还成立的标准。

## 三、四项硬约束

本文所有架构取舍以此为准。凡与下表冲突的设计，应先修改本表，而不是绕过它。

| 维度 | 量级目标 | 对设计的约束 |
|---|---|---|
| **规模** | 文章千级、注册用户万级、日均 PV 万级 | 单机足够；不追求水平扩展能力，不为未来规模预置分片 |
| **可用性** | **接受单机故障导致的全站停机**，目标是「可恢复」而非「不停机」 | 不做跨机容灾；备份、恢复演练与故障定位是必要组成 |
| **一致性** | 内容可见性允许**秒级延迟**（缓存所致）；写操作在模块内强一致 | 读路径可放心缓存；写路径不引入最终一致；跨模块不引入分布式事务 |
| **成本** | 单机资源可承载 | 每引入一个中间件、服务或缓存层，必须说明它解决了当下的什么问题 |

**数值是量级判断，随运营数据校准** —— 但量级本身即是取舍依据，不得缺省。规模变化时，先重审本表，再重审依赖它的设计。

## 四、八条设计原则

原则是**冲突时的排序依据**，不是口号。每条都配一个可执行的操作检验；检验不通过，说明设计还没做完。

### P1 边界先于拆分

**陈述**：模块边界由数据所有权与契约定义，与部署形态解耦。进程拆分是一个独立的、可以延迟的决策。

**为什么**：拆进程的代价（跨进程调用、契约双份维护、分布式事务）当下就要付，收益（独立扩缩、故障隔离、独立发布）只在某个域单独承压时才兑现。先立边界，收益出现时再拆，两次成本都更低。

**操作检验**：任意两个模块之间不存在共享表、共享事务与直接函数调用。满足这一条，拆进程时只需要改调用方式。

**常见反例**：因为「微服务」而先拆进程，再回头补边界；把「部署在一起」误认为「逻辑上耦合」。

**拆分触发信号**：某业务域需要独立扩缩；某业务域的故障已波及他域；出现独立于主干的发布节奏。出现任一信号即重新评审，而不是等到不可维护。

### P2 单一真相源与单一判定入口

**陈述**：每类事实只有一个权威来源，每条规则只有一个判定入口。

**为什么**：重复实现必然漂移，而漂移的后果不对称 —— 漏写一处可见性条件就是内容泄漏，漏掉一处权限失效就是越权。把「多处保持一致」变成「只有一处」，是唯一可靠的解法。

**操作检验**：同一条规则能否在代码里找到第二个实现？能找到就是违规。

**适用对象**：

| 事实 | 唯一来源 |
|---|---|
| 接口契约 | `protocol` |
| 业务实体与关系 | 拥有它的模块 |
| 「已发布 + 公开」可见性 | 单一谓词，所有读出口经同一入口 |
| 错误标识到 HTTP 状态 | 响应出口 |
| 权限变更 | 唯一入口，失效与写操作同事务边界 |

**注意**：单一真相源不等于单一物理位置。缓存、副本、视图都可以存在，但**它们不能成为第二个裁决者** —— 缓存不可用时必须回源，而不是自行给出结论。

### P3 权威分级

**陈述**：先问「丢了会怎样」，再决定持久化、隔离与能否清空。权威性分权威 / 可重建 / 可重置三档，与可清空性是**两个正交维度**，不能只答一个。

**为什么**：把「可重建」误当「可清空」，会在故障时丢掉唯一副本；把「不可清空」误当「权威」，会让缓存层背上不属于它的持久化负担。两个维度分开，存储策略才有唯一答案。

| 数据 | 权威性 | 可清空性 | 存储要求 |
|---|---|---|---|
| 业务实体与关系 | 权威（丢失不可恢复） | 不得清空 | 持久化、备份 |
| 会话与令牌状态 | 权威（丢失即安全事件） | 不得清空 | 持久化、独立实例、运维禁止清空 |
| 在线列表、验证码 | 可重建（清空只中断在途流程） | 不得清空（与令牌同侧） | 可与会话存储同实例 |
| 内容缓存、限流计数 | 可重建 | 可随时清空 | 无需持久化 |
| 点赞关系 | 可重置（无持久副本） | 可随时清空 | 业务缓存实例；清空只重置用户点赞，聚合计数以 DB 为准 |

**第三类是「可重置状态」**：既非权威、也不可重建，清空只重置用户动作，不造成不可恢复的数据丢失。它不能被当作「回源重建」来承诺，也不能参与授权或审计判定。

**操作检验**：每个存储都标注「权威 / 可重建 / 可重置」与「可清空 / 不得清空」；两个维度都有答案，且存储策略与之一致。

**常见反例**：令牌与内容缓存共用一个 Redis 库；权威数据与可清空数据共享持久化策略。

### P4 失败语义显式

**陈述**：每个外部依赖都必须回答：不可用时**拒绝**、**放行**还是**兜底**？三选一，不允许「未定义」。

**为什么**：故障时最危险的不是依赖挂了，而是系统在没人决定的情况下自行选了一个方向。静默放行会让安全机制失效，静默拒绝会让非关键增强项拖垮主链路。

**判据**：

- 放行是否产生**不可撤销**的后果？是 → 拒绝。
- 失败的是安全判定还是体验增强？安全 → 拒绝，增强 → 放行。
- 兜底路径能否给出**可观测的信号**？不能 → 不叫兜底，叫静默降级。

**操作检验**：画出「依赖 × 不可用行为」表，表中没有空格。每一格都能指向一条决策。

**常见反例**：权限缓存不可用时默认放行；可选的第三方风控接口超时导致评论不可用。

### P5 时效用数字承诺

**陈述**：不说「立即」「实时」「最终一致」。每个时效承诺都必须给出**上限**，并说明由什么机制保证。

**为什么**：没有数字的承诺无法验证，也无法在评审时被质疑。行业里「立即生效」几乎都对应一个有界窗口 —— 承认它，设计才完整；不承认它，就是在把时效交给运气。

**分档示例**（具体取值由各篇定义）：

| 场景 | 时效 | 保证机制 |
|---|---|---|
| 令牌吊销 / 强制下线 | 立即（下一次请求） | 会话撤销 |
| 权限变更（角色、策略） | ≤ 5 分钟 | 失效广播加速 + 缓存 TTL 兜底 |
| 菜单与按钮可见性 | ≤ 5 分钟 | 同权限变更 |
| 内容可见性 | 秒级 | 缓存版本号 + 短 TTL |

**操作检验**：读者能否在该篇里找到数字和保证机制？找不到就是没设计完。

**常见反例**：写「权限变更立即生效」，实际依赖 5 分钟的缓存 TTL；写「实时推送」，却不承诺断线后的补偿上限。

### P6 推送只加速，拉取保正确

**陈述**：不可靠通道（SSE、STOMP、MQ）只负责让状态**更快到达**；正确性由权威源的**快照拉取、游标重放与重连补偿**承担。

**为什么**：断网、切后台、多端登录、进程重启都发生在通道侧。把正确性押在「消息一定送达」上，等于把系统可用性押在不可控的链路上。

**操作检验**：关掉推送通道，功能是否仍然正确（只是变慢）？答案必须为是。

**常见反例**：未读计数只靠推送事件维护；聊天消息只存在于通道，不先落库；撤回只在推送里发事件，不改变库内状态。

### P7 最小暴露

**陈述**：服务端决定调用方能看见什么。视图裁剪在服务端完成，共享缓存不承载任何随用户变化的字段。

**为什么**：把全字段交给前端裁剪，最小暴露在进程边界上就已经破了 —— 一次日志、一次调试、一个反序列化缺陷就会泄漏。缓存同理：只要响应里混入一个用户相关字段，整条共享缓存链就失效。

**操作检验**：

- 同一条匿名内容响应，能否被任意用户复用？能，才可进入共享缓存。
- 客户端收到的每个字段，是否都是它当前场景需要的？不是，就裁掉。

**常见反例**：rpc 返回全字段、由 api 层裁剪；匿名响应下发 `Set-Cookie`；内部错误原文透传给客户端。

### P8 成本是判据

**陈述**：每引入一个中间件、服务或缓存层，都必须说明它解决了**当下的**什么问题。规模变化时重新审视，而不是提前为未来买单。

**为什么**：复杂度是有利息的 —— 多一个组件就多一套部署、监控、故障模式与升级路径。个人博客量级下，大部分「业界标配」的收益无法兑现。

**操作检验**：能否用一句话写出「没有它会怎样」？写不出，就不该引入。

**常见反例**：为未来的百万用户预置分库分表；为「看起来专业」拆出多个 rpc 进程；引入独立检索引擎而 MySQL 全文尚未跑满。

## 五、关键决策：方法与分工

### D1 设计文档只写决策层

**决策**：`docs/design/` 只记录决策、约束、不变量与失败语义；实现细节归代码。

**代价**：读者无法从文档直接抄出代码，需要跳转代码库。

**重审触发**：当某类实现细节反复被误解、且代码本身无法自解释时，考虑补充注释或 README，而不是写进设计文档。

### D2 引用用标题与决策号，不用章节号

**决策**：跨文档引用写成 `《标题》` 或 `《标题》D编号`。

**理由**：章节号在编辑中必然漂移；标题与决策号是稳定的。

**代价**：引用比「《04》§三」略长。

### D3 设计记录应然，冲突单独裁决

**决策**：写作时以代码核对事实，但文档记录的是应有设计。发现实现与设计冲突时，只记录设计，冲突单独列出裁决。

**理由**：把现状直接写成设计，会让缺陷获得合法性，并永久固化。

**代价**：文档可能短暂领先于实现，需要在 feature 层追踪落地。

### 什么算架构决策

| 属于架构决策（写进设计文档） | 不属于（代码与评审决定） |
|---|---|
| 模块边界、数据所有权 | 具体库与框架版本 |
| 外部契约与兼容性规则 | 函数签名、字段命名 |
| 失败语义与降级方向 | 局部算法与数据结构 |
| 部署形态与运行约束 | 配置项取值 |
| 安全边界与信任模型 | 日志文案 |
| 跨仓库协作顺序 | 目录与文件布局 |

每条决策记录五要素：**约束**（逼出它的事实）、**备选**（至少两个）、**选择**、**代价**、**重审触发**。只写「我们采用 X」的条目不算决策记录。

## 六、术语

同一概念在所有文档中使用同一个词，不另造同义词。

| 术语 | 含义 | 易混点 |
|---|---|---|
| **模块** | 按数据所有权与职责划分的逻辑单元 | 不等于进程；多个模块可以同进程 |
| **服务** | 可独立部署与扩缩的运行单元 | 当前只有一个 rpc 服务，内含多个模块 |
| **契约** | 对外的接口形状与语义，存放于 `protocol` | 不含实现；实现可以替换 |
| **身份主体** | 注册用户、访客、订阅者三类 | 后两类不参与授权 |
| **标识凭据** | 证明「这个请求属于某个访客/设备」，失败只降级 | 不是准入凭据 |
| **准入凭据** | 决定「能否进入」，失败即拒绝 | 登录令牌、实时连接令牌 |
| **权威数据** | 丢失后不可恢复、或缺失即安全事件的数据 | 与「可清空性」是两个维度 |
| **权威源** | 持有权威数据的位置（表、服务或会话存储） | 不是缓存副本；副本不能成为第二个裁决者 |
| **可重建数据** | 丢失只造成短时降级，可由权威源重建 | 不代表可以随意清空 |
| **有界陈旧** | 允许旧值，但旧值有明确上限 | 无上限的陈旧等于没有承诺 |
| **单一谓词** | 判定「内容是否可见」的唯一条件表达式 | 所有读出口必须经同一入口 |
| **视图裁剪** | 服务端按调用方场景裁剪返回字段 | 发生在服务端，不在前端 |
| **投递语义** | 至少一次、幂等、顺序等消息保证 | 「至少一次」意味着重复是常态 |
| **加速通道** | 只让状态更快到达、不承担正确性的通道 | 推送、SSE、STOMP、MQ |
| **会话存储** | 承载令牌与在线状态的 Redis 角色 | 与业务缓存隔离部署，不得清空 |
| **业务缓存** | 承载可重建读数据的 Redis 角色 | 任何时刻可清空 |

## 七、非目标

非目标不是「暂时不做」，而是**当前约束下明确不做**。每一条都给出重新审视的条件。

| 非目标 | 理由 | 重新审视的条件 |
|---|---|---|
| 多机房 / 异地多活 | 可用性目标只要求「可恢复」 | 业务出现跨地域连续性要求 |
| 分库分表 | 数据量级远低于单库上限 | 单表写入或容量成为瓶颈 |
| 独立检索引擎 | MySQL 全文尚未跑满 | 检索质量或组合查询成为核心体验瓶颈 |
| 多 rpc 进程拆分 | 拆分代价当下就要付，收益未兑现 | 出现 P1 的拆分触发信号 |
| 跨模块分布式事务 | 模块内强一致已足够，跨模块用契约与兜底 | 出现无法用补偿表达的一致性要求 |
| 消息顺序保证 | 顺序成本高，业务可用版本号或时间戳消解 | 出现必须全局有序的业务语义 |
| 推送必达 | 通道不可靠，正确性已由拉取承担 | 出现「推送不到即业务失败」的场景 |
| 前端框架级 ISR / SSG | 缓存与 SEO 可分开解决，不引入整套渲染框架 | SEO 需求超出预渲染 + 注入 meta 的能力 |
| 原生 App | 当前只有 Web 端 | 出现明确的原生端需求 |
| 多租户 / SaaS | 单站点部署 | 需要托管多个独立站点 |
| 评论全量预审 | 个人博客评论量小，预审会杀死互动 | 垃圾评论比例高到分层治理无法覆盖 |

## 八、与其余文档的关系

- **本文**定义约束与判据；**各篇**定义机制，并在「目标与约束」一节引用本文的原则编号（如 `P4`）。
- **`README.md`** 是文档地图与阅读路径；本文是判据的唯一来源。
- 任何一篇的结论与本文冲突时，以本文为准；若认为本文需要修改，先改本文并走评审，再改其余篇。
