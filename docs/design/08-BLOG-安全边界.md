# blog 博客系统 — 安全边界

初稿：2026-09-16　·　最近更新：2026-09-16

## 一、定位

系统的多数输入来自客户端，其中一部分**可被任意伪造**。本节的职责是集中回答三个问题：**哪些输入不可信、各自如何验证、验证失败时如何降级**。

**为什么不分散在各篇**：同一套信任模型横跨认证（《03》）、实时通信（《04》）、部署（《05》）、限流与中间件（《07》）。分散书写会迫使读者跨四篇文档自行拼出全貌——而安全漏洞恰恰产生于「每一处都以为别处处理过了」。

## 二、不可信输入清单

**本表是信任边界的唯一真相源。**新增任何「从请求中读取标识」的设计，都必须先在此登记。

| 输入 | 是否可信 | 验证方式 | 验证失败时 |
|---|---|---|---|
| 访问令牌 | 不可信 | 签名校验 + 与 Redis 会话存储比对版本号（《03》§1.2） | 拒绝，`4100` / `4110` |
| 刷新令牌 | 不可信 | 同上；且仅存于 `HttpOnly` Cookie，脚本不可读（《03》§1.3） | 拒绝，要求重新登录 |
| 设备令牌 | 不可信 | 服务端签名校验（《03》§1.4） | **分场景**：作访客身份依据时降级；作已登录令牌的设备绑定凭据时拒绝（见 §三） |
| 客户端自报的设备标识 / 指纹 | **完全不可信** | 不作为身份依据，仅作令牌内的记录字段 | 不适用 |
| 客户端转发的来源 IP（`X-Forwarded-For` 等） | 不可信 | 由 Nginx 覆写，网关只信任最后一跳（《07》§2.4） | 不适用——该头永不被信任 |
| OAuth `state` | 不可信 | 与发起授权的会话绑定，一次性消费（《03》§1.3） | 拒绝 |
| OAuth 回调的平台标识 | 不可信 | 命中服务端配置的平台白名单（《03》§1.3） | 拒绝 |
| 排序字段（`sorts`） | 不可信 | 服务端白名单（《02》§1.3「已知遗留」） | 拒绝该字段 |
| 请求路径 / 方法 | 不可信 | 经接口资源授权判定（《03》§2.2） | 拒绝，`4200` |
| 前端依菜单资源渲染的可见性 | **不参与服务端判定** | 仅决定前端渲染什么 | 不适用 |
| 访客身份 | 弱标识，可被伪造 | **不作为授权依据**（《03》§1.4） | 不适用——**不参与任何授权判定** |
| 评论正文 / 昵称 / 邮箱 / 主页 URL、来源 IP / UA | 不可信 | 仅作反垃圾判定的**输入**；用于判定的上下文（所属文章的标签与分类）**由服务端从父文章取，绝不接受客户端传入** | 不适用——不作授权依据，且判定失败不阻断请求（见 §四） |
| 退订令牌 | 不可信 | 服务端签发的签名令牌 | 拒绝，不执行退订 |
| 内容访问口令 | 不可信 | 服务端校验——口令**不存明文**，校验通过后签发**只对该篇内容有效**的短期令牌，并设失败次数限制 | 拒绝，不返回内容 |

## 三、通用原则

**1. 服务端是唯一裁决者。** 前端的可见性、禁用、隐藏处理都只是体验优化，不构成准入。每一处服务端操作独立判定，不假设「前端已经拦过」。

**2. 自报标识一律不可信。** 凡客户端可自由填写的内容（设备标识、来源 IP、平台名、排序字段），都必须有一个**服务端签发或服务端配置**的对照物，验证的对象是那个对照物，而非自报值本身。

**3. 区分凭据的作用，再决定失败如何处理。** 「缺失」与「非法」必须区别对待，且准入凭据与标识凭据的失败处理不同：

| 情形 | 准入凭据（访问 / 刷新令牌、OAuth `state`、防重放签名） | 标识凭据（设备令牌） |
|---|---|---|
| 未提供 | 按该接口的准入要求决定：匿名可访问的接口放行，且不赋予任何身份结论 | 放行，不建立访客身份 |
| 提供了但验证失败 | **拒绝** | **放行，但不建立访客身份、不参与归并** |

- **准入凭据必须严格**：一旦进入验证流程，失败即不可放行——否则攻击者只需提供一个非法值，就能降级到「未提供」这一放行分支，验证形同虚设。
- **标识凭据只需降级**：它不是准入门槛，只决定「要不要赋予额外身份」。若非法即拒绝，一枚过期的设备令牌就会让用户彻底无法匿名浏览；而它承担的风险仅是「拿不到浏览足迹」，降级足以覆盖。

**这一条是本节的要点**——把两类凭据混为一谈，无论倒向哪一边都会出事。

**设备令牌横跨两类**：同一枚凭据有两种用途，失败处理随之不同。

| 用途 | 场景 | 验证失败时 |
|---|---|---|
| 访客身份的依据 | 未登录访问 | **降级**——不建立访客身份，请求继续（《03》§1.4） |
| 设备绑定的凭据 | 已登录，且访问令牌签发时记录了设备 | **拒绝**——设备不匹配，认证失败（《03》§1.2） |

**分野在于它是否已成为准入链条的一环**：未登录时它只决定要不要额外赋予身份；已登录时它已是令牌有效性判定的一部分，此时放行等于让设备绑定可被「省略请求头」绕过。

## 四、依赖不可用时的降级方向

降级方向必须在设计期定，事故时来不及判断。

| 依赖 | 不可用时 | 方向 |
|---|---|---|
| Redis 会话存储 | 无法比对令牌版本 | **fail-closed，拒绝请求**——放行等于吊销机制失效 |
| Redis 业务缓存 | 限流计数、热点内容不可用 | **fail-open，放行并回源**——只影响性能 |
| 权限判定（缓存或查询） | 无法判定权限 | **fail-closed，拒绝** |
| 外部通知通道 | 邮件 / 短信发送失败 | 转入失败终态，由管理端重发（《02》§3.3） |
| 外部反垃圾 API | 内容安全检测不可用 | **fail-open，放行评论**——放行的代价可逆（事后可标记为垃圾），阻断的代价不可逆（全站无法评论） |

**判据：降级的代价是否可逆。** 会话与权限判断的错误放行**不可逆**（攻击已经成立）；缓存的错误放行**可逆**（只是变慢）。不可逆的一侧一律 fail-closed。
