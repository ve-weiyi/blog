# 13 数据模型

> **本文回答**：表怎么分、标识怎么选、约束放在哪、派生数据从哪来。
>
> 初稿：2026-10-27 · 最近更新：2026-10-27

## 一、目标与约束

**目标**：数据模型以**实体与不变量**为第一性。索引、类型、字段长度都是它的推论，不是可以独立拍板的选项。

**约束**：

- 存储为 MySQL 8 / InnoDB，只使用其原生能力（无分区、无触发器、无存储过程）。
- 领域划分以《互动与治理》《通知》《媒体、站点与分发》《统计与报表》为准；本文不重新裁决已定领域边界，只补它们没有覆盖的**结构性**问题。
- 引用完整性由谁保证必须先声明，不能默认「应用层会管」。
- 业务数据接近空，允许一次性重整；API 契约单独的演进成本另算。

**非目标**：

- 不追求范式极值。反范式只在**有明确来源与校正手段**时允许。
- 不为尚未出现的查询预建索引。

## 二、关键决策

### D1 领域边界尊重既有裁决

- **约束**：评论、留言、说说同属讨论域，但主题引用与生命周期不同；《互动与治理》已裁决「同一模块、三张表」。
- **决策**：不因字段相似而合并表。合并会掩盖「挂在主题上」与「站点级」两种生命周期的差别，并让主题引用失去边界。
- **备选**：按字段相似度合并为一张多态表。字段重合度高，但留言没有主题、没有回复链、审核策略也不同。
- **代价**：两套 CRUD 的重复样板需要用共享基础实现消除，而不是靠合并表消除。
- **重审触发**：留言需要挂到主题上，或两类互动的字段集合收敛。

### D2 通知按事件、条目、投递三层分表

- **约束**：一次通知意图可能面向一个收件人，也可能面向全部用户；一次投递可能重试多次；收件人的读状态与渠道的发送结果无关。三者的基数是 1 : N : M，状态机与生命周期各不相同。
- **决策**：按**角色**分三层，不按渠道拆。意图成事件表，兼作扇出工作单元与载荷唯一副本；收件人成条目表；外部渠道的发送尝试成投递表，邮件、短信、推送共用。拆分轴是「谁的状态」，不是「走哪个渠道」。
- **备选**：单表 + 渠道判别。字段一半对另一半永远为空，同一列的状态取值域随渠道变化，收件人一列同时承载用户标识、手机号与邮箱。
- **代价**：读取收件箱需要关联事件；三张表各自维护索引。
- **重审触发**：出现一种既进收件箱又需要多次发送的渠道，或三层严格 1:1。

> 裁决权属《通知》D1、D2；2026-10-29 由单表改为三层。原「按渠道拆表」提案因此关闭：它诊断对了痛点（一半字段永远为空），但把拆分轴落在了渠道而非角色上。

### D3 会话与日志各归其位

- **约束**：《认证与令牌》要求会话可撤销、可轮换、以 family 为单位失效，并规定「会话存储是权威」。会话实体已由令牌存储承载（Redis）。
- **决策**：会话只存在于会话存储，不落业务表。登录日志只追加事件；登出是**一条独立事件**，不回写「最近一条登录记录」的时间戳。在线状态只由会话回答。
- **备选**：在登录日志上按「同用户同设备且未登出」推断在线。同一设备重复登录会产生多条未登出记录，在线状态不可判定，且登出会改写历史事件。
- **代价**：登出事件需要一条新记录，日志量增加。
- **重审触发**：会话改由关系库承载，或需要长期归档会话历史。

### D4 列表不进主表

- **约束**：轮播图、说说配图、通知目标用户都是**一对多**，且各自带顺序或属性。
- **决策**：一对多一律落子表或原生 JSON；逗号分隔字符串不承载可增长集合。
- **备选**：逗号分隔存一列。无法按元素查询、无法约束元素合法、长度上限成为业务天花板。
- **代价**：读取需要额外一次查询或一次 JSON 解析。
- **重审触发**：集合元素需要参与查询或排序。

### D5 媒体存引用，不拼地址

- **约束**：《媒体、站点与分发》规定「直传对象存储，业务接口只保存引用」。
- **决策**：业务表保存存储键或媒体标识，不保存拼接后的完整 URL。地址由访问层按当前存储与分发策略生成。
- **备选**：各表存完整 URL。换存储、换域名、加签名时没有统一切换点，且无法识别孤儿对象。
- **代价**：读取路径需要一次解析；删除需要引用计数或延迟回收。
- **重审触发**：引入多存储后端或 CDN 签名。

### D6 一个自增主键，一个对外标识

- **约束**：所有表统一使用自增整数主键，代码生成、批量写入与按主键更新都依赖这一假设；用户还需要一个对外稳定、不可枚举的标识。
- **决策**：`t_user` 保留 `id` 作为主键，`user_id` 作为对外标识并加唯一约束；子表用 `user_id` 关联。全库不引入复合主键。
- **备选**：内部关联改整数（需在每个入口把外部标识解析成 id）；以外部标识为主键（破坏统一主键假设，生成代码需为单表开特例）。
- **代价**：关联列是 64 字节字符串，二级索引随之变大；主键与业务标识之间需要一条不变量保持同步。
- **重审触发**：字符串索引成为瓶颈，或引入分库分表需要全局 ID。

### D7 联表同样用自增主键

- **约束**：生成代码、批量写入与按主键更新都假设每张表有单一自增主键；关联表没有独立生命周期。
- **决策**：关联表同样使用自增 `id`，不额外加唯一索引，也不使用复合主键。关系重复由「同一事务内先删后插」的写入路径保证，并作为一条不变量被测试覆盖。
- **备选**：复合主键。唯一性由聚簇索引保证，少一列一索引；代价是生成器必须支持无代理主键的表，现有 CRUD 方法在这类表上全部失效。
- **代价**：唯一性不在库上，并发写入可能产生重复关系，依赖事务与方法实现。
- **重审触发**：出现跨进程并发写同一关联集合，或关系需要保留历史。

### D8 约束由模型表达

- **约束**：唯一性、引用完整性如果不落在库上，就只能靠调用方自觉。
- **决策**：业务不变量用唯一约束表达；引用完整性要么建外键，要么在文档里写明由谁保证并给出校验手段。**用一次查询做「是否重复」的预检，等于承认缺约束。**
- **备选**：全部由应用层保证。并发下必然出现脏数据，且没有兜底审计。
- **代价**：约束冲突会以数据库错误的形式暴露，需要在错误映射层翻译成业务语义。
- **重审触发**：引入分库分表或需要跨库引用。

### D9 类型按语义选

- **约束**：同一概念在全库应只有一种表示。
- **决策**：状态枚举按域统一宽度；数字用数值类型、日期用日期类型、结构化扩展用原生 JSON；定长值用定长类型；保留字不做列名。
- **备选**：按表的创建时间各行其是。同一字段在不同表里宽度、类型、可比较性都不同，聚合与排序要逐表适配。
- **代价**：改类型需要数据迁移，且新旧读代码要短暂共存。
- **重审触发**：无。

### D10 派生数据必须有来源

- **约束**：计数、聚合、缓存都是派生值，必须有可重算的源头；口径由《统计与报表》定义。
- **决策**：计数类字段允许存在，但必须能由明细重建；若源头只在缓存里，则明确声明「不可重建」并标注可接受偏差。统计的快照与实时值不得混用同一口径。
- **备选**：只存计数不留明细。无法去重、无法判断「我是否点过赞」、计数错了也修不回来。
- **代价**：明细表数据量增长，需要归档策略。
- **重审触发**：计数精度要求下降，或改为完全由缓存承载。

### D11 索引是查询的投影

- **约束**：索引有写成本，只在能服务真实访问路径时才有价值。
- **决策**：只对代码中真实存在的等值、范围、排序建索引；复合索引按「等值在前、范围与排序在后」排列；能覆盖排序时在尾部加主键列；单列索引若是某复合索引的前缀则删除。函数包裹列、前导通配、不等式谓词不计入索引设计依据。
- **备选**：按直觉给每个可能过滤的列建索引。写放大、优化器选择变差、维护成本上升。
- **代价**：新增查询模式时需要回头补索引。
- **重审触发**：出现跨表聚合或报表类查询。

### D12 通知模板的身份是场景与渠道

- **约束**：运行时按「场景 + 渠道 + 启用」查找模板；模板编码只用于管理端展示，投递侧的编码由提供方按场景给出。
- **决策**：模板的唯一身份是「场景 + 渠道」。同一场景在同一渠道只能有一条记录，启用状态作开关；模板编码是标签，不参与唯一性。
- **备选**：以「编码 + 渠道」为唯一键。同一场景可有两条启用记录，查找结果取决于物理顺序，投递不稳定。
- **代价**：同一场景无法并存多套文案（多语言等），需要时再引入维度列。
- **重审触发**：出现多语言或多版本模板。

## 三、机制与数据流

**实体分层**：

| 层 | 实体 | 说明 |
|---|---|---|
| 身份 | 用户、第三方绑定、角色、会话 | 对外标识与内部标识分离；会话独立于登录事件 |
| 内容 | 文章、页面、说说、相册、照片、分类、标签 | 类型决定分发行为；媒体按引用保存 |
| 互动 | 评论、留言、说说 | 按主题与生命周期分表，共享基础实现 |
| 治理 | 菜单、接口、角色关系、操作记录 | 权限按「角色—资源」关联表表达 |
| 通知 | 场景、事件、公告内容、收件箱条目、渠道投递、偏好 | 按事件 / 条目 / 投递分三层；文案在代码，不建模板表 |
| 观测 | 访问、登录、上传、每日快照 | 事件流只追加；快照是统计模块的物化数据 |

**所有权**：每张表只归属一个模块，跨模块读写走接口，不直接改别人的表。

**事务边界**：一次写操作只在一个模块内完成；跨模块一致性走异步消息与事务性发件箱，不靠跨表事务。

## 四、不变量

1. 联表不出现重复关系；该保证由「同一事务内先删后插」的写入路径承担，不依赖库上唯一约束。
2. 收件箱条目按「收件人 + 去重键」唯一（可分组场景含触发者，不可分组场景含事件），外部投递按「条目 + 渠道」唯一；两者各自成立，互不波及。
3. 在线状态只由会话回答，登录日志不用于判定在线。
4. 业务表保存存储引用，不保存拼接后的完整地址。
5. 内部关联列与被引用表的主键同类型；跨类型关联视为缺陷。
6. 每个唯一约束都对应一条业务不变量；不存在「只为了查得快」的唯一键。
7. 每个计数字段都能指出它的明细来源，或显式声明为不可重建。
8. 统计的快照值与实时值不会以同一口径对外；当天的实时值不写入历史快照。
9. 每个索引都能指向一段真实的查询代码；没有查询支撑的索引视为缺陷。
10. 同一语义字段在全库只有一种类型与长度。

## 五、失败与降级

| 场景 | 行为 |
|---|---|
| 唯一约束冲突 | 翻译成业务错误码返回，不暴露数据库错误文本；调用方可据此判定「已存在」 |
| 引用指向不存在的行 | 有外键时由数据库拒绝；无外键时由读取方返回「关联对象缺失」，不得静默填充默认值 |
| 计数与明细不一致 | 以明细为准重新计算；不可重建的计数在文档中标明可接受偏差 |
| 快照缺失 | 当天以实时值回答并标注为实时口径，不与历史快照混用 |
| 会话存储不可用 | 拒绝需要身份的请求（fail-closed），不因存储故障放行 |
| 主题已删除 | 互动记录保留，读取时以「主题不可见」呈现，不级联物理删除 |

## 六、边界与重新审视

### 待裁决提案

以下提案与既有设计文档结论不一致，尚未裁决，落地前需单独评审：

| 提案 | 与既有结论的冲突 | 支持理由 | 反对理由 |
|---|---|---|---|
| 留言并入评论（多态） | 《互动与治理》：留言与评论不合并 | 字段高度重合，可省一套表与 API | 留言无主题、无回复链，生命周期不同；合并后主题引用失去边界 |
| 新增点赞明细表 | 现有模型只有计数、无明细 | 计数可重建，可判定「我是否点过赞」 | 明细增长快，需要归档与缓存分层 |
| 新增统一媒体表 | 《媒体、站点与分发》：业务接口只保存引用 | 统一清理孤儿对象、切换存储 | 现有上传记录与相册已承担部分职责，可能只需要引用规则而非新表 |

### 结构性边界

- 出现第二类存储（文档库、列存）时，D6 与 D11 需要重评。
- 单表预计超过千万行时，D11 的索引策略要结合执行计划复评，并考虑归档。
- 引入分库分表后，D8 的外键方案失效，必须改为应用层保证并补对账。
