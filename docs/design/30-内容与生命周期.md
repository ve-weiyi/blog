# 30 内容与生命周期

> **本文回答**：内容有哪些形态，状态如何流转，读者何时能看到它。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、内容类型

| 类型 | 形态 | 归档 / 订阅 | 评论 | 可见性 |
|---|---|---|---|---|
| **文章** | 长文，带分类、标签 | 是 | 是 | 草稿 / 私密 / 公开 |
| **页面** | 静态页（关于、友链） | 否 | 视页面配置 | 公开 |
| **说说** | 短内容，可带图 | 并入时间线 | 是 | 私密 / 公开 |
| **相册 / 照片** | 媒体集合 | 否 | 否 | 私密 / 公开，照片继承相册 |

**类型决定分发行为，不是标签。** 文章进入归档、订阅与按标题 / 分类 / 标签筛选；页面只按固定入口出现；说说按时间线聚合；相册是媒体集合。把「是否进入 feed」做成一个字段，会让每新增一种类型都要重新组合行为。

## 二、可见性

### 2.1 单一谓词

**「读者能看到」只有一个判定：`status = 公开 AND is_delete = 0`。**

所有读者端读出口——详情、列表、归档、推荐、筛选——必须经同一条件；外部传入的过滤条件与之**合并而非替换**。禁止各处自行拼装过滤条件：漏写一处就是内容泄漏。

| 类型 | 读者可见条件 |
|---|---|
| 文章 | `status = public AND is_delete = 0` |
| 说说 | `status = public` |
| 相册 | `status = public AND is_delete = 0` |
| 照片 | 所属相册可见 |
| 页面 | 公开（页面没有私密态） |

**管理端读全量**：管理端的查询与读者端分开，显式包含草稿、私密与已删除；不通过「读者接口 + 管理端传参」复用，避免一个参数失误把草稿暴露给读者。

### 2.2 状态与评论策略分开

文章的 `status` 只表达**生命周期与可见性**：草稿、私密、公开。**评论是否可见是独立策略**，不进入文章状态。

把「评论可见」塞进状态枚举，会让状态机出现一条既不是生命周期、也不是可见性的分支；后续新增「评论需登录」「评论关闭」时，只能在同一个枚举里继续堆值，组合爆炸。评论策略属于互动域，文章只提供开关或引用。

### 2.3 删除

- 删除是**软删除**：`is_delete = 1`，数据保留，读者不可见。
- 恢复是把标记改回 0，**默认回到草稿而不是原状态** —— 避免已下线内容被误恢复上线。
- 物理销毁是独立动作、独立权限，不可逆；它与「删除」不是同一个词，也不共用同一个端点。
- 回收站清理由可靠定时任务驱动，不挂在「后台被访问」这类隐藏依赖上。

## 三、文章模型

| 维度 | 约定 |
|---|---|
| 作者 | `user_id`；内容是用户产物，作者不可为访客 |
| 分类 | **一对一**；分类当前是扁平集合，不建层级 |
| 标签 | **多对多**；标签是扁平集合，仅作横向聚合 |
| 封面 | 存储引用，不内嵌二进制 |
| 类型 | 原创 / 转载 / 翻译；转载与翻译必须带原文链接 |
| 置顶 | 布尔值，只影响列表排序，不改变可见性 |
| 计数 | 浏览数、点赞数；展示用途，不参与业务判定 |

**分类与标签的区别是结构性的**：分类驱动归档页，标签只做聚合。当前分类扁平；若引入层级，**只加一个 `parent` 字段**，不维护去规范化的 `children` 数组 —— 后者需要双写且容易失同步。

**上一篇 / 下一篇 / 推荐不落库**：它们由当前文章的分类、ID 与公开条件实时计算。落库会在每次发布、删除、改分类时引入同步问题，而计算成本在千级内容下可以忽略。

## 四、生命周期

```
草稿 ──▶ 公开 ⇄ 私密
  │        │
  └────────┴──▶ 软删除 ──▶ 恢复（回到草稿）
                   │
                   └──▶ 物理销毁（不可逆，独立权限）
```

- **草稿**：仅管理端可见；可以随时编辑、发布。
- **公开**：读者可见；进入列表、归档、推荐。
- **私密**：仅管理端可见；用于暂不公开但已定稿的内容。
- **软删除**：读者不可见；可恢复；到保留期后可销毁。

**发布事务**：文章与标签关联在同一事务内写入；事务提交后递增内容版本号，由缓存侧整体失效。事务内不做投递、不发通知 —— 这些动作不得阻塞发布，也不得让发布因为外部依赖失败而回滚。

**编辑**：编辑不改变 `created_at`；列表排序使用创建时间，避免旧文因修改标签而跳到首页。若需要「最近更新」排序，另设字段，不复用创建时间。

## 五、读路径与计数

- 读者端列表默认按创建时间倒序；置顶只在列表头部生效。
- 详情读取返回文章、分类、标签与关联文章；字段裁剪由 rpc 按读者/管理员视图完成。
- **浏览数**：Redis 计数优先，异步落库；Redis 不可用时以数据库值为准，不阻断阅读。
- **点赞**：Redis 集合记录用户与目标的点赞关系，数据库只保存聚合计数；Redis 不可用时点赞失败，不猜测状态（猜错会把「取消」做成「再次点赞」）。
- **计数不渲染进可缓存的 HTML**：页面留占位，由客户端异步拉取；否则每条评论、每个浏览都会让缓存失效。
- 缓存角色与失效方式见《缓存与一致性》。

## 六、关键决策

### D1 读者可见性收敛到单一谓词

- **约束**：多个读出口各自拼条件，漏一处即泄漏。
- **备选**：每个查询自行过滤；或在应用层二次过滤。
- **选择**：单一条件，所有读者出口经同一入口；外部条件合并而非替换。
- **代价**：查询构造需要统一入口，不能随手写原生查询。
- **重审触发**：出现无法用同一谓词表达的新可见性维度（如按订阅等级）。

### D2 状态只表达生命周期与可见性

- **约束**：状态枚举混入评论策略会导致组合爆炸。
- **备选**：用一个枚举表达所有开关。
- **选择**：状态只含草稿 / 私密 / 公开；评论策略独立。
- **代价**：需要单独的评论策略字段或配置。
- **重审触发**：评论策略需要与文章状态联动到无法拆分。

### D3 分类扁平，层级只加 `parent`

- **约束**：当前只有单层分类；层级需求尚未出现。
- **备选**：预建多级分类表；或维护 `children` 数组。
- **选择**：扁平；需要层级时加单一 `parent`。
- **代价**：层级查询需要递归或预计算路径。
- **重审触发**：出现稳定的多级归档需求。

### D4 软删除与物理销毁分离

- **约束**：可恢复与不可逆是两种权限、两种后果。
- **备选**：删除即物理删除；或只做软删除。
- **选择**：软删除可恢复；物理销毁独立动作、独立权限。
- **代价**：需要保留期与清理任务。
- **重审触发**：合规要求「删除即彻底」。

### D5 计数不参与业务判定

- **约束**：Redis 计数可能丢失或延迟。
- **备选**：用计数做热门排序或准入。
- **选择**：计数只用于展示；判定回权威源。
- **代价**：热门排序需要额外的离线口径。
- **重审触发**：出现必须实时按计数决策的业务。

### D6 关联文章实时计算，不落库

- **约束**：落库需要在发布、删除、改分类时同步维护。
- **备选**：维护关系表；或实时查询。
- **选择**：实时按分类与 ID 计算。
- **代价**：详情页多一次查询。
- **重审触发**：内容量增长到实时计算成为瓶颈。

## 七、不变量

- [ ] 读者端所有读出口使用同一可见性谓词。
- [ ] 管理端查询与读者端查询分离，不靠参数切换。
- [ ] 草稿与私密内容不出现在任何读者响应、feed 与索引中。
- [ ] 删除是软删除；恢复默认回到草稿。
- [ ] 物理销毁独立权限、独立端点、不可逆。
- [ ] 分类与标签都是扁平集合；层级只通过 `parent` 表达。
- [ ] 计数不参与权限、配额或可见性判定。
- [ ] 发布事务只写本模块数据；投递与通知在事务外。

## 八、失败与降级

| 情形 | 行为 | 用户可见后果 |
|---|---|---|
| 数据库不可用 | 读在缓存命中时可用；写失败 | 未命中缓存的页面不可用 |
| Redis 计数不可用 | 浏览数以数据库为准；点赞失败 | 计数暂停更新，阅读不受影响 |
| 缓存不可用 | 回源 | 延迟上升 |
| 软删除与并发编辑冲突 | 以条件更新裁决 | 后到的操作返回状态不允许 |
| 物理销毁失败 | 整体失败，不部分删除 | 管理端看到错误 |

## 九、边界与重新审视

- **修订历史**：当前不保存版本快照。若需要，按「全量快照 + 条数上限 + 最小保存间隔」设计，回滚是复制成新版本，不是指针回退。
- **定时发布**：当前只有草稿与发布。若引入，用「状态 + 时间」的轮询推进，条件更新保证幂等，不依赖流量触发。
- **预览与密码保护**：当前没有。若引入，使用可撤销的短期令牌，不使用「不可猜的固定 URL」；预览响应必须 `no-store`。
- **全文检索**：当前只有标题模糊匹配；引入 MySQL 全文或独立检索引擎需要重新评审。
- **多作者 / 协作**：当前作者单一；引入协作需要重新设计归属与编辑冲突。
- **分类层级**：只在出现稳定需求时加 `parent`，不预建多级表。
