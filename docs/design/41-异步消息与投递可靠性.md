# 41 异步消息与投递可靠性

> **本文回答**：哪些路径走异步，消息如何组织，丢了、重了、乱了分别怎么办。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、异步边界

异步不是「慢操作都扔进队列」，而是一条明确的判定：**这次投递是否在用户的等待路径上**。

| 路径类别 | 例子 | 选择异步的理由 | 发布失败时 |
|---|---|---|---|
| **用户等待结果** | 邮箱 / 短信验证码 | 外部通道延迟不可控 | **请求失败**，返回「服务暂不可用」 |
| **可当场完成** | 站内信扇出 | 接收者多，避免阻塞发布接口 | **降级为同步执行**，当场完成 |
| **管理动作** | 管理端重发投递 | 管理员必须知道是否受理 | **明确失败**，可重试 |
| **观测类** | 登录 / 登出日志 | 不影响主流程 | **尽力而为**，失败只记日志 |

**发布失败的行为由业务后果决定，不由消息队列统一决定。** 这是本节最重要的约定：同一个 `Publish` 调用，在验证码路径上失败必须让用户知道，在登录日志路径上失败不能阻断登录。把失败语义下沉到 MQ 组件、让所有路径共用一种行为，必然有一边是错的。

**判定规则**：

- 用户需要立刻知道结果 → 同步，或异步但发布失败即返回错误。
- 业务状态已经落库、仅需派生动作 → 异步；若队列不可用且能当场完成，降级同步。
- 纯观测、可丢失 → 异步且尽力而为。
- 需要与库内状态保持一致的投递 → 走事务性 outbox，见 §五。

## 二、拓扑

按业务域划分 topic exchange，routing key 即事件类型；需要独立并发或隔离的事件各自一个队列：

```
生产者 ──▶ exchange（topic, durable）
                ├── notification.email ──▶ queue（邮件）
                ├── notification.sms   ──▶ queue（短信）
                ├── notification.inbox ──▶ queue（站内信）
                └── audit.#            ──▶ queue（审计）
```

| 约定 | 内容 |
|---|---|
| 交换机 | 每个业务域一个 topic；持久化、不自动删除 |
| 队列 | 每个需要独立并发或隔离的事件一个，按消费组命名 |
| 路由键 | 事件类型，如 `notification.email`、`audit.login` |
| 连接 | 每进程一条 AMQP 连接，共享发布器池与订阅 channel |
| 预取 | 每消费者有界预取，限制在途消息数 |
| 启动 | 懒连接：broker 不可用不阻断服务启动，发布返回明确的「未连接」错误 |

**为什么不再按事件划分交换机**：连接数与交换机数不再随事件类型增长；routing key 真正参与路由，死信可投递到独立目的地，消费者也能按前缀选择性订阅。代价是同域内故障不再相互隔离——隔离粒度从「事件」变成「域」。

**队列仍按事件拆开**：不同事件的处理耗时差异很大（站内信扇出 vs 验证码投递），共用队列会让慢事件阻塞快事件。交换机与连接按域收敛，队列按事件隔离，两者不矛盾。

**交换机名与队列名是部署契约，不是普通常量。** 改名会在 broker 上留下孤儿交换机与队列，旧队列可能继续堆积而无人消费。改名必须按迁移处理：新建 → 双写/迁移 → 观察 → 删除旧拓扑。

## 三、事件契约

事件是生产者与消费者之间的契约，演进规则与接口契约一致：**只增不改、字段不得复用、未知字段忽略**。

每个事件至少包含以下信息，信封字段写入消息头，不进入业务负载：

| 字段 | 用途 |
|---|---|
| `mqx.event_id` | 稳定唯一标识，消费者幂等键 |
| `mqx.occurred_at` | 事件发生时间，用于排障与乱序判断 |
| `mqx.schema_version` | 负载契约版本 |
| 业务字段 | 消费者完成动作所需的最小集合 |

**不为消费者预取全量业务对象。** 事件只携带消费者完成任务所需的最小信息；需要更多状态时，消费者按业务键回查权威源，而不是依赖事件快照。

**事件中不出现凭据、令牌与完整敏感信息。** 日志同样按此约束脱敏。

**事件类型由 routing key 决定**，不依赖消息体里的类型字段做路由 —— 否则新增类型会变成消费者内部的 `switch` 扩散。

## 四、投递语义

| 项 | 约定 | 理由 |
|---|---|---|
| **至少一次** | 允许重复投递 | 崩溃、重连、未确认都会导致重投 |
| **幂等** | 消费者按 `event_id` 或业务键去重 | 重复不得产生第二条记录、不得重复发送 |
| **去重窗口** | 不短于最长重试窗口 + 业务记录保留期 | 窗口过短，迟到的重试会二次生效 |
| **顺序** | **不保证** | 顺序成本高；先后由时间戳或版本号表达 |
| **确认** | 处理成功后才确认 | 处理中崩溃 → 未确认 → broker 重投 |
| **重试** | 有界重试（默认 3 次，指数退避 + 抖动 + 总时限） | 无界重试会让毒消息占满消费者；长退避不占用消费线程 |
| **毒消息** | 解析失败视为永久失败，进入死信并记录 | 解析失败的消息重投多少次都不会成功 |
| **耗尽后** | 不再进程内重试；按策略进入死信或显式丢弃 | 避免无限循环；失败必须落到业务记录或死信 |
| **死信写入失败** | 不确认原消息：requeue / 留 pending / 停订阅 | 丢死信比重复投递更糟 |

**「不再重新入队」不等于「静默丢弃」。** 消息在耗尽重试后，必须满足其一：

1. 业务失败状态已经落库（例如投递记录进入失败终态，可由管理端重发）；
2. 进入死信队列，供人工检查；
3. 该路径本身是可丢失的观测数据，并留下错误日志。

三者都不满足的路径，不允许使用「耗尽即丢」的语义。

## 五、可靠投递：outbox

**问题**：数据库事务提交成功、消息发布失败，会出现「库内说已发布，投递从未发生」。在事务外补发无法消除这个窗口。

**决策**：需要与库内状态保持一致的投递，使用**事务性 outbox**——

```
业务事务：状态变更 + 写 outbox 事件（同一事务）
                         │
                         ▼
                    relay 读取未发送事件 ──▶ 发布 ──▶ 标记已发送
```

| 项 | 约定 |
|---|---|
| 写入 | outbox 事件与业务状态在**同一事务**内提交 |
| 发布 | 独立 relay 异步发布；发布失败不影响业务事务 |
| 语义 | 至少一次；消费者幂等 |
| 清理 | 已发送事件按保留期清理；relay 可重入 |
| 顺序 | 仍不保证；需要先后时用事件版本号 |

**哪些路径使用 outbox**：

| 路径 | 使用 | 理由 |
|---|---|---|
| 通知发布（站内信扇出） | 是 | 投递记录由事件派生，丢失后无其他补偿入口 |
| 通知重投（管理端） | 是 | 人工补救动作，必须持久化后由 relay 投递 |
| 通知撤回 | 否 | 状态与未读记录在同一事务内更新；广播只是加速信号，丢失由拉取兜底 |
| 验证码 | 否 | 验证码有 TTL，用户可以重发；发布失败直接返回错误 |
| 登录 / 登出日志 | 否 | 观测数据，可丢失 |

**为什么不用分布式事务**：outbox 用「同一库内的一次本地事务」换取了跨系统一致性，代价是至少一次与短暂延迟。这符合系统「跨模块不引入分布式事务」的约束。

**认领令牌（fencing）**：relay 认领时写入 `lock_token`，标记已发布/失败/死亡时校验 token；`ResetStuck` 回收时清空 token。迟到的 relay 无法覆盖新 owner 的状态，多副本并行认领安全。

**relay 的失败分类**：

- broker 不可用：留在 outbox，按退避持续重试，不判死；积压本身就是需要人行动的信号。
- 消息无法解码或校验失败：直接标 dead，等待人工处理。
- 权限、exchange 类型不匹配、消息过大等永久性 broker 错误：直接标 dead。
- 其余发布错误：有界重试后标 dead。

## 六、消费者设计

- **幂等是第一要求**：重复投递是常态，不是异常。
- **回查权威状态**：处理前确认业务对象仍处于可处理状态（例如消息已被撤回则跳过），不盲信事件快照。
- **永久失败与瞬时失败分开**：瞬时失败返回错误触发重试；永久失败先落库失败状态，再确认消息。
- **不吞错**：任何被确认的消息，都必须有对应的成功结果或已记录的失败结果。
- **有界并发**：预取与并发数决定在途消息上限；慢消费者不得无界堆积。
- **隔离**：一个消费者失败不影响其他队列；消费者之间不共享可变状态。
- **关闭**：停止接收新消息，等待在途处理完成，再关闭连接；未确认的消息由 broker 重投。关闭有截止时间，超时后不再无限等待。
- **可观测**：订阅暴露致命错误通道；永久断连必须上报，不允许静默停止消费。
- **去重键与副作用同事务**：库只提供稳定的 `mqx.event_id`，不提供通用 inbox。邮件/短信按 `biz_id + channel`，站内信按 `(message_id, recipient)`，登出按幂等更新；登录日志是可丢失的观测数据。通用去重若需要，只能是同一业务库里的 `processed_event` 表，不能放 Redis。

## 七、关键决策

### D1 发布失败的行为由业务后果决定

- **约束**：验证码失败必须让用户知道；日志失败不能阻断登录。
- **备选**：MQ 组件统一返回错误；或所有路径都降级同步。
- **选择**：每个生产者在发布失败时显式选择——失败请求、同步降级、明确可重试、尽力而为。
- **代价**：每个调用点都要写清楚失败语义，不能依赖组件默认值。
- **重审触发**：出现无法用这四类归纳的新路径。

### D2 至少一次 + 幂等，不追求恰好一次

- **约束**：恰好一次需要分布式事务或去重存储，成本远高于收益。
- **备选**：至少一次；或尽力而为。
- **选择**：至少一次；消费者按事件 ID 去重。
- **代价**：消费者必须处理重复。
- **重审触发**：出现重复会产生不可撤销副作用的路径。

### D3 与库内状态一致的投递使用 outbox

- **约束**：事务提交与消息发布之间有一个无法消除的窗口。
- **备选**：事务后直接发布（接受丢失）；或两阶段提交。
- **选择**：同一事务写 outbox，relay 异步发布。
- **代价**：多一张表、一个 relay 与至少一次语义。
- **重审触发**：消息中间件原生支持事务消息，且运维成本更低。

### D4 有界重试，耗尽后必须有明确落点

- **约束**：无界重试会让毒消息长期占用消费者；静默丢弃则无法追查。
- **备选**：无限重投；立即丢弃；进入死信。
- **选择**：有界重试（指数退避 + 抖动 + 总时限）；耗尽后按订阅声明进入死信，或对可丢失的观测数据显式声明丢弃。
- **代价**：每个订阅都要声明去向，配置校验拒绝「既不进死信、又没声明可丢」。
- **重审触发**：出现无法记录失败状态、又不能丢失的路径。

### D5 不保证顺序

- **约束**：顺序需要单分区单消费者，吞吐与可用性代价高。
- **备选**：全局有序；或按业务键分区有序。
- **选择**：不保证；需要顺序的路径用单队列单消费者（例如审计 login→logout），其余用时间戳或版本号表达先后。
- **代价**：消费端需要处理乱序。
- **重审触发**：出现必须严格有序的业务语义。

### D6 按业务域划分交换机，连接共享

- **约束**：连接与交换机数量不应随事件类型线性增长；routing key 需要真正参与路由，死信与选择性订阅才成立。
- **备选**：每事件 fanout + 独立连接（隔离强、连接多）；每事件 fanout + 单连接（连接少、routing key 退化为占位）；每域 topic + 单连接。
- **选择**：每域 topic exchange + 单连接 + 发布器池；队列按事件类型与消费组划分。
- **代价**：同域内事件共享故障半径；隔离粒度从事件变成域。
- **重审触发**：某个域的事件量或故障影响大到需要独立连接甚至独立 broker。

## 八、不变量

- [ ] 所有异步路径按至少一次投递设计，消费者幂等。
- [ ] 每个事件的消息头带稳定 `mqx.event_id`、`mqx.occurred_at` 与 `mqx.schema_version`。
- [ ] 处理成功后才确认；处理中崩溃导致重投是可接受的。
- [ ] 重试有界；耗尽后必须进入死信，或由订阅显式声明丢弃，不得静默消失。
- [ ] 死信写入失败时不得确认原消息。
- [ ] 解析失败的消息按永久失败进入死信，不重投。
- [ ] 需要与库内状态一致的投递走 outbox。
- [ ] outbox relay 尽力在消费拓扑就绪后启动；发布使用 mandatory 并检查 basic.return，未路由的消息不得标记已发布。
- [ ] broker 不可用时，发布返回明确错误，不静默成功。
- [ ] 订阅关闭有截止时间；永久断连通过错误通道上报。
- [ ] 交换机与队列名变更按迁移处理，不直接改名。
- [ ] 事件与日志中不出现凭据与完整敏感信息。

## 九、失败与降级

| 情形 | 行为 | 业务后果 |
|---|---|---|
| broker 不可用 | 验证码/日志按 §一 的语义处理；站内信留在 outbox | 验证码失败、日志丢失、通知延迟 |
| 发布成功但消费者下线 | 消息留在队列 | 恢复后继续消费 |
| 消费者处理中崩溃 | 未确认，broker 重投 | 重复处理，由幂等兜住 |
| 消费者永久失败 | 落库失败状态后确认，或进死信 | 可人工重发或排查 |
| 毒消息 | 进入死信并记录 | 不阻塞队列，且可追查 |
| 死信写入失败 | 不确认原消息：requeue / 留 pending / 停订阅 | 消息最终仍可投递；可能重复 |
| outbox relay 停机 | 事件堆积，业务事务仍成功 | 恢复后补发；状态一致 |
| broker 长时间不可用（outbox 路径） | 事件在 outbox 退避重试，不判死 | 投递延迟；恢复后补发 |
| 重复投递 | 按事件 ID 去重 | 无可见影响 |
| 乱序到达 | 按时间戳/版本判断最终状态 | 不保证中间态顺序 |

## 十、边界与重新审视

- **不做**：恰好一次、全局顺序、跨机房复制、分布式事务。
- **重新审视**：出现必须有序的业务语义；出现重复会产生不可撤销副作用；事件类型或吞吐增长到单 broker 成为瓶颈。
