# blog 博客系统 — 通知与实时通信

初稿：2026-09-11　·　最近更新：2026-09-16

## 一、通知

### 1.1 三层模型

通知被拆为**三个独立层次**，各自有独立生命周期：

| 层 | 含义 | 变更频率 |
|---|---|---|
| **模板** | 通知的形态：文案模板、占位符、适用场景 | 低——运营配置 |
| **内容** | 一次发布的实例：选模板、填参数、决定投递目标 | 中——每次运营动作 |
| **投递记录** | 内容落到每个接收者后的一条记录 | 高——随接收者数量增长 |

**分层理由**：三者的**变更主体与频率完全不同**。模板由运营长期维护；内容是事件性动作；投递记录是系统产物。混在一起会导致高频的投递记录写入反复触及模板定义。

### 1.2 投递通道

| 通道 | 语义 | 时效要求 |
|---|---|---|
| 站内信 | 用户在站内查看 | 无（拉取式） |
| 邮件 | 经外部邮件服务投递 | 中 |
| 短信 | 经外部短信服务投递 | 高 |

**通道与内容解耦**：同一条内容可选择多个通道投递，每个通道产生各自的投递记录。通道的**技术实现属于基础设施适配器**——与对象存储适配器同属一类做法（业务只依赖接口，实现可替换，见《02》§4.3）；通知域只负责编排"投给谁、走哪个通道"，不感知通道实现。

**两条由业务触发的通知链路**，都走邮件通道，且都必须**异步投递**——不得阻塞触发它们的写路径：

| 触发 | 接收者 | 说明 |
|---|---|---|
| 有新的评论 / 有待审评论 | 管理员 | 默认开启 |
| 自己的评论收到回复 | 评论者 | **评论系统唯一能把访客拉回站点的机制**，不可省略 |

**订阅相关邮件同属本域**：确认邮件用于验证邮箱归属，是订阅成立的前提；且**每封投递出去的邮件都必须携带免登录退订入口**——退订不得要求登录。含商业广告内容的邮件还须在标题前部标注，这是国内法规的硬性要求（见《[互联网电子邮件服务管理办法](https://www.gov.cn/gongbao/content/2007/content_554185.htm)》第十三、十四条）。

### 1.3 内容状态与投递状态

**两者的状态机不同，必须分开表达**：

- **内容**关注"是否已发出"——发布后可以被撤回
- **投递记录**关注"是否送达 + 是否已读"：
  - 站内信：未读 / 已读（用户动作驱动）
  - 外部通道：待发送 / 已发送 / 失败（外部服务驱动）

**撤回的边界**：撤回**只对「尚未投递」的记录生效**，使其不再投递；**已投递的既不追回也不删除**——邮件已发出、站内信已可见，都不因撤回而消失。已可见的站内信由内容治理流程单独处理，不与撤回混为同一动作。因此撤回是**单向、不可逆**的状态迁移。

**已读是投递记录的属性，不是内容的属性**——同一条内容投给多人，各人的已读状态互相独立。因此"全部已读"是一次批量状态更新，而非内容级标记。

### 1.4 接收者

接收者标识按通道而异（用户 ID / 手机号 / 邮箱）。这一差异**收敛在投递记录内部**，内容层只描述"投给哪些人"，不感知通道差异。

## 二、验证码

验证码**不是通知的业务内容，而是复用了通知的投递通道**——它是一个带 TTL 与一次性消费语义的短消息。

**生命周期归属**：生成、存储、投递、校验**四步同边界**，全部在通知域内完成。

**为何不归认证域**：若把校验移入认证域，认证域就必须跨服务读取通知域的存储才能完成校验，**数据所有权被劈开**。认证域只调用"发验证码"与"校验验证码"两个动作，不关心验证码如何产生与保存。

**存储归属**：验证码存 **Redis 的会话存储**（见《02》§4.2），**不落库**，过期由存储原生 TTL 实现。理由：验证码是短生命周期的一次性凭据，高频写入且无需长期留存；落库会让通知域的表被短期数据冲刷，与 §1.1 分层的初衷相悖。**验证码与「投递记录」不共用存储**——后者的定位是长期审计数据，两者生命周期相反。

**设计约束**：

- 验证码**一次性消费**，校验成功即失效，防止重放
- 带 **TTL**，且 TTL 与文案中的提示时长必须一致（否则用户按提示等待却已过期）
- **场景隔离**：同一手机号/邮箱在不同业务场景下的验证码互不干扰，避免注册验证码被用于重置密码。隔离以**场景作为键的一部分**实现，各场景独立计数、独立过期

## 三、实时通信

### 3.1 选型

采用 **STOMP over WebSocket**，内嵌于核心服务 `blog-rpc`，不单独部署。选择 STOMP 而非裸 WebSocket 的理由：**它自带订阅/发布的语义**（destination + subscription），消息路由不必自定义协议。

**与 HTTP 链路并行**，不共用认证中间件——原因见 §3.2。

### 3.2 身份校验

身份在**协议层**校验，而非连接建立前的 HTTP 请求：

```
WebSocket 建立 ──▶ STOMP CONNECT 帧（携带凭证）──▶ 校验 ──▶ 进入已连接状态
```

**三个设计点**：

- **凭证走 CONNECT 帧而非 URL**，避免令牌出现在访问日志与浏览器历史中
- **校验失败先延迟（约 1 秒）再返回错误帧**——**延迟用于抵抗暴力破解**。延迟**必须异步实施**（定时器 / 时间轮），不得阻塞连接处理线程——否则每个失败连接都占住一份处理资源，延迟反而成为放大攻击的杠杆
- **连接建立到校验通过之间不分配身份**，未校验的连接不能进入在线列表

实时通道的令牌是**准入凭据**，校验失败即拒绝——与设备令牌（标识凭据）「失败只降级」的语义不同，两类凭据的划分见《08》§三。

**实时通道的限流与连接控制**——HTTP 侧的限流不覆盖 STOMP（见《07》§2.4），需独立设置：

| 项 | 约定 |
|---|---|
| 连接数上限 | 按源 IP 与全局各设上限，超限拒绝新连接 |
| CONNECT 频次 | 按源 IP 限制**失败**次数，超出后**直接拒绝**，不再进入延迟流程——延迟是给偶发失败的正常用户留的余量，不是给持续试探留的 |
| 未认证连接 | 设**存活时限**，超时未通过校验即断开，避免连接被长期空占 |

### 3.3 与业务的边界

STOMP 层**不含博客业务语义**，是通用的协议实现。业务通过**事件钩子**接入：

| 钩子 | 业务用途 |
|---|---|
| 连接 | 上线通知、初始化用户上下文 |
| 订阅 | 补发历史消息 |
| 消息 | 内容过滤、持久化 |
| 断开 | 下线通知、清理状态 |

**消息的投递语义**（改动需重新走设计评审）：

| 项 | 约定 |
|---|---|
| 持久化时序 | **先持久化，再广播**。持久化失败即**不广播**，并向发送方回报失败——不接受「发送方已看到消息、刷新后消失」 |
| 广播失败 | 广播是尽力而为，不重试、不回报给发送方；未收到者由订阅时的补发兜住 |
| 补发 | 按会话维度的**游标**补发，客户端携带上次收到的位置；**必须设条数上限**，超限时截断并告知客户端已截断，避免一次订阅拉起全量历史 |
| 顺序 | 由持久化时分配的**自增序号**表达，保证**单会话内的先后**；不保证跨会话或跨副本的全局顺序 |

**边界收益**：STOMP 层可独立测试与替换；业务规则集中在钩子实现中，不污染协议层。

### 3.4 状态外置

在线列表与连接状态持久于 **Redis**，使核心服务可多副本部署：

- 副本间通过共享存储感知彼此的用户
- 单一副本重启不影响整体在线列表
- 与 HTTP 链路的会话 / 令牌状态同属**会话存储**实例（见《02》§4.2），**不与业务缓存混用可清空的库**。归入该实例的判据是**运维不得清空**，而非丢失后果——在线状态可由重连重建，与令牌状态的权威性不同级，但二者同属「不可随意清空」的一侧
