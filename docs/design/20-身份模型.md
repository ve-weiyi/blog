# 20 身份模型

> **本文回答**：请求背后可能是谁，系统承认哪几种主体，身份用什么标识表达、如何流转。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、身份的三个问题

| 问题 | 由什么回答 | 归属 |
|---|---|---|
| 这是谁？ | 主体分类与标识 | 本文 |
| 怎么证明？ | 凭据的签发与校验 | 《认证与令牌》 |
| 能做什么？ | 角色与权限判定 | 《授权与权限时效》 |

本文只回答第一个问题：系统承认哪些主体、它们的标识长什么样、生命周期如何变化。

## 二、主体分类

系统承认两类当前主体：

| 主体 | 是否有凭据 | 标识 | 参与授权 | 生命周期 |
|---|---|---|---|---|
| **注册用户** | 有：密码、验证码、第三方授权 | `user_id` | 是；管理员是「用户 + 角色」 | 注册 → 正常 → 停用 / 注销 / 删除 |
| **访客** | 无 | `guest_id`，由设备标识承载 | **否** | 首次匿名交互时创建；清 Cookie 即换新 |

**管理员不是独立主体**，而是拥有角色的注册用户。把「管理员」建成第三种身份，会让同一自然人在两套主体里各有一份数据，且登录、令牌、审计都要分叉。

**访客不是弱化的用户。** 它有自己的数据主体地位，可以被管理端查询、可以产生评论与留言；但它**不参与任何授权判定**。凡是需要「能做什么」的地方，只认注册用户。

**订阅者当前不存在。** 若引入邮件订阅，它应作为独立主体：只有邮箱与同意记录，没有凭据，不与用户共享数据表；不得先在用户表上加字段作为临时方案。理由与「用户 / 访客并列」一致：主体不同，生命周期不同，合并会引入一个罩住两者的宽泛上位词。

## 三、标识形态

### 3.1 主体标识

| 标识 | 形态 | 生成方式 |
|---|---|---|
| `user_id` | 36 位小写 UUIDv7，带横线 | 注册时生成 |
| `guest_id` | 32 位小写十六进制 | 首次匿名交互时生成 |

**标识是透明的、无类型前缀的字符串。** 不采用 `user_xxx` / `guest_xxx` 这类前缀：它会改变所有公共接口的字段形态，而类型判定本可以靠形态完成。

**形态判定只是提示，不是保证。** 按长度与字符集可以区分绝大多数标识，但历史数据可能呈另一种形态。消费方在查无结果时**必须回查另一类**，不能因为形态不符就丢弃记录。

**标识不携带权限、角色、租户或版本语义。** 它只回答「是谁」；「能做什么」由授权设计判定。

### 3.2 设备标识

读者端存在未登录但有状态的场景（浏览足迹、评论、点赞）。系统用**设备标识**承载访客身份：

- **由服务端签发**，客户端不得自报一个未经服务端生成的标识。
- 存放在第一方 Cookie，`HttpOnly`、`SameSite=Lax`、有效期 400 天；HTTPS 下加 `Secure`。
- **Cookie 是权威值**：存在时覆盖请求头；缺失时保留请求头，供非浏览器客户端使用。
- 形态不合法（长度、字符集不符）时视为不存在，重新签发。

**设备标识不是身份证明。** 它标识「这个客户端实例」，不证明「这个人是访客本人」；清除 Cookie 或换设备即换新标识，系统不承诺跨设备识别同一人。

### 3.3 设备令牌

设备令牌用于让「声明了身份」的请求可校验：

- **由服务端签发**：对设备标识与时间戳做带密钥的签名（HMAC），密钥只在服务端。
- 请求同时携带设备标识、时间戳与令牌；时间戳超出允许窗口（±5 分钟，另加 30 秒时钟偏差）即拒绝。
- **未声明设备标识的请求直接放行**，不产生访客身份结论；**声明了就必须校验**，缺件或签名不符即拒绝。
- 设备令牌是**标识凭据**，不是准入凭据：失败只影响访客身份，不影响匿名浏览。

**客户端可自行计算的哈希不是签名。** 如果令牌等于 `sha256(设备标识, 时间戳)`，任何知道这两个值的人都能算出它，令牌就退化为一致性检查，不能作为凭据。带密钥的签名是本设计的最低要求。

## 四、生命周期

### 4.1 访客

```
首次匿名交互 ──▶ 服务端生成 guest_id ──▶ 写入 t_guest ──▶ 下发 Cookie
                                                    │
清 Cookie / 换设备 ─────────────────────────────────┘ 生成新的 guest_id
```

- 访客记录在首次访问 `GET /guests/current` 时创建；设备指纹（OS、浏览器、IP、归属地）只作为**记录字段**，不作为标识依据。
- 清除站点数据后不承诺识别同一客户端 —— 这是有意的取舍，换取「不依赖设备指纹冒充他人」。
- **访客不自动升级为用户**。登录后是否归并既有行为，必须是一次显式动作，并以有效设备标识为依据；不得因邮箱相同就静默合并。

### 4.2 注册用户

| 状态 | 含义 | 对身份的影响 |
|---|---|---|
| 正常 | 可登录、可授权 | 令牌有效 |
| 停用 | 管理端禁用 | 不得签发新令牌；既有会话应被撤销 |
| 注销 | 用户主动注销 | 不得登录；数据按注销策略处理 |
| 删除 | 内部软删除 | 任何入口都不可见 |

- 注册经邮箱或手机验证码；注册成功即签发令牌，不要求二次登录。
- 第三方授权首次登录时创建用户与绑定关系；**绑定与解绑是显式动作**，不因第三方登录隐式合并账号。
- 状态从正常变为停用/注销时，必须撤销该用户全部会话 —— 身份状态改变不能等到令牌过期才生效。

## 五、消费方语义

- 日志、消息、在线名册里可能出现 `user_id` 或 `guest_id`。消费方**先按形态提示查询，查无结果时回查另一类**。
- 访客标识可以出现在业务数据里（评论作者、留言作者），但**不参与准入、配额、权限**判定。
- 同一设备可以先后登录多个用户；令牌绑定「用户 + 设备」，设备标识不随登录改变。
- 任何从外部输入得到的标识都视为不可信：使用前必须确认它属于当前请求的主体。

## 六、关键决策

### D1 用户与访客并列，不引入上位词

- **约束**：两者的凭据、生命周期、授权语义完全不同。
- **备选**：合并为「账号」，用类型字段区分；或把访客建成匿名用户。
- **选择**：两个并列主体，各自拥有数据。
- **代价**：跨主体查询需要回查两类；日志消费方要处理两种形态。
- **重审触发**：访客长出独立能力（行为归因、跨设备识别），或职责萎缩到不值得单独成主体。

### D2 标识无类型前缀，形态判定只作提示

- **约束**：加前缀会改变全部公共接口；不加前缀则形态判定可能误判历史数据。
- **备选**：加前缀；或引入独立的类型字段。
- **选择**：无前缀；形态仅作提示，查无结果必须回查。
- **代价**：消费方多一次查询。
- **重审触发**：历史数据形态成为主要误判来源。

### D3 设备标识由服务端签发，Cookie 权威

- **约束**：客户端自报标识可被任意伪造；设备指纹不可靠。
- **备选**：信任客户端自报；或用指纹生成。
- **选择**：服务端生成；第一方 Cookie 存储；请求头作为非浏览器客户端的补充。
- **代价**：清 Cookie 即失去历史；跨设备不可识别。
- **重审触发**：出现必须跨设备识别的合法场景。

### D4 设备令牌必须是带密钥的签名

- **约束**：无密钥的哈希可被任何客户端重算，不能证明任何事。
- **备选**：客户端自算哈希；或服务端签名。
- **选择**：服务端以密钥签名设备标识与时间戳；声明即校验。
- **代价**：密钥需要轮换与分发；时间戳需要容忍时钟偏差。
- **重审触发**：出现无法共享密钥的第三方客户端。

### D5 邮箱重合不自动合并

- **约束**：同一邮箱可能对应注册用户、访客、第三方绑定；自动合并会把不同主体的数据混在一起。
- **备选**：按邮箱自动合并；或显式绑定。
- **选择**：只有显式绑定动作才建立关联；未绑定即各自独立。
- **代价**：用户可能需要手动绑定已有账号。
- **重审触发**：产品要求统一账号视图，且能提供可靠的归属证明。

## 七、不变量

- [ ] 只有注册用户参与授权判定；访客标识不得进入权限分支。
- [ ] `user_id` 与 `guest_id` 的形态稳定，且变更视为契约变更。
- [ ] 设备标识由服务端生成；客户端自报值不作为身份依据。
- [ ] 设备令牌带服务端密钥；无密钥的哈希不得称为签名。
- [ ] 声明设备身份后必须校验；未声明则按匿名处理。
- [ ] 清除 Cookie 即视为新访客，不承诺跨设备识别。
- [ ] 用户状态变化必须撤销既有会话，不能等待令牌自然过期。
- [ ] 标识只是标识，不携带权限或角色。

## 八、失败与降级

| 情形 | 行为 | 用户可见后果 |
|---|---|---|
| Cookie 缺失 | 按匿名处理，不创建访客记录 | 个性化状态不可用，浏览正常 |
| Cookie 形态非法 | 视为不存在，重新签发 | 获得新的访客身份 |
| 声明了设备标识但缺令牌/时间戳 | 拒绝，`PARAM_MISSING` | 请求失败 |
| 设备令牌签名不符 | 拒绝，`REQUEST_SIGNATURE_INVALID` | 请求失败 |
| 标识查无结果 | 回查另一类；仍无则视为未知主体 | 记录保留，不臆造身份 |
| 用户状态为停用/注销 | 拒绝签发与校验令牌 | 需重新登录或联系管理员 |
| 会话存储不可用 | 身份校验失败（fail-closed） | 登录态请求失败；匿名可读 |

## 九、边界与重新审视

- **订阅者**：若引入邮件订阅，按独立主体设计；不与用户合并。
- **原生客户端**：设备标识与令牌需要适配非 Cookie 的存储；不改变主体模型。
- **跨设备识别**：当前明确不做；若产品需要，必须重新评审设备指纹的可信度与隐私影响。
- **历史标识**：形态可能不符合当前规范；消费方的回查规则不能被「长度判断」替代。
