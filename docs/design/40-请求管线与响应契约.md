# 40 请求管线与响应契约

> **本文回答**：所有 HTTP 请求共享哪条管线，错误如何表达，客户端按什么分支。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、请求管线

### 1.1 两层中间件

| 层 | 归属 | 内容 |
|---|---|---|
| **框架内置层** | 框架 | 追踪、请求日志、指标、并发上限、熔断、过载降载、超时、panic 恢复、请求体大小、解压、`Content-Type` 校验、方法匹配 |
| **自定义层** | 业务 | 全局链与路由组链，按「是否声明身份」与「需要什么权限」装配 |

**装配次序的原则**：越靠外，越早拒绝无效请求。全局链只做**廉价的合法性判定**（上下文、时效、签名、凭据完整性）；需要读缓存或查权限的判定留到路由组链，按需装配。

**限流在所有自定义中间件的最外层。** 认证与授权要读缓存、查权限，是 IO；若限流排在它们之后，攻击者可用无效凭据反复触发昂贵判定而不受约束。限流此时保护的是它之后的一切，包括它自己。

### 1.2 全局链

两个网关共用同一条全局链，由外向内：

| 次序 | 职责 | 设计要点 |
|---|---|---|
| 1 | 粗粒度限流 | 按客户端真实 IP + 路径；计数落在业务缓存 |
| 2 | 上下文透传 | 把请求头写入上下文，供下游 gRPC 消费 |
| 3 | 设备 Cookie | 读取或补发设备标识，只用于访客身份，不作准入 |
| 4 | 防重放 | 时间戳超出允许窗口即拒绝；**未声明签名头则放行** |
| 5 | 设备令牌校验 | 声明了设备身份就必须校验；缺件或签名不符即拒绝 |
| 6 | 访问日志 | 仅读者端；记录访问足迹，不参与判定 |

**「可选增强」的分界是「有没有声明身份」，不是「头齐不齐」**：

| 中间件 | 保护对象 | 未声明相应请求头 | 已声明但校验不过 |
|---|---|---|---|
| 防重放 | 本次请求的时效 | 放行 | 拒绝，`REQUEST_SIGNATURE_INVALID`（`401`） |
| 设备令牌 | 访客身份 | 放行，不产生身份结论 | 拒绝：缺件 `PARAM_MISSING`（`400`），签名不符 `REQUEST_SIGNATURE_INVALID`（`401`） |

**为什么声明之后必须拒绝而不能降级**：降级等于开出一条绕过校验的通道 —— 提交一个坏签名即可落到「未受保护」的匿名分支，签名随之失去意义。设备令牌仍不是门禁：不带设备标识即可绕过，它的价值是对已配合的调用方提供额外保护。凭据分类见《安全边界》。

### 1.3 路由组链

按「访问所需的身份强度」分级：

| 分组 | 链 | 说明 |
|---|---|---|
| 公开 | 无 | 健康检查、验证码等 |
| 登录 / 验证码 | 限流 | 未认证，但会被高频调用 |
| 需登录 | 认证 | 读者端个人中心、写操作 |
| 需权限 | 认证 → 授权 → 操作日志 | 管理端全部业务接口 |
| 需权限的写操作 | 同上 | 操作日志在最内层，只记录真正进入业务的请求 |

**授权只出现在管理端**。读者端不区分角色，登录即可 —— 内容对所有读者一视同仁，读者链路不引入权限查询。

**认证与授权必须分离**：认证回答「你是谁」，授权回答「你能做什么」；二者的失败语义不同（`UNAUTHENTICATED` 与 `PERMISSION_DENIED`），合并会让客户端无法区分「需要重新登录」与「权限不足」。

**主体维度的限流只能排在认证之后** —— 配额的分母是主体，不认证就取不到。全局链按 IP 粗限流，路由组按主体细限流。

## 二、错误表达

### 2.1 两层分工

| | HTTP 状态码 | 机器可读标识 |
|---|---|---|
| 回答 | 请求**能否被处理** | 处理**结果是什么** |
| 稳定性 | 标准语义 | 契约：稳定、可枚举、可文档化 |
| 消费者 | 网关、代理、监控 | 客户端业务分支 |

**标识只在一处映射为状态码。** 业务逻辑与中间件只产出标识，不产出 HTTP 状态；映射发生在响应出口。表外标识一律按服务端错误兜底 —— 这是防止「新增标识忘了定状态」的唯一可靠位置。

**`message` 不是契约。** 它面向开发者排错，客户端**不得**解析自然语言判断原因。

### 2.2 标识分类

分类依据是**客户端该如何反应**，不是「哪个模块抛出的」：

| 类别 | 场景 | 客户端应有的反应 |
|---|---|---|
| 流控 / 安全 | 请求过快、签名或时效不符 | 降速、重新签名、重新验证 |
| 请求参数 | 请求不合法 | 修正请求 |
| 身份认证 | 身份缺失或无效 | 补身份、重新登录 |
| 权限授权 | 有身份但无权限 | 引导用户 |
| 业务规则 | 请求合法，但业务上不成立 | 引导用户 |
| 服务端 | 服务端问题 | 按状态决定是否重试 |

**标识集合是封闭的。** 新增一个标识必须同时确定三件事：产出层、HTTP 映射、gRPC canonical 对照。集合的权威清单是代码中的标识常量；本文只定义分类与映射规则，不复制逐条取值。

**标识一经发布不得修改、不得回收复用。** 同一语义只有一个标识，可跨模块复用；模块维度的细分放在更具体的标识上（如 `ARTICLE_NOT_FOUND`），分类骨架保持稳定。

### 2.3 状态码选择

| 状态 | 用于 | 不用于 |
|---|---|---|
| `400` | 请求不完整：无法解析、必需请求头缺失 | 请求内容语义不合法 |
| `401` | 未认证：凭据缺失、无效、过期、签名不符 | 已认证但无权限 |
| `403` | 已认证但无权限；账号被禁用 | 未认证 |
| `404` | 路径或目标资源不存在 | 无权限查看（避免泄漏存在性） |
| `409` | 与资源当前状态冲突：已存在、状态不允许 | 并发编辑冲突 |
| `412` | 条件请求的前提不成立（并发编辑） | 一般业务规则失败 |
| `422` | 请求格式正确但内容语义不合法（字段校验） | 请求体无法解析 |
| `429` | 触发限流 | 服务端过载 |
| `500` | 未预期的服务端错误 | 可归类的依赖故障 |
| `502` / `503` / `504` | 上游无效响应 / 依赖暂不可用 / 下游超时 | 本地逻辑错误 |

**`401` 的 `WWW-Authenticate` 由标识决定，不由状态码决定**：令牌失效、登录凭据失败、权限不足、签名失败对应四种不同的 challenge。同为 `401`，客户端根据 challenge 判断该刷新、该重新登录，还是该重新签名。

**`Retry-After` 与余量头由产出方写入，出口不臆造。** 拿不到精确值就省略，不用默认值充数。

### 2.4 gRPC 一跳

下游返回的错误要在网关保持标识，不能让调用方只看到「内部错误」：

| 载体 | 内容 |
|---|---|
| canonical code | 标识在 gRPC 侧的粗粒度表达，供标准中间件按类处理 |
| `details[].ErrorInfo.reason` | 业务标识本身 |
| `details[].BadRequest.field_violations` | 字段级明细 |

**兜底规则**：details 缺失时，按 canonical code 还原为最粗的标识。该映射是单向的 —— 多个细标识合并到同一 canonical 是刻意的，不能反向推导细分语义。

**内部错误原文不跨进程边界。** 非业务错误在服务端日志记录，跨 RPC 只返回通用文案；调用方拿到的是「服务端错误」，不是数据库语句或堆栈。

## 三、响应信封

所有 JSON 响应使用同一信封：

| 字段 | 含义 |
|---|---|
| `code` | 业务标识；成功为 `SUCCESS` |
| `message` | 面向开发者的描述；不参与客户端分支 |
| `data` | 成功时为业务数据；失败时为空对象或字段级明细 |
| `trace_id` | 与 `traceparent` 头同源，便于跨网关、反代与 APM 关联 |

**规则**：

- 成功响应的 `data` 必须存在；无数据时给空对象，不给 `null`。
- 失败响应的 `data` 必须存在；无明细时为空对象，有字段级错误时为 `field_violations` 数组。
- 所有非 `2xx` 响应必须 `Cache-Control: no-store`。
- `traceparent` 使用 W3C Trace Context，响应头与信封同源。

**传输层路径的例外**：只有「有状态、无业务标识」的路径可以写不带 `code` 的 body —— 白名单只含 `200` / `201` / `400`：普通成功、创建成功与请求解析失败。该入口使用白名单，白名单外按内部错误兜底，**不得成为绕过标识表的后门**。

**信封之外的路径必须显式声明自己的契约**：SSE 流、文件下载、OAuth 重定向不承载 JSON 信封，客户端按各自形状处理，不得当作普通 JSON 响应解析。

## 四、客户端分发

- 客户端**只判断 `code`**，不解析 `message`，不按 HTTP 状态猜测业务原因。
- 未知标识走通用错误分支：提示重试或上报，不静默忽略。
- 前端的标识枚举必须与后端标识集合逐项对应；新增标识时同步更新，缺项视为契约破坏。
- 需要「重新登录」与「刷新令牌」的区分时，依据 challenge 与标识，不依据文案。

## 五、关键决策

### D1 标识与状态码分离，只在出口映射

- **约束**：同一状态承载多个原因；客户端需要稳定分支。
- **备选**：logic 直接写状态码；或用数字错误码。
- **选择**：logic 与中间件只产出字符串标识，出口统一映射。
- **代价**：多一层查表；新增标识需要同时登记映射。
- **重审触发**：出现无法用标识表达的传输层语义。

### D2 客户端只判标识

- **约束**：`message` 会随文案调整而变化，不能作为契约。
- **备选**：客户端匹配错误文本；或按状态码分支。
- **选择**：只判 `code`；未知标识走通用分支。
- **代价**：客户端需要维护枚举。
- **重审触发**：出现多个客户端无法共享同一套标识语义。

### D3 限流在最外层，计数不可得时放行

- **约束**：限流是保护性约束，不是正确性约束；Redis 故障时不能把全站挡在 `429` 后面。
- **备选**：计数失败时拒绝（fail-closed）；或跳过限流但静默。
- **选择**：放行并记录错误；放行是一个**显式声明**的降级方向。
- **代价**：Redis 故障期间失去限流保护。
- **重审触发**：限流从保护性约束变成计费或配额约束。

### D4 认证与授权分离

- **约束**：二者的失败语义不同，客户端反应不同。
- **备选**：合并为一个中间件；或把授权判断放进认证。
- **选择**：两个中间件、两个标识、两个状态语义。
- **代价**：需要认证结果在上下文中传递。
- **重审触发**：出现无法用「身份 / 权限」二分表达的新准入维度。

### D5 声明身份必须校验，不降级

- **约束**：降级会开辟绕过通道。
- **备选**：签名不符时按匿名放行；或仅在敏感接口校验。
- **选择**：未声明放行，声明即校验；失败拒绝。
- **代价**：调用方必须正确签名才能获得访客身份。
- **重审触发**：出现无法携带设备标识的合法客户端。

### D6 信封统一，例外显式

- **约束**：客户端需要统一的解析入口；流式与文件路径无法承载 JSON。
- **备选**：所有响应统一 JSON；或让各端点自定形状。
- **选择**：JSON 一律信封；SSE、下载、重定向各自声明形状。
- **代价**：例外路径需要独立的客户端处理。
- **重审触发**：出现第三种无法归入现有形状的响应类型。

## 六、不变量

- [ ] 业务逻辑与中间件不写 HTTP 状态码，只产出标识。
- [ ] 标识集合封闭；表外标识按服务端错误兜底。
- [ ] 客户端只按 `code` 分支，不解析 `message`。
- [ ] 所有非 `2xx` 响应 `Cache-Control: no-store`。
- [ ] 成功与失败响应的 `data` 字段都存在，不为 `null`。
- [ ] 内部错误原文不跨进程、不进响应体。
- [ ] `401` 的 challenge 由标识决定。
- [ ] 限流计数不可得时放行，并留下可观测的错误日志。
- [ ] 操作日志位于路由组链最内层，只记录进入业务的请求。

## 七、失败与降级

| 依赖 / 情形 | 行为 | 用户可见后果 |
|---|---|---|
| 限流计数（Redis）不可用 | 放行并记录 | 暂时失去限流保护，请求正常 |
| 会话存储不可用 | 需身份的请求拒绝（fail-closed） | 登录态请求失败，匿名可读 |
| 授权缓存不可用 | 回源判定；回源失败则拒绝 | 管理端请求可能失败，不越权 |
| 标识未登记映射 | 按服务端错误兜底 | 客户端看到通用错误，服务端日志保留标识 |
| gRPC 错误缺 details | 按 canonical code 还原粗标识 | 客户端得到类别正确的提示 |
| panic | 恢复并返回通用服务端错误 | 不泄漏堆栈 |
| 响应写出失败 | 记录错误 | 连接中断，无业务影响 |

## 八、边界与重新审视

- **不做**：GraphQL、按端点自定义状态语义、把错误码写进接口类型。
- **重新审视**：出现外部第三方调用方；前端需要按状态码做差异化缓存；标识集合增长到无法用六类归纳。
