# 32 互动与治理

> **本文回答**：读者如何参与互动，匿名内容如何防滥用、如何审核。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、互动形态

| 对象 | 谁创建 | 是否需登录 | 是否审核 | 是否可点赞 |
|---|---|---|---|---|
| 评论 | 读者 | 否，访客可评 | 是 | 是 |
| 留言 | 读者 | 否 | 是 | 否 |
| 说说 | 管理员 | — | — | 是 |
| 文章 | 管理员 | — | — | 是 |

**评论、留言、说说合在讨论域，但不合并为一个实体**：三者承载同一项能力（面向页面的用户发言），但评论挂在文章 / 友链 / 说说上，留言是站点级留言板，说说本身是内容。共用一个表会让主题引用与生命周期混在一起，拆成三个模块又会产出三个围绕单表的薄 CRUD。当前的组合是「同一模块、三张表」。

## 二、评论与留言

### 2.1 作者

- 已登录读者：记录 `user_id`。
- 访客：记录 `device_id`，由设备标识承载；**不伪造 `user_id`**。
- 同一请求里同时出现的 `user_id` 与 `device_id` 必须与认证上下文一致；客户端自报的作者字段一律忽略。

### 2.2 审核

评论创建时**默认未审核**，读者端只返回已通过审核且未删除的记录：

```
读者提交 ──▶ 未审核（仅管理端可见）
                ├─ 人工通过 ──▶ 读者可见
                └─ 人工拒绝 / 删除 ──▶ 仅保留审计
```

**默认预审是刻意的**：个人博客评论量小，逐条审核的成本可控；而一条垃圾评论公开展示的代价远高于审核成本。这与「大站默认不预审」相反，原因是规模不同，不是原则不同。

**自动通过**只对满足明确条件的记录开放：

- 同一身份（用户或设备）此前已有通过审核的评论；
- 命中本地白名单规则（无外链、无敏感词、频率正常）。

自动通过必须留下记录，便于事后追溯；规则调整后只影响新提交，不回溯已通过内容。

### 2.3 内容与结构

| 项 | 约定 |
|---|---|
| 长度 | 有上限；超长拒绝而不是截断 |
| 嵌套 | 有深度上限；达到上限后**降级为 `@` 平铺**，而不是隐藏回复按钮 |
| 编辑 | 编辑后标记状态为「已编辑」；不覆盖原内容的历史留痕由审计承担 |
| 删除 | 软删除；作者不可见，管理端保留 |
| 撤回 | 仅留言 / 说说支持；评论用删除 |

**达到嵌套上限后降级为平铺**：隐藏回复按钮会让深层评论彻底无法被回复，读者只能另起一条，讨论被割裂。平铺 + `@` 保留语义，也限制了渲染深度。

### 2.4 读者可见性

读者端的评论查询固定附加：

```
is_review = 已通过 AND status != 已删除
```

回复数与列表使用同一条件；**不得因为「回复数看起来不对」而放宽条件** —— 那等于把未审核内容泄漏到计数里。

## 三、治理

反垃圾按三层，前两层不依赖外部服务：

| 层 | 手段 | 失败时 |
|---|---|---|
| ① 本地规则 | 外链数阈值、关键词、IP / 设备频率、蜜罐字段、同身份历史通过 | 规则本身无外部依赖 |
| ② 外部内容安全 API | 可选；由配置开启；启用后内容出境，需在隐私政策披露 | **放行**，记录错误与次数 |
| ③ 人工 | 管理端审核队列 | 队列积压时不影响读者提交 |

**外部 API 失败时放行，不阻断评论**：它是可选增强，不是评论成立的前提。这与「准入凭据失败即拒绝」方向相反，判据是后果是否可撤销：垃圾评论可以事后删除，评论不可用会让互动直接停摆。

**「垃圾」态保留原数据**：误判恢复需要原文；直接删除会让误判不可挽回。管理端可以拒绝展示，但不物理删除。

**频率限制按主体与 IP 双重计数**：只按 IP 会误伤 NAT 后的正常用户；只按主体会被换设备绕过。

## 四、点赞

**点赞只有一份状态：`t_like`。** 是否已赞与点赞数都在读取时从它派生 —— 不设缓存副本，也不维护计数列。

| 查询 | 派生方式 |
|---|---|
| 某用户是否赞过某对象 | 按「用户 + 类型 + 目标 ID 集合」批量查明细 |
| 对象的点赞数 | 按目标 ID 分组计数 |

**写入是一条语句，判定来自受影响行数。** 点赞靠唯一键去重：冲突时插入不修改任何行、返回 0 行，据此判定「已赞」；取消点赞按删除的受影响行数判定「本来就没赞」。没有先读后写，因此不存在并发竞态；没有计数列，因此不存在增量算错。

**读路径按页取回。** 客户端不持有全量点赞集合；列表接口对当前页的 ID 批量判定已赞状态、批量统计点赞数。让客户端拉全量集合再自行判断，会把每次列表渲染变成「全量集合 × 列表长度」的比较。

**为什么不保留计数列。** 它完全可以从明细算出，且从不参与排序或筛选。留一份副本就要维护它（增量更新、行锁争用），还要为「算错了」准备重算任务；省下的只是一次分组计数。这一判断与「不引入不必要的派生状态」是同一条原则。

**拐点。** 当单个目标的点赞数进入数万量级、且它高频出现在列表首页时，分组计数的成本才会显现。届时按热点目标局部物化，而不是给所有目标加回一列。

**为什么不用消息队列。** 点赞是一次本地写：明细落库即是全部副作用，没有跨系统调用，也没有需要补偿的派生动作。异步化换来的只是微秒级的写延迟，代价却是消费链路、顺序保证与最终一致 —— 与本系统「不为不存在的规模付费」一致。

## 五、列表与计数

- 评论列表按创建时间排序；置顶只用于说说，不用于评论。
- 回复数来自「已通过且未删除」的子评论计数；与列表同条件。
- 分页有上限；深层回复按父评论分页拉取，不一次性展开全树。
- 读者端不返回审核状态、设备标识等内部字段；作者标识按视图裁剪为昵称 / 头像 / 游客标记。

## 六、关键决策

### D1 默认预审，可信身份自动通过

- **约束**：个人博客评论量小；垃圾评论公开展示的代价高。
- **备选**：默认公开、事后审核；或全部人工预审。
- **选择**：默认未审核；可信身份与本地规则可自动通过。
- **代价**：新读者首次评论需要等待审核。
- **重审触发**：评论量增长到人工审核无法承受，或垃圾评论比例低到预审不划算。

### D2 匿名互动，作者由上下文决定

- **约束**：读者端以浏览器为主，要求登录会杀死互动。
- **备选**：评论必须登录；或允许客户端自报作者。
- **选择**：访客可评论；作者标识来自认证上下文或设备标识。
- **代价**：需要设备标识与治理规则配合。
- **重审触发**：出现需要实名或强身份的场景。

### D3 外部内容安全失败放行

- **约束**：外部 API 是可选增强，不是评论成立的前提。
- **备选**：失败即拒绝；或静默跳过。
- **选择**：放行并记录；启用在隐私政策中披露。
- **代价**：外部服务故障期间垃圾评论可能进入。
- **重审触发**：垃圾评论比例高到放行的代价不可接受。

### D4 嵌套上限后平铺

- **约束**：无限嵌套会让渲染与分页失控。
- **备选**：隐藏深层回复按钮；或限制总楼层。
- **选择**：深度上限；超出降级为 `@` 平铺。
- **代价**：深层讨论的树形结构丢失。
- **重审触发**：出现必须保留完整树形的产品需求。

### D5 软删除，拒绝态保留数据

- **约束**：误判需要可恢复；审计需要原文。
- **备选**：直接物理删除。
- **选择**：软删除；拒绝展示但保留数据。
- **代价**：存储随历史增长。
- **重审触发**：合规要求彻底删除。

### D6 点赞只有一份状态，读写都从明细派生

- **约束**：需要快速判定是否已赞；点赞数只用于展示，不参与排序与筛选。
- **备选**：Redis 缓存已赞状态；维护计数列；只保留明细，读取时派生。
- **选择**：`t_like` 是唯一状态；已赞状态按页批量查明细，点赞数按目标分组计数；写入是一条靠唯一键去重的语句。
- **代价**：列表渲染多一次分组计数，成本随该页目标的点赞总数增长。
- **重审触发**：单个目标的点赞数进入数万量级且高频出现在首页。

## 七、不变量

- [ ] 读者端只返回已通过审核且未删除的评论与留言。
- [ ] 作者标识来自认证上下文或设备标识，不接受客户端自报。
- [ ] 回复数与列表使用同一审核条件。
- [ ] 嵌套有深度上限；超出降级为 `@` 平铺。
- [ ] 外部内容安全失败时放行，且记录错误与次数。
- [ ] 点赞的唯一状态是 `t_like`；已赞状态与点赞数都在读取时派生。
- [ ] 点赞的写入判定来自受影响行数，重复调用不产生额外副作用。
- [ ] 读者端按页返回是否已赞，不下发全量点赞集合。
- [ ] 删除目标时，在同一事务内清理其点赞明细。
- [ ] 计数不参与权限或可见性判定。
- [ ] 管理端可看到未审核与已删除内容；读者端不可见。
- [ ] 频率限制同时按主体与 IP 计数。

## 八、失败与降级

| 情形 | 行为 | 用户可见后果 |
|---|---|---|
| 外部内容安全 API 不可用 | 放行并记录 | 评论正常提交，垃圾可能进入 |
| 数据库不可用 | 点赞失败 | 点赞暂不可用 |
| 审核队列积压 | 新评论仍可提交，仅延迟可见 | 作者看不到自己的评论 |
| 评论内容超长 | 拒绝 | 需缩短内容 |
| 设备标识缺失 | 按匿名处理，记录 IP | 可评论，治理按 IP 计数 |

## 九、边界与重新审视

- **评论通知**：回复通知属于通知域；本文只定义「回复事件」的产生，不定义投递。
- **富文本 / 图片评论**：当前不支持的形态需要新的内容清洗规则。
- **垃圾态**：当前用「未审核 + 删除」表达；若引入独立的垃圾状态，需要重新设计审核状态机。
- **自动通过规则**：规则变化只影响新提交，不回溯。
