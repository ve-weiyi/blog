# 10 系统上下文与运行视图

> **本文回答**：系统边界在哪，一次读、一次写、一次登录、一次投递、一次连接分别经过哪些部件。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、系统上下文

系统是一个博客站点：读者浏览与互动，管理员维护内容、审核互动、配置站点。

**边界内**：内容、互动、媒体、站点、通知、身份与访问控制，以及它们依赖的存储与消息设施。

**边界外**：搜索引擎与订阅器、第三方 OAuth 平台、邮件与短信服务商。外部系统只通过契约交互，系统不假设它们可用。

| 外部参与者 | 交互方式 | 系统对他们的承诺 |
|---|---|---|
| 读者 / 管理员 | HTTPS、WebSocket | 匿名可读；写操作需身份，管理操作需权限 |
| 搜索引擎 / 订阅器 | RSS / Atom、sitemap.xml、robots.txt | 只暴露「已发布 + 公开」的内容；格式可被标准解析器解析 |
| OAuth 平台 | 授权码流程 | 平台不可用时该登录方式不可用，其他方式不受影响 |
| 邮件 / 短信服务商 | 异步投递 | 失败进入失败终态，可由管理端重发 |
| 对象存储 | 直传与读取 | 大对象不经过网关；存储不可用时上传显式失败 |

```
        读者                 管理员            搜索引擎 / 订阅器
          │                    │                      │
          ▼                    ▼                      ▼
   ┌─────────────┐      ┌─────────────┐        ┌─────────────┐
   │  app-web    │      │ admin-web   │        │  RSS / etc. │
   └──────┬──────┘      └──────┬──────┘        └──────┬──────┘
          │ HTTPS / WS         │ HTTPS / WS           │ HTTPS
          ▼                    ▼                      ▼
   ┌─────────────┐      ┌─────────────┐               │
   │  app-api    │      │ admin-api   │◀──────────────┘
   │ + STOMP hub │      │ + STOMP hub │
   └──────┬──────┘      └──────┬──────┘
          └────────┬───────────┘
                   │ gRPC
                   ▼
            ┌─────────────┐
            │  blog-rpc   │
            └──────┬──────┘
                   │
     ┌─────────┬───┴────┬─────────┬──────────┐
     ▼         ▼        ▼         ▼          ▼
   MySQL    Redis    RabbitMQ   Nacos     MinIO
```

## 二、容器视图

| 容器 | 职责 | 不负责 |
|---|---|---|
| `app-web` / `admin-web` | 静态资源与交互；读者端与管理端各自的产品形态 | 不直接访问数据库，不承载业务规则 |
| `app-api` / `admin-api` | HTTP 入口：参数校验、认证与授权中间件、调用 gRPC、响应封装 | 不落库，不做跨服务编排之外的业务判定 |
| `blog-rpc` | 业务逻辑、数据所有权、事务边界；12 个模块同进程 | 不定义对外契约，只实现 |
| STOMP hub | 长连接接入、订阅与广播、在线状态回调 | 不承担业务持久化；中继状态进程内，不跨实例 |
| MySQL | 业务实体的权威源 | 不承载会话与短期状态 |
| Redis | 会话存储与业务缓存两种角色 | 两种角色不得混用同一个库；职责见《缓存与一致性》 |
| RabbitMQ | 异步投递与日志落库 | 不承担请求链路的同步调用 |
| Nacos | 启动时拉取配置与服务发现 | 运行期不参与每次请求 |
| MinIO | 图片等二进制对象 | 不经过网关传输大对象 |

**两个网关各内嵌一个 STOMP hub**。站点在线用户与管理端在线分别使用独立的 Redis 集合；topic / queue 的中继状态各自进程内保存 —— 跨 hub 的消息扇出不在当前设计内，理由见 D3。

## 三、关键运行场景

场景只描述部件之间的顺序与职责，不描述函数与字段。

### S1 匿名读内容

```
浏览器 ──▶ 反向代理 ──命中──▶ 直接返回
              │ 未命中
              ▼
           app-api ──gRPC──▶ blog-rpc ──▶ MySQL
                                  │
                                  └──▶ Redis（业务缓存）
```

读路径的缓存层次、失效方式与一致性承诺见《缓存与一致性》；内容可见性的判定见《内容与生命周期》。

### S2 内容发布

```
admin-web ──▶ admin-api ──gRPC──▶ blog-rpc
                                   ├─ 事务内：写内容与关联
                                   └─ 事务后：递增内容版本号
```

**事务内只做本模块的写入**。缓存失效由版本号承担，不逐条清除；是否需要通知订阅者由《通知》定义，不得阻塞发布请求。

### S3 登录与令牌

```
浏览器 ──▶ app-api ──gRPC──▶ blog-rpc(auth)
                              ├─ 密码 / 验证码 / OAuth 校验
                              ├─ tokenx 签发
                              └─ 会话写入 Redis
```

第三方授权由浏览器跳转平台完成，回调落在网关；`state` 的生成、校验与消费见《认证与令牌》。登录成功后客户端如何存放令牌由令牌形态决定，不由网关决定。

### S4 通知发布与撤回

```
admin-api ──gRPC──▶ blog-rpc(notification)
                     ├─ 事务内：内容状态（发布时写 outbox 事件；撤回时同步更新未读记录）
                     └─ 事务后：投递 / 广播
                           ├─ MQ → 消费者：生成投递记录
                           └─ 实时通道：只推送「发生了变化」的信号
```

**发布与撤回走同一条管道**，只是事件类型与状态迁移方向不同。投递语义、去重窗口与多副本下的路由见《通知》；异步可靠性见《异步消息与投递可靠性》。

### S5 实时连接

```
浏览器 ──WebSocket──▶ app-api / admin-api
                        ├─ STOMP CONNECT：协议层校验身份
                        ├─ SUBSCRIBE：建立订阅
                        └─ SEND：业务钩子先持久化，再广播
```

两条通道（HTTP 与 STOMP）**并行且不共用中间件**：HTTP 的中间件链不覆盖长连接，长连接的限流、身份校验与存活时限必须独立定义，见《实时通信》。

### S6 定时任务

定时推进面向「状态 + 时间」：定时发布、物化统计刷新、回收站清理。任务由 `blog-rpc` 拥有，以「条件更新 + 受影响行数」推进，天然幂等、多副本安全。**不依赖「有请求才触发」的隐式定时器** —— 低流量站点上它可能长时间不触发，且失败静默。

## 四、关键决策

### D1 单个 rpc 服务，模块在进程内分界

- **约束**：个人博客量级；拆分收益（独立扩缩、故障隔离、独立发布）当前无法兑现。
- **备选**：按域拆多个 rpc 服务；或所有逻辑收进网关。
- **选择**：单 rpc 进程，12 个模块按数据所有权分界。
- **代价**：无法按域独立扩缩；一次部署影响全部模块。
- **重审触发**：某域需要独立扩缩；某域故障已波及他域；出现独立发布节奏。

### D2 网关只做编排，数据写入只在 rpc

- **约束**：数据所有权必须单一；网关不应成为第二个读写入口。
- **备选**：网关直连数据库以减少一跳；或网关承担部分业务逻辑。
- **选择**：网关只做参数校验、中间件与 gRPC 调用；事务与持久化全部在 rpc。
- **代价**：多一次进程间调用与序列化。
- **重审触发**：某类读请求的延迟无法通过缓存满足，且网关直读能显著改善。

### D3 实时通道内嵌两个网关，各持一个 hub

- **约束**：STOMP 需要长连接；单独部署一个实时服务会新增一套扩缩、鉴权与故障模式（P8）。
- **备选**：独立部署 STOMP 服务；只在一个网关内嵌。
- **选择**：`app-api` 与 `admin-api` 各自内嵌一个 hub，不单独部署。站点在线与管理端在线分别使用独立 Redis 集合；**topic / queue 的中继状态进程内保存，不跨 hub 扇出**。
- **代价**：跨网关或跨副本的实时消息不可达；读者端与管理端的广播互相不可见。
- **重审触发**：需要多副本承载长连接；出现跨网关必须互通的消息；单实例连接数成为瓶颈。

### D4 依赖同机，单机故障可恢复

- **约束**：成本与可用性目标只要求「可恢复」，不要求「不停机」。
- **备选**：依赖跨机部署；引入高可用集群。
- **选择**：MySQL / Redis / RabbitMQ / Nacos / MinIO 与业务容器同机或同集群；接受宿主机故障导致的全站停机。
- **代价**：单点故障即全站不可用；恢复时间取决于备份与恢复流程。
- **重审触发**：业务出现跨机连续性要求；单机资源成为瓶颈。

### D5 服务无状态，状态外置

- **约束**：需要在单机内增加副本；重启不应丢失会话。
- **备选**：会话留在进程内；用数据库承载会话。
- **选择**：业务容器不持有会话；令牌状态与在线状态外置到 Redis；业务缓存外置但可随时清空。
- **代价**：每次鉴权多一次 Redis 访问（可用极短本地缓存缓解）。
- **重审触发**：Redis 成为可用性瓶颈；需要跨机多副本。

### D6 大对象直传，不过网关

- **约束**：网关带宽与内存有限；图片是多规格派生的输入。
- **备选**：网关中转上传；后端代理下载。
- **选择**：客户端经存储适配器直传，接口只传引用（存储键）；派生图按需生成，参数进 URL。
- **代价**：上传链路依赖对象存储的可用性与客户端配合；权限校验必须前置到「签发上传凭据」这一步。
- **重审触发**：需要服务端强制扫描或转码后才允许入库。

### D7 HTTP 与实时通道并行，不共用中间件

- **约束**：长连接在协议层完成身份校验，HTTP 中间件链无法覆盖。
- **备选**：复用 HTTP 认证中间件；在升级请求前做一次性鉴权。
- **选择**：STOMP 在 CONNECT 帧校验身份；连接数、失败频次与未认证存活时限独立治理。
- **代价**：两套鉴权入口需要保持一致的身份语义，测试与审计各覆盖一遍。
- **重审触发**：两条链路的身份语义出现分叉。

## 五、不变量

评审与测试可直接对照：

- [ ] `cmd/api/*` 不持有数据库连接，不直接读写业务表。
- [ ] 业务数据的写入只发生在 `blog-rpc`。
- [ ] 跨进程只有 HTTP、gRPC、MQ、WebSocket 四种形态。
- [ ] 读者端与管理端共享同一份 gRPC 契约，差异在网关的路由、认证与视图裁剪。
- [ ] 视图裁剪在 rpc 完成；网关不通过「先取全字段再删」实现最小暴露。
- [ ] 读路径不触发物化表刷新；统计不参与业务判定。
- [ ] 业务容器不持有会话；令牌与在线状态只在 Redis。
- [ ] 两个网关的 STOMP hub 不假设对方的中继状态可见。

## 六、失败与降级

| 依赖不可用 | 系统行为 | 用户可见后果 |
|---|---|---|
| MySQL | 写请求失败；内容读在缓存命中时仍可返回 | 写操作报错；未命中缓存的页面不可用 |
| Redis 会话存储 | 需要身份的请求拒绝（fail-closed）；匿名读不受影响 | 登录态请求失败，匿名可继续浏览 |
| Redis 业务缓存 | 回源数据库 | 延迟上升，功能正常 |
| RabbitMQ | 异步投递不可用；发布方收到明确的「未投递」信号，不静默成功 | 邮件 / 短信 / 站内信延迟或需重发；主链路可用 |
| Nacos | 已加载的配置继续生效；新实例无法启动 | 重启与新扩副本失败；运行中的服务不受影响 |
| MinIO | 上传与派生图失败，显式报错 | 媒体上传不可用；已存在的引用按存储可用性返回 |
| OAuth 平台 | 该平台登录不可用 | 其他登录方式不受影响 |
| 邮件 / 短信服务商 | 重试至上限后进入失败终态 | 用户收不到，但可在管理端看到并重发 |
| 单个 STOMP hub | 该网关的长连接断开 | 前端重连；HTTP 功能不受影响 |

**降级方向的具体判据与凭据分类见《安全边界》**；本表只给系统级后果，不重复各域的机制。

## 七、边界与重新审视

- **跨机多副本**：当前只承诺单机内多副本；跨机需要重新评审会话、在线状态与 STOMP 中继。
- **读写分离**：当前不做；若做，读路径的缓存与一致性承诺必须重新推导。
- **拆分 rpc**：只在 D1 的重审触发出现时讨论，且拆分只改调用方式，不改模块边界与契约。
- **独立实时服务**：见 D3；若长连接规模或跨网关互通成为需求，再评估。
