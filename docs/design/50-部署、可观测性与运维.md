# 50 部署、可观测性与运维

> **本文回答**：系统如何部署、配置如何注入、发布与回滚如何保证可逆、故障如何被发现与恢复。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、部署形态

系统支持两种生产形态，**共用同一套镜像命名**（`ghcr.io/ve-weiyi/<service>`）：

| 形态 | 适用 | 编排 | 依赖服务 |
|---|---|---|---|
| **Kubernetes（k3s）** | 需要自愈、滚动更新、证书自动续期 | `deploy/k8s/` 清单 | 集群内中间件 |
| **Docker 单机** | 一台机器、手工运维、发版走 CI | CI 直接 `docker run` | 宿主机 Compose |

本地开发另有一种：依赖服务用 Compose 拉起，业务进程在本机运行，便于断点调试。**它只负责依赖，不负责业务容器**。

**五个服务**：

| 类别 | 服务 | 说明 |
|---|---|---|
| 前端 | `app-web`、`admin-web` | 容器内 Nginx 托管静态资源 |
| 网关 | `app-api`、`admin-api` | HTTP 入口；各自内嵌一个 STOMP hub |
| 服务 | `blog-rpc` | 业务与数据；12 个模块同进程 |

**依赖同机或同集群**：MySQL、Redis、RabbitMQ、Nacos、MinIO。**接受单机故障导致的全站停机**，目标不是不停机，而是可恢复 —— 这决定了备份与恢复演练是部署的一部分，而不是运维的加分项。

**Redis 按角色拆分**：会话存储与业务缓存独立实例；K8s 清单必须分别声明，后者不需要持久卷，前者需要。判据与后果见《缓存与一致性》。

## 二、配置

| 类别 | 来源 | 约束 |
|---|---|---|
| 运行时配置 | Nacos（按环境隔离） | 应用启动时拉取；不打包进镜像 |
| Nacos 连接参数 | 启动参数 / 环境变量 | 只用于找到配置中心 |
| 密钥 | 环境变量或密钥对象 | **不进仓库、不进镜像、不进文档** |
| 本地默认值 | 配置文件 | 只用于开发；缺失关键项时启动失败 |

**配置外置**：改配置不需要重新构建镜像；Nacos 不可用时，已加载的配置继续生效，新实例无法启动 —— 这是可接受的，因为配置中心本身就是启动依赖。

**启动时校验，缺失即失败**：数据库、Redis、SMTP、短信模板、OAuth 平台列表等关键配置缺失时，进程必须**显式失败并打印缺哪个变量**。禁止静默回落到「看起来能用」的默认值 —— 那会让一个配置错误在生产环境以「功能偶发失效」的形式出现。

**配置分层**：应用行为配置（超时、分页上限、限流配额）与凭据分开管理；凭据轮换不应要求改代码或重建镜像。

## 三、镜像与发布

### 3.1 构建

- 后端：一个 Dockerfile 通过构建参数指定服务目录，产出不同服务镜像。
- 前端：一个 Dockerfile 通过构建参数指定产物目录与后端地址，产出两个前端镜像。
- **构建逻辑单点维护**：新增服务只增加条目，不复制 Dockerfile。

### 3.2 发布

```
CI（push v* tag）──▶ 构建并推送 5 个镜像（不部署）
workflow_dispatch ──▶ 按服务构建，可选部署到 docker / k8s
```

- **普通 CI 只做静态检查与测试，不部署**。
- 部署经 SSH 到目标机执行；K8s 路径在节点上更新镜像。**不把 kubeconfig 存进 CI Secret**：它含集群最高权限。
- 滚动更新：先起新实例，健康检查通过后再摘旧实例；单副本形态下会有短暂中断，这是单机目标允许的。

### 3.3 数据库迁移

**迁移必须先于代码，且向前兼容**：

| 步骤 | 内容 |
|---|---|
| expand | 新增列 / 表 / 索引，旧代码仍可运行 |
| migrate | 新代码写入新结构，兼容旧数据 |
| contract | 确认无旧版本读写后，删除废弃结构 |

- **禁止在启动时自动迁移**：多副本同时启动会竞争；迁移失败会让服务无法启动，且难以回滚。
- 迁移脚本版本化，与应用发布解耦；每次迁移必须可在旧代码上执行。
- 破坏性变更（删列、改类型）只能在 contract 阶段做，且必须在旧版本完全下线之后。

### 3.4 回滚

- 镜像回滚是首选：保留上一版本镜像，直接切换。
- **迁移不可回滚时，代码也不可回滚** —— 这正是「先 expand、后 contract」的原因。回滚窗口内，数据库必须同时兼容新旧代码。
- 配置变更与镜像发布分开；先改配置再发代码，或反之，必须能独立回退。

## 四、可观测性

| 维度 | 内容 | 用途 |
|---|---|---|
| 日志 | 结构化、脱敏、带 trace id | 定位单次请求 |
| 指标 | 请求量、错误率、延迟分位、依赖状态 | 发现趋势与容量 |
| 追踪 | W3C `traceparent`，贯穿网关与 rpc | 跨进程定位慢点 |
| 健康 | `/ping` 与探针 | 滚动更新与自愈 |
| 审计 | 登录、操作日志 | 追溯谁做了什么 |

**核心指标**：

- 请求：QPS、5xx 比例、P50/P95/P99 延迟。
- 依赖：数据库连接与慢查询、Redis 命中率与错误率、MQ 积压与消费延迟、对象存储错误率。
- 业务：登录失败率、验证码发送成功率、通知投递失败数、审核队列长度。
- 资源：CPU、内存、磁盘、PVC 使用率、证书到期时间。

**告警只对「需要人行动」的指标发**：5xx 持续升高、依赖不可用、磁盘将满、证书将过期、MQ 积压持续增长。对每个请求级的瞬时抖动告警，会让告警被静音，真正的问题随之被淹没。

**日志脱敏是默认**：密码、令牌、授权码、完整手机号 / 邮箱不进入日志；错误原文只进服务端日志。

## 五、备份与恢复

| 数据 | 方式 | 恢复目标 |
|---|---|---|
| MySQL | 定期全量 + binlog（可选） | 恢复到最近一次可用备份 |
| Redis 会话存储 | 开启持久化 | 丢失即全员重新登录；不承诺零丢失 |
| 业务缓存 | 不备份 | 可重建 |
| MinIO | 持久卷 / 对象存储版本 | 恢复到备份时点 |
| Nacos 配置 | 版本化导出 | 重建配置中心 |

**备份必须演练恢复**：没有恢复演练的备份只是「以为有备份」。恢复演练至少覆盖：数据库恢复到空环境、对象存储引用可读、服务能启动。

**RPO / RTO 是量级判断**：个人博客允许「丢失最近一段时间的数据、停机一段时间恢复」。建议目标 **RPO ≤ 24 小时、RTO ≤ 4 小时**；具体数值由备份频率与恢复演练结果确认，不承诺零丢失。

**清理**：日志、统计物化表、outbox 已发送事件、软删除内容按保留期清理；清理任务必须幂等、可重入，且有上限，不能一次删除全表。

## 六、安全运维

- **TLS 终止在入口**：K8s 用 cert-manager 自动签发续期；Docker 形态手工证书 + 宿主机 Nginx。
- **只暴露必要端口**：入口 `80/443`、K8s API `6443`、SSH `22`；数据库、缓存、MQ、对象存储不直接暴露公网。
- **凭据轮换**：数据库口令、Redis 口令、MQ 口令、OAuth secret、JWT / 设备令牌密钥都要有轮换路径；轮换不需要重建镜像。
- **最小权限**：服务账号只授予所需权限；kubeconfig 不入库、不入镜像、不进对话上下文。
- **文档不含凭据**：口令、授权码、AK、私钥不得写进文档、注释、提交信息。

## 七、关键决策

### D1 两种生产形态，共用镜像

- **约束**：不同规模与运维能力需要不同形态；复制镜像命名会增加发布错误。
- **备选**：只支持 K8s；或只支持 Docker。
- **选择**：两种形态并存，镜像命名统一。
- **代价**：两套部署路径都要维护。
- **重审触发**：一种形态长期无人使用。

### D2 配置外置，启动时校验

- **约束**：配置随环境变化；错误配置必须在启动时暴露。
- **备选**：配置打包进镜像；或缺失时回落默认值。
- **选择**：Nacos + 环境变量；关键项缺失即失败。
- **代价**：启动依赖配置中心。
- **重审触发**：配置中心成为不可接受的启动单点。

### D3 迁移向前兼容，先 expand 后 contract

- **约束**：代码可回滚，schema 不可回滚。
- **备选**：启动时 AutoMigrate；或迁移与代码同版本强绑定。
- **选择**：版本化迁移；expand-contract；禁止启动自动迁移。
- **代价**：一次变更多个发布步骤。
- **重审触发**：出现无法用 expand-contract 表达的 schema 变更。

### D4 单机故障可恢复，不追求不停机

- **约束**：成本与规模目标只要求可恢复。
- **备选**：多机高可用。
- **选择**：单机 / 单节点集群；备份与恢复演练作为必要组成。
- **代价**：宿主机故障即全站停机。
- **重审触发**：出现跨机连续性要求。

### D5 可观测性是部署的一部分

- **约束**：单机故障后必须能定位；没有日志与指标就无法恢复。
- **备选**：出问题再补。
- **选择**：日志、指标、追踪、健康检查随服务一起交付。
- **代价**：需要维护采集与告警配置。
- **重审触发**：观测成本超过其带来的恢复收益。

### D6 凭据不进仓库、镜像与文档

- **约束**：仓库、镜像与对话都可能被复制或泄漏。
- **备选**：把凭据写在配置文件里，靠权限控制。
- **选择**：环境注入；文档只写变量名与来源。
- **代价**：部署时需要额外的密钥管理。
- **重审触发**：出现无法用环境注入的运行时场景。

### D7 备份必须可恢复

- **约束**：未演练的备份不可信。
- **备选**：只做备份，不做恢复演练。
- **选择**：定期演练恢复到空环境。
- **代价**：需要额外的环境与时间。
- **重审触发**：恢复流程自动化到无需人工演练。

## 八、不变量

- [ ] 五个服务使用统一镜像命名；两种形态可互换镜像。
- [ ] 运行时配置不打包进镜像；关键配置缺失时启动失败。
- [ ] 凭据不出现在仓库、镜像、文档与日志。
- [ ] 数据库迁移先于代码，且旧代码能在新 schema 上运行。
- [ ] 禁止在应用启动时自动迁移。
- [ ] 回滚窗口内，schema 同时兼容新旧代码。
- [ ] 所有服务有健康检查；入口只暴露必要端口。
- [ ] 日志脱敏；错误原文不跨进程、不进响应。
- [ ] 备份有恢复演练；清理任务幂等且有上限。

## 九、失败与降级

| 情形 | 行为 | 影响 |
|---|---|---|
| 配置中心不可用（启动） | 启动失败 | 新实例无法拉起；运行中实例不受影响 |
| 数据库不可用 | 写失败；缓存命中的读仍可用 | 部分功能不可用 |
| Redis 会话存储不可用 | 需身份的请求拒绝 | 登录态不可用；匿名可读 |
| MQ 不可用 | 异步投递失败或降级 | 通知延迟；主链路可用 |
| 对象存储不可用 | 上传失败 | 媒体功能不可用 |
| 镜像回滚 | 切回上一版本 | 依赖 schema 兼容 |
| 磁盘将满 | 告警；清理任务 | 未处理会导致写入失败 |
| 证书过期 | 入口不可信 | 全站 HTTPS 失败 |

## 十、边界与重新审视

- **多机房 / 异地多活**：不做；与可用性目标冲突。
- **服务网格 / 自动扩缩**：当前单机与固定副本；出现流量波动再评估。
- **集中日志平台**：当前依赖容器日志与基础采集；日志量增长后再引入。
- **密钥管理服务**：当前环境注入；出现多环境、多团队共享时再评估。
