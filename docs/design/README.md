## 阅读路径

按角色选路径，不必从 00 顺序读到 51。

| 读者 | 路径 |
|---|---|
| **新人** | 00 → 10 → 11 → 12 → 40 → 50，半天建立全局 |
| **做需求** | 00 → 对应领域（30–35）→ 涉及身份看 20–23 → 涉及接口看 12 → 涉及响应看 40 |
| **评审** | 00 → 目标卷 → 该篇「关键决策」与「不变量」 |
| **排障** | 50（可观测性）→ 41 / 42（异步与缓存）→ 对应领域篇的「失败与降级」 |

新人的路径用于建立全局；第二遍再按业务域深入（20–35），不必一次读完。

## 写作与引用约定

### 单篇结构

每篇固定六节，读者不需要适应不同文风：

1. **目标与约束** —— 这一层要满足什么、不满足什么
2. **关键决策** —— `D1…Dn`，每条含约束、备选、代价、重审触发
3. **机制与数据流** —— 决策如何落地为结构、时序与所有权
4. **不变量** —— 可直接转成评审项或测试断言的清单
5. **失败与降级** —— 依赖不可用时系统往哪边走
6. **边界与重新审视** —— 什么条件变化会推翻本文

`00` 是宪法，按约束、原则、决策与术语组织，不套用单篇六节模板。

文首固定为：

```markdown
> **本文回答**：一句话。
>
> 初稿：YYYY-MM-DD · 最近更新：YYYY-MM-DD
```

### 引用规则

- 跨文档引用写 `《标题》` 或 `《标题》D编号`，**不写编号与章节号** —— 章节号会随编辑漂移，标题与决策号不会。
- 同一事实只定义一次。需要复述时写成一句结论 + 指针，不复制表格。

### 事实来源

- 设计文档记录**应然**：约束、决策与不变量。
- 写作时以代码与部署清单核对事实。若实现与应有设计冲突，只记录设计，冲突单独提出裁决 —— **不把现状写成设计**。
- 实现进度与改造偏移属于 `docs/feature/` 的日期快照，不属于本目录。

## 文档契约

| 内容 | 归属 |
|---|---|
| 决策、约束、不变量、失败语义、边界、权衡 | `docs/design/` |
| 分步实施、某次改造的方案与偏移 | `docs/feature/` |
| 编码规范、API 风格、提交规范 | `docs/standards/` |
| 历史审查结论 | `docs/review/` |
| 函数签名、DDL、字段拼写、配置全文、目录清单 | 代码 / README / 部署清单 |

判定一句话：**这条内容变了，需要重新走设计评审吗？** 需要 → `design/`；不需要 → 它属于 `feature/`、代码，或什么文档都不是。
