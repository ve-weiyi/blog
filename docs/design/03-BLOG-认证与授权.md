# blog 博客系统 — 认证与授权

初稿：2026-09-11　·　最近更新：2026-09-16

## 一、认证

### 1.1 登录方式

| 方式 | 凭据 | 使用场景 |
|---|---|---|
| 密码 | 账号 / 邮箱 / 手机号 + 密码 | 通用 |
| 邮箱验证码 | 邮箱 + 一次性验证码 | 免密登录、注册 |
| 手机验证码 | 手机号 + 一次性验证码 | 免密登录、注册 |
| 第三方授权 | OAuth2.0 授权码 | GitHub / Gitee / QQ / 微信 |

四种方式**最终收敛到同一身份主体**——无论从哪条路径进来，都产出统一的用户身份与令牌，后续认证与授权不区分来源。验证码的生成与校验属通知域（见《04》），认证域只消费其校验结果。

**注册**走邮箱 / 手机验证码（`POST /auth/registrations`，见《02》§1.3），与登录共用同一套验证码校验；注册成功即签发令牌，不要求注册后再登录一次。密码登录与第三方授权**不承载注册**——前者要求账号已存在；后者在首次授权时创建本地用户，已有本地用户时按 §1.3 走显式绑定，不隐式合并。

### 1.2 令牌体系

采用**双令牌**设计：

| 令牌 | 有效期 | 用途 |
|---|---|---|
| 访问令牌 | 短（小时级） | 每次接口调用携带 |
| 刷新令牌 | 长（天级） | 仅用于换取新的访问令牌 |

**设计约束**：

- 令牌**可主动失效**——登出、改密、注销须立即生效
- **吊销状态存 Redis 的会话存储**（见《02》§4.2），形态为**按主体维度的一个版本号**：签发时把版本写入令牌，校验时与存储比对，版本不一致即失效。登出 / 改密 / 注销即递增版本。不落库、不维护逐条令牌记录——**递增是唯一的吊销手段**，因此无需存储任何令牌本身
- **吊销粒度随登录模式而变**：单点模式递增**用户级**版本（该用户全部令牌失效）；多点模式递增**设备级**版本（仅该设备失效）。版本维度由登录模式决定，不是两套机制并存
- 令牌中**不承载权限明细**，权限每次由服务端判定（见 §2.3）
- **设备维度**：签发时**若请求携带有效的设备令牌**（见 §1.4），则把其设备标识写入令牌、形成绑定；**未携带时不绑定**——登录端点匿名可访问，直接登录的客户端本就没有设备令牌。校验时只对**已绑定**的令牌比对，**不引入「默认设备」**：把缺失标识的请求归一化到同一主体，会使该主体在单点模式下被多个客户端互相吊销，且让设备绑定可被「省略请求头」绕过。已绑定的令牌若请求未携带设备令牌，视为**不匹配**（认证失败），不放行
- **设备绑定的强度是「尽力而为」，不是强制**：绑定只在签发时恰有设备令牌的情况下成立，因此它防的是**令牌泄露后在另一设备重放**，不防「客户端从一开始就没有设备令牌」的情形。若要求强制绑定（先取得设备令牌才能登录），需重新走设计评审——那会改变登录接口的准入条件
- 登录模式取**单点**：同一用户新登录即吊销其全部旧令牌，保证任意时刻只有一条活跃会话。多点模式作为可选项保留在同一套令牌管理器中，改配置即可切换
- **刷新令牌轮换**：每次刷新签发新的刷新令牌并作废旧的；刷新令牌**不随普通请求下发**

### 1.3 第三方授权

采用标准 OAuth2.0 授权码流程：

```
前端 ──▶ 授权页（带平台标识）──▶ 第三方
                                    │ 回调
                                    ▼
后端 ──▶ 校验授权码 ──▶ 换取第三方身份 ──▶ 关联或创建本地用户 ──▶ 签发本站令牌
```

**关键决策**：

- **同一用户可绑定多个第三方账号**，绑定关系独立存储，与主身份分离
- **第三方身份仅用于识别**，不作为授权依据——本系统不读取第三方平台的资源权限
- **绑定与解绑是显式动作**，不会因第三方登录而隐式合并账号，避免身份混淆
- **回调防 CSRF**：发起授权时生成一次性 `state` 并与会话绑定，回调时校验并消费；缺失或不匹配即拒绝
- **`platform` 走服务端白名单**：平台标识必须命中已配置的平台列表，回调地址由服务端按平台决定，**不接受请求方传入任意地址**

**令牌在客户端的存放**（属信任边界，见《08 安全边界》）：

| 令牌 | 存放 | 理由 |
|---|---|---|
| 访问令牌 | 前端内存或 `sessionStorage`，随请求头显式发送 | 短有效期，泄露窗口有限 |
| 刷新令牌 | 服务端以 `HttpOnly` + `Secure` + `SameSite` Cookie 下发，**前端脚本不可读** | 长有效期凭据不得暴露给脚本，避免 XSS 直接换到长期访问权 |

**不采用「两者都放 `localStorage`」**。代价是刷新令牌依赖 Cookie 自动携带，需在刷新端点配套 CSRF 防护（见《08 安全边界》）。

### 1.4 匿名身份

读者端存在**未登录但有状态**的场景（浏览足迹、留言、点赞）。系统为匿名访问者建立**访客身份**：

- **设备令牌由服务端签发**：首次匿名访问时下发一枚签名令牌，后续请求随带。**客户端自报的设备标识不被信任**——设备指纹（设备标识、操作系统、浏览器、IP）仅作为令牌内的记录字段，不作为身份依据
- **令牌缺失或签名无效时：放行请求，但不建立访客记录、不参与行为归并**。这样既不给伪造留出口，也不阻断匿名浏览（爬虫、链路预取、禁用存储的浏览器都能正常读）
- **上述缺口是有意接受的**：无设备令牌的访问者拿不到浏览足迹等个性化状态。对以「读多写少」为主的读者端，这比「任何人都能冒充他人访客身份」的代价小得多
- 访客身份**不是弱化的用户**——它有独立的数据主体地位，可被管理端查询；但**不参与任何授权判定**（见《08 安全边界》）
- **访客可升级**：登录后，该设备上的既有行为可按策略归并到用户身份。归并依据是**服务端签发的设备令牌**，因此只有持有有效令牌的设备才能触发归并

**系统的身份主体共三类**——注册用户（有凭据）、访客（只有设备令牌）、订阅者（只有邮箱与同意记录）。后两者**都不经过本节的认证流程**：访客由设备令牌标识，订阅者由邮件确认成立、由退订令牌解除（两枚令牌的性质见《08》§二）。**三者的邮箱重合时不自动合并**，理由见《02》§2.3。

## 二、授权

### 2.1 模型

采用 **RBAC**：用户 → 角色 → 资源授权。

**授权对象有两类**：

| 对象 | 含义 |
|---|---|
| 菜单资源 | 界面可见性与导航结构 |
| 接口资源 | 服务端操作的准入 |

两者**独立授权、独立存储**，但同属一个角色。这样一个角色可以"看得到某个页面但按不动某个按钮"，而不必为按钮单独建角色。

### 2.2 权限粒度

| 层级 | 服务端控制点 | 效果 |
|---|---|---|
| 模块级 | 接口资源授权 | 能否访问某模块 |
| 操作级 | 接口资源授权 | 能否执行某个操作 |
| 界面级 | 菜单资源下发 | 前端据此渲染导航与按钮 |

**服务端只有一条判定链**：请求路径 + 方法 → 接口资源 → 角色。模块级与操作级的差别只是授权的粗细，不是两套机制。

**服务端是唯一裁决者**——前端基于菜单资源做的可见性处理只是体验优化，任何接口调用都在服务端重新判定；**菜单资源不参与服务端判定**，它只决定前端渲染什么。

### 2.3 判定时机

授权判定发生在**请求进入业务逻辑之前**，以中间件形式统一实施：

- 认证中间件确认身份，授权中间件确认权限，**二者分离**——认证失败与授权失败是不同的错误语义
- **权限明细不进入令牌**，每次请求由服务端查询判定。代价是一次查询，收益是**权限变更立即生效**，无需等待令牌过期

**判定的缓存与失效**——二者必须同时定义，否则「立即生效」不成立：

| 项 | 约定 |
|---|---|
| 缓存内容 | 角色 → 接口资源集合的映射，**按角色缓存而非按用户**（用户数远多于角色数） |
| 主动失效 | 授权关系变更时删除受影响角色的缓存条目。变更入口集中在 `access` 模块，失效动作与写操作在**同一事务边界**内发起 |
| 兜底 | 缓存条目带**短 TTL**，作为主动失效失败时的兜底。「立即生效」的实际保证是**主动失效 + 短 TTL**，而非「永不缓存」 |
| 降级 | 权限缓存不可用时**回源查询**，不得放行 |

### 2.4 双端差异

| 维度 | 读者端 | 管理端 |
|---|---|---|
| 认证 | 必需（部分接口匿名可访问） | 必需 |
| 授权 | 不区分角色，登录即可 | 完整 RBAC 判定 |
| 匿名 | 允许，转化为访客身份 | 不允许 |

读者端的授权模型**刻意保持简单**：内容对所有读者一视同仁，不存在"部分用户能看某篇文章"的需求。这避免了在读者链路引入权限查询的开销。

## 三、中间件

两条链路各自装配中间件，职责不重叠：

| 链路 | 中间件 | 挂载范围 | 职责 |
|---|---|---|---|
| 管理端 | 认证 | 需登录及以上 | 确认管理员身份 |
| | 授权 | 需权限 | RBAC 判定 |
| | 操作日志 | 需权限 | 记录写操作审计 |
| 读者端 | 认证 | 需登录 | 确认用户或访客身份 |
| | 访问日志 | 全局 | 记录访问足迹 |
| 两端 | 限流 | 公开组（登录、验证码） | 防突发 |

**授权中间件只出现在管理端**——读者端不做角色判定（见 §2.4）。

**操作日志只覆盖管理端**：读者端的写操作（评论、留言、点赞）**不产生操作日志**，仅有访问日志。这是有意的——读者端写入量大且无权限语义，逐条审计的收益不抵开销。**代价是读者端的内容违规缺少操作级审计线索**，只能由访问日志与内容本身回溯。若该缺口不可接受，需重新走设计评审（见 §1.4 对访客身份同类的取舍）。

**装配次序**：需权限的组固定为 **认证 → 授权 → 操作日志**——先确认身份，再判定权限，最后才记录；日志在最内层，只记录实际进入业务的请求。**全局中间件与限流的分层装配见《07》§2.3**，本文只给出两条链路各挂什么。

错误码体系见《07》。
