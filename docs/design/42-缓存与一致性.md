# 42 缓存与一致性

> **本文回答**：什么能缓存、缓存多久、怎么失效，各类数据允许旧到什么程度。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、Redis 的三个角色

Redis 在本系统承担三种性质不同的职责：**会话存储**、**业务缓存**、**可重置热状态**。前两者必须分开；可重置热状态放在业务缓存实例上，但语义不同。

| | 会话存储 | 业务缓存 |
|---|---|---|
| 承载 | 令牌会话、在线状态、验证码 | 内容读缓存、权限判定、限流计数、浏览计数 |
| 权威性 | 令牌会话是权威数据；在线状态与验证码可重建 | 全部是派生数据 |
| 丢失后果 | 令牌会话丢失 → 所有用户重新登录（fail-closed）；在线/验证码可重建 | 回源重建，无数据损失 |
| 持久化 | **必须开启** | 不需要 |
| 淘汰 | **不得淘汰未过期的键** | 可随时清空，可用 LRU 淘汰 |
| 运维约束 | **禁止清空** | 任意时刻可清空 |

**可重置热状态**是第三类：点赞关系没有数据库副本，**不能回源重建**；清空只会重置用户点赞，聚合计数仍以数据库为准。它放在业务缓存实例上，但不享受「可重建」的承诺，也不进入授权或审计判定。

**「权威」与「不可清空」是两个正交维度**：在线状态可重建，但与令牌同属「不得清空」的一侧；业务缓存可清空，不代表它承载的数据没有价值。存储策略必须同时回答两个维度，不能只答一个。

**隔离方式**：生产环境使用独立实例；本地可用同一实例的不同逻辑库近似。隔离的判据是**运维不得清空**，不是丢失后果 —— 把令牌与内容缓存放进同一个可清空的库，一次误操作就会让全部会话失效。

**淘汰策略**：会话存储使用不淘汰策略（内存满时拒绝写入并告警，而不是悄悄丢掉令牌）；业务缓存可使用 LRU 淘汰。把两者混用，会让业务缓存的淘汰压力挤掉会话。

**失效方向**：

- 会话存储不可用 → **fail-closed**：需要身份的请求全部拒绝。放行等于吊销机制失效，后果比拒绝服务严重。
- 业务缓存不可用 → **回源**：功能正常，延迟上升。

## 二、数据分类

按「权威性 × 失效方式 × 陈旧上限」分类。**每个缓存键都必须能在这张表里找到归属**；找不到就不允许写入。

| 数据 | 角色 | 权威性 | 失效 / 更新方式 | 陈旧上限 | 丢失后果 |
|---|---|---|---|---|---|
| 令牌会话 | 会话存储 | 权威（无其他副本） | 显式撤销 + TTL | **0**：不允许使用过期状态 | 全员重新登录（fail-closed） |
| 在线状态 | 会话存储 | 可重建 | 续租 TTL | 一个 TTL 周期 | 在线列表暂时不准，重连恢复 |
| 验证码 | 会话存储 | 可重建 | TTL | TTL | 用户重新获取 |
| 权限判定缓存 | 业务缓存 | 派生 | 代际号 + 失效广播 + TTL | 由授权设计给出的分档 | 回源重建 |
| 限流计数 | 业务缓存 | 派生 | 滑动窗口 TTL | 一个窗口 | 暂时失去限流保护 |
| 内容读缓存 | 业务缓存 | 派生 | 内容版本号 + TTL | 秒级 | 回源重建 |
| 点赞状态 | 可重置热状态 | 无持久副本 | 写时更新 | 无（写路径直接读写） | 点赞状态重置；聚合计数以 DB 为准 |
| 聚合计数（浏览、点赞数） | 业务缓存 | 派生，DB 为权威 | 异步累加 + 定期校正 | 刷新周期 | 展示偏差，不影响业务判定 |

**点赞状态是刻意接受的重置**：它为读多写少的展示场景服务，不承载权限或审计语义；Redis 丢失后状态的代价是用户可再次点赞，而不是数据错误。若将来点赞需要参与业务判定，必须先落库，再谈缓存。

**统计与计数不参与业务判定。** 任何依赖「当前计数」做准入、配额或排序的规则，都必须回到权威源，不能读缓存。

## 三、失效原语

缓存失效有四种原语，**每类数据只选一个主原语**，其余只能作为兜底：

| 原语 | 作用 | 适用 |
|---|---|---|
| **版本号 / 代际号** | 键里带版本，写操作递增版本即整体失效 | 内容读缓存、权限判定 |
| **TTL** | 到期自动失效，给出陈旧上界 | 所有业务缓存与可重置热状态；短生命周期数据 |
| **失效广播** | 写操作后通知各实例丢弃本地副本 | 多实例下的本地缓存 |
| **写时更新 / 删除** | 写路径同步更新或删除缓存 | 点赞状态等写少读多、可精确更新的数据 |

**为什么版本号优先于逐条清除**：反向代理的内置缓存没有按条目删除的能力，逐 URL 清除需要第三方模块或商业版。把版本号嵌进缓存键，写操作递增版本即整体失效，零依赖、零误伤。

**为什么失效广播只能做加速**：广播会丢、消费者会漏。正确性必须由「版本号 + TTL」保证；广播只让失效更快到达。

**代际号的作用是防止「在途加载写回旧值」**：读请求在失效前读到旧值、失效后写回缓存，会把已撤销的状态重新固化。代际号让写回时能判断「我读到的这一代是否已经过期」，过期则丢弃。

## 四、读路径

### 4.1 基本模式

采用 **cache-aside**：读缓存 → 未命中回源 → 写回缓存。写路径更新权威源后，按 §三 的原语失效。

**不使用 write-through 作为默认**：写路径不应等待缓存更新；缓存失败不应让写操作失败。

### 4.2 击穿与穿透

| 问题 | 处理 |
|---|---|
| **缓存击穿**（热点键过期瞬间大量回源） | 同键请求合并（single-flight）或短暂重算锁；边缘层用短 TTL 微缓存吸收突发 |
| **缓存穿透**（查询不存在的键） | 只对公开资源缓存空结果，TTL 很短；私有资源不缓存空结果，避免泄漏存在性 |
| **缓存雪崩**（大量键同时过期） | TTL 加随机抖动；版本号失效不依赖统一过期时刻 |
| **热键** | 本地短缓存，最大年龄不得超过上游陈旧上界；不得绕过失效广播 |

### 4.3 一致性承诺

| 数据 | 承诺 |
|---|---|
| 写操作（模块内） | 强一致：事务提交后立即可读 |
| 内容可见性 | 允许秒级延迟；上限由缓存 TTL 与版本号共同给出 |
| 权限判定 | 有界陈旧，具体分档由授权设计给出 |
| 聚合计数 | 最终一致，刷新周期即延迟上限 |
| 令牌状态 | 不允许陈旧；查不到即拒绝 |

**「允许旧」不等于「可以无限旧」。** 每个派生缓存都必须有陈旧上界；上界由所属设计给出，并在键的 TTL 或版本策略中落实。

## 五、客户端与边缘缓存

**只有匿名、与用户无关的响应可以进入共享缓存。** 判定规则：

- 响应不含随用户变化的字段（登录态、个人化推荐、权限相关字段）。
- 响应不依赖 Cookie，不下发 `Set-Cookie`，不引入 `Vary: Cookie`。
- 登录态请求整体绕过共享缓存，**不按登录态分桶** —— 分桶等于仍在缓存个人化响应。

**内容响应的缓存头**：

```
Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=86400, stale-if-error=86400
Vary: Accept-Encoding
```

- `max-age` 短（浏览器），`s-maxage` 长（共享缓存）。
- `stale-while-revalidate` 兜住缓存击穿，`stale-if-error` 兜住源站抖动；二者只对共享缓存生效，浏览器基本不支持。
- **反向代理的微缓存不服从上游 `Cache-Control`**，使用自身更短的 TTL（10 秒量级）并开启同键请求合并。若服从上游 300 秒，微缓存将形同虚设。
- 私有响应（含用户数据、错误响应）使用 `no-store`。

**缓存键必须显式声明**：默认键包含完整查询串，跟踪参数会让同一份内容各占一份缓存。键按归一化参数生成，不包含 Cookie。

**禁止清空缓存目录或整库 flush**：整体清空会让全部请求瞬时回源，且丧失单条清理能力。失效由版本号承担。

## 六、关键决策

### D1 会话存储与业务缓存隔离

- **约束**：两者的丢失后果、持久化要求与运维约束完全不同。
- **备选**：共用一个 Redis 实例，用逻辑库区分；或完全共用。
- **选择**：生产独立实例；本地可用逻辑库近似；两侧的淘汰策略分开配置。
- **代价**：多一个实例的运维成本。
- **重审触发**：单实例资源成为瓶颈，或运维无法保证隔离。

### D2 权威数据 fail-closed，派生缓存回源

- **约束**：会话存储不可用时，放行等于吊销机制失效。
- **备选**：统一回源；或统一放行。
- **选择**：会话存储拒绝；业务缓存回源；限流计数放行（显式声明）。
- **代价**：Redis 故障时登录态请求不可用。
- **重审触发**：出现比「拒绝」更安全的降级路径。

### D3 失效以版本号 / 代际号为主，TTL 只做兜底

- **约束**：反向代理无法逐条清除；在途加载可能写回旧值。
- **备选**：逐 URL 清除；或只靠 TTL。
- **选择**：键内嵌版本；写操作递增版本；代际号阻止旧值写回；TTL 给出上界。
- **代价**：缓存键需要理解版本语义；旧键自然过期，占用短期内存。
- **重审触发**：缓存后端原生支持可靠的按标签失效。

### D4 共享缓存只放匿名响应

- **约束**：响应里混入一个用户相关字段，整条共享缓存链就失效，且可能泄漏。
- **备选**：按用户分桶缓存；或用 `Vary` 区分。
- **选择**：登录态请求整体绕过；共享缓存只放匿名响应。
- **代价**：登录用户的读请求不走共享缓存。
- **重审触发**：需要为登录用户提供可缓存的公共内容且无法拆分接口。

### D5 每个业务缓存键必须有 TTL 与命名空间

- **约束**：无 TTL 的键会无限增长；无命名空间的键无法定位归属。
- **备选**：依赖内存淘汰；或不设 TTL。
- **选择**：键格式 `blog:<域>:<用途>:<标识>`；所有业务缓存与可重置热状态的键必须带 TTL。
- **代价**：需要维护键规范与过期策略。
- **重审触发**：出现必须永久保留的缓存数据（它不属于缓存，应落库）。

### D6 缓存不可用时不返回超期数据

- **约束**：超期数据可能违反可见性或权限承诺。
- **备选**：stale-if-error 无限期兜底；或无缓存即失败。
- **选择**：回源；回源失败按所属设计的失败语义处理。边缘层的 `stale-if-error` 只在声明的窗口内有效。
- **代价**：缓存与源站同时故障时请求失败。
- **重审触发**：出现可接受更长陈旧窗口的只读场景。

## 七、不变量

- [ ] 会话存储与业务缓存不共用同一个可清空的库。
- [ ] 会话存储开启持久化，且不使用会淘汰未过期键的策略。
- [ ] 业务缓存任意时刻可清空，不造成**不可恢复的**数据丢失；可重置热状态（点赞）清空只会重置用户点赞。
- [ ] 每个缓存键都在 §二 的分类表中有归属，并带 TTL 与命名空间。
- [ ] 共享缓存中的响应不含用户相关字段，不依赖 Cookie。
- [ ] 失效以版本 / 代际为主；失效广播只做加速。
- [ ] 本地缓存的最大年龄不超过上游陈旧上界。
- [ ] 需要身份的请求在会话存储不可用时拒绝。
- [ ] 聚合计数不参与业务判定。

## 八、失败与降级

| 情形 | 行为 | 用户可见后果 |
|---|---|---|
| 会话存储不可用 | 需身份的请求拒绝 | 登录态请求失败；匿名可读 |
| 业务缓存不可用 | 回源 | 延迟上升，功能正常 |
| 限流计数不可用 | 放行并记录 | 暂时失去限流保护 |
| 失效广播丢失 | TTL / 版本号兜底 | 失效延迟到达，上限可证明 |
| 本地缓存与上游不一致 | 按最大年龄淘汰 | 短暂旧值，不超上界 |
| 边缘缓存不可用 | 直接回源 | 延迟上升 |
| 缓存键无 TTL（误写） | 视为缺陷，告警并清理 | 内存增长风险 |

## 九、边界与重新审视

- **不做**：跨机房缓存复制、分布式锁式强一致缓存、把缓存当数据库。
- **重新审视**：出现必须跨机共享的本地缓存；出现陈旧窗口无法用 TTL + 版本表达的数据；Redis 内存成为瓶颈。
