# blog 博客系统 — 总体设计

初稿：2026-09-11　·　最近更新：2026-09-16

## 一、概述

### 1.1 项目背景与目标

现代化的全栈博客系统：Go 微服务后端 + Vue 3 双前端。面向两类使用者——**读者**浏览内容并参与互动，**管理员**维护内容、审核互动、配置站点。

**规模与可用性目标**——本文所有架构取舍以此为准。凡与下表冲突的设计，应先修改本表，而不是绕过它：

| 维度 | 目标 | 对设计的影响 |
|---|---|---|
| 规模 | **个人博客量级**：文章千级、注册用户万级、日均 PV 万级 | 单机容器化足够，不追求水平扩展能力 |
| 可用性 | **接受单机故障导致的全站停机**，目标是"可恢复"而非"不停机" | 不做跨机容灾；备份与恢复演练是该形态的必要组成（见《05》§4.4） |
| 一致性 | 内容可见性允许**秒级延迟**（缓存所致）；写操作强一致 | 读路径可放心缓存；写路径不引入最终一致 |
| 成本 | 单机资源可承载 | 每引入一个中间件，须说明它解决了当下的什么问题 |

**数值是量级判断，随运营数据校准**——但量级本身即是取舍依据，不得缺省。

**不在范围内**：多机房 / 异地多活、分库分表、独立检索引擎（§1.2 已述检索自 MySQL 全文起步）。

### 1.2 技术选型

| 项 | 选型 |
|------|------|
| 语言 | Go 1.26 |
| 框架 | go-zero：api 层用 rest（HTTP 网关），rpc 层用 zrpc（gRPC） |
| 数据库 | MySQL 8（GORM） |
| 对象存储 | MinIO：上传的二进制（图片、附件），经存储适配器访问，可切换为本地实现 |
| 图片处理 | 上传只存原图；多规格与 WebP / AVIF **按需变换**生成，变换参数进 URL——参数变则 URL 变，天然免失效 |
| 缓存 | Redis：业务缓存，可随时清空 |
| 会话与令牌 | Redis：**权威存储**，与业务缓存隔离部署并开启持久化（见《02》§4.2） |
| 消息队列 | RabbitMQ（异步通知、日志） |
| 注册与配置 | Nacos |
| 实时通信 | STOMP over WebSocket，内嵌于核心服务 `blog-rpc`，不单独部署 |
| 认证 | JWT + OAuth2.0（GitHub / Gitee / QQ / 微信，按配置启用） |
| 检索 | MySQL 全文索引起步；检索实现收敛在 `content` 模块内，保留后续替换为独立检索引擎的边界 |
| 代码生成 | goctl + 自研 `goctlx`，模板集中管理 |
| 公共库 | 自研 `vkit`：外部服务适配器、基础设施组件、标准库扩展 |
| 前端 | Vue 3 + TypeScript；前台 Naive UI，后台 Element Plus |
| 部署 | Docker Compose（本地）/ Kubernetes（生产） |

### 1.3 服务拆分

```
┌───────────────────────────────────────────────────────────────────┐
│                              客户端                               │
│      博客前台（blog-app）           管理后台（blog-admin）        │
└────────────────────────┬──────────────────────────────────────────┘
                         │ HTTP / WebSocket
┌────────────────────────▼──────────────────────────────────────────┐
│                        HTTP 网关层（rest）                        │
│                                                                   │
│   app-api                           admin-api                     │
│   面向读者的只读为主接口            面向管理员的全量 CRUD         │
│                                                                   │
│   · 只做编排：参数校验 → 调 gRPC client → 响应封装                │
│   · 不直接访问数据库，不承载业务逻辑                              │
└────────────────────────┬──────────────────────────────────────────┘
                         │ gRPC
┌────────────────────────▼──────────────────────────────────────────┐
│                        RPC 服务层（zrpc）                         │
│                                                                   │
│                             blog-rpc                              │
│                                                                   │
│   单服务内按业务域划分多个模块，模块表见《02》§2.2                │
│                                                                   │
│   · 业务逻辑与数据持久化的唯一归属                                │
│   · 事务边界所在                                                  │
└────────────────────────┬──────────────────────────────────────────┘
                         │
┌────────────────────────▼──────────────────────────────────────────┐
│                             基础设施                              │
│   MySQL · Redis · RabbitMQ · Nacos · MinIO 对象存储               │
└───────────────────────────────────────────────────────────────────┘
```

**拆分理由**：api 与 rpc 分离，使**契约（HTTP 面向客户端）与实现（gRPC 面向服务间）解耦**。两个 api 服务共享同一份 rpc 契约——读者端与管理端的差异集中在 api 层的路由、认证与授权、视图裁剪，不重复实现业务逻辑。

**为何 RPC 层当前只有一个服务**：按业务域拆成多个 rpc 服务，收益是独立扩缩与故障隔离，代价是跨进程调用、契约双份维护与分布式事务。在本系统的规模目标下（§1.1），**代价是当下就要付的，收益只在某个业务域单独承压时才兑现**。因此先立边界、不拆进程：模块边界按《02》§2.2 划定并强制（跨模块只经契约调用，不直接读写对方的数据），部署形态保持单服务。

**拆分的触发信号**——出现任一即应重新评审，而不是等到不可维护：某业务域的读写压力需独立于其余域扩缩；某业务域的故障已波及他域；出现独立于主干的发布节奏。**拆分只改部署拓扑与调用方式，契约与模块边界不变**——这正是 api/rpc 分离现在就要做的原因。

**视图裁剪在 rpc 层完成，不在 api 层**：读者端不得看到草稿、内部状态与审计字段。若 rpc 回传全字段、再由 app-api 裁掉，最小暴露在进程边界上就已破防——一次日志、一次调试、一个反序列化缺陷即泄漏。因此同一实体按调用方提供不同字段集，api 层只做参数侧收窄；**视图划分属模块契约，其字段集由 `protocol` 定义，不在本文展开**。

**支撑模块**（非业务服务）：

| 模块 | 职责 |
|---|---|
| `goctlx` | 代码生成工具，从协议定义与数据模型生成代码 |
| `vkit` | 公共库：外部服务适配器、基础设施组件、标准库扩展 |

### 1.4 部署拓扑

生产环境采用**单机容器化部署**：五个服务容器 + Nginx 反向代理，共享宿主机的运行时与配置目录。

```
                        ┌─────────────────────┐
                        │    Nginx（宿主）    │
                        │ 前台域名 / 后台域名 │
                        └──────────┬──────────┘
                                   │
      ┌────────────┬───────────────┼───────────────┬────────────┐
      │            │               │               │            │
┌─────▼─────┐ ┌────▼─────┐  ┌──────▼─────┐  ┌──────▼─────┐ ┌────▼──────┐
│ app-web   │ │admin-web │  │ app-api    │  │ admin-api  │ │ blog-rpc  │
│ static    │ │static    │  │ rest       │  │ rest       │ │ gRPC      │
│ (nginx)   │ │(nginx)   │  │ gateway    │  │ gateway    │ │ core      │
└───────────┘ └──────────┘  └────────────┘  └────────────┘ └───────────┘
                                   │               │            │
                                   └───────┬───────┴────────────┘
                                           │
                    ┌──────────────────────▼──────────────────────┐
                    │  MySQL · Redis · RabbitMQ · Nacos · MinIO   │
                    └─────────────────────────────────────────────┘
```

| 要点 | 说明 |
|---|---|
| **前端静态化** | 两个前端各自构建为静态资源，由容器内 Nginx 托管 |
| **端口分层** | 前端静态、网关、服务三层各占独立端口段，互不重叠；具体取值以部署配置为准 |
| **配置外置** | 运行时可变的配置（Nacos 连接、数据源）通过挂载卷注入容器，不打进镜像 |
| **单机多副本** | 服务无状态，会话与在线状态集中在 Redis，因而可增加副本。**这是单机内的并行度，不是跨机水平扩展**（见 §1.1）；容器名与端口由编排层分配 |
| **依赖同机** | 数据库、缓存、消息队列、注册中心与对象存储运行在容器外、同一宿主机上——宿主机故障即全站不可用（见《05》§4.4） |

**命名对应**：`blog-app` / `blog-admin` 是两个前端**应用**（仓库名），上图与上表里的 `app-web` / `admin-web` 是它们构建产物所在的**容器**。**部署形态的完整约定见《05》§一**，本节只给拓扑。

## 二、系统全景

### 2.1 双端能力对照

| 业务域 | 读者端（app） | 管理端（admin） |
|---|---|---|
| 内容 | 浏览文章、分类、标签、归档、搜索 | 文章/分类/标签全量管理、导出；草稿 / 预览 / 定时发布 |
| 讨论 | 评论、留言、说说、点赞 | 审核（通过 / 待审 / 垃圾 / 回收站）、嵌套深度上限、批量状态变更、删除；三层反垃圾 |
| 媒体 | 相册浏览 | 相册/照片管理、上传；按需生成多规格派生图 |
| 站点 | 首页、关于、友链、自定义页面 | 站点配置、页面管理、友链维护 |
| 分发 | **RSS 2.0 / Atom、sitemap.xml、robots.txt** | — |
| 订阅 | 邮件订阅、退订 | 订阅者列表管理、导出 |
| 用户 | 资料、头像、密码、第三方绑定、注销 | 用户管理、状态与密码重置 |
| 访问控制 | — | 角色、菜单、接口资源、授权关系 |
| 统计 | — | 仪表盘、访问趋势、地域分布 |

**本表是产品视角的能力对照，与《02》§2.2 的模块并非一一对应**——分发出口落在 `site` 模块、订阅落在 `subscriber` 模块。**模块划分与数据所有权以《02》§2.2 为唯一真相源。**

**读多写少**是读者端的核心特征，因此 app-api 的接口以查询为主，写操作集中在评论、留言、点赞与个人资料。

**「统计」域的数据来源暂缓决定**，但受一条硬约束：**服务端埋点与全页缓存互斥**——页面若由缓存层直接应答，应用的计数中间件根本不执行，访问永远不被统计。将来落地时只能走**客户端信标**（独立端点、自身不可缓存）或**反向代理日志的旁路聚合**，**不得在渲染路径上计数**。这也是仪表盘保留占位、暂不实现的原因。

### 2.2 内容模型

**内容类型决定分发行为**——同为"内容"，各类型在归档、订阅与索引上的归属不同：

| 类型 | 编辑形态 | 归档 | RSS / Atom | sitemap | 评论 |
|---|---|---|---|---|---|
| 文章 | 长文 | ✅ 按月 | ✅ | ✅ | ✅ |
| 页面 | 静态页（关于 / 友链） | ❌ | ❌ | ✅（可配） | 视配置 |
| 说说 | 短内容 | 并入时间线 | 可选 | ✅ | ✅ |
| 相册 | 媒体集 | ❌ | ❌ | 可选 | ✅ |

**状态、可见性与评论开关是三个正交的问题**，不能塞进同一个字段（Ghost 的 `status` × `visibility`、WordPress 的 `post_status` × 口令/capability、Halo 的 `phase` × `VisibleEnum`——三家独立收敛到同一结论）：

| 轴 | 取值 | 回答的问题 |
|---|---|---|
| 状态 | 草稿 / 已发布 / 定时待发 / 已下线 | 处在生命周期的哪一步 |
| 可见性 | 公开 / 私密 / 密码保护 | 谁能读 |
| 评论开关 | 开 / 关 | 能否被讨论 |

分开之后，"草稿 + 密码保护"这类组合才能表达；合成一个枚举则每个新增取值都要穷举它与其他维度的组合。

**「已发布 + 公开」是进入归档、订阅与索引的唯一条件，且该判定必须收敛到单一谓词**——归档、feed、sitemap、搜索、详情页全部经**同一个入口**判定，外部传入的过滤条件与之**合并而非替换**。**禁止各处自行拼装过滤条件**：漏写一处就是内容泄漏。这是《02》模块契约的一部分。

存储上是否共表、以何字段区分类型，属《02》的模块契约。

### 2.3 内容生命周期

**修订历史用全量快照，不用行级差异**——保存时复制标题与正文全文，保留最近若干条；**条数上限 + 最小保存间隔双重节流**，避免自动保存把表写爆。**回滚是把旧版本复制成新版本，而不是把指针移回去**——使历史 append-only，回滚本身也可再回滚。行级差异省的是存储，代价是补丁链、对换行符敏感、还原失败无降级路径；在千级内容的量级下不划算。

**定时发布用「状态 + 时间」的轮询推进，不用需要请求才跑的站点内定时器**——落库「定时待发」状态与发布时间，由固定周期任务以「条件更新 + 受影响行数」推进，并据其结果触发后续动作（清缓存、发订阅通知）：天然幂等，多副本安全。**不采用流量驱动的伪 cron**——低流量站点上它可能长时间不触发，且失败静默，表现为"文章消失"而非延迟出现。

**预览用可撤销的随机令牌，不用"不可猜的固定 URL"**——令牌带**显式过期时间**，可在后台撤销。预览响应必须 `private, no-store`——**否则缓存层会把草稿分发给所有人**。"不可猜即安全"的模型一旦泄漏无法撤回。

**回收站**是软删除的用户界面：删除进回收站、可恢复、可彻底销毁（《02》§1.3 的 `delete` / `restore` / `destroy` 三词语即为此）。两条经验：**恢复默认回到「草稿」而非原状态**，避免已下线内容被误恢复上线；**清理必须由可靠定时器驱动**，不能挂在"后台被访问"这类隐藏依赖上。

**密码保护**同样用可撤销的短期令牌，不用"固定 URL 即秘密"的模型；口令的存储与校验口径见《08》§二。

### 2.4 讨论与治理

**读者互动允许匿名**——评论、留言、点赞不以登录为前提，访客由服务端签发的设备令牌标识，只有「用户」域要求登录。这是《03》§1.4 匿名身份与《07》§2.3 设备令牌中间件的上游依据。

**互动需要治理，但默认不逐条预审**——个人博客评论量小，全量预审会直接杀死互动。反垃圾按三层，**前两层不需要任何外部服务**：

| 层 | 手段 |
|---|---|
| ① 本地规则 | 外链数阈值、关键词、IP 频率、蜜罐字段；**老用户免审**（同昵称 + 邮箱有过已通过评论即直接放行） |
| ② 外部内容安全 API | **默认不启用**。只预留适配器接口，由配置开启；启用后评论数据将出境，需在隐私政策披露 |
| ③ 人工 | 管理端审核队列；「垃圾」态**保留原数据**，以便误判恢复 |

**外部 API 失败时放行，不阻断评论**——这让评论不因一个可选的增强项而全站不可用；降级方向及其判据见《08》§四。

**评论嵌套必须有深度上限**，达到上限后**降级为 `@` 平铺**，而不是隐藏回复按钮——后者会让深层评论彻底无法被回复。

### 2.5 分发与订阅

**「分发」是博客系统区别于通用 CMS 的对外契约**——订阅器与搜索引擎的入口，不是后台功能的附属产物。其格式归属 `protocol` 定义：

| 出口 | 形态 |
|---|---|
| RSS 2.0 | **必做**——全生态唯一无差别支持的格式。输出最近 **10–20 条**、**全文**（个人博客无广告变现，PV 的商业价值接近于零，而订阅者是核心资产） |
| Atom | 可选。技术上是更严格的规范（强制唯一 ID、RFC 3339 时间），适合作为长期存档格式 |
| sitemap.xml | 只输出 `<loc>` + `<lastmod>`——搜索引擎**明确忽略** `priority` 与 `changefreq`，写了是纯噪音 |
| robots.txt | 静态托管，`Sitemap:` 必须用绝对 URL。这里是**唯一能按爬虫名选择性放行 / 屏蔽 AI 爬虫**的地方 |

**页面级的社交与结构化元数据**（Open Graph、JSON-LD）**不属于"出口"**——它们嵌在内容页的 `<head>` 里、随页面一起分发，因此受渲染方式的约束，见 §2.6。

**订阅是「分发」的自然延伸**——订阅者与注册用户是**两类身份主体**，其模型与"不自动合并"的理由见《02》§2.3。

### 2.6 核心数据流

```
读者请求 ──▶ CDN / 反向代理 ──命中──▶ 直接返回
                    │ 未命中
                    ▼
                 app-api ──gRPC──▶ blog-rpc ──▶ MySQL
                                      │
                                      ├──▶ Redis（会话存储 · 业务缓存，二者隔离部署）
                                      └──▶ RabbitMQ ──▶ 异步消费者（邮件、短信、日志落库）

管理员请求 ──▶ admin-api ──gRPC──▶ blog-rpc（同上；管理端不经内容缓存层）
```

三条设计约束：

1. **api 层不落库** —— 数据访问与事务只在 rpc 层发生，保证数据所有权单一
2. **大对象不过网关** —— 图片等二进制经存储适配器直传，接口只传引用
3. **异步解耦** —— 通知投递、日志落库等非关键路径走消息队列，不阻塞主链路

**读路径是博客系统的性能主战场**——上图里，读者浏览文章是占比最高的流量，且内容发布后几乎不变，是最容易被缓存的负载。**搜索与个人化接口不在此列**：前者参数组合无限、不宜缓存，后者响应随用户而变、必须绕过缓存层。内容读取按三层设计，**越靠前的层命中，后端越不参与**：

| 层 | 缓存对象 | 失效方式 |
|---|---|---|
| ① 客户端 / CDN | 已发布内容的完整响应 | 写操作递增**内容版本号**，缓存键随之变化即整体失效（无 CDN 时另依赖 `Cache-Control` 到期） |
| ② 反向代理 | 匿名请求的完整响应 | 同上，TTL 独立（见下） |
| ③ Redis 业务缓存 | 组装响应所需的领域数据 | 同上（缓存角色见《02》§4.2） |

**失效用「版本号」，不逐 URL 清除**——反向代理的内置缓存**没有按条目删除的能力**（Nginx 需第三方模块或商业版才有 `proxy_cache_purge`）。因此在第 ②③ 层的缓存键中嵌入一个按内容域递增的版本号，写操作递增即整体失效：零依赖、零误伤。这与《03》§1.2 用版本号吊销令牌是同构手法。

**缓存行为由响应头表达**——匿名内容响应的形态固定为：

```
Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=86400, stale-if-error=86400
Vary: Accept-Encoding
```

`max-age` 短（浏览器）、`s-maxage` 长（共享缓存）；`stale-while-revalidate` 兜住缓存击穿，`stale-if-error` 兜住源站抖动——**二者只对共享缓存生效**，浏览器基本不支持，不要指望它们对终端用户起作用。

**第 ② 层不服从这个响应头**——反向代理**忽略上游的 `Cache-Control`**，改用自身更短的 TTL 作微缓存。二者面向的对象不同：`s-maxage` 给 CDN 与浏览器，微缓存给反代自身。若反代服从上游头，300 秒的 TTL 会让微缓存形同虚设。落地口径见《05》§1.3。

**读路径的四条约束**：

- **匿名读者的内容响应必须可缓存**——响应中不得混入随用户变化的字段（登录态、个人化内容）。需要个人化时走独立接口，不与内容响应混合，否则整条缓存链失效
- **评论数、浏览数等计数不得渲染进被缓存的 HTML**——它们每请求都在变。做法是页面留空占位元素，由客户端异步拉取填充
- **响应不依赖 Cookie**——不下发 `Set-Cookie`、不引入 `Vary: Cookie`。**登录态请求整体不进内容缓存**，而不是按登录态分桶：分桶等于仍在缓存个人化响应
- **失效由写操作主动触发，不依赖 TTL**。TTL 只是兜底，缓存过期时间即内容更新的最坏延迟（与《02》§4.1 物化表的刷新周期口径一致）

**前台形态与 SEO**——当前为 Vue 3 SPA。这不只是性能问题：**Open Graph 与 JSON-LD 必须出现在服务端渲染的 HTML `<head>` 里**，而社交平台的抓取器与搜索引擎**不执行 JS**，SPA 返回的空壳 HTML 拿不到分享卡片与结构化数据。因此两件事应分开决策、互不绑定：

- **SEO 是硬需求**——至少让文章详情页产出带内容与 meta 的 HTML（构建期预渲染，或由服务端注入 meta）。与缓存无关
- **缓存层无需为此改动**——第 ①② 层由 CDN / 反向代理承担已经足够。调研过的增量再生方案（Next.js / Nuxt / Halo）在「主动失效」上都不如本设计完整，Nuxt 甚至没有公开的缓存失效 API。**不引入 ISR / SSG**

### 2.7 实时通信

聊天室与在线状态经 STOMP 链路提供，与 HTTP 链路**并行**。**完整约定见《04》§三**，此处只记结论：

- STOMP 内嵌于核心服务（`blog-rpc`），不单独部署
- 身份在**协议层**校验（CONNECT 帧携带凭证），不依赖升级前的 HTTP 请求
- 在线列表外置于 Redis，使核心服务可多副本部署

## 三、项目结构

**本节只描述顶层单元的职责边界，具体布局以代码为准。**

| 单元 | 职责边界 | 不负责 |
|---|---|---|
| `protocol` | 全部对外与对内的**契约**，是接口语义的唯一真相源 | 不含实现 |
| `blog-cloud` | 后端全部业务实现与数据所有权 | 不定义契约，只消费 |
| `blog-admin` / `blog-app` | 各自产品面的交互与呈现 | 不直接访问数据库 |
| `goctlx` | 从契约与模型生成代码 | 不参与运行时 |
| `vkit` | 跨项目复用的公共能力 | 不含本项目特有逻辑 |
| `deploy` | 运行环境的编排与配置 | 不含业务 |

**分层职责**（api 与 rpc 同构）：路由与参数校验 → 业务编排 → 依赖注入容器；rpc 层额外承载持久化与事务。**api 层的业务编排只做跨服务的调用编排，不承载领域规则。**

**契约变更的跨仓库顺序**：`protocol` 是独立单元，实现仓库以固定版本引用它，因此一次接口变更**无法在单个提交内原子完成**。顺序固定为：**① 提交并合入 `protocol` → ② 更新实现仓库对该版本的引用 → ③ 再提交实现**。反向操作会让构建拉到尚未发布的契约，必然失败。

**契约的跨版本兼容是硬约束**：每次变更都必须让**新旧两个版本的实现同时可用**——只增不改：新增字段可空、不复用已废弃的字段名与取值、不改既有字段的语义。理由与《05》§3.4 的数据库迁移同源：**契约与 schema 都是"代码可回滚、它们不可回滚"的对象**，一旦破坏兼容，回滚代码即失败。
