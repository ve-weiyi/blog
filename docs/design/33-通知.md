# 33 通知

> **本文回答**：一条通知如何从发布到被看见、被撤回，投递失败与重复如何处理。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、三层模型

通知拆成三个独立层次，各自有独立生命周期：

| 层 | 含义 | 变更频率 | 例子 |
|---|---|---|---|
| **模板** | 形态：文案、占位符、适用场景与渠道 | 低 | 「评论回复」邮件模板 |
| **内容** | 一次发布：标题、正文、目标、分类、等级 | 中 | 「站点维护通知」 |
| **投递记录** | 内容落到每个接收者后的一条记录 | 高 | 某用户的未读站内信 |

**分层理由**：三者的变更主体与频率完全不同。模板由运营长期维护；内容是事件性动作；投递记录是系统产物。混在一起会让高频的投递写入反复触及模板定义。

**两类目标共用投递记录模型**：

| 目标 | 解析方式 |
|---|---|
| 广播（all） | 展开为全部注册用户 |
| 点对点（user_ids） | 按给定用户列表展开 |

差别只在目标解析，后续的「一条内容 / N 条记录」完全一致。读时求值不可行：定向列表是一个集合，读路径无法索引。

## 二、状态机

### 2.1 内容

```
草稿 ──▶ 已发布 ──▶ 已撤回
```

- **草稿**：可编辑；不产生投递。
- **已发布**：产生投递；可撤回。
- **已撤回**：终态；不可逆；不可重新发布 —— 需要重新发布时新建一条内容。

### 2.2 投递记录

| 渠道 | 状态 |
|---|---|
| 站内信 | 未读 → 已读；未读 → 已撤回 |
| 邮件 / 短信 | 待发送 → 已发送 / 失败 |

**撤回只作用于「未读」的站内信**：已读的保留原样，不追回、不删除。邮件与短信已经离开系统，撤回只阻止尚未发送的记录。撤回是**单向、不可逆**的状态迁移。

**已读是投递记录的属性，不是内容的属性**：同一条内容投给多人，各人的已读状态独立；「全部已读」是批量状态更新，不是内容级标记。

## 三、发布

```
管理端发布
   │
   ▼
事务：内容状态 draft → published（WHERE 原状态 = draft）
     + 写 outbox 事件（PUBLISHED）
   │
   ▼
relay 读取 outbox → 发布站内信投递事件（MQ）
   │
   ▼
消费者：行锁读取内容 → 状态仍为 published？
   ├─ 否：跳过（撤回已先到）
   └─ 是：解析接收者 → 去重 → 批量插入未读记录
                │
                ▼
           事务提交后广播「有变化」信号
```

**事务内只做状态更新与 outbox 写入。** 投递耗时不得进入发布请求的链路；接收者可能有上万人，逐条插入会直接把发布接口拖死。outbox 的落库、relay 与至少一次语义见《异步消息与投递可靠性》D3。

**消费者必须重新检查内容状态**：事件发出到被消费之间，内容可能已经撤回。撤回路径只回收「当时已存在」的未读记录；如果消费者不拦，为一条已撤回内容新插入的记录不会被回收，公告会照常出现在所有人的未读列表里。

**去重键是 `message_id + recipient`**：查询与插入在同一事务内完成，避免查重与插入之间的并发窗口。重复投递是常态，不是异常。

**广播在事务提交之后**：客户端收到信号后会立即回查未读；若信号早于记录写入，那次回查查不到，通知要等下一次信号才可见。

## 四、撤回

```
事务：内容状态 published → revoked（WHERE 原状态 = published）
     未读站内信记录 → revoked
     （已读记录保持原样）
   │
   ▼
事务提交后广播撤回事件
```

**撤回不需要 outbox**：状态与未读记录已在同一事务内更新，提交后的广播只是加速信号，丢失由拉取兜底。

- 内容状态与投递记录必须**一起改**：只改其一，会让已撤回的通知仍留在读者的可见列表里，而且外面看不出失败。
- 并发撤回由「条件更新 + 影响行数」裁决；先读状态再按 ID 更新不是原子的。
- 撤回不删除记录：墓碑让离线客户端能区分「被撤回」与「不存在」。

## 五、投递语义

| 项 | 约定 |
|---|---|
| 至少一次 | 允许重复；消费者按业务键去重 |
| 去重窗口 | 不短于最长重试窗口 + 记录保留期 |
| 顺序 | 不保证；发布与撤回的竞争由状态判断消解 |
| 失败终态 | 邮件 / 短信重试到上限后标记失败，可由管理端重发；站内信不经外部服务，不重试 |
| 重发 | 针对失败记录重新投递；需幂等，不得重复产生已成功的记录 |
| 模板缺失 | 回退到内置文案；模板渲染失败同样回退，不因模板问题阻断通知 |

**验证码属于通知域**：它复用投递通道，但有 TTL 与一次性消费语义，不产生站内信记录。生成、存储、投递、校验四步同边界；其他域只调用「发验证码」与「校验验证码」两个动作。

## 六、拉取与推送

| 通道 | 语义 | 内容 |
|---|---|---|
| 拉取（HTTP） | **当前状态快照** | 当前可见的通知列表、未读数 |
| 推送（实时通道） | **事件** | 「某通知已发布 / 已撤回」 |

**推送只发信号，不发内容。** 客户端收到信号后回查拉取接口。这样：

- 离线期间的变更不会因为推送丢失而永久不可见；
- 推送通道不必承载正文，隐私面更小；
- 客户端不需要合并「推送内容」与「拉取快照」两套状态。

**未读数由已读状态派生，不做增量维护**：增量计数在撤回、重复投递、乱序时必然漂移；重算永远正确。

**跨实例**：信号经 Redis Pub/Sub 广播，所有网关实例都能收到；不需要知道目标连接在哪个实例上。当前实时信号由管理端 SSE 消费；信号本身与消费端无关，读者端接入时复用同一事件。

**推送丢失的兜底**：客户端定时对账（拉取未读）；服务端不承诺推送必达。关掉推送，功能仍然正确，只是变慢。

## 七、关键决策

### D1 模板 / 内容 / 投递记录三层分离

- **约束**：三者的变更频率与责任主体不同。
- **备选**：一张表存全部。
- **选择**：三层分开，投递记录独立增长。
- **代价**：读取时需要组合三层。
- **重审触发**：模板与内容长期一一对应，分层不再带来收益。

### D2 权威状态在库，推送只发信号

- **约束**：通道不可靠；断线、重启、多端都会发生。
- **备选**：推送直接带内容，客户端据此渲染。
- **选择**：库内状态是唯一真相；推送只触发回查。
- **代价**：每次变更多一次拉取。
- **重审触发**：出现无法拉取的推送场景（如系统级提醒）。

### D3 发布与撤回共用一条管道

- **约束**：两条链路会产生两套可靠性与补偿逻辑。
- **备选**：撤回单独实现。
- **选择**：同一事件管道，只是类型与状态迁移方向不同。
- **代价**：事件模型需要同时表达发布与撤回。
- **重审触发**：撤回语义复杂到无法用同一事件表达。

### D4 撤回只作用于未读，且不可逆

- **约束**：已读内容已经在用户侧可见，追回会造成二次伤害与不一致。
- **备选**：撤回删除所有记录；或允许重新发布。
- **选择**：未读标记撤回；已读保留；撤回终态。
- **代价**：已读用户仍能看到旧内容。
- **重审触发**：出现必须全局下架的内容治理要求。

### D5 至少一次 + 业务键去重

- **约束**：重复投递不可避免。
- **备选**：恰好一次；或不去重。
- **选择**：至少一次；`message_id + recipient` 唯一键去重。
- **代价**：需要唯一索引与事务内查重。
- **重审触发**：出现重复会产生不可撤销副作用的渠道。

### D6 未读数派生，不做增量

- **约束**：撤回、重复、乱序都会让增量计数漂移。
- **备选**：维护计数列；或每次重算。
- **选择**：由已读状态重算。
- **代价**：查询成本随记录数增长，需要索引与分页。
- **重审触发**：重算成为读路径瓶颈。

### D7 失败终态 + 管理端重发

- **约束**：外部通道会失败，用户必须知道没收到。
- **备选**：无限重试；或静默丢弃。
- **选择**：有界重试；失败终态；管理端可重发。
- **代价**：需要保留失败原因与重发入口。
- **重审触发**：外部通道提供可靠的投递回执与重试机制。

## 八、不变量

- [ ] 通知的权威状态在数据库；推送只发信号。
- [ ] 发布在事务内只更新状态；投递在事务外异步进行。
- [ ] 消费者在展开前重新检查内容状态。
- [ ] 投递记录按 `message_id + recipient` 唯一去重。
- [ ] 撤回只作用于未读记录；已读记录保留。
- [ ] 撤回是单向终态，不可重新发布。
- [ ] 未读数由已读状态派生，不做增量维护。
- [ ] 推送丢失不影响正确性；拉取返回快照。
- [ ] 验证码不产生站内信记录，使用独立 TTL 与一次性消费。

## 九、失败与降级

| 情形 | 行为 | 用户可见后果 |
|---|---|---|
| MQ 不可用（发布） | 站内信降级为同步展开；其他渠道明确失败 | 发布可能变慢或失败 |
| 消费者下线 | 事件留在队列 | 恢复后继续投递 |
| 内容已撤回 | 消费者跳过 | 不产生新的未读记录 |
| 重复投递 | 唯一键去重 | 无重复通知 |
| 邮件 / 短信失败 | 有界重试；失败终态 | 管理端可见并可重发 |
| 模板缺失 / 渲染失败 | 回退内置文案 | 通知仍可发出 |
| 推送信号丢失 | 客户端定时对账 | 延迟可见，不丢失 |
| Redis Pub/Sub 不可用 | 无实时信号 | 依赖拉取，功能仍正确 |

## 十、边界与重新审视

- **频次控制**：当前没有每用户推送上限；若引入，超限丢弃而不是排队。
- **聚合**：多条同类通知合并展示属于展示层策略，不改变投递记录。
- **读者端通知中心**：当前信号由管理端消费；读者端接入时复用同一拉取与信号模型。
- **渠道扩展**：新增渠道需要定义自己的状态机与失败终态，不复用站内信的未读语义。
