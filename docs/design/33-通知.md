# 33 通知

> **本文回答**：一条通知如何产生、扇出、被看见、被撤回；渠道如何扩展；重复、失败与乱序如何收敛。
>
> 初稿：2026-10-22 · 最近更新：2026-10-29

## 一、目标与约束

**目标**：业务事件（评论回复、点赞、审核结果、安全提醒）与运营公告共用一条管线；收件人怎么解析、用户要不要收、走哪个渠道、同类如何合并，都在这条管线里裁决一次；新增场景不需要改表结构。

**约束**：

- 通知不得进入业务请求的关键路径。发布的语义是「已受理」，不是「已投递」。
- 通知是历史事实：触发者后续的逆向动作（取消点赞等）不回收已发出的通知，也不改写它。但内容被撤回或被删除时，指向它的条目要清理 —— 已经无法呈现的通知留着只会变成死链。**文案属于展示**，改文案会改变历史通知的外观。
- 收件人规模不可假定。广播可能面向全部用户，扇出不能一次性载入内存。
- 外部渠道（邮件、短信、推送）有外部副作用且不可靠；站内信没有。
- 存储为 MySQL；跨进程投递走事务性发件箱与至少一次语义。

**非目标**：

- 不追求端到端「恰好一次」。重复由业务唯一键收敛。
- 不做多语言渲染，但渲染入口保留语言参数。
- 不做延迟投递、按收件人时区分发、多步工作流编排。
- 不把验证码做成通知。

## 二、关键决策

### D1 事件、条目、投递三层分离

- **约束**：一次通知意图可能面向一个收件人，也可能面向全部用户；一次投递可能重试多次；收件人的读状态与渠道的发送结果完全无关。三者的基数是 1 : N : M。
- **决策**：意图、收件箱条目、渠道投递各成一层。条目描述「某人的收件箱里有这一条」，投递描述「这条在某个外部渠道上的发送尝试」。
- **备选**：单表用渠道字段判别。字段一半对另一半永远为空，同一列的状态取值域随渠道变化，收件人一列同时承载用户标识、手机号与邮箱。
- **代价**：读取收件箱需要关联事件表取载荷；三张表各自维护索引。
- **重审触发**：出现一种既进收件箱又需要多次发送的渠道，或三层严格 1:1。

### D2 事件表兼作扇出工作单元与载荷唯一副本

- **约束**：广播的正文对所有收件人相同，逐条复制是纯冗余；扇出可能中途中断，必须有可恢复的进度；载荷丢失后没有补偿入口。
- **决策**：一次通知意图落一行事件，载荷只存一份；收件人条目引用事件。扇出游标、状态与重试都挂在事件行上，事件行本身就是工作队列；发件箱只负责把消费者叫醒，丢了由兜底扫描补上。
- **备选**：把载荷写进 MQ 消息、游标也随消息传递。省一张表，但消息丢失后扇出停滞且无痕迹，也无法回答「这条公告推送到哪了」。
- **代价**：多一次关联读取；事件行在被引用的条目清理前不能删。
- **重审触发**：所有场景都退化为单收件人，扇出与载荷共享不再成立。

### D3 聚合是读时投影，不存折叠计数

- **约束**：同一对象被多次互动会产生多条通知，用户不想逐条看；但存折叠计数就要面对重复消费多加一次，而且丢失「谁做过」。
- **决策**：每个收件人按去重键落一条条目 —— 可分组场景按「场景 + 对象 + 触发者」去重，不可分组场景按事件去重，写入天然幂等。收件箱在读取时按场景声明的维度分组，组内取最新触发者与计数。「A 等 50 人赞了你」是投影结果，不是存储事实。
- **备选**：写入时折叠为一行并累计计数。读路径简单，但重复消费会污染计数，且无法追溯成员。
- **代价**：行数随互动次数增长；列表必须按组键聚合后分页，比按主键分页重；未读数需要按分组去重计算；同一触发者对同一对象再次互动不会重新提醒。
- **重审触发**：分组成为读路径瓶颈，或单条通知的行数增长到需要物化分组。

**按触发者去重是为了让计数说真话**：一个人点赞、取消、再点赞，若按事件计数，组大小会变成 2，而文案读起来是「两个人赞了你」。去重之后，组大小等于实际互动过的人数。

### D4 文案在代码，读时渲染

- **约束**：通知是历史事实，但文案是展示。文案需要单一来源、可测试、随版本走；运营自助改文案当前没有需求。
- **决策**：场景的标题、正文与跳转由代码按「场景 + 载荷」渲染，不落库。站内、邮件、短信共用同一套文本，渠道只额外套一层外壳。不建模板表。
- **备选**：模板存表。多一套 CRUD、缓存与回退路径，且与代码内置文案并存时会出现两个来源；运营改坏语义也无法在编译期发现。
- **代价**：改文案需要发版；历史通知的外观会随文案变化。
- **重审触发**：需要运营在不发版的前提下改文案，或需要保留「用户当时看到的确切文本」。

### D5 偏好按分组与渠道，安全场景不可退订

- **约束**：用户想关闭的是「点赞通知」这一类，而不是逐个子类型点选；安全与公告不能关闭。
- **决策**：偏好以「分组 × 渠道 × 开关」表达，没有记录时取场景默认。标记为强制的分组忽略偏好表。**站内信是锚点渠道**：关闭它即关闭该分组的全部渠道，因为条目同时是外部投递的载体；外部渠道在站内信开启的前提下单独控制。
- **备选**：全局总开关（关掉即失聪）；按场景设开关（数量随场景线性膨胀）。
- **代价**：粒度较粗，无法只关某个子场景；站内信作为锚点，用户也不能「只要邮件、不要站内信」。
- **重审触发**：需要单场景粒度的开关。

### D6 公告是内容源，不是管道的一层

- **约束**：公告需要草稿、编辑、定向、撤回，这些是内容管理；业务通知没有这个过程。
- **决策**：公告内容独立成表，发布时生成一条事件并进入同一条扇出管线；撤回时回收派生条目。公告正文只存一份，事件载荷只带内容引用，正文以内容表为准。因此**编辑已发布公告会改变已发出条目的展示**，删除内容必须连同派生条目与投递一起清理。
- **备选**：公告与业务通知双轨，各一套表与查询。读者侧要合并两个列表、两个未读数、两套偏好。
- **代价**：公告是「内容 → 事件 → 条目」三跳；内容状态与条目状态需要一起维护。
- **重审触发**：公告不再需要草稿与编辑。

### D7 实时只发信号，按收件人频道投递

- **约束**：实时通道不可靠、会断线、可能多端；通知正文可能较大；读者在线连接数远高于管理端。
- **决策**：推送只声明「你的收件箱变了」，客户端收到后回查。信号按收件人频道投递，不向全站在线连接广播。
- **备选**：推送直接带正文（通道成为第二真相源，客户端要合并两套状态）；全局广播后各自回查（每次事件放大成全站回查）。
- **代价**：每次变更多一次拉取；实例要维护「本连接订阅了哪些收件人」。
- **重审触发**：出现无法拉取的推送场景；或需要客户端与通知双向交互。

### D8 广播分批推进，游标持久化

- **约束**：全量广播的收件人是万级，一次性载入并单事务写入会拖垮扇出与数据库；中途失败不能从头再来。
- **决策**：按收件人标识分批，每批独立事务，游标写回事件行；穷尽后标记完成。中断后从游标继续。
- **备选**：一次事务展开全部。实现简单，但内存与锁持有时间随用户数线性增长。
- **代价**：投递完成时间拉长；需要处理「用户集合在扇出期间变化」。
- **重审触发**：收件人规模稳定在小到一次展开无压力的量级。

### D9 撤回删除条目，不留墓碑

- **约束**：拉取返回当前快照，离线客户端恢复后靠快照对齐，不需要区分「被撤回」与「从未存在」。
- **决策**：撤回公告时删除其派生条目，已读的一并删除。用户自己删除通知同样是物理删除。
- **备选**：标记为已撤回。会让已读用户看到一条本应撤下的公告，并给读路径增加第三种状态。
- **代价**：用户无法追溯「这条通知去哪了」。
- **重审触发**：需要向用户解释单条通知的消失原因。

### D10 验证码不进入通知模型

- **约束**：验证码有 TTL、一次性消费、不计入未读，与收件箱语义无关；它的生命周期属于认证流程。
- **决策**：验证码的权威状态在会话存储；通知域只提供复用邮件/短信传输的发送能力，不产生事件、不产生收件箱条目。发送失败留日志与指标，不建投递记录。
- **备选**：复用通知模型。验证码会出现在通知列表与未读数里，且高频写入污染收件箱。
- **代价**：成功发送的验证码没有落库审计。
- **重审触发**：需要验证码发送的合规审计。

## 三、机制与数据流

### 3.1 五张表

| 表 | 角色 | 说明 |
|---|---|---|
| `t_notification_event` | 通知意图 + 扇出工作单元 | 一次意图一行，载荷只此一份；携带状态与扇出游标 |
| `t_notification` | 收件箱条目 | 每个收件人一行，引用事件；`收件人 + 去重键` 唯一 |
| `t_notification_delivery` | 外部渠道发送尝试 | 每个条目每个渠道一行；`条目 + 渠道` 唯一 |
| `t_notification_preference` | 退订开关 | 偏好分组 × 渠道 |
| `t_announcement` | 公告内容 | 草稿、编辑、定向、撤回 |

**条目冗余了场景与对象引用**：两者在条目生成后不再变化，复制一份是为了让「按场景过滤」「按对象分组」「对象删除时清理」都能走索引，不必回连事件表。

**投递表不承载站内信**：站内信的「投递」就是条目本身，没有第二次发送。

### 3.2 场景

| 场景 | 偏好分组 | 触发 | 收件人 | 默认渠道 | 可退订 | 展示分组 |
|---|---|---|---|---|---|---|
| 公告 | 公告 | 管理员发布 | 全部 / 指定用户 | 站内信 | 否 | 不分组 |
| 内容收到评论 | 评论 | 评论审核通过 | 文章或说说的作者 | 站内信 | 是 | 按内容 |
| 评论被回复 | 评论 | 评论审核通过 | 被回复者；没有回复对象时取父评论作者 | 站内信 | 是 | 不分组 |
| 评论被点赞 | 点赞 | 点赞 | 评论作者 | 站内信 | 是 | 按评论 |
| 文章被点赞 | 点赞 | 点赞 | 文章作者 | 站内信 | 是 | 按文章 |
| 说说被点赞 | 点赞 | 点赞 | 说说作者 | 站内信 | 是 | 按说说 |
| 内容审核结果 | 审核 | 审核驳回 | 内容作者 | 站内信 + 邮件 | 是 | 不分组 |
| 账号安全 | 安全 | 密码、邮箱、登录异常 | 本人 | 站内信 + 邮件 | **否** | 不分组 |

**通知在内容对读者可见之后才产生**。审核中的评论对读者不可见，若在写入时就发通知，收件人会收到一条点进去看不到的评论；审核不通过时，通知则永远指向不存在的内容。因此「评论被回复」的触发点是**审核通过**，不是写入。

**触发点定义在状态迁移上，不依赖配置开关**：评论从「未通过」变为「通过」的那一刻产生通知。站点配置里的「评论审核」开关目前没有被服务端读取，评论一律先审后发；即便日后修复该开关，只要在创建时把评论置为通过，同一处迁移就会触发通知，本设计无需改动。

**「内容审核结果」只在驳回时发**：通过是预期结果，再通知一次只是噪音；驳回才需要作者知道。

**保留期是场景属性**：已读、未读两档都由场景声明，清理按场景分别执行，未声明的取全局默认。点赞这类低价值通知与账号安全这类长期有效的通知，生命周期本就不该相同。

**回复同时通知两个人**：一条回复产生两条事件 —— 一条给被回复者（评论被回复），一条给内容作者（内容收到评论）。内容作者就是被回复者时只发前者；评论者是内容作者本人时，不再通知自己。友链评论没有作者，只通知被回复者。

**偏好分组与展示分组是两个维度**：前者决定退订开关的粒度 —— 用户关的是「点赞」这一类，不分子类型；后者决定收件箱里怎么合并展示。两者的取值互相独立：评论被回复是「评论」组、且不展示分组。

触发者是自己时跳过。

**访客不产生收件箱条目**：匿名评论属于访客身份，没有收件箱、没有偏好，也没有可投递的地址。被回复者或点赞对象是访客时直接跳过，不写事件。访客要收通知，前提是先绑定可投递的邮箱，那是独立需求，不在通知域内兜底。

**公告默认只落站内信**。对外广播会让全站用户收到邮件，必须作为独立动作显式发起，不能由「发布」隐式触发。

### 3.3 产生

```
业务事务内
   └─ 写业务数据 + 写通知事件（待扇出）+ 写发件箱唤醒
```

**事件与业务数据同事务**：避免「业务已成功、通知从未产生」。发件箱只负责唤醒，事件行才是通知的权威状态。

**同事务的代价必须接受**：事件写入失败会让业务写入一起回滚。这是刻意的 —— 静默丢掉通知比整体失败更难排查。实现时不得改成 best-effort。

**只对「产生」发通知**：取消点赞、取消关注这类逆向动作不发通知。连续重复点赞时，点赞明细的唯一键使影响行数为 0，不写事件；取消后再赞会写事件，但由通知的去重键吞掉，不会重复提醒。

**公告**：先落内容（草稿），发布时状态迁移与生成事件同事务；撤回时状态迁移、删除派生条目与投递记录同事务。删除内容与撤回同级 —— 必须先回收派生条目，否则列表渲染找不到正文。编辑不迁移状态，但会改变已发出条目的展示。

### 3.4 扇出

```
消费者领取事件（状态迁移 + 行锁，避免并发重复扇出）
  1. 解析场景与受众；未知场景直接失败（编程错误，重试无意义）；事件已终止则停止扇出
  2. 按游标取一批收件人
  3. 剔除触发者本人
  4. 按偏好筛掉关闭了该分组站内信的收件人；外部渠道在此基础上单独判定
  5. 批量插入条目（冲突即跳过，重复消费安全）
  6. 回查本批收件人对应的条目，为其中需要外部渠道的写待发送投递记录
  7. 推进游标；未穷尽则以新游标重新入队
  8. 穷尽后标记完成
  9. 本次确有新插入条目时，提交后按这些收件人发实时信号
```

**扇出必须可重入**：任何一步失败都从游标重来，已插入的条目由唯一键吞掉。

**没有新条目就不发信号**：去重键让重复互动与事件重放走「插入 0 行」的路径；无条件发信号会让客户端收到一次「收件箱变了」，回查却什么都拉不到。

**插入条目、写投递、推进游标在同一事务**。拆成两步提交会出现「条目已写、投递未写」的窗口；而重放时条目又被去重键吞掉，若投递只跟着「本次新插入的行」走，这条通知就永远没有外部投递。所以投递的依据是**本批收件人对应的条目**，不是「本次新插入的条目」。

**续跑批次同样走发件箱**：若提交后直接发消息、发送失败，事件会停在「扇出中」直到兜底扫描。把续跑批次也写进发件箱，中断就只剩进程崩溃一种，兜底扫描只兜它。

**状态机**：待扇出 → 扇出中 → 已完成 / 已失败 / 已终止。停留在「扇出中」超过阈值的由兜底扫描重新入队。

**终止先于删除**：删除对象或公告内容时，先把关联事件置为终止，再删条目。扇出每批写入前复查事件状态、并在事件行上加锁，使终止与扇出串行 —— 否则清理删掉的是「当时的条目」，扇出随后又补写新条目，收件箱重新冒出死链。

### 3.5 读

| 读法 | 返回 |
|---|---|
| 列表 | 收件箱快照，以**分组**为分页单位；组内取最新触发者、组大小与未读状态，并带渲染后的标题、正文与跳转 |
| 过滤 | 按偏好分组、按全部 / 未读切换 |
| 未读数 | **未读分组数**，不是未读条目数 |
| 偏好 | 偏好分组 × 渠道的开关矩阵，未设置项显示场景默认 |

**渲染在服务端完成**：客户端没有场景渲染逻辑，列表与邮件、短信共用同一套渲染。客户端只负责展示与跳转。

**仅未读视图下，组大小与最新触发者都只看组内未读条目** —— 过滤发生在聚合之前。若最新触发者仍取全组最新，会显示一个已经读过的触发者，而真正未读的是更早那一条。

**分页单位是分组，不是条目**：按条目分页会让同一个组横跨两页 —— 组大小只统计到半截，「标记整组已读」也无法定位当前页之外的成员。

**组键由展示分组决定**：按对象分组的场景取「场景 + 对象」，不分组场景取条目自身（用事件标识，它在收件人内唯一，插入前即可算出）。

**组键在写入时物化，但它不是计数**：物化只为让分组分页、组大小与未读聚合走同一条索引；组大小与未读数仍是读取时聚合的结果。物化也意味着场景日后调整分组维度不会改写历史条目 —— 这是期望行为。

**未读数按分组计**：一条与五十条在视觉上都是「一组」，按条目计数会出现「角标 50、列表只有 1 组」的割裂。

**已读可以按条目或按分组**：按分组标记时更新该组全部条目，包括当前页之外的成员。已读是条目的属性，不是分组的属性。

### 3.6 投递

| 项 | 约定 |
|---|---|
| 唯一性 | `条目 + 渠道`；重复消费不产生第二次发送 |
| 状态 | 待发送 → 已发送 / 失败 / 已取消；失败可达上限，成为终态 |
| 回执 | 保存渠道侧消息标识，供对账与排障 |
| 重发 | 针对失败记录重投；需幂等，不得重复产生已成功的发送 |
| 退订 | 邮件正文附带签名退订链接，点击即更新偏好；签名防止替他人退订 |

**发送前复查条目**：投递消费者在发送前确认条目仍存在、事件未终止。撤回与发送是并发的 —— 撤回事务删掉条目时，可能已有一条投递记录被消费者取走，不复查就会把已撤回的公告发出去。

**发送前还要复查偏好**：投递记录可能在重试队列里待上几分钟，用户在这期间退订，邮件仍然会发出去 —— 退订挡不住在途投递，而拦住在途投递正是退订要解决的问题。发送前重新判定该分组的站内信与渠道开关；不通过时把记录置为已取消，不能只跳过 —— 留在待发送会被扫描反复捞起重试。

**对不可重试的错误直接确认**：邮箱不存在、号码停机这类失败，重试只会把消息推进死信。判定依赖渠道适配层，不由业务层猜测。

**保留按终态时间分档**：已发送与失败终态各自保留一段时间，供对账与重发；终态之后记录不再更新，所以终态时间就是最后更新时间。待发送与被取消的记录随条目一起删除，不单独保留。

### 3.7 撤回与清理

| 动作 | 行为 |
|---|---|
| 公告撤回 | 内容状态转已撤回、事件转已终止、删除派生条目与其投递记录（含已读），同一事务 |
| 公告内容删除 | 与撤回同级：先终止事件，再删条目与投递 |
| 用户删除通知 | 物理删除本人条目及其投递记录 |
| 对象被删除 | 文章、评论、说说、用户删除时，先终止关联事件，再按对象引用清理条目与投递；删文章或说说时，挂在它下面的评论产生的条目一并回收 —— 评论还在库里，但读者点进去只有 404 |
| 评论复核驳回 | 审核通过后又驳回时，删除它已产生的条目并发出审核结果。「评论被回复」按对象定位；**「评论了你的内容」挂在主题上（按主题聚合），只能按互动定位**，按对象回收会误伤同主题下别人的互动。同作者在该主题下还有别的已通过评论时，那条通知仍然成立，不撤回 |
| 过期保留 | 已读与未读分别设保留期（未读更长），**由场景声明**；到期连同投递记录一起清理；事件行只清理已终止且已无引用条目的 |

**条目与投递记录必须一起删**：只删条目会留下孤儿投递行，消费者仍可能据它把已撤回内容的邮件发出去。过期清理同理，且投递表自身按状态分档保留 —— 已发送的保留短，失败终态保留长，供排障与重发。

**未读条目也要过期**：只清理已读，长期不登录的用户收件箱会无限增长；且越积越多的未读本身也不再有用。未读的保留期设为已读的数倍，兼顾「回来还能看到」与「不会无限涨」。

**仍在扇出的事件不得被清理**：判断条件是「已终止且无引用条目」。只看有无引用会误删停在扇出中、条目又恰好被删光的事件，扇出从此断在半路，而且没有任何痕迹。

**对象删除必须清理引用它的条目**：否则收件箱留下点开即 404 的死链，且清理入口一旦缺失就再没有补偿路径。清理入口包括文章、评论、说说的批量删除与**硬删除用户** —— 注销是软删除，条目与载荷快照仍能独立渲染，不在此列。

**清理必须能走索引并分批**：条目上的索引都以收件人打头，而清理任务不知道收件人是谁 —— 必须有一条以场景打头的索引，否则全表扫描，表越大越慢、锁越久。删除按批进行、每批独立事务，条目与其投递在同一批里删，避免一个事务锁住几万行。

### 3.8 实时

| 通道 | 用途 |
|---|---|
| 站内实时（SSE） | 页面打开时接收「收件箱变了」的信号 |
| 外部推送（Web Push） | 页面关闭后的触达，作为投递渠道之一，后续接入 |
| 邮件 / 短信 | 投递渠道，由投递表承载 |

**按收件人频道动态订阅**：网关维护本实例的在线用户集合，连接建立时订阅该用户的频道、断开时退订。信号只到达持有该用户的实例，不向全站广播。

**广播的代价**：信号按收件人发布，一条面向万人的公告会产生万级 publish。当前规模可以接受；若成为瓶颈，改为按批发布到聚合频道、由网关用本地在线集合过滤 —— 信号那时退化成广播，但只落在一个频道上，不再按人扩散。

**管理端是另一条流**：只推公告状态变化，供多管理员协作时刷新列表。它与读者端的「收件箱变了」是两种语义，共用 Redis 与 SSE 基础设施，频道与载荷分开。

**不实时复用聊天长连接**：通知是单向的，用双向协议承载要额外维护订阅帧、确认语义与跨服务桥接。两类通道的可靠性模型不同，不因「都是实时」合并。

**推送丢失不影响正确性**：客户端定时对账拉取；关掉实时通道，功能仍然正确，只是变慢。

### 3.9 验证码

生成、存储、投递、校验在同一流程内完成；权威状态在会话存储，具备 TTL、一次性消费与失败次数上限。它复用传输能力，但不产生事件、条目与投递记录。

## 四、不变量

- [ ] 通知的权威状态在数据库；推送只发信号，不携带正文。
- [ ] 事件与业务数据同事务写入，事件写入失败即业务写入失败；扇出在事务外异步进行。
- [ ] 载荷在事件行只存一份；条目引用事件，不复制载荷。
- [ ] 收件箱条目按「收件人 + 去重键」唯一：可分组场景的去重键含触发者，不可分组场景的含事件；重复扇出不产生第二条。
- [ ] 通知只在内容对读者可见之后产生。
- [ ] 外部渠道投递按「条目 + 渠道」唯一，重复消费不产生第二次发送。
- [ ] 投递记录随条目一起删除；发送前复查条目仍存在、事件未终止、偏好仍未关闭。
- [ ] 聚合与未读数都是读取时的投影，不维护折叠计数。
- [ ] 列表以分组为分页单位，组大小与未读数都是按组键聚合的结果；仅未读视图只看未读条目。
- [ ] 只有真正写入了新条目才发实时信号。
- [ ] 直接触发者是收件人本人时不产生通知；逆向动作（取消点赞）不产生通知。
- [ ] 扇出可重入：中断后从游标继续，已写入的条目由唯一键吞掉。
- [ ] 插入条目、写投递、推进游标在同一事务；投递按本批收件人对应的条目生成，不依赖是否本次新插入。
- [ ] 过期清理按场景索引分批执行，条目与投递在同一批里删除。
- [ ] 撤回删除条目，不保留墓碑；公告内容本身保留，删除内容时派生条目与投递一并清理。
- [ ] 撤回、内容删除、对象删除都先终止事件再删条目；扇出每批写入前复查事件状态。
- [ ] 过期清理覆盖已读与未读，事件行只回收已终止且已无引用条目的。
- [ ] 评论复核驳回时，回收此前发出的「评论被回复」与「评论了你的内容」（同作者仍有可见评论时保留后者）；删除文章或说说时，连带回收其下评论产生的通知。
- [ ] 收件箱的读、写、删都以会话主体作为收件人条件，请求参数不得指向他人。
- [ ] 偏好按分组与渠道生效；站内信是锚点渠道，关闭它即关闭该分组全渠道；强制分组忽略偏好。
- [ ] 公告默认只落站内信，对外广播必须显式发起。
- [ ] 验证码不产生事件、条目与投递记录。

## 五、失败与降级

| 情形 | 行为 | 用户可见后果 |
|---|---|---|
| broker 不可用 | 事件行已在库内，发件箱唤醒退避重投 | 投递延迟，恢复后补发 |
| 发件箱 relay 停机 | 事件在库内堆积；业务事务仍然成功 | 恢复后补发；需要积压告警 |
| 扇出中断 | 状态停在扇出中，兜底扫描从游标重新入队 | 部分用户先收到 |
| 事件停留在扇出中过久 | 阈值触发重新领取；至少一次 | 可能重复尝试，条目被唯一键吞掉 |
| 未知场景 | 事件标记失败，不重试 | 该场景通知缺失，需发版修复 |
| 事件已终止（撤回、内容删除、对象删除） | 扇出在每批写入前复查并停止；已写入条目由删除事务清理 | 不产生新条目 |
| 对象删除与扇出并发 | 删除先终止事件，扇出在事件行上加锁复查，两者串行 | 收件箱不出现死链 |
| 重复消费 | 条目与投递的唯一键收敛 | 无重复通知 |
| 邮件 / 短信失败 | 有界重试；不可重试直接确认；终态可重发 | 管理端可见并可重发 |
| 发送时条目已删除或已退订 | 消费者复查条目与偏好后丢弃 | 不发出已撤回内容，也不发出用户已关闭的通知 |
| 保留期清理停机 | 已读与未读条目一起堆积 | 收件箱变长，不影响正确性 |
| 文案渲染失败 | 回退通用文案 | 通知仍可发出 |
| 实时信号丢失 | 客户端定时对账 | 延迟可见，不丢失 |
| 会话存储不可用 | 无实时信号 | 依赖拉取，功能仍正确 |
| 对象已删除 | 清理任务移除条目 | 收件箱不出现死链 |

## 六、边界与重新审视

- **频次控制**：可分组场景由分组吸收视觉噪音；不可分组场景（评论回复）的刷屏由内容侧审核与发言限流负责，不在通知侧再设上限。
- **扇出消息量随互动量线性增长**：每次互动写一条事件、发一条唤醒。这是「事件即工作单元」的直接代价，当前规模可以接受；若空跑占比高，可以改成低频唤醒加扫描待扇出事件，与投递侧同一套模型。
- **离线摘要**：按日汇总的低频邮件需要独立调度与模板，不与实时通知共用管线。
- **渠道扩展**：新增外部渠道只需实现发送、回执映射与不可重试判定；新增**站内**展示形态（弹窗、角标）属于展示层，不新增渠道。
- **受众扩展**：当前只有「全部用户」与「指定用户」。引入「主题订阅者」时扩展受众解析，不影响条目模型。
- **安全通知的豁免**：强制分组不可退订是安全底线；若将来支持「全部静音」，安全分组必须在静音期后补发而非丢弃。
- **文案的历史一致性**：读时渲染意味着改文案或改公告正文都会改写历史外观。若出现合规或争议场景，需要改为写入时快照。
- **展示分组变更**：组键在写入时物化，改分组规则等于数据迁移，需要对历史条目回填；否则应约定展示分组一经发布不可改。
- **定时任务依赖单副本**：兜底扫描与保留期清理都跑在 rpc 进程内，当前部署是单副本。扩到多副本前必须先加单活约束，否则清理会并发争锁、扫描会重复入队。
- **退订签名密钥**：密钥轮换期间必须同时接受新旧密钥，过期时间承担防重放。
