# blog 博客系统 — 数据与接口

初稿：2026-09-11　·　最近更新：2026-09-16

## 一、契约分层

### 1.1 两类契约

系统有**两类契约**，面向不同的消费者，职责不重叠：

| 维度 | HTTP 契约 | gRPC 契约 |
|---|---|---|
| 消费者 | 前端（浏览器 / Tauri） | 后端服务之间 |
| 形态 | RESTful 资源路径 + JSON | 方法 + 消息 |
| 关注点 | **用例**：一个请求对应一个界面动作 | **领域**：一个方法对应一个业务能力 |
| 粒度 | 面向客户端聚合，可裁剪字段 | 面向数据所有权，保持完整 |
| 变更影响 | 影响前端，需前后端协同 | 影响后端各服务，可独立发布 |

**设计约束**：HTTP 契约**按用例切**（如"后台的评论管理页要什么"），gRPC 契约**按领域切**（如"评论这个资源归谁拥有"）。两者的模块划分**允许且应当不同**——强行对齐会让两边都变差。这一原则贯穿 §二。

### 1.2 契约的存放与生成

- **契约是接口语义的唯一真相源**，集中存放于 `protocol/`，与实现仓库解耦
- 生成物（服务端骨架、客户端、类型定义、接口文档）**一律不手工编辑**，由代码生成工具从契约产出
- 契约的修改遵循固定次序：**先改契约 → 重新生成 → 再改实现**。跳过前两步直接改生成物，会在下次生成时被覆盖

### 1.3 契约形态的具体约定

§1.1 定的是"RESTful 资源路径"。以下是落地时必须遵守的约定——**改动它们需要重新走设计评审**。

**通则：契约只描述成功路径。** 请求/响应类型、路由、中间件是契约内容；错误语义、分页排序等横切约定不进入单个接口的类型定义（见下表末两行）。

| 约定 | 内容 | 理由 |
|---|---|---|
| **前缀** | 读者端 `/api/v1/*`，管理端 `/admin-api/v1/*` | 两端同源不同面。`admin-api` 不是资源名、违反 REST 命名，是**有意例外**——换取双端前缀的区分度 |
| **动作表达** | 动作作为独立路径段：`POST /articles/batch-delete`、`POST /articles/{id}/like`。**不用 AIP-136 的 `:动作`** | 工具链约束：goctl 的 `.api` 语法不支持冒号后缀。这是对 AIP-136 的有意偏离 |
| **批量操作** | `POST /资源/动词`，动词表达**业务意图**并与前端动作一致：`batch-delete`（删除）、`batch-restore`（恢复）、`batch-destroy`（销毁）、`export`、`sync`。**不用 `DELETE` 带 body** | RFC 对 DELETE 的 content 无语义定义，中间件可能丢弃；body 丢失会让 `ids` 变空——批量操作最不该有这种歧义。AIP-135 亦规定批量删除应定义为自定义方法 |
| **意图进 URL，字段不进** | 批量字段变更拆成表达意图的端点，**不用 `batch-update-{字段}` + 参数值** | 用参数值编码动作，客户端要查文档才知道怎么调；URL 名还会随字段漂移——曾因此产出 `batch-update-status`，而相册与照片的批量操作实际改的是软删标记，名字直接是错的 |
| **删除的词汇区分** | 「**删除**」（可恢复，进回收站）用 `delete` / `restore`；「**销毁**」（不可逆的物理删除）用 `destroy` | 二者是不同业务动作、不同权限点。混用一个 `delete` 会让读者把可恢复的与不可逆的搞反；共用一个端点则无法做「能恢复、不能销毁」的授权 |
| **字段级状态变更（单个）** | 单资源 `PATCH /资源/{id}` + 局部更新体 | PATCH 的"部分更新"语义正好；批量场景走上面的意图动词 |
| **关联关系** | 建模为子资源集合：`PUT /roles/{id}/menus`（全量替换）、`POST`/`DELETE /资源/{id}/子资源` | 绑定关系本身就是资源集合，`PUT` 的幂等语义恰好表达"替换为这份列表" |
| **同一概念可有多个视图类型** | 直接喂给前端的结构可偏离仓库命名通则，与同一概念的「管理视图」类型**不同轴**——字段命名风格、布尔与整型的表达均可不同 | 两个消费者不同——管理表单要能原样回填、回传落库，路由表要直接喂给前端框架。统一到任一侧都是让一边多转一次；用词分歧源自两个前端生态的既定惯例，非同名反义 |
| **auth 的 URL 形态** | ① 登录**按方式拆端点**（`POST /auth/login-by-{password,email,mobile}`），不合并为 `POST /token` + `grant_type`；② 第三方登录**按平台建模为子资源**：`GET /auth/oauth/{platform}/authorize` + `POST /auth/oauth/{platform}/login`；③ 验证码沿用社区的 `GET /auth/captchas`；④ 登出用 `DELETE /auth/session`（不叫 `/logout`）；⑤ 密码重置建模为资源：`POST /auth/password-resets`；⑥ 注册用 `POST /auth/registrations` | ① 四种登录的请求体形状确实不同（`{account,password,captcha_*}` / `{email,code}` / `{mobile,code}`），合并会得到 6+ 个 optional 字段的联合类型，与「契约只描述成功路径」相悖；② `platform` 是天然的子资源维度，比塞进 `login-by-X` 一族更整齐；③ `GET /captchas` 是社区压倒性惯例，虽严格说不满足 RFC 9110 §9.2 的 safe（每次调用都写一条 captcha，浏览器预取与爬虫会消耗配额），但改 POST 需前端改请求方法与既有客户端；该偏离的风险由**限流**承担（见《07》§2.4）；④ 比 Auth0/Supabase 的 `POST /logout` 更 RESTful；⑥ 与 `password-resets` 同轴——都是「发起一次认证流程」，产出流程实例而非用户资源；用户资源由 `user` 模块拥有（见 §2.2），不在 `auth` 下暴露集合 |
| **分页** | 偏移分页（`page` + `page_size` → `total` + `list`） | 读者端与管理端均按后台风格消费，需跳页与总数展示 |
| **错误码** | **不进契约** | 错误是全局横切语义，不属于任何单个接口；|
| **排序** | 契约层现为 `sorts`（字符串数组），迁移到 `order_by` 待定 | **已知遗留**：`sorts` 以裸字符串下传，存在排序字段注入面。迁移完成前，服务端**必须**对排序字段做白名单校验，不得拼入排序子句 |

**遗留项与约定的区别**：上表标为「**已知遗留**」的条目是**已识别、未修复**的问题，是对最终设计的有意偏离，不是定案。约定不可在实现中变更；遗留项可以，但只能朝表中给出的方向收敛。**遗留项必须在该方向落地后从本表移除**，不得长期驻留。

### 1.4 gRPC 契约的命名约定

§1.1 的两类契约里，gRPC 契约的完整规则见《[RPC设计规范](../standards/RPC设计规范.md)》。落地时的两条取值约定——**改动它们需要重新走设计评审**：

| 约定 | 内容 | 理由 |
|---|---|---|
| **单资源 vs 多目标** | 单资源用 `Patch{Resource}`；**多目标一律 `Batch{Action}{Resources}`** | 从名字直接看出"改一个"还是"改一批"，不必读请求体。依据规范 §5.2 与 AIP-136 |
| **部分更新用 `Patch`** | `Update{Resource}` = 覆盖全部客户端可写字段；`Patch{Resource}` = 只改一部分；状态位（软删标记、发布状态、置顶标记）归 `Patch` | 与 AIP-134 的 `FieldMask` 路线不同，换取方法名上的直接可见（差异说明见规范 §5.3） |

**与 HTTP 契约不同轴，这是刻意的**：api 层按**用户意图**命名（`batch-delete` 进回收站 / `batch-restore` / `batch-destroy` 销毁），rpc 层按**技术语义**命名（`BatchPatch{Resources}` 改字段 / `BatchDestroy{Resources}` 物理删除）。两层粒度不同是 §1.1 允许的。

**两条红线**：

1. **不得同名反义**——同一个词不得在两层指相反的事。
2. **可恢复性必须在跨层时保持可辨**——api 层的 `delete`（可恢复）在 rpc 层**没有**同名方法，它映射为改软删标记的 `BatchPatch{Resources}`。该映射本身是必要的（rpc 层不承载「回收站」这个业务概念），代价是「可恢复」这一语义跨层后不再可见。因此规定：凡 api 层存在 `delete` / `restore` / `destroy` 三种意图，rpc 层必须能用方法名区分「改状态位」（可恢复）与「物理删除」（不可恢复），**不得让可恢复与不可恢复落到同一方法名上**。跨层排障时需回查本节完成映射。

## 二、模块边界与数据所有权

### 2.1 划分判据

模块划分采用三条判据，按优先级排列：

| 判据 | 内容 | 来源 |
|---|---|---|
| **聚合聚类** | 总是被一起修改的资源，构成天然模块 | DDD 限界上下文 |
| **耦合验收** | 若两个候选模块会共享数据表（公共耦合）或互相伸手进内部（内容耦合），则不应拆开 | Nygard 耦合分类学 |
| **反模式规避** | 不为单张表造薄 CRUD 模块；同理，也不把多个**同构**资源拆成多个模块 | Nygard「实体模块」反模式 |

### 2.2 模块与数据所有权

**每个资源有且只有一个所有者模块**，其他模块只持有引用：

| 模块 | 代码名 | 拥有的资源 | 说明 |
|---|---|---|---|
| 用户 | `user` | 用户、个人中心、账号绑定、账号生命周期 | 注册身份主体 |
| 访客 | `guest` | 访客 | 匿名身份主体，以**服务端签发的设备令牌**标识；设备指纹仅作令牌内的记录字段，不作标识依据（见《03》§1.4） |
| 认证 | `auth` | 登录、注册、登出、第三方授权、密码重置 | 技术能力，不拥有业务数据 |
| 访问控制 | `access` | 角色、菜单、接口资源、授权关系 | RBAC 四件套，改动联动 |
| 内容 | `content` | 文章、分类、标签、修订版本 | 发布时同时选分类、打标签，聚合关系强；修订与正文同聚合，不独立成模块 |
| 媒体 | `media` | 相册、照片 | 相册包含照片 |
| 讨论 | `discussion` | 评论、留言、说说 | 用户产出、需审核的讨论内容 |
| 聊天 | `chat` | 聊天室消息 | 实时消息流，经 STOMP 提供（见《04》） |
| 站点 | `site` | 站点配置、自定义页面、友链、分发出口（feed / sitemap / robots） | 站点呈现层，含对外的机器可读出口 |
| 订阅 | `subscriber` | 订阅者（订阅状态、退订凭据、同意记录） | 邮件订阅身份主体：无凭据、可不依附账号 |
| 通知 | `notification` | 通知模板、通知内容、投递记录、验证码 | 定义 → 发布 → 投递的完整生命周期 |
| 日志 | `syslog` | 登录 / 操作 / 上传 / 访问日志 | 四类同构、同用途。代码名 `syslog` 与 syslog 协议同名，不满足 §2.4「名实相符」，经评估按「一致性优先」保留，见 §2.4 末 |
| 统计 | `stats` | 统计数据（含物化表） | 拥有自己的物化数据，非纯只读投影 |

**本表是模块与数据所有权的唯一真相源。**

**分类与标签同在 `content`，但差别是结构性的**——不在命名，而在层级、URL 形态、归档模板与计数口径。分类**层级化**（可嵌套、有稳定 slug、驱动归档页），标签**扁平**（仅作横向聚合）。若将来引入分类层级，**直接加单一 `parent` 字段**，不要维护去规范化的 `children` 数组——那需要双写且易失同步，社区里有系统用了多年后又废弃该字段改回 `parent`。

### 2.3 模块边界的取舍

§2.1 的判据落在边界地带时，有几处需要判断的情形：

**评论、留言、说说不拆**：三者各自独立建表，技术上可拆；但拆开等于产出三个「围绕单表的薄 CRUD 模块」，正是判据三前半句所警示的实体模块反模式。三者承载的是**同一项能力**——面向页面的、需审核的用户发言。

**聊天独立成模块**：它与上述三者虽同属"用户产出内容"，但数据模型与生命周期不同——带冗余用户快照（发送者信息内嵌于消息）、无主题引用、经 STOMP 实时通道。业界的评论系统（WordPress / Halo / Discourse）也不把聊天与评论置于同一域。

**用户、访客、订阅者三者并列，不合并**：三者同为身份主体，但各自拥有数据表、生命周期不同——注册主体有凭据，匿名主体只有**服务端签发的设备令牌**，订阅主体只有邮箱与同意记录。按判据二，三者无公共耦合，独立成立。合并则须引入一个上位词同时罩住三者，这会让**层级一致的具体名词**退化成一个宽泛词。**邮箱重合时不自动合并**，与《03》§1.3「绑定与解绑是显式动作」同源。

**统计独立**：它拥有物化数据，是数据所有者，不与任何模块构成公共耦合。

**已评估、明确不引入的建模方式**——记录下来以免反复论证：

| 不引入 | 理由 |
|---|---|
| **多分类法三表**（词条 → 词条在分类法中的身份 → 关系） | 它解决的是"同一词条复用到多种分类法 + 每种独立配置层级/描述/计数"。本项目只有分类与标签两种，**成本当下就付、收益用不到** |
| **内容付费表族**（会员 / 档位 / 订阅关系 / 支付商缓存） | 本系统没有支付集成，引入后绝大多数表空转 |
| **动态集合 + 查询语言**（用过滤表达式定义内容集合） | 归档 / 分类 / 标签三个固定视图用固定条件即可，为千级内容实现一套查询语言属过度设计 |
| **联邦协议**（ActivityPub / Webmention） | 需常驻的联邦网关与额外的滥用治理面；RSS + sitemap 已覆盖"被订阅"的需求 |
| **把可见性写成正文里的短代码** | 权限必须落在可索引、可审计的结构化字段上。写在正文里意味着"改可见性 = 改正文"，会破坏修订历史与缓存失效的判断 |

### 2.4 命名

模块名应表达**它拥有什么**，而非"它跟什么有关"。四条取舍：

| 原则 | 说明 | 实例 |
|---|---|---|
| **名实相符** | 模块名要指向它实际拥有的资源，而非一个它并不拥有的概念 | 只装「角色 / 菜单 / 接口资源」的模块，名字应指向访问控制，而不是它并不拥有的「权限」 |
| **层级一致** | 并列的概念用同一层级的名词，不把上位词与具体词混用 | 「用户」与「访客」并列，不引入同时罩住两者的上位词 |
| **具体优于宽泛** | 具体名词优于通用抽象；通用名会让读者各自附会含义 | 由用户产出、需审核的发言内容，用具体的「讨论」，不用宽泛的「互动」 |
| **一致性优先** | 本仓库内已一致的术语，即使与行业惯例有出入也不改名 | 「日志」沿用仓库既有叫法 |

**结论**：命名优先服从本项目语境的一致性；但当原名与它拥有的资源对不上，或宽泛到产生歧义时，接受一次性改名成本。**曾被否决或已认可的术语不再重提**，避免反复。

**唯一的显式例外：`syslog`**。它与 syslog 协议同名，而实际拥有的是登录 / 操作 / 上传 / 访问四类**业务**日志，严格说不满足「名实相符」。保留原名的理由：该模块的边界本身无歧义（四类日志同构同用途），更名会触动代码中全部引用处，收益不抵改动面，故按「一致性优先」处理。**这是被记录的例外，不是未被发现的疏漏**——后续不再作为改名建议提出。

### 2.5 何时重新审视

下列信号出现时，应重新走设计评审：

- 某模块的资源**不再总是被一起修改**（聚合关系瓦解）
- 两个模块开始**共享同一张表**（公共耦合）
- 讨论域中评论、留言、说说之一演化出**独立的数据模型与生命周期**，与其余二者不再同节奏
- 访客长出独立能力（如行为归因），或其职责萎缩到不再值得单独成模块
- 订阅者长出账号能力（可登录、可评论），或订阅者与用户的邮箱重合需要统一视图

## 三、通信方式

### 3.1 网关到服务

- 网关层经 **gRPC** 调用服务层，**不直接访问数据库**
- 网关层的编排只做**跨服务调用编排**，不承载领域规则
- 数据访问与**事务边界只在服务层**

### 3.2 实时通信

聊天室与在线状态经 STOMP 链路提供，与 HTTP 链路并行。**实时通信的完整约定见《04》§三**（身份在协议层校验、状态外置、业务经事件钩子接入而不侵入协议层）。

数据层面只需记住一条——**聊天独立成模块**，理由见 §2.3。

### 3.3 异步消息

非关键路径走消息队列，不阻塞主链路：

| 场景 | 原因 |
|---|---|
| 邮件 / 短信投递 | 依赖外部服务，延迟不可控 |
| 日志落库 | 高频写入，不应拖慢业务响应 |

**投递语义**：验证码类消息对时效敏感、可容忍丢失（用户可重发），采用**尽力投递**；业务通知需可追溯，采用**投递记录持久化 + 状态流转**。

**三条兜底约定**（改动它们需要重新走设计评审）：

| 项 | 约定 |
|---|---|
| **重试** | 仅外部通道（邮件 / 短信）重试，采用**有上限的退避**；超过上限转入**失败终态**并在投递记录上留痕，供管理端重发。站内信不经外部服务，不重试 |
| **幂等** | 消费者按投递记录 ID 去重，**重复投递不得产生第二条记录、不得重复发送**。禁止依赖「消息只会投一次」这一假设。本条**只适用于业务通知**——验证码走尽力投递且不产生投递记录（见《04》§二），不在此列 |
| **不作保证** | 不承诺消息不丢失，也不承诺投递顺序。丢失由「失败终态 + 管理端重发」兜住；顺序由投递记录的时间戳表达。**不引入任何需要顺序保证的设计** |

## 四、存储策略

### 4.1 持久化

- **MySQL** 是**业务实体**的唯一权威数据源；会话与令牌状态是另一类权威数据，由 Redis 承载（见 §4.2）
- 关联关系以**独立关联表**表达，与实体表分离——如角色与菜单、角色与接口资源、用户与角色、文章与标签
- 统计类数据以**物化表**承载，避免实时聚合大表
- 物化表由**定时任务**离线刷新，**刷新周期即统计口径的数据延迟上限**；查询路径不触发物化。这是有意的取舍：统计只用于展示与分析，**不参与任何业务判定**，因此接受最终一致
- 内容需区分**发布时间**与**实质内容变更时间**：`sitemap` 的 `lastmod` 只有在"一致且可验证"时才会被搜索引擎采用，而通用的 `updated_at` 会因改标签、改状态而变动——用它做 `lastmod` 会让整站的日期信号失信。该区分属 `content` 模块的模型约定

### 4.2 缓存与会话存储

Redis 承担两种**性质完全不同**的职责。二者**必须隔离部署**（独立实例，或至少独立逻辑库 + 独立持久化策略），不得混用同一个库：

| 角色 | 用途 | 丢失的后果 | 持久化 |
|---|---|---|---|
| **业务缓存** | 热点内容等读多写少的展示数据；限流计数等短生命周期数据 | 无——回源重建 | 不需要，可随时清空 |
| **会话存储** | 会话 / 令牌状态；在线列表（见 §3.2）；验证码（见《04》§二） | 令牌状态丢失 = **已吊销的令牌复活**（三者中唯一的安全事件）；在线列表与验证码**可重建** | **必须开启** |

**归入「会话存储」的判据是运维约束，不是丢失后果**——上表把在线状态与验证码与之并列，是因为它们**与令牌同实例、同属「不得清空」的一侧**；但三者中只有**会话 / 令牌状态**是权威数据（丢失即安全事件），在线状态与验证码**可重建**，清空只会中断在途流程，不产生不可逆后果。这两个判据此前被混用，此处分开声明。

**约束**：

- **业务缓存**不承载权威数据，任何时刻清空都不应导致数据丢失
- **会话存储是权威数据，不享受上述豁免**。系统不引入数据库承载会话状态，其权威性因此由三者共同保证：**与其他 Redis 用途隔离** + **开启持久化** + **运维规程禁止清空**。这三条缺一不可——它们是对「只用 Redis」这一选型的直接补偿
- **降级方向**：会话存储不可用时 **fail-closed**（拒绝请求）——放行等于吊销机制失效，其后果比拒绝服务严重。完整的降级方向表见《08》§四

### 4.3 对象存储

图片等二进制经**存储适配器**直传，接口只传引用（存储键）：

- 适配器可切换后端（本地磁盘 / 对象存储），业务无感知
- **大对象不过网关**，避免占用网关带宽与内存
