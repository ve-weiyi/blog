# 34 实时通信

> **本文回答**：长连接如何建立、校验、投递与恢复，在线状态放在哪里。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、定位与边界

采用 **STOMP over WebSocket**。选它而不是裸 WebSocket，是因为它自带订阅 / 发布语义（destination + subscription），消息路由不必自定义协议。

| 能力 | 内容 |
|---|---|
| topic | 广播：聊天室、在线人数 |
| queue | 点对点：带 ack 与重入队 |
| 连接生命周期 | 握手、心跳、断开清理、在线状态 |

**它不是消息中间件**：无持久化、无集群、无跨节点路由。业务通过三个接口注入：

| 接口 | 用途 |
|---|---|
| `Authenticator` | CONNECT 帧身份校验 |
| `EventHook` | 连接、订阅、消息、确认、断开等业务钩子 |
| `PresenceManager` | 在线状态的读写与回收 |

业务持久化由消费方完成，STOMP 层不感知聊天记录存储在哪里。

**部署形态**：`app-api` 与 `admin-api` 各内嵌一个 hub，不单独部署。两个 hub 的**中继状态各自进程内保存**；在线状态外置到 Redis 共享。跨 hub 的消息扇出不在当前设计内。

## 二、连接与身份

```
WebSocket 建立 ──▶ STOMP CONNECT（login / passcode / client）──▶ 校验 ──▶ 已连接
```

| 头 | 内容 | 约束 |
|---|---|---|
| `login` | 用户标识 | 与令牌声明一致 |
| `passcode` | access token | 只接受 access，不接受 refresh |
| `client` | 设备标识 | 必填；与令牌的设备绑定一致 |

- **读者端允许游客连接**：`login` 与 `passcode` 都为空时，以 `client` 作为身份放行；只能进入公开主题，不能代表用户。
- **管理端要求登录**：三个头都必填，令牌必须有效。
- **身份校验在协议层**：凭证走 CONNECT 帧，不走 URL —— 避免令牌进入访问日志与浏览器历史。
- **校验前不分配身份**：未通过校验的连接不进入在线列表，不能订阅业务主题。
- **失败即拒绝**：返回 ERROR 帧并关闭连接；不做「先接受再降级到匿名」的中间态。

**吊销事件通道**：会话撤销（停用、注销、强制下线、改密）时发布按用户/设备索引的吊销事件；各 hub 订阅后断开本地匹配连接。该通道只传播控制信号，不做消息扇出，因此不与 §六 的「不跨 hub 扇出」冲突。事件丢失时，连接在下一次业务动作前校验会话；不能把 CONNECT 时的身份视为永久有效。

**失败延迟**：认证失败先延迟约 1 秒再返回错误，用于抵抗暴力猜测。延迟必须异步实施（定时器），不得阻塞连接处理线程 —— 否则每个失败连接都占住一份处理资源，延迟反而成为放大攻击的杠杆。

**为什么长连接不共用 HTTP 认证中间件**：HTTP 中间件链在升级请求前执行一次，之后连接上的每一帧都不再经过它。身份必须在协议层重新校验，并随连接生命周期保持。

## 三、投递与消息

### 3.1 先持久化，再广播

```
客户端 SEND ──▶ 业务钩子：校验 → 持久化（经 rpc）
                    │ 成功
                    ▼
                广播给订阅者
                    │ 失败
                    ▼
              回报发送方失败，不广播
```

**持久化失败即不广播。** 不接受「发送方已看到消息、刷新后消失」——那会让用户认为消息已发出，而系统里根本没有这条记录。

**广播是尽力而为**：不重试、不向发送方回报投递结果；未收到者由订阅时的补发兜住。

### 3.2 补发

- 订阅时按会话维度拉取最近消息，客户端携带上次收到的位置；**必须设条数上限**，超限时截断并明确告知客户端已截断。
- 补发失败必须返回显式信号，客户端据此决定「重新全量拉取」还是「没有新数据」。
- 顺序由持久化时分配的序号或时间表达，保证**单会话内**的先后；不保证跨会话或跨 hub 的全局顺序。

### 3.3 编辑与撤回

编辑、撤回、删除都先改持久化状态，再广播状态变化事件。**不把正文放在广播里**：客户端只收到「某条消息已变化」，回查权威状态。这样离线、乱序、多端都能收敛到同一结果。

### 3.4 内容治理

聊天是公开、实时的互动，**不做逐条预审**——预审会让实时性失去意义，也会把管理端变成瓶颈。治理放在事前限制与事后处置：

| 层 | 手段 |
|---|---|
| 事前 | 单条长度上限；按连接 / 主体 / IP 的频率限制；重复内容检测 |
| 事中 | 本地关键词规则（可选）；命中即拒发，不依赖外部服务 |
| 事后 | 作者编辑 / 撤回；管理员撤回 / 删除；反复违规断开并临时封禁 |

- **作者只能改自己的消息**；管理员可以处置任意消息。归属校验在服务端完成，不接受客户端自报。
- **撤回 / 删除是状态变更**：先落库，再广播状态变化；历史查询过滤已删除记录。
- **封禁是身份级的**：注册用户用账号状态，访客用设备标识的短期封禁键；封禁在 CONNECT 与 SEND 两处都校验，不能只挡连接。
- **本地关键词规则失败不阻断聊天**：它是增强项，不是准入条件；规则误判的代价应低于整条聊天链路不可用。

## 四、在线状态

- 在线状态存 **Redis**，按用户与连接（或设备）记录，带 TTL。
- 连接建立后写入，续租由心跳驱动；断开时删除。TTL 是兜底：实例崩溃后残留的连接会在 TTL 后消失。
- **站点在线人数是全局口径**：`app-api` 的实例共享同一个 Redis 集合，读者端看到的是跨实例的站点在线人数。管理端连接写入独立集合（`blog:online:admin`），不与站点在线混算。
- 订阅在线主题时先补发当前人数，再接收变化；广播只在人数确实变化时发出，避免每次连接都刷一遍。
- 查询在线人数失败时按 0 上报并记录日志：在线人数只是提示，不应因为查询失败打断问候或订阅应答。

## 五、连接治理

| 项 | 约定 |
|---|---|
| 心跳 | 按 STOMP 协商的 `heart-beat`，下限 30 秒；发数据帧心跳，不用 WebSocket 控制帧 ping 充数 |
| 在线 TTL | 60 秒，大于心跳间隔的三倍；漏掉一两次心跳不应误判离线 |
| 单连接协程 | 读循环、写循环、处理循环各一；写出由写循环独占 |
| 中继状态 | 单 goroutine 写者；所有中继操作经请求通道，不直接改 map |
| 投递缓冲 | 每连接有界；满了即判慢消费者，断开而不是无限堆积 |
| 连接上限 | 全局上限 + 按来源 IP 的连接数上限；超限拒绝新连接 |
| Origin 校验 | 只允许配置的来源，与 HTTP CORS 共用同一来源白名单；不得默认放行 |
| 未认证存活 | 连接建立后限时未通过 CONNECT 即断开 |
| CONNECT 频次 | 按来源 IP 限制**失败**次数；超限直接拒绝，不再进入延迟流程 |
| 关闭 | 停止接收新连接，关闭既有连接；客户端指数退避重连 |

以上是连接治理的目标约定。按 IP 计数时，IP 取自受信代理的 `X-Forwarded-For` 最右可信跳；直连取 `RemoteAddr`，不受信来源的转发头忽略。

**慢消费者必须断开**：投递缓冲无界会让一个卡住的客户端拖垮整个进程的内存；断开是可恢复的，内存耗尽不是。

**重连风暴**：客户端重连使用指数退避 + jitter（基数 500 ms、上限 20 秒）；服务端对建连限流。实例重启会让其承载的连接同时重连，实例越多风暴越集中。

## 六、跨 hub 与多副本

| 状态 | 是否跨 hub 共享 |
|---|---|
| 站点在线状态（`app-api` hub） | 是，Redis 同一集合，跨 app 实例共享 |
| 管理端在线状态（`admin-api` hub） | 独立 Redis 集合，不与站点混算 |
| topic / queue 中继状态 | **否，进程内** |
| 聊天消息持久化 | 是，数据库 |

**当前不提供跨 hub 扇出**：`app-api` 的聊天广播不会到达 `admin-api` 的连接，反之亦然。这是刻意的边界：

- 单机单副本下，两个网关各服务一类客户端，跨 hub 聊天没有产品需求；
- 引入跨 hub 路由需要连接注册表、实例间转发与失败重试，成本远高于当前收益（P8）。

**重新审视的信号**：需要多副本承载长连接；出现跨网关必须互通的消息；单实例连接数成为瓶颈。届时的最小方案是共享连接注册表 + 广播通道，而不是把中继状态整体外置。

## 七、关键决策

### D1 STOMP 内嵌两个网关，不单独部署

- **约束**：单独部署会新增一套扩缩、鉴权与故障模式。
- **备选**：独立实时服务；或只在一个网关内嵌。
- **选择**：两个网关各持一个 hub；站点与管理端在线分别使用独立 Redis 集合，中继状态进程内。
- **代价**：跨 hub 消息不可达；连接数分散在两个进程。
- **重审触发**：多副本或跨网关互通成为需求。

### D2 身份在 CONNECT 帧校验

- **约束**：HTTP 中间件覆盖不到升级后的每一帧。
- **备选**：升级前一次性鉴权；或每帧携带令牌。
- **选择**：CONNECT 帧携带凭证，协议层校验一次，连接生命周期内保持身份。
- **代价**：连接期间身份变化需要额外处理（见 D6）。
- **重审触发**：出现必须逐帧校验的高安全场景。

### D3 凭证走帧，不走 URL

- **约束**：URL 会进入访问日志、浏览器历史与代理缓存。
- **备选**：查询参数携带令牌。
- **选择**：CONNECT 帧头。
- **代价**：非 STOMP 客户端接入成本略高。
- **重审触发**：出现不支持自定义帧头的客户端。

### D4 先持久化后广播

- **约束**：广播成功但持久化失败，会造成「看到了但查不到」。
- **备选**：先广播后异步落库。
- **选择**：持久化成功才广播；失败回报发送方。
- **代价**：发送延迟多一次数据库写入。
- **重审触发**：出现允许丢失的临时消息类型。

### D5 慢消费者断开

- **约束**：无界缓冲会耗尽进程内存。
- **备选**：丢弃最旧消息；或阻塞中继。
- **选择**：有界缓冲，满了断开连接。
- **代价**：慢客户端会被强制重连。
- **重审触发**：出现必须保证不丢的推送场景。

### D6 权限变更不关闭长连接，身份吊销走吊销事件通道

- **约束**：长连接建立后权限被冻结；HTTP 侧的中间件覆盖不到它。
- **备选**：权限变更即断开所有连接；或完全不管；或逐帧校验会话。
- **选择**：权限收紧在下一次业务动作重新判定；身份吊销通过**吊销事件通道**传播到各 hub，hub 按本地连接表断开匹配连接；事件丢失时，下一次业务动作仍校验会话。
- **代价**：hub 需要维护本地连接索引并订阅吊销通道；该通道只传控制信号，不做消息扇出，因此不与 D7 冲突。
- **重审触发**：出现必须实时撤销连接内权限的场景；或吊销事件通道本身成为单点。

### D7 不提供跨 hub 扇出

- **约束**：跨 hub 路由需要注册表与实例间转发，当前收益不足。
- **备选**：引入 Redis Pub/Sub 或 MQ 做 hub 间广播。
- **选择**：不提供；站点在线状态共享已覆盖「谁在线」的需求。
- **代价**：跨网关的实时消息不可达。
- **重审触发**：多副本长连接或跨网关消息成为需求。

### D8 聊天不做预审，治理放在事后

- **约束**：预审会让实时聊天失去意义，并把管理端变成瓶颈。
- **备选**：逐条预审；或所有消息先过外部内容安全 API。
- **选择**：事前限制长度与频率，事中可选的本地关键词规则，事后撤回 / 删除 / 封禁。
- **代价**：违规内容可能短暂可见；依赖管理员及时处置。
- **重审触发**：出现必须在发送前阻断的合规要求。

## 八、不变量

- [ ] CONNECT 通过前不分配身份、不进入在线列表。
- [ ] 凭证不出现在 URL 与访问日志。
- [ ] 先持久化，后广播；持久化失败不广播。
- [ ] 补发有上限，且「是否截断」有显式信号。
- [ ] 中继状态只有一个协程写；投递与回执非阻塞。
- [ ] 慢消费者被断开，缓冲不无界增长。
- [ ] 在线状态带 TTL；实例崩溃后残留会被清理。
- [ ] 在线人数查询失败按 0 上报，不阻断连接。
- [ ] 权限变更不触发下线；身份吊销通过吊销事件通道断开本地连接，事件丢失时由下一次业务动作校验兜底。
- [ ] 聊天不做逐条预审；违规靠撤回 / 删除 / 封禁等事后处置。
- [ ] 作者只能修改自己的消息；管理员可以处置任意消息。
- [ ] 封禁在 CONNECT 与 SEND 两处都校验。
- [ ] 撤回 / 删除先落库再广播；历史查询过滤已删除记录。

## 九、失败与降级

| 情形 | 行为 | 用户可见后果 |
|---|---|---|
| 令牌无效 | ERROR 帧 + 关闭 | 无法连接；重新登录 |
| 缺少 `client` 头 | 拒绝连接 | 客户端接入错误 |
| 未在时限内 CONNECT | 断开 | 需重连 |
| 持久化失败 | 不广播，回报发送方 | 消息发送失败 |
| 广播失败 | 不重试；由补发兜底 | 可能延迟收到 |
| 在线状态查询失败 | 按 0 上报并记录 | 人数显示为 0 |
| 慢消费者 | 断开 | 客户端重连并补发 |
| 单个 hub 不可用 | 该网关连接断开 | HTTP 不受影响；重连 |
| 跨 hub 消息 | 不可达 | 当前设计边界 |

## 十、边界与重新审视

- **多副本长连接**：需要共享连接注册表与跨实例路由。
- **跨网关互通**：见 D7。
- **消息持久化位置**：由聊天域拥有；实时层只调用持久化接口。
- **推送与通知**：通知的信号通道是 Redis Pub/Sub + SSE，不复用 STOMP；两者的可靠性模型不同，不能因为「都是实时」就合并。
