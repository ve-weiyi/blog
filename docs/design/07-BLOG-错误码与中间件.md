# blog 博客系统 — 错误码与中间件

初稿：2026-09-11　·　最近更新：2026-09-17

## 一、错误码

**本文是本项目错误码取值的唯一真相源**——取值表是契约的一部分，客户端依赖它做分支，因此在本维护。

行业层面的通用做法与方案权衡（错误信息如何分层、业务错误挂哪个 HTTP 状态、标识取什么形式）见《[错误码设计规范](../standards/错误码设计规范.md)》。**该文给出的是通用取舍依据，不给定具体取值；取值以本文为准。**

### 1.1 两层错误信息

一次失败要同时回答两个问题。**社区规范对此的分工是一致的**——RFC 9457 与 Google AIP-193 都把"粗粒度类别"交给 HTTP 状态码，把"细粒度原因"交给 body 里一个机器可读标识：

| | **HTTP 状态码** | **业务错误标识** |
|---|---|---|
| 回答 | 这个请求**能否被处理** | 处理**结果是什么** |
| 归属 | **logic 之前**：框架、中间件、请求解析 | **logic 之内**；准入判定类另由中间件产出 |
| 载体 | HTTP 状态行 | 响应信封的 `code` 字段 |
| 取值 | 标准 HTTP 语义 | 自描述的字符串标识，命名规则见 §1.7 |

**为什么不能只有一层**：状态码是粗粒度的类别，同一状态码下有客户端反应不同的多个原因——`401` 同时覆盖"未登录"（该登出）与"登录已过期"（该静默刷新），`409` 同时覆盖"资源已存在"与"状态不允许"。RFC 9457 因此要求客户端在机器可读的 `type` 上分支；AIP-193 因此把 `ErrorInfo.reason` 定为必填，并同样指明**多个错误会共享同一个状态码，控制流应依赖 reason 而非状态码**。RFC 9457 还进一步声明响应体里的 `status` **仅为参考**，不是权威。三者也都明确禁止用人类可读的 message 做判断。

**术语**：本文中

- **HTTP 状态码**——状态行上的三位数字，值域与语义由 HTTP 规范定义
- **业务错误标识**——写入信封 `code` 字段的字符串值（对应 AIP-193 的 `reason`、Microsoft 指南的 `code`、RFC 9457 的 `type`）
- **信封**——统一响应体 `{ code, message, data, trace_id }`，定义见 §三

**两者的分界就是 logic 的边界**：进入 logic 之前的一切（框架保护、中间件准入、请求解析）属于传输层，其结论以标准 HTTP 状态码表达（准入判定类经响应出口按标识映射，见 §1.2）；logic 之内属于业务层，产出业务错误标识。

**归属是排他的**：HTTP 状态码属传输层，**logic 一律不产出**。中间件也只产出标识——它对应的状态码由响应出口按 §1.4 的映射产出；只有框架保护（§2.6 甲）与请求解析失败（§2.6 乙）不经标识、直接写出状态码。

业务错误标识内部再分两类，**分别只由一层产出、互不交叉**，因此"这个标识是谁抛的"始终可判定：

| 类别 | 产出层 | 标识 |
|---|---|---|
| 准入判定类 | 中间件 | `RATE_LIMIT_EXCEEDED` `REQUEST_SIGNATURE_INVALID`（凭据与配额）、`PARAM_MISSING`（设备令牌缺参）、`UNAUTHENTICATED` `LOGIN_EXPIRED` `PERMISSION_DENIED` `ROLE_MISMATCH`（身份与授权） |
| 业务规则类 | logic | `PARAM_INVALID` `PARAM_FORMAT_INVALID` `PARAM_VALUE_NOT_ALLOWED`、`CREDENTIALS_INVALID` `ACCOUNT_DISABLED` `CAPTCHA_INCORRECT`、`RESOURCE_NOT_FOUND` `RESOURCE_ALREADY_EXISTS` `RESOURCE_STATE_NOT_ALLOWED` `PRECONDITION_FAILED` `OPERATION_NOT_ALLOWED`、`INTERNAL_ERROR` `DATABASE_ERROR` `EXTERNAL_SERVICE_ERROR` `SERVICE_UNAVAILABLE` `SERVICE_TIMEOUT` |

**归属按标识逐个划定，不按命名前缀类推**——同属 `PARAM_*` 一族，`PARAM_MISSING`（缺参）属准入判定，`PARAM_INVALID` / `PARAM_FORMAT_INVALID` / `PARAM_VALUE_NOT_ALLOWED` 属业务规则（参数的值与格式，只有在业务上下文里判定才成立）。归属以 §1.4 取值表的「产出层」列为准。

判据是**谁在做判定**：中间件判的是"这个请求允不允许进来"（凭据、配额、身份），logic 判的是"业务上这件事成不成立"。**验证码校验属后者**——它在登录流程内部执行，不构成一道门禁，因此归 `CAPTCHA_INCORRECT`。**请求头缺失是否算中间件错误，取决于该头有没有声明身份**：未声明设备身份的请求放行（按匿名处理）；**声明了设备身份（带了 `x-device-id`）却不齐三件套的，由设备令牌中间件拒绝为 `PARAM_MISSING`**（§2.3）。

为什么必须排他——先看合并的代价：

- **合并后客户端无法判断"该做什么"**。同一个 `429` 既可能来自限流（该降速重试）也可能来自业务规则（该改参数），客户端只能再解析 body 反推
- **合并后状态码对网关失去意义**。反代、CDN、监控告警只读状态行，它们要的是"传输层是否正常"这个粗粒度结论，不是业务细分
- **logic 一旦能产出 HTTP 状态，业务语义就渗进传输层**，而传输层被框架与基础设施共享（超时、降载、熔断也写这个状态行），两侧会互相污染

**于是分工是**：logic 只表达"业务上发生了什么"，由响应出口统一翻译成标准状态码（见 §1.3）；中间件的准入判定给出"能否被处理"的结论，**同时给出准入类标识**（其状态码由响应出口按 §1.4 的映射产出）——客户端仍需区分 `UNAUTHENTICATED`（该登出）与 `LOGIN_EXPIRED`（该刷新），两者同为 `401`，只能靠标识细分。框架自身的失败（超时、降载、熔断、请求体过大、路由未匹配、方法未允许）**只有标准状态码，没有业务错误标识**，见 §2.6。

### 1.2 HTTP 状态码的场景

HTTP 状态码回答"**这个请求能否被处理**"。它的场景全部发生在 logic 之前，分三类：

**A. 准入判定**——由中间件产出。失败时写入对应的准入类标识，状态码由响应出口按 §1.4 的映射一并产出——标识不可省，因为状态码粒度不足以支撑客户端分支：`UNAUTHENTICATED`（该登出）与 `LOGIN_EXPIRED`（该刷新）同为 `401`，客户端只能靠标识区分。具体取值见 §1.4。

| 场景 | HTTP |
|---|---|
| 未携带凭据、凭据无效、令牌与设备不匹配 | `401` |
| 令牌已过期 | `401` |
| 时间戳过期，或请求签名不符 | `401` |
| 身份无该操作权限，或角色不匹配 | `403` |
| 超出配额（限流） | `429` |
| 声明了设备身份却缺必需请求头（缺 `Timestamp` 或 `x-device-token`） | `400` |

**B. 请求解析**——由 handler 产出，**只写状态码，不写业务错误标识**：

| 场景 | HTTP |
|---|---|
| 请求无法解析：非法 JSON、必填缺失、类型不符 | `400` |

它与 A 的差别**不在层次**（两者都在 logic 之前、都属传输层），而在**产出层与是否携带标识**：A 是准入判定、由中间件产出，且必须带准入类标识；B 由 handler 产出，**不带标识**。

为什么 B 不产标识：**「请求读不懂」没有客户端可分支的细分语义**。`400` 之下无论是非法 JSON、必填缺失还是类型不符，调用方要做的是同一件事——看 `data` 里指出的是哪个字段，然后改请求。给它硬安一个标识，只会是一个每处都映射到 `400`、客户端也从不分支的空壳。

**`400` 与 `422` 的分界**就是"读不懂"与"读懂了但不接受"，两者各自只有一个含义：

| 状态 | 含义 | 对应本文的哪一类 | 是否带标识 |
|---|---|---|---|
| `400` | 请求**不完整或无法被解析**——语法层 | B（解析失败）与 A 的缺参档（`PARAM_MISSING`） | 解析失败**不带**、缺参**带** |
| `422` | 请求已读懂，但**内容语义不合法**——RFC 9110 §15.5.21 把适用域限定在请求**内容**（请求体字段与参数值），不涵盖请求头 | §1.3 的参数校验类 | 是 |

这样切分之后，`422` 只承担"内容语义不合法"一个含义——**请求头的问题一律不进 `422`**。`400` 之下则有两类，判据也不同：**不带标识的解析失败**（客户端看 `data` 里的字段明细）与**带标识的 `PARAM_MISSING`**（客户端按 `code` 分发），前者判"能否读懂请求"，后者判"请求是否完整"。代价是 `400` 不再承担"参数错误"这一常见义，与部分框架的习惯不同。

**C. 框架保护**——由框架在进入路由之前直接写出，**没有 body、没有业务错误标识**（见 §2.6）：

| 场景 | HTTP |
|---|---|
| 路由不存在 | `404` |
| 方法未允许 | `405` |
| 请求体超过上限 | `413` |
| `Content-Type` 不受支持 | `415` |
| 本服务自身处理超过超时阈值 | `503` |
| 处理器 panic | `500` |
| 过载降载 / 并发超限 / 熔断 | `503` |
| API 文档等插件路径内部错误 | `404` / `500` |

### 1.3 业务错误标识的场景

业务错误标识回答"**业务上成不成立**"。它的场景**全部由 logic 判定**，且**请求本身是合法且可处理的**——这是与 §1.2 的分界。

| 场景 | 业务错误标识 | 出口 HTTP |
|---|---|---|
| 参数校验不通过（格式、取值） | `PARAM_INVALID` `PARAM_FORMAT_INVALID` `PARAM_VALUE_NOT_ALLOWED` | `422` |
| 凭据不通过（账号不存在、密码错误） | `CREDENTIALS_INVALID` | `401` |
| 凭据通过但账号已被禁用 | `ACCOUNT_DISABLED` | `403` |
| 验证码错误 | `CAPTCHA_INCORRECT` | `422` |
| 资源不存在 | `RESOURCE_NOT_FOUND` | `404` |
| 资源已存在 | `RESOURCE_ALREADY_EXISTS` | `409` |
| 资源状态不允许当前操作 | `RESOURCE_STATE_NOT_ALLOWED` | `409` |
| 条件请求的前提不成立（并发编辑冲突） | `PRECONDITION_FAILED` | `412` |
| 操作不被允许 | `OPERATION_NOT_ALLOWED` | `403` |
| 服务器内部错误 | `INTERNAL_ERROR` | `500` |
| 数据库操作失败 | `DATABASE_ERROR` | `500` |
| 外部服务返回无效响应 | `EXTERNAL_SERVICE_ERROR` | `502` |
| 依赖暂时不可用 | `SERVICE_UNAVAILABLE` | `503` |
| 等待下游超时 | `SERVICE_TIMEOUT` | `504` |

**出口 HTTP 状态由业务错误标识推导而来**，推导**只发生在响应出口一处**，logic 与中间件都不做这件事。映射在**逐个标识**粒度上定义——不是类别粒度，因为流控类与安全类都属"客户端需调整行为"，却映射到不同的状态码。

七条推论：

- **映射按语义而非按命名对齐**。`SERVICE_TIMEOUT` 映射到 HTTP `504`（网关超时）而非 `503`（服务不可用），两者含义不同，命名相近不构成映射依据
- **`502` 与 `503` 按"答得不对"与"连不上"二分**。下游**返回了无效响应**属 `502`（RFC 9110 §15.6.3）；下游**不可达**、或依赖**暂时性故障**（连接被拒、服务未启动、熔断打开、数据库主从切换与连接池耗尽）属 `503`。二者客户端的处置相同（都可重试），但对服务端的归因完全不同——前者要查下游逻辑，后者要查容量与发布。**数据库的暂时性故障因此归 `SERVICE_UNAVAILABLE` 而非 `DATABASE_ERROR`**：`DATABASE_ERROR` 保留给查询与约束类错误，那属 `INTERNAL`
- **服务端类标识的价值在归因，不在客户端分支**。五个标识映射到 5xx，让日志、监控与告警能按**依赖维度**聚合（是内部逻辑、数据库、外部服务、暂时不可用还是超时出的问题）；至于客户端能否重试，由状态码给出——`502` / `503` / `504` 可重试，`500` 不可。标识不额外承载可重试性
- **`SERVICE_TIMEOUT` 指本服务等待下游超时**，不是本服务自身处理超时。此时 API 层正是在扮演网关角色，符合 RFC 9110 对 `504` 的定义。本服务**自身**的处理超时由框架产出 `503`（见 §1.2 C），两者不是一回事
- **并发编辑冲突用 `412` 而非 `409`**。RFC 9110 §15.5.13 的 `412 Precondition Failed` 专指**条件请求**（`If-Match` / `If-None-Match`）的前提不成立，正是乐观锁的场景；`409` 用于"与资源当前状态冲突"这类**无条件**的业务规则判定。二者都涉及资源状态，但判据不同：**前提由客户端以头字段声明**的用 `412`，**由服务端自行判定**的用 `409`
- **登录失败不区分"账号不存在"与"密码错误"**。两者合并为 `CREDENTIALS_INVALID`——分开返回等于给出一条可枚举账号的信道（OWASP 认证备忘单要求登录失败返回统一结果）。`ACCOUNT_DISABLED` 因此移到**凭据校验通过之后**才返回：持有正确凭据者看到禁用原因，不构成枚举
- **越权访问按「资源对调用方是否可见」二分**。调用方**看不到**的资源（他人草稿、非本人数据）返回 `RESOURCE_NOT_FOUND`（`404`）而非 `PERMISSION_DENIED`——否则错误码本身构成一条枚举资源的信道（OWASP API1:2023 破坏对象级授权）；调用方**看得到**的资源上操作不被允许（如只读角色尝试删除）才返回 `PERMISSION_DENIED`（`403`）。判据是**可见性**，不是资源是否存在

### 1.4 取值表

按标识索引。**产出层决定它属于哪一层**（§1.1），**出口 HTTP 是推导结果**（§1.2 / §1.3）。最后一列给出对应的 AIP-193 canonical code，作为跨进程传递时的对照锚点（见 §1.9）：

| 标识 | 含义 | 产出层 | 出口 HTTP | AIP-193 canonical |
|---|---|---|---|---|
| `SUCCESS` | 成功 | 响应出口 | `200` / `201` | `OK` |
| `RATE_LIMIT_EXCEEDED` | 请求被限流（配额耗尽） | 中间件（限流，全局链与路由组链） | `429` | `RESOURCE_EXHAUSTED` |
| `REQUEST_SIGNATURE_INVALID` | 请求签名无效 | 中间件（防重放） | `401` | `UNAUTHENTICATED` |
| `PARAM_INVALID` | 参数错误（通用兜底） | logic | `422` | `INVALID_ARGUMENT` |
| `PARAM_MISSING` | 请求头缺失（声明了设备身份却缺必需请求头） | 中间件（设备令牌校验） | `400` | `INVALID_ARGUMENT` |
| `PARAM_FORMAT_INVALID` | 参数格式错误 | logic | `422` | `INVALID_ARGUMENT` |
| `PARAM_VALUE_NOT_ALLOWED` | 参数值不允许 | logic | `422` | `INVALID_ARGUMENT` |
| `UNAUTHENTICATED` | 未登录 | 中间件（认证 / 授权） | `401` | `UNAUTHENTICATED` |
| `LOGIN_EXPIRED` | 登录已过期 | 中间件（认证） | `401` | `UNAUTHENTICATED` |
| `CREDENTIALS_INVALID` | 凭据无效 | logic | `401` | `UNAUTHENTICATED` |
| `ACCOUNT_DISABLED` | 账号已被禁用 | logic | `403` | `PERMISSION_DENIED` |
| `CAPTCHA_INCORRECT` | 验证码错误 | logic | `422` | `INVALID_ARGUMENT` |
| `PERMISSION_DENIED` | 无操作权限 | 中间件（授权） | `403` | `PERMISSION_DENIED` |
| `ROLE_MISMATCH` | 角色不匹配 | 中间件（授权） | `403` | `PERMISSION_DENIED` |
| `RESOURCE_NOT_FOUND` | 资源不存在 | logic | `404` | `NOT_FOUND` |
| `RESOURCE_ALREADY_EXISTS` | 资源已存在 | logic | `409` | `ALREADY_EXISTS` |
| `RESOURCE_STATE_NOT_ALLOWED` | 资源状态不允许当前操作 | logic | `409` | `FAILED_PRECONDITION` |
| `PRECONDITION_FAILED` | 条件请求的前提不成立 | logic | `412` | `ABORTED` |
| `OPERATION_NOT_ALLOWED` | 操作不被允许 | logic | `403` | `PERMISSION_DENIED` |
| `INTERNAL_ERROR` | 服务器内部错误 | logic | `500` | `INTERNAL` |
| `DATABASE_ERROR` | 数据库操作失败 | logic | `500` | `INTERNAL` |
| `EXTERNAL_SERVICE_ERROR` | 外部服务返回无效响应 | logic | `502` | —（见 §五） |
| `SERVICE_UNAVAILABLE` | 依赖暂时不可用 | logic | `503` | `UNAVAILABLE` |
| `SERVICE_TIMEOUT` | 等待下游超时 | logic | `504` | `DEADLINE_EXCEEDED` |

**标识一经发布不得修改、不得回收复用**（见 §1.8）。取值表是本层唯一的查表入口——**客户端只判断 `code`，不判断 `message`**。**模块细分标识同样必须逐条登记在本表**（§1.6 提到的 `ARTICLE_NOT_FOUND` 之类）——本表是查表入口，未登记即不得使用。此前规划过的两套数字码整体作废：早期使用的 3 位码（`200`/`410`/`420` …）随本次迁移一并废弃；规范中曾拟定的 4 位码（`2000`/`4100` …）从未落地，一并作废。**不保留数字别名**——两套标识并存会让"客户端该判断哪个"无法回答。

**本表的增与删都是破坏性变更**。本次相对上一版删除了 `PASSWORD_INCORRECT`（并入 `CREDENTIALS_INVALID`）与 `REQUEST_TOO_FREQUENT`（与 `RATE_LIMIT_EXCEEDED` 语义重复），新增了 `CREDENTIALS_INVALID`、`PRECONDITION_FAILED` 与 `SERVICE_UNAVAILABLE`。**`PARAM_MISSING` 一度规划删除，最终保留**——设备令牌中间件的规则是"未声明设备身份则放行、声明了就必须校验并拒绝"，它因此有真实产出路径（§2.3）；出口 HTTP 定为 `400`（缺失请求头属"请求不完整"，不是 `422` 覆盖的内容语义）。删除与新增同样需要评审与同窗口发布，见 §1.8 规则 5 的说明。

### 1.5 分类依据：按场景，不按模块

**按错误场景分类，而非按业务模块分类。** 同一标识可跨模块复用——`RESOURCE_NOT_FOUND` 对用户、文章、评论一视同仁。

**分类依据是"客户端该如何反应"**，而非"服务端哪个模块抛出的"：

| 类别 | 含义 | 客户端应有的反应 |
|---|---|---|
| 成功 | 请求已正常处理 | 正常处理 |
| 流控 | 客户端请求过快 | 降速 |
| 安全 | 请求签名或时效不符 | 重新签名、重新验证 |
| 请求参数 | 请求不合法 | 修正请求 |
| 身份认证 | 身份缺失或无效 | 补身份、重新登录 |
| 权限授权 | 有身份但无权限 | 引导用户 |
| 业务规则 | 请求合法，但业务上不成立 | 引导用户 |
| 服务端 | 服务端问题 | 按状态码决定：`502` / `503` / `504` 可自动重试，`500` 不重试；均需上报 |

**类别是文档分组，不编码进标识**——标识是自描述的，客户端要按类别做粗处理时查本表的分组与 §1.4 的「产出层」列，而不是从标识文本里猜。这与 AIP-193 把分组交由 `ErrorInfo.domain` 承载、`reason` 只承担唯一标识的分工一致（本项目单一 `domain`，故分组退化为文档约定）。

### 1.6 为什么不用「按模块分段」

另一条常见路线是按业务模块划分标识空间（如文章模块的标识统一带 `ARTICLE_` 前缀、用户模块带 `USER_` 前缀），每个模块占一个命名空间。本项目**不采用**：

- 客户端拿到标识之后要做的是"我该怎么反应"，而不是"这是谁抛的"——**模块信息对客户端没有意义**
- 模块分段会逼出**大量语义重复的标识**：每个模块都要各备一套"不存在 / 已存在 / 状态不允许"，客户端的处理分支随之膨胀
- **模块划分会变，标识不能变**。一旦模块重组，模块分段就成了必须背下去的历史包袱

模块维度的区分放在**标识本身**：`RESOURCE_NOT_FOUND` 是通用标识，确需区分时用 `ARTICLE_NOT_FOUND` / `ALBUM_NOT_FOUND`。这样分类骨架稳定，模块细分可按需增加，也不违反"同一标识可跨模块复用"。

### 1.7 标识格式与命名规则

**`UPPER_SNAKE_CASE`，字母开头。** 形式与 AIP-193 对 `ErrorInfo.reason` 的约束一致。

| # | 规则 |
|---|------|
| 1 | **自描述**——不查表即可读懂语义。这是选字符串而非数字的初衷，见 §1.8 末 |
| 2 | **唯一**——同一语义只有一个标识。**判据是语义**：服务端发生的事不同、且客户端需要分别辨识，就各立一个标识；两者客户端动作恰好相同，不构成合并理由 |
| 3 | **稳定**——只增不改、不复用；语义变更等于新标识（边界见 §1.8 规则 5） |
| 4 | **与 HTTP 状态码天然区分**——字符串与三位数字不同形，同处一个响应中不会被混淆 |

规则 2 的判据值得单独说明：**"语义相同"的含义是服务端实际发生了什么相同，而不是产出点在哪个中间件或模块**。同一条限流规则可能装配在全局链与路由组链两处，产出点不同但语义相同，因此共用一个标识（`RATE_LIMIT_EXCEEDED`）；反之"防重放的时间戳过期"与"令牌过期"都在 `401` 上，但前者要重新签名、后者要刷新令牌，语义不同，必须分成两个标识。

**为什么不取「数字 + 位数隔离」**：数字方案下必须额外规定"业务码不得与 HTTP 状态码同值"（3 位会撞 `410 Gone`、`411 Length Required`、`413 Payload Too Large`）。字符串天然没有这个问题，这条约束连同为它而设的整节规则一并取消。

**为什么不取 URI（RFC 9457 的 `type`）**：URI 的价值在于"每个错误指向一份公开文档"。本系统的消费方是自己的两个前端与内部 gRPC 调用，没有对外的错误文档站；纯字符串标识已满足机器可读与稳定两项要求，且与 AIP-193 对 `reason` 的定义一致。

### 1.8 新增标识的规则

| # | 规则 |
|---|------|
| 1 | 标识必须**自描述且唯一**；同一语义不得有两个标识 |
| 2 | **新增标识需要走设计评审**——它增加的是客户端的处理分支，属契约变更 |
| 3 | 同一标识**可以**跨模块复用（这是通用标识存在的意义） |
| 4 | 能用一个通用标识表达的，不为某个模块另立标识 |
| 5 | 标识**只增不改**——已发布的不得改变含义、不得回收复用。含义变更等于新标识 |
| 6 | 新增标识必须同时确定**产出层**（§1.1）与 **HTTP 状态映射**（§1.3），两者缺一不可；同时登记 §1.4 末列的 canonical 对照，跨进程传递时必需 |

**规则 5 的边界**：它禁止的是**改名、改义、复用名**；**删除**不在其列，但删除同样是破坏性变更——消费方会在失去该标识后落进未知分支。删除必须走与新增同级的评审，并与全部消费方同窗口发布。

**canonical 对照的用法**：它不是新的契约字段，而是**跨进程传递的载体选择**（见 §1.9）。新增标识时若找不到对应的 canonical code，登记为"无对应"，而不是挑一个近似值——对照的作用是让下游能达意，错配比缺失更糟。

**为什么不用数字码**——留档备查，避免日后反复：

- **必须查表**：`4100` 不查表读不出语义，日志、看板、告警都要 join 一张对照表；字符串自描述
- **代价会外溢**：数字派（Twilio `20003`、Cloudflare `81044`）普遍要额外配一份逐码文档 URL 来补偿；实际调用方还会退化成匹配错误文本（Cloudflare 的公开 Go 客户端即以 `strings.Contains(err.Error(), "81053")` 判错），而"解析错误文本判因"是 RFC 9457 与 AIP-193 都点名禁止的反模式
- **与 HTTP 状态码撞值**：见 §1.7
- **区间判断是唯一实质优势，但本项目未使用**：本项目没有任何按区间归类业务错误的判定，故该优势不成立

### 1.9 标识跨 gRPC 的承载

本项目有 HTTP 网关与 gRPC 服务两层，业务错误标识**必须跨这一跳**而不被降级成通用错误——否则 §1.3 说的"按依赖维度归因"在网关层就断了。承载方式按 AIP-193：

| 通道 | 承载字段 |
|---|---|
| HTTP 响应 | 信封的 `code` 字段（§三） |
| gRPC 响应 | `google.rpc.Status` 的 `details[].ErrorInfo.reason` |

**两侧同值**——一个标识在 HTTP 上是 `RESOURCE_NOT_FOUND`，在 gRPC 上其 `ErrorInfo.reason` 也是 `RESOURCE_NOT_FOUND`。这是标识取字符串之后的自然结果：标识本身即 `reason`，无需编解码，也天然满足 AIP-193 对 `reason` 的格式约束。

字段级校验明细在 gRPC 侧用同族的 `details[].BadRequest`（`google.rpc.BadRequest`）承载，在 HTTP 侧落到信封的 `data`（§三），两侧同构。

**传递规则**：

- 下游服务是标识的**权威产出者**。API 层收到已带 `ErrorInfo` 的错误时**原样上抛**，不重新包装——重新包装会把它降级成 `INTERNAL_ERROR`，归因信息随之丢失
- API 层只在**没有 `ErrorInfo`** 时才自行产生标识，即传输层失败（连接不可达、等待超时），此时产出 `SERVICE_UNAVAILABLE` / `SERVICE_TIMEOUT`
- 因此"**已是业务错误则不覆盖**"是一条必须显式实现的规则，不能靠调用方自觉

### 1.10 无标识时的兜底归一

下游可能因版本不一致、序列化故障等原因只返回 canonical code 而无 `ErrorInfo`。此时 API 层按下表兜底，使客户端始终能拿到一个标识：

| canonical code | 兜底标识 | 出口 HTTP |
|---|---|---|
| `UNAUTHENTICATED` | `UNAUTHENTICATED` | `401` |
| `PERMISSION_DENIED` | `PERMISSION_DENIED` | `403` |
| `INVALID_ARGUMENT` `OUT_OF_RANGE` | `PARAM_INVALID` | `422` |
| `NOT_FOUND` | `RESOURCE_NOT_FOUND` | `404` |
| `ALREADY_EXISTS` | `RESOURCE_ALREADY_EXISTS` | `409` |
| `FAILED_PRECONDITION` | `RESOURCE_STATE_NOT_ALLOWED` | `409` |
| `ABORTED` | `PRECONDITION_FAILED` | `412` |
| `RESOURCE_EXHAUSTED` | `RATE_LIMIT_EXCEEDED` | `429` |
| `UNAVAILABLE` | `SERVICE_UNAVAILABLE` | `503` |
| `DEADLINE_EXCEEDED` | `SERVICE_TIMEOUT` | `504` |
| `UNIMPLEMENTED` `INTERNAL` `UNKNOWN` `DATA_LOSS` `CANCELLED` | `INTERNAL_ERROR` | `500` |

**兜底表是单向的**——它只用于"下游没给出标识"这一种情形，不构成反向推导的依据（不能从 canonical code 反推业务标识）。表中多个 canonical code 合并到同一标识是刻意的：`FAILED_PRECONDITION` 在 gRPC 侧语义比"资源状态不允许"宽，本项目不为它单立标识。`CANCELLED` 归入 `INTERNAL_ERROR` 同理：它表示调用被取消（多为调用方上下文取消——客户端已断开，或本服务自行取消），此时响应往往已无人接收，归到「不自动重试」一侧比归入可重试类更安全。

## 二、中间件

### 2.1 分层

中间件分两层，**职责与归属不同**：

| 层 | 归属 | 装配方式 |
|---|---|---|
| **框架内置层** | 框架 | 默认全开，无需逐个配置 |
| **自定义层** | 业务 | 分「全局链」与「路由组链」两级装配 |

**装配次序的含义**：越靠外层的中间件，越早拒绝无效请求。**限流在所有自定义中间件的最外层**——它是保护其后的全部计算与 IO 的那一环。此后的全局链只做**廉价的合法性判定**（上下文、时效、签名）；授权判定与主体维度的配额控制需要读缓存或查权限，留到路由组层按需装配。

### 2.2 框架内置层

框架自动挂载的能力覆盖**稳定性与可观测性**：

| 类别 | 能力 |
|---|---|
| 链路 | 分布式追踪（贯穿网关与服务）、请求日志 |
| 监控 | 指标端点、接口耗时统计 |
| 保护 | 并发上限、熔断、过载降载、超时、panic 恢复 |
| 请求 | 请求体大小限制、自动解压、`Content-Type` 校验、方法匹配 |

**执行次序**（由外向内）：追踪 → 日志 → 指标 → 并发控制 → 熔断 → 降载 → 超时 → 恢复 → 请求体处理 → **自定义链**。

### 2.3 自定义层

**全局链**（两个网关共用，由外向内）：

| 次序 | 职责 | 设计要点 |
|---|---|---|
| 1 | 限流 | 按客户端真实 IP + 路径的粗粒度配额，保护其后全部计算与 IO。见 §2.4 |
| 2 | 上下文透传 | 将请求头写入上下文，供下游 gRPC 消费 |
| 3 | 防重放 | 校验时间戳时效 |
| 4 | 设备令牌校验 | 校验签名的设备令牌。它同时承担两种角色——访客身份的**标识凭据**、已登录令牌的**设备绑定凭据**，二者失败处理不同，见下文 |

**为什么限流在最外层**：认证中间件要读缓存或查权限，这些是 IO。若限流排在认证之后，攻击者可以用无效令牌反复触发昂贵的判定而不受任何约束——限流此时保护的是它自己之后的东西，而不是它自己。代价是全局链上多了一次 Redis 往返，这是刻意的：它是唯一值得放在最外层的一次 IO。

**两处「可选增强」的分界是"有没有声明身份"**，而不是"头齐不齐"：

| 中间件 | 保护的对象 | 未声明相应请求头 | 已声明但校验不过 |
|---|---|---|---|
| 防重放 | **本次请求的时效**——时间戳超出允许窗口即视为重放 | 放行 | **拒绝**，`REQUEST_SIGNATURE_INVALID`（`401`） |
| 设备令牌 | **访客身份**——只决定是否赋予访客身份 | 放行，不产生身份结论 | **拒绝**：三件套不齐给 `PARAM_MISSING`（`400`），签名不符给 `REQUEST_SIGNATURE_INVALID`（`401`） |

**判据是「是否声明了设备身份」**：请求带了 `x-device-id` 就是声明了身份，此时 `timestamp` 与 `x-device-token` 必须齐，且 `x-device-token` 必须与按 `x-device-id`、`timestamp` 重算的签名一致——**缺一即拒、对不上即拒**。反过来，一个 `x-device-id` 都不带的请求按匿名处理、直接放行，以兼容无签名的普通请求与链路预取。

**为什么声明之后必须拒绝而不能降级**：降级等于开出一条绕过校验的通道——提交一个坏签名即可让请求落到"未受保护"的匿名分支，签名随之失去意义。这与本节后段受限内容口令的原则同源（口令失败必须拒绝，不能降级到未受保护分支）。

**但它仍不是门禁**：不带 `x-device-id` 即可绕过，因此它的价值是"对已配合的调用方提供额外保护"，而非"阻止攻击者"。用词上不称其为"准入凭据"，以免与真正的门禁（认证、授权）混淆。信任边界的完整论述见《08》§三（该节是唯一真相源）。

**「设备不匹配」的拒绝不在本条**——当访问令牌签发时绑定了设备、而请求携带的设备令牌与之不符时，拒绝发生在**认证中间件**（`UNAUTHENTICATED`）。归属如此划分，是因为**拒绝的理由是"令牌失效"而非"设备令牌非法"**，错误语义属认证。同一枚凭据的两种用途对照见《08》§三。

**路由组链**按"访问所需的身份强度"分级装配：

| 分组 | 链 |
|---|---|
| 公开（登录、验证码） | 全局限流已覆盖，不再追加 |
| 需登录（个人中心） | 认证 → **限流（主体维度）** |
| 需权限（管理操作） | 认证 → 授权 → 操作日志 → **限流（主体维度）** |
| 受限内容（密码保护、预览） | 内容口令 / 预览令牌校验——**准入门禁**，失败即拒绝 |

**「已认证主体」维度的限流只能排在认证之后**——配额的分母是主体，不认证就取不到。这与 §2.4 的两级限流对应：全局链按 IP 粗限流，路由组链按主体细限流。

**受限内容的两种凭据都不含身份**——内容访问口令与预览令牌**不回答"你是谁"**，只回答"这篇内容可否返回"，因此它们**不产生任何身份结论**，也不进入认证链。这与设备令牌（增强型）方向相反：后者失败只降级，前者失败必须拒绝——否则攻击者提交一个错误口令即可降级到"未受保护"分支。

**认证与授权分离**是刻意的：认证回答"你是谁"，授权回答"你能做什么"，二者的失败语义不同（`UNAUTHENTICATED` 与 `PERMISSION_DENIED`），合并会导致客户端无法区分"需要重新登录"与"权限不足"。

读者端的组链**刻意保持简单**——只有认证，不做角色判定（理由见《03》§2.4）。

### 2.4 限流策略

限流采用**滑动窗口**，计数落 Redis 的**业务缓存**角色（可重建，见《02》§4.2）。

**两级装配**——维度不同，缺一不可：

| 级别 | 装配位置 | 维度 | 作用 |
|---|---|---|---|
| 粗粒度 | 全局链最外层 | 客户端真实 IP + 路径 | 保护认证前的全部计算与 IO，防匿名流量单点刷取 |
| 细粒度 | 路由组链，认证之后 | 已认证主体 + 路径 | 管理端配额，按管理员个体而非出口 IP 计量 |

两级**共用同一个标识** `RATE_LIMIT_EXCEEDED`——产出点不同，但语义相同（§1.7 规则 2）。

**为什么管理端必须按主体而非 IP**：管理员数量少，且常处于同一出口 IP（同一办公室 / 内网）。按 IP 限流会把整个管理端当成一个用户——既误伤又毫无约束力。反之读者端面向匿名流量，没有主体可用，只能按 IP。

**配额档位**：读者端较低（读多写少，正常流量平缓），管理端较高（管理员少但操作密集，过低会误伤）。

**客户端真实 IP 的获取口径**——必须先定义，否则 IP 维度的限流形同虚设：

- 请求经宿主机 Nginx 反代（见《05》§1.3），**网关直接看到的源地址是 Nginx 的**
- 因此必须在 Nginx 侧**覆写**转发头而非追加，网关只信任该头的**最后一跳**；**不接受客户端自行传入的转发头**——否则攻击者用一个请求头即可伪造 IP，绕过全部 IP 维度限制
- 若将来在 Nginx 之前引入 CDN，需同步扩展可信跳数。**这是引入 CDN 的前置工作项**，不是上线后的调优项

**限流的响应头**：

| 响应头 | 何时给出 | 取值 | 依据 |
|---|---|---|---|
| `Retry-After` | 所有 `429`，以及所有 `503` | 退避秒数：`429` 取**当前窗口的剩余时长**；`503` 取预估恢复时长，给不出时省略 | RFC 9110 §10.2.3（头字段本身）；`503` 见 RFC 9110 §15.6.4、`429` 见 RFC 6585 §4 |
| `RateLimit-Limit` | **所有响应**（含 `2xx`）；`429` 必须给出 | 当前窗口的配额上限 | 字段名依据见下 |
| `RateLimit-Remaining` | 同上 | 当前窗口的剩余次数 | 字段名依据见下 |
| `RateLimit-Reset` | 同上 | 窗口重置的剩余秒数 | 字段名依据见下 |

**回传余量的意义**：客户端据此**提前降速**，而不是撞到 `429` 才知道——这与 §四 的"自动重试必须限幂等"配套，把限流从"惩罚"变成"协作"。**给不出精确值时不臆造**：`Retry-After` 宁可省略，也不写一个恒定的假值。

**字段名的依据**：三枚分列字段（`RateLimit-Limit` / `RateLimit-Remaining` / `RateLimit-Reset`）是 de-facto 通行写法——各大厂客户端与网关插件普遍识别的 `X-RateLimit-*` 即其原型，本项目按 RFC 6648 去掉已废弃的 `X-` 前缀（§三）。IETF 的 `draft-ietf-httpapi-ratelimit-headers` **至今仍是 Internet-Draft、未成为 RFC**，且其修订过程已把这三枚收敛为 `RateLimit` + `RateLimit-Policy` 两个结构化字段，字段名尚在变动，故不作为本项目的依据；待其成为 RFC 且字段稳定后再评估迁移。

**三枚头规定为所有响应给出，而不是只在 `429` 上**：上文说的「客户端提前降速」只有在成功响应上就能读到余量时才成立——只在 `429` 上给，客户端仍只能撞到限流之后才知道。**`RateLimit-Reset` 取「窗口重置的剩余秒数」**，与 GitHub 的 `X-RateLimit-Reset`（绝对 epoch 秒）不同——客户端不得按后者解析本头。

**设计约束**：限流计数**共享 Redis 而非进程内存**，使限流在多副本部署下依然准确。

**Redis 不可用时的取舍**：计数取不到时**放行**（fail-open）并打点告警。限流是保护性约束而非正确性约束——把全站请求挡在 `503` 后面造成的可用性损失，远大于短时失去限流；缺口期间的异常流量由告警驱动人工处置。**读不到计数不等于配额为零**，两者必须分开处理。

**实时通道不适用本表**——STOMP 的连接数上限与 CONNECT 频次限制见《04》§三.2。

### 2.5 中间件与错误码的对应

中间件是**准入层**，它的失败属于传输层。各中间件对应的**场景与 HTTP 状态见 §1.2**、**取值见 §1.4 取值表的「产出层」列**，此处不重复维护。本节只记**不产生错误的几处例外**——它们不构成准入被拒，也不对应任何业务错误标识：

| 中间件 | 场景 | 行为 |
|---|---|---|
| 防重放 | 未携带 `Timestamp` | **不报错**——按未携带处理，见 §2.3 |
| 设备令牌校验 | 未携带 `x-device-id`（未声明设备身份） | **不报错**——放行且不产生身份结论，见 §2.3 |

其余情形都是**拒绝**：时间戳过期与设备令牌签名不符 → `REQUEST_SIGNATURE_INVALID`（`401`）；声明了设备身份却缺 `Timestamp` 或 `x-device-token` → `PARAM_MISSING`（`400`）。

**规律**：**请求参数 / 身份认证 / 权限授权 / 业务规则四类 = 客户端修正请求后可重试（改参数、补身份、加权限）；流控与安全两类 = 客户端需调整行为而非请求本身（降速、重新签名）；服务端类 = 客户端无从修正。** 判据是**客户端该做什么**，而非「谁的责任」——限流可明确归因于客户端，但客户端该做的是降速而非改请求，故归流控。

注意这条判据解释的是**标识的类别**，与 HTTP 状态码的分段**不是同一套**：流控类映射到 HTTP `429`（属 4xx 段）、`SERVICE_TIMEOUT` 映射到 HTTP `504`。两者各自成体系，不要用一套的归类去推另一套。

### 2.6 信封之外的路径

有两类响应**不产出业务错误标识**，因此都不带信封的 `code` 字段：

**甲、框架保护**——由框架在进入路由之前直接写出，**body 为纯文本、无 `code`**：

| 来源 | 场景 | HTTP | 附加头 |
|---|---|---|---|
| 超时 | 请求超过配置的 `Timeout` | `503` | `Retry-After` |
| 崩溃恢复 | 任意 handler panic | `500` | — |
| 过载降载 | CPU 超阈值 | `503` | `Retry-After` |
| 并发上限 | 并发连接超限 | `503` | `Retry-After` |
| 熔断 | 依赖熔断打开 | `503` | `Retry-After` |
| 方法未允许 | 路径存在但方法不匹配 | `405` | `Allow`（**MUST**，RFC 9110 §15.5.6） |
| `Content-Type` 不受支持 | 请求体媒体类型无法处理 | `415` | — |
| 请求体上限 | body 超过 `MaxBytes` | `413` | — |
| 路由未匹配 | 路径不存在 | `404` | — |

**乙、请求解析失败**——由 handler 在解析请求时写出，**有 body 但没有 `code`**（§1.2 B）：

| 来源 | 场景 | HTTP |
|---|---|---|
| 请求解析 | 非法 JSON、必填缺失、类型不符 | `400` |

请求体形如 `{ "message": "…", "data": { "field_violations": […] }, "trace_id": "…" }`。`message` 面向开发者、供排错——它**不保证不含内部细节**（这正是 §四 硬约定"客户端不得展示 `message`"的理由）；`field_violations` 给出结构化的字段定位，格式见 §三。

**上表列举的是框架可产出的全部已知情形**；客户端的分发规则（非信封 → 按状态码给通用文案）对任何未列举的状态同样成立，因此不依赖此表的完备性。甲是框架的内建保护，执行时机早于任何自定义代码，且框架不使用本项目的响应封装；乙的判定依据是"能否读懂请求"，按 §1.1 不属于业务语义，故不产出标识。

> **客户端不得假定任何响应都是信封**。分发前先判定形状：非 JSON、或 JSON 但无 `code` 字段，一律按 HTTP 状态码给**客户端自有的通用文案**；若该 body 带 `data.field_violations`，用它定位出错字段。只有拿到信封才进入业务错误标识的分发。

**这是 HTTP 状态码必须"标准"的现实理由**：甲类响应只有状态码可读，如果状态码被业务语义挪用（例如用 `503` 表示"服务超时"的业务码），客户端与网关都无法还原框架本意。

## 三、响应信封

**除 §2.6 的路径外，所有响应都是信封**：

```json
{
  "code": "SUCCESS",
  "message": "…",
  "data": {},
  "trace_id": "…"
}
```

| 字段 | 语义 | 约定 |
|---|---|---|
| `code` | 业务错误标识 | 成功为 `SUCCESS`；失败为 §1.4 取值表中的标识 |
| `message` | 面向**开发者**的描述 | 失败时说明"哪里不对、怎么改"，供排错与日志。**不面向终端用户、不做本地化**，客户端不得将其作为面向用户的文案，也不得解析它做判断——因此服务端**不对它做脱敏**，前提正是客户端不展示它。成功时为空串 |
| `data` | 载荷 | **成败都必须存在**——失败时为空对象，不得省略字段。校验类失败在 `data` 中给出 `field_violations`，见下 |
| `trace_id` | 链路追踪标识 | 客户端应随错误上报；**不靠标识定位问题**，靠此字段关联日志 |

`data` 必须存在这一条是刻意的：若错误响应省略 `data`，客户端的取值会在失败路径上抛类型错误——**而失败路径恰恰是最需要行为稳定的地方**。

**`message` 的定位决定了响应不随请求头变化**：终端用户看到的文案由客户端按 `code` 从自身国际化资源取，服务端只保证 `code` 稳定。因此响应**不给出 `Vary` 与 `Content-Language`**——不做内容协商，就不声明协商。

**字段级校验明细**——参数校验失败时，`data` 携带结构化明细，而非把字段名塞进 `message`：

```json
{
  "code": "PARAM_INVALID",
  "message": "参数校验不通过",
  "data": {
    "field_violations": [
      { "field": "title", "description": "不能为空" },
      { "field": "tags[2].name", "description": "长度超过 32" }
    ]
  },
  "trace_id": "…"
}
```

| 约定 | 说明 |
|---|---|
| 依据 | AIP-193 的 `google.rpc.BadRequest.FieldViolation`。gRPC 侧承载于 `details[].BadRequest`，两侧同构（§1.9）；与 JSON:API error object 的 `source.pointer` 属同一族——两者都把「哪个字段出错」从散文里拿出来放进结构 |
| 字段路径 | `field` 用**请求体中的字段路径**，数组元素带下标（`tags[2].name`），使客户端能直接定位到控件 |
| 必给场合 | `422` 与带字段信息的 `400`（§2.6 乙）。无法定位到具体字段时给空数组，不省略该键 |
| `description` 的定位 | 与 `message` 同为开发者向，客户端**不直接展示**；界面文案由客户端按字段与规则自行组织 |
| 多条并列 | 一次请求的全部校验失败**一次返回**，不逐条报错重试 |

**成功响应的状态码**：

| 场景 | HTTP | 附加头 |
|---|---|---|
| 创建了资源 | `201` | `Location` 指向新资源（RFC 9110 §15.3.2） |
| 其余成功 | `200` | — |

**`201` 的落地状态**：契约已定，现有创建类接口尚未切换到 `201`，首个用例落地时一并调整。

**显式状态出口**——除"由标识推导状态"之外，出口另有一条**显式声明状态**的路径，只用于 §2.6 那类**有状态、无标识**的传输层响应：

| 状态 | body 形状 | 用途 |
|---|---|---|
| `200` / `201` | 信封，`code` 为 `SUCCESS` | 成功但非 `200`（如创建返回 `201` + `Location`） |
| `400` | `{ message, data, trace_id }`，**无 `code`** | 请求读取/解析失败（§2.6 乙） |

- **只接受白名单内的状态**（`200` / `201` / `400`）；白名单外一律记日志并按 `500` 兜底——它**不得成为绕过标识表传业务状态的后门**
- **非 `2xx` 的 body 不带 `code`**，客户端按 §2.6 的形状判定走通用文案分支
- `data` 传空时按该状态的契约给缺省值：非 `2xx` 给空的 `field_violations` 数组（该键不可省略）
- `Location` 等附加头由调用方先写响应头，出口只保证不覆盖、不臆造

**不允许由调用方同时传入状态码与业务标识**：那会让取值表从"唯一真相源"降级为"参考值"，两处推导必然漂移。有标识的一律走标识，无标识的才走本路径。

**不返回 `204 No Content`**：信封要求每个响应都有 body，`204` 无 body，与信封契约直接冲突。这是保留信封形态的直接推论（见 §五），不是独立取舍。

**条件请求与并发控制**——可并发编辑的资源（文章、配置）用 `ETag` 支持乐观锁：

| 环节 | 约定 |
|---|---|
| 读取 | 响应带 `ETag`（RFC 9110 §8.8.3），标识资源当前版本 |
| 提交 | 客户端更新或删除时带 `If-Match`，声明自己改的是哪个版本 |
| 不一致 | 版本已变 → `412` + `PRECONDITION_FAILED`，客户端拉取最新版本后由用户决定是否重提交 |
| 未携带 | 按后写覆盖处理；**若某操作在业务上不允许覆盖，由业务规则拒绝**并返回 `RESOURCE_STATE_NOT_ALLOWED`(`409`) |
| 不设强制 | 本项目**不要求**所有写操作都带 `If-Match`。RFC 6585 §3 的 `428 Precondition Required` 用于服务端强制条件请求的场景，本项目不引入该要求，故不产出 `428` |

**落地状态**：`ETag` / `If-Match` 的契约已定，当前没有可并发编辑的接口在使用，属**待落地项**。

**凭据的传输**——challenge 声明哪个方案，请求就必须接受哪个方案，否则 challenge 是假的：

| 凭据 | 请求头 | 依据 |
|---|---|---|
| 访问令牌 | `Authorization: Bearer <token>` | RFC 6750 §2.1。§三 的 `401` challenge 声明 `Bearer`，客户端据此携带——服务端**必须**接受这一形式 |
| 设备令牌 | `Device-Token` + `Device-Id` | 应用自定义凭据，无对应标准 |
| 请求时间戳 | `Timestamp` | 应用自定义 |

自定义头**不使用 `X-` 前缀**（RFC 6648 / BCP 178 已废弃该约定）。唯一例外是 `traceparent` 的退路 `X-Request-Id`——该名称是既成事实，生态识别度远高于其 RFC 6648 形式，迁移没有收益。

**`Content-Type` 是契约的一部分**，客户端的第一步形状判定就依赖它：

| 响应来源 | `Content-Type` |
|---|---|
| 信封（本节的表） | `application/json; charset=utf-8` |
| 框架保护（§2.6 甲） | `text/plain; charset=utf-8` |
| 请求解析失败（§2.6 乙） | `application/json; charset=utf-8`（body 无 `code`） |

**配套响应头**——下列头由状态码或响应性质决定，必须与响应同时给出：

| 响应头 | 何时给出 | 依据与说明 |
|---|---|---|
| `WWW-Authenticate` | **所有 `401`** | RFC 9110 §15.5.2（**MUST**）：产生 `401` 的服务端必须至少给出一个 challenge |
| `WWW-Authenticate` | **`PERMISSION_DENIED` / `ROLE_MISMATCH`（`403`）** | RFC 6750 §3.1 把 `insufficient_scope` 定义为带 challenge 的 `403`。**只有这两个标识带**——同为 `403` 的 `ACCOUNT_DISABLED`（账号状态）与 `OPERATION_NOT_ALLOWED`（业务规则）不是权限范围问题，不适用该错误码 |
| `Retry-After` | **所有 `429`，及所有 `503`** | RFC 9110 §10.2.3（头字段本身）；`503` 见 RFC 9110 §15.6.4、`429` 见 RFC 6585 §4。取值口径见 §2.4 |
| `RateLimit-Limit` `RateLimit-Remaining` `RateLimit-Reset` | **所有响应**（含 `2xx`） | 见 §2.4 |
| `traceparent` | **所有响应** | 与信封 `trace_id` 同源，使网关、反向代理、日志采集与 APM **不必解析 body** 即可关联链路。用 W3C Trace Context 标准的头名以对接 OpenTelemetry；若不引入该标准，退而用 `X-Request-Id` |
| `ETag` | **可并发编辑的资源** | RFC 9110 §8.8.3，见上「条件请求与并发控制」 |
| `Location` | **`201`** | RFC 9110 §10.2.2 |
| `Allow` | **`405`** | RFC 9110 §10.2.1（**MUST**） |
| `Cache-Control: no-store` | **所有非 `2xx` 响应** | 错误响应可能含请求相关细节，不应被中间层或浏览器缓存 |

**`401` 的 challenge 让中间层不必解析 body 即可拿到原因**；因**令牌**失败的套用 RFC 6750 的错误参数：

| 场景 | challenge |
|---|---|
| 资源请求上因**令牌**失败（`UNAUTHENTICATED` / `LOGIN_EXPIRED`） | `Bearer realm="blog", error="invalid_token"` |
| 因**请求签名或时效**失败（`REQUEST_SIGNATURE_INVALID`） | 用方案自身名，如 `Signature realm="blog"`——失败的**不是** Bearer 令牌，故不套用 RFC 6750 的 `error` 参数（那三个错误码描述的都是令牌问题） |
| 权限不足（`PERMISSION_DENIED` / `ROLE_MISMATCH`） | `Bearer realm="blog", error="insufficient_scope"` |
| 登录端点因**凭据**失败（`CREDENTIALS_INVALID`） | `Bearer realm="blog"`——请求未出示令牌，不适用 `error` 参数（RFC 6750 的三个错误码均描述令牌问题） |

**`401` / `405` / `429` 的头是规范要求，不是可选项**——它们的缺失会让标准客户端与中间层无法正确响应（无法发起认证挑战、无法得知允许的方法、无法退避）。

## 四、客户端的统一分发

客户端的 code 分发**只有一个入口**，两个响应通道（HTTP 2xx 与 HTTP 非 2xx）走同一条路径：

1. **判定形状**（§2.6）——非信封则按 HTTP 状态码给**客户端自有的通用文案**（带 `data.field_violations` 时用它定位字段），流程结束
2. **信封则按 `code` 分发**，分发**不依赖 HTTP 状态码**：

| code | 客户端行为 |
|---|---|
| `SUCCESS` | 正常处理。`201` 时读 `Location` 以跳转到新资源 |
| `LOGIN_EXPIRED` | 自动刷新令牌一次并重试原请求；刷新失败则登出 |
| `UNAUTHENTICATED` | 会话结束，登出 |
| `CREDENTIALS_INVALID` | 提示凭据有误，**留在登录页**，不触发登出流程 |
| `ACCOUNT_DISABLED` | 提示账号已被禁用，引导联系管理员 |
| `PERMISSION_DENIED` `ROLE_MISMATCH` `OPERATION_NOT_ALLOWED` | 提示权限不足 |
| `PARAM_INVALID` `PARAM_FORMAT_INVALID` `PARAM_VALUE_NOT_ALLOWED` `CAPTCHA_INCORRECT` | 按 `data.field_violations` 逐字段标记错误，留在当前页面 |
| `PARAM_MISSING` | 提示请求头缺失，留在当前页面（该失败没有字段级明细可标） |
| `RESOURCE_NOT_FOUND` | 提示并从服务端重新拉取列表或详情 |
| `RESOURCE_ALREADY_EXISTS` `RESOURCE_STATE_NOT_ALLOWED` | 提示并重新拉取该资源的最新状态 |
| `PRECONDITION_FAILED` | 提示"内容已被他人修改"，拉取最新版本后由用户决定是否重新提交 |
| `RATE_LIMIT_EXCEEDED` | 按 `Retry-After` 提示等待时长；参考 `RateLimit-Remaining` 提前降速 |
| `REQUEST_SIGNATURE_INVALID` | 重新签名后重试一次；仍失败则登出 |
| `EXTERNAL_SERVICE_ERROR` `SERVICE_UNAVAILABLE` `SERVICE_TIMEOUT` | 提示服务异常，**可自动重试**（受下条硬约定约束），退避至 `Retry-After` 给出的时长 |
| `INTERNAL_ERROR` `DATABASE_ERROR` | 提示服务异常，**不自动重试**（是否让用户手动重试由页面决定） |
| *未列出的标识* | 用**客户端自有的通用文案**提示。这是**前向兼容分支**，不是兜底设计——标识只增不减（§1.8 规则 5），客户端必然遇到比自身版本更新的标识。**不展示 `message`** |

**文案的来源**：上表每一行展示的文案都由**客户端按 `code` 从自身国际化资源取**，服务端 `message` 只进日志。这样新增标识时前端只需补一条文案，不需要服务端同步维护多语言表。

**四条硬约定**：

- **不得在 HTTP 错误分支里只读传输库自身的 message**。非 2xx 的响应体同样是信封，其中的 `code` 必须被读取——否则 `LOGIN_EXPIRED` 在 `401` 上永远处理不到，自动续期整条链路失效
- **刷新令牌的请求自身必须跳过刷新分支**。否则刷新失败时该请求会再次进入刷新逻辑、并等待自己那笔尚未结束的请求，造成**永久挂起**。跳过刷新是准入判定而非业务逻辑：命中即直接登出
- **自动重试必须限定在幂等请求上**。`502` / `503` / `504` 只说明服务端这一次没成功，不说明它没生效——对 `POST` 这类非幂等方法自动重试会造成重复写入。判定依据是 HTTP 方法的幂等性，或请求携带了幂等键（RFC 9110 §9.2.2）
- **不得解析 `message` 或 `description` 反推语义**。字段级错误一律走 `data.field_violations`；两者的文案都可能随时改动

**幂等键的契约**——非幂等方法的请求可携带幂等键，使重试安全：

| 项 | 约定 |
|---|---|
| 头名 | `Idempotency-Key`，由客户端生成，取值唯一（de-facto 通行名，IETF 草案沿用同一名称） |
| 适用范围 | 仅 `POST` / `PATCH` 这类非幂等方法；幂等方法本身无需携带 |
| 服务端行为 | 同一键的请求在有效期内**只生效一次**；重放返回**首次的结果**（含状态码与 `code`），不重复副作用 |
| 键冲突 | 同一键携带**不同**请求体时返回 `422` + `PARAM_INVALID`，并在 `field_violations` 中指出冲突。取 `422` 与 §1.2 对「内容语义不合法」的定义一致（各家 API 在此处选码并不统一） |
| 有效期限 | 由服务端按业务设定并在接口文档中给出 |
| 未携带时 | 请求照常处理，但**客户端不得对其自动重试**——这正是上一条硬约定 |

**落地状态**：幂等键的契约已定，当前没有需要它的写入接口，属**待落地项**。

## 五、与行业规范的对照声明

**本文符合**：

- RFC 9110 的状态码语义，以及 `Allow` / `Location` / `Retry-After` / `ETag` 等头的给出条件（§1.2 / §1.3 / §三）
- RFC 6750 的 `Bearer` 方案与 challenge 错误参数（§三）
- RFC 6648（BCP 178）自定义头不加 `X-` 前缀（§三）
- AIP-193 对错误标识的形式约束（`UPPER_SNAKE_CASE` 的 `reason`）、"控制流依赖 reason 而非状态码"的分工，以及 `BadRequest.FieldViolation` 的字段级明细结构（§1.1 / §1.7 / §1.9 / §三）

**一处需要说清的边界**：「状态码由标识集中推导」在本文是**架构选择**，不是行业规范。规范层面只要求"同一错误在不同接口给出一致状态"（AIP-193 给出对照表、Smithy 用 `@httpError` 把状态绑在错误类型上）；**由谁推导**——中心化映射，还是调用点各自选择状态——两派都有成熟实践。本项目选中心化，理由是本项目的三条约束：同一标识要跨 HTTP 与 gRPC 两跳（§1.9）、一致性可由测试机械保证、业务层不引入 HTTP 依赖（§1.1）。**不得把这条当作规范去主张，也不得用它否决"某个调用点状态更准"的具体论证——遇到那种论证，要判断的是"改表"还是"另立标识"。**

**本文与行业规范的偏离分两类。** 形态类只有一处来源：保留扁平信封，不采用 RFC 9457 的 Problem Details 形态——以下四条都是这一处的推论，而非各自独立的取舍：

| # | 取舍点 | 行业做法 | 本文做法与理由 |
|---|---|---|---|
| 1 | 响应体形态 | RFC 9457 规定独立的问题对象（`type` / `title` / `status` / `detail` / `instance`）与 `application/problem+json` 媒体类型；JSON:API 属同族——错误放独立的 `errors` 数组，每项含 `code` / `status` / `source.pointer` | **沿用扁平信封，成功与失败同构**，使客户端只需一处解析逻辑。**代价是本做法不符合 RFC 9457——不得声称符合** |
| 2 | 细分标识放在哪一层 | AIP-193 放 `details[].ErrorInfo.reason`；Microsoft 把根级 `code` 用作服务自定义的子状态码，更细的原因再放 `innererror.code` | **HTTP 侧直接放根级 `code`**——扁平信封没有 `error` 包裹层可用。**gRPC 侧仍落在 `ErrorInfo.reason`**（§1.9），即 AIP-193 的原位；两侧同值，这一层不构成偏离 |
| 3 | 错误标识用 URI 还是纯字符串 | RFC 9457 用 `type` URI | **纯字符串**（§1.7）。URI 的价值是每个错误指向公开文档，本项目无对外错误文档站；`code` 既是标识也是 AIP-193 的 `reason`，一物两用 |
| 4 | 无 body 的成功响应 | REST 惯例对无返回内容的操作（如删除）用 `204 No Content` | **仍返回 `200` + 信封**。信封要求每个响应都有 body，`204` 与之直接冲突；这是保留信封的推论。创建成功仍按标准返回 `201` + `Location`，因为它不冲突 |

**映射类偏离与形态无关，逐条声明**（都是 HTTP 状态码与头字段的取舍，客户端按 `code` 分发不受影响）：

| # | 取舍点 | 行业做法 | 本文做法与理由 |
|---|---|---|---|
| 5 | 参数校验挂哪个状态码 | AIP-193 把 `INVALID_ARGUMENT` 映射到 `400` | `422`（§1.3）。RFC 9110 §15.5.21 已把 `422` 定为「读懂了但内容语义不合法」，与参数校验吻合，且把 `400` 净化为唯一的「解析失败」；与 AIP-193 的 HTTP 映射不一致，但标识的 canonical 锚点仍是 `INVALID_ARGUMENT` |
| 6 | 并发冲突挂哪个状态码 | AIP-193 把 `ABORTED` 映射到 `409` | `412`（§1.3）。RFC 9110 §15.5.13 的 `412` 专指条件请求的前提不成立，正是乐观锁场景；`409` 留给无条件的业务状态判定 |
| 7 | 请求签名失败挂哪个状态码与 challenge | 无统一做法：AWS SigV4 用 `403`，GitHub webhook 用 `401` | `401`（§1.2）——签名即本次请求出示的凭据，「凭据无效」属准入判定，与 §1.1 的分层一致。因它不是 Bearer 令牌，challenge 不套用 RFC 6750 的错误码，改用方案自身名（§三） |
| 8 | `RateLimit-*` 的字段名 | IETF 草案现行修订用 `RateLimit` + `RateLimit-Policy` 两枚结构化字段（**尚未成为 RFC**） | 三枚分列字段（§2.4）。草案字段名仍在变动，de-facto 写法识别度更高；待其定稿后评估迁移 |

**此前记录在案的其余偏离已全部消解**：`PARAM_*` 的状态码改采 `422`；下游失败按"答得不对 / 连不上"分为 `502` / `503`；数据库暂时性故障归 `503`；资源状态冲突保留 `409`（RFC 9110 §15.5.10 原生语义，非偏离）；并发编辑冲突采用标准 `412`；登录失败的 `401` 与主流 API 实践一致；`Allow` / `Location` / `Retry-After` / `ETag` 等标准头均已补齐。上表 5—8 行是本次按行业标准核对后新识别出的偏离，此前未在本文登记。
