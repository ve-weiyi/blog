# 12 契约与演进

> **本文回答**：接口如何定义、从哪里生成、如何升级，兼容性的底线是什么。
>
> 初稿：2026-10-22 · 最近更新：2026-10-22

## 一、两类契约

系统有两类契约，面向不同消费者，职责不重叠：

| 维度 | HTTP 契约 | gRPC 契约 |
|---|---|---|
| 消费者 | 浏览器前端 | 后端模块之间 |
| 形态 | HTTP + JSON | 方法 + 消息 |
| 关注点 | **用例**：一个请求对应一个界面动作 | **领域**：一个方法对应一项业务能力 |
| 粒度 | 面向客户端聚合，可按场景裁剪 | 面向数据所有权，保持完整 |
| 变更影响 | 前端需同步 | 后端模块间需同步 |

**两层的模块划分允许不同，且应当不同。** HTTP 按用例切（「后台的评论管理页需要什么」），gRPC 按领域切（「评论归谁拥有」）。强行对齐会让两边都变差。

两条红线：

1. **不得同名反义** —— 同一个词不得在两层指相反的事。
2. **可恢复性跨层必须保持可辨** —— HTTP 的 `delete`（进回收站，可恢复）与 `destroy`（物理删除，不可恢复）在 gRPC 层必须落到能区分「改状态位」与「物理删除」的方法名上。

## 二、唯一真相源与生成

`protocol/` 是接口语义的唯一真相源：`api/` 定义 HTTP 契约，`proto/` 定义 gRPC 契约。

**所有生成物都不是手写代码**：服务端骨架、客户端、类型定义、路由表、前端 TypeScript 调用代码与接口文档都由生成工具从契约产出。手工修改生成物会在下一次生成时被覆盖，且不会被评审发现。

### D1 契约源与生成物必须同时落地

- **约束**：契约源在父仓，实现仓库（当前主要是 `blog-cloud`，前端另有独立仓库）是独立 git 子模块；生成工具直接从 `protocol/` 写入实现仓库的工作区。
- **备选**：把 `protocol/` 做成独立的版本化依赖，由实现仓库按版本引用。
- **选择**：契约源与生成物分属两个 git 仓库，但**一次契约变更必须在同一次变更窗口中完成**：改契约 → 重新生成 → 实现 → 提交实现（含生成物），再更新父仓的契约与子模块指针。
- **代价**：父仓与子模块的两次提交无法原子化；中间态可能短暂不一致。
- **重审触发**：出现多个实现仓库消费同一份契约，或需要按版本锁定契约。

**为什么不能只改契约、不提交生成物**：实现仓库的构建只依赖自己仓库内的生成物，不看父仓的 `protocol/`。契约已提交而生成物未更新，构建仍然通过，但线上接口与契约已经不一致 —— 这是一个不会报错的错误。

**为什么不能只改生成物、不改契约**：下一次生成会把它覆盖；且评审看到的是生成物，无法判断契约语义是否被有意修改。

## 三、HTTP 契约约定

采用 **RPC 风格**：URL 表达动作，查询用 `GET`，其余用 `POST`；不追求资源导向的路径形态。

| 约定 | 内容 | 理由 |
|---|---|---|
| 前缀 | 读者端 `/api/v1/*`，管理端 `/admin-api/v1/*` | 两端同源不同面；`admin-api` 不是资源名，是有意例外 |
| 动作表达 | 动作作为独立路径段：`POST /articles/batch-delete`、`POST /articles/{id}/like` | 接口名即文档；不依赖调用方理解资源模型 |
| 批量操作 | `POST /资源/动词`，动词表达业务意图：`batch-delete` / `batch-restore` / `batch-destroy` / `export` / `sync` | 意图进 URL，字段不进；不用 `DELETE` 带 body |
| 删除词汇 | `delete` = 可恢复（进回收站），`restore` = 恢复，`destroy` = 不可逆销毁 | 三者是不同业务动作与不同权限点，混用会让调用方搞反 |
| 单资源局部更新 | `PATCH /资源/{id}` | PATCH 的部分更新语义正好 |
| 关联关系 | 建模为子资源集合：`PUT /roles/{id}/menus` 全量替换，`POST` / `DELETE` 增减 | 绑定关系本身就是资源集合 |
| 认证路径 | 登录按方式拆端点 `login-by-{password,email,mobile}`；OAuth 按平台建子资源；登出用 `DELETE /auth/session` | 四种登录请求体形状不同，合并会得到大量 optional 字段的联合类型 |
| 分页 | 偏移分页：`page` + `page_size` → `total` + `list` | 读者端与管理端都需要跳页与总数 |
| 字段命名 | JSON 字段使用 `snake_case`，与前端生成代码一致 | 生成链路统一 |
| 排序 | 排序字段是受控值，**服务端必须按白名单校验**，不得拼入查询语句 | 客户端可控的排序表达式是注入面 |
| 错误 | **不进入契约** | 错误是全局横切语义，不属于任何单个接口 |

**契约只描述成功路径。** 请求 / 响应类型、路由与中间件是契约内容；错误语义、分页与排序的横切约定不进入单个接口的类型定义。

**同一概念允许有多个视图类型。** 读者端路由表与管理端表单对同一实体的字段偏好不同；统一到任一侧都会让另一边多转一次。视图类型可以不同，但**语义不得相反**。

## 四、gRPC 契约约定

gRPC 契约按领域切：一个模块一个服务，服务名与方法名表达业务能力。

| 约定 | 内容 |
|---|---|
| proto package | `blog.<module>.v1` |
| `go_package` | `./<module>rpc` |
| 服务划分 | 与数据所有权一致；不按页面或调用方拆分 |
| 标准方法 | `List` / `Get` / `Create` / `Update` / `Patch` |
| 批量方法 | `Batch{Action}{Resources}`，名字直接区分「改一批」与「改一个」 |
| 部分更新 | `Patch{Resource}` 只改传入字段；`Update{Resource}` 覆盖客户端可写字段 |
| 自定义方法 | 用动词表达领域动作（如 `LikeArticle`、`IncrementArticleView`），不用 `Get` 掩盖写操作 |
| 写响应 | 单个实体的 `Create` / `Update` 返回写入后的实体；批量写返回 `success_count`；领域动作返回各自的结果（如 `{liked, changed}`） |
| 错误 | 不使用消息体表达错误；使用 gRPC 状态 + 业务标识，见《请求管线与响应契约》 |

**命名细则**（字段、枚举、时间类型、分页结构）以 [`docs/standards/RPC设计规范.md`](../standards/RPC设计规范.md) 为准；本文只锁定分层与命名语义。

## 五、演进与兼容

系统允许前端、网关与服务**独立部署**。滚动发布期间，新旧版本必须同时可用 —— 这是兼容性规则的唯一来源。

| 规则 | 内容 |
|---|---|
| **只增不改** | 新增字段必须可缺省；不修改既有字段的类型与语义 |
| **不复用** | 废弃字段的字段号、字段名与枚举值不得回收复用 |
| **不删即弃** | 删除字段先标记废弃并保留一个发布周期；客户端停止使用后再移除 |
| **枚举只增** | 新增枚举值必须让旧版本能安全忽略；不改变既有值的含义 |
| **破坏性变更走新版本** | 包名或路径升到 `v2`，旧版本在迁移期内继续服务；不在 `v1` 内做破坏性修改 |
| **契约变更走评审** | 新增接口属于常规变更；字段语义变化、删除与路径调整必须重新走设计评审 |

**可恢复性跨层不可丢失**：HTTP 的 `delete`（可恢复）映射到 gRPC 的「改软删状态位」，`destroy` 映射到「物理删除」。rpc 层不承载「回收站」这个业务概念，因此映射本身是必要的；但**不得让可恢复与不可恢复落到同一个方法名上**。跨层排障时必须能回到这条映射。

## 六、关键决策

| 决策 | 内容 | 备选 | 代价 | 重审触发 |
|---|---|---|---|---|
| **D1 契约源与生成物同一提交** | 改契约 → 重新生成 → 实现，一次变更窗口完成 | 把 `protocol` 做成版本化依赖 | 父仓与子模块无法原子提交 | 多个实现仓库消费同一契约，或需要按版本锁定 |
| **D2 两类契约粒度允许不同** | HTTP 按用例切，gRPC 按领域切 | 两层统一粒度 | 需要维护跨层语义映射 | 两层语义出现分叉 |
| **D3 只增不改** | 新增字段可缺省；不改类型与语义；不复用字段号 | 允许破坏性变更并同步发布 | 废弃字段需要保留一个发布周期 | 所有实现可以原子升级 |
| **D4 破坏性变更升版本** | 新包名 / 新路径；旧版本迁移期内继续服务 | 在 `v1` 内做破坏性修改 | 需要同时维护两版 | 没有旧版本需要兼容 |
| **D5 错误不进入契约** | 错误是全局横切语义，由响应出口统一表达 | 每个接口类型自带错误码 | 客户端需要查全局标识表 | 出现无法用全局表表达的端点级错误 |
| **D6 跨层可恢复性必须可辨** | `delete` / `restore` / `destroy` 在 rpc 层不得落到同一方法名 | 统一 `delete` 语义 | 需要维护映射规则 | rpc 层引入回收站概念 |

## 七、不变量

- [ ] `protocol/` 是接口语义的唯一来源；代码中不存在第二份手写的接口定义。
- [ ] 生成物不手工修改；从干净工作区重新生成不产生额外差异。
- [ ] 契约变更与生成物在同一个实现提交中落地。
- [ ] HTTP 与 gRPC 的粒度可以不同，但同一语义不得在两层相反。
- [ ] `delete` / `restore` / `destroy` 的可恢复性在跨层后仍可区分。
- [ ] 字段号、字段名与枚举值一旦发布，不回收复用。
- [ ] 错误语义不写入成功响应类型。
- [ ] 排序字段在服务端按白名单校验，不拼接客户端输入。

## 八、失败与降级

契约层没有运行时降级 —— 它的失败模式都发生在变更与发布过程中：

| 失败模式 | 后果 | 约束 |
|---|---|---|
| 契约已改、生成物未提交 | 构建通过，但线上接口与契约不一致 | 契约与生成物必须同一提交 |
| 生成物被手工修改 | 下次生成被覆盖，问题被掩盖 | 生成失败时修契约或工具，不手改产物 |
| 破坏性变更直接落在 `v1` | 回滚代码无法恢复旧契约 | 破坏性变更必须升版本 |
| 新旧版本并存时语义不兼容 | 滚动发布期间部分请求失败 | 只增不改；新增字段可缺省 |
| 跨层语义映射丢失 | 排障时无法判断操作是否可恢复 | 保留 `delete` / `destroy` 的映射规则 |

## 九、边界与重新审视

- **不做**：GraphQL、契约注册中心、服务网格、运行时 schema 校验。
- **不承诺**：对外公开 API 的长期版本支持；当前契约只服务本系统前端与模块。
- **重新审视**：出现外部第三方消费者；出现多个实现仓库消费同一份契约；单次发布无法同时升级前端与后端。
