**参照 `yocto/scan` 的 SSE 实现做了 6 处补强**（该项目的 `internal/core/sse` + `docs/feature/2026-09-14-实时推送迁移SSE实施方案.md` Task 5/10 为准）：

1. **心跳改为 handler 层的 SSE 注释行**（`handler/notification/notify_stream/beat.go`，15s）：注释行不进入业务通道、不参与帧编解码，客户端完全无感；原先把 `{"event":"ping"}` 塞进 channel 是让心跳穿过了整条业务链路
2. **`X-Accel-Buffering: no`** 写进生成的 handler 首行
3. **前端静默检测**（`staleTimeout` 默认 45s = 3× 心跳）：覆盖 TCP 半开——进程被杀/网络中断不产生 FIN，读操作不报错，连接会一直显示"已连接"却收不到数据
4. **优雅关闭接线**：`ServiceContext.Shutdown()`（停订阅 + 关连接通道）+ `admin.go` 的 **`proc.AddShutdownListener(ctx.Shutdown)`**（不能用 `defer`，见下）
4b. **关闭钩子只能用 `proc.AddShutdownListener`，`defer` 无效**：go-zero 收到 SIGTERM/SIGINT 时先跑关闭监听、再用 `syscall.Kill(getpid(), sig)` 自杀（`core/proc/shutdown.go:96`），**main 不会返回，所有 defer 都不执行**。scan 的 `defer svcCtx.Shutdown()`（`scan3d.go:118`）同样踩了这个坑，此处的写法是修正后的
5. **泛型广播器 `sse.Broker[T]`，每频道一实例**（替代原先非泛型的 `common/sse.Hub`）：新增频道 = 再建一个 Broker + 一个订阅器 + 一个端点，结构不再动
6. **前端通道非单例**：`useSse()`（全局单例）→ `createSseChannel()`（每频道一实例，实例由 `composables/sse/index.ts` 持有），与后端"每频道一实例"对齐

### 2.5 go-zero 的 SSE 能力与 `.api` 定义方式（本次调研结论）

**结论：SSE 是 go-zero 的框架能力（v1.8.2+ / PR #4729），`.api` 里用组级 `sse: true` 声明，项目模板已就位。**

**（1）`.api` 语法 —— `sse: true` 是 `@server` 组属性**

```api
@server(
	prefix:     /admin-api/v1
	group:      notify-sse
	middleware: AdminAuth
	sse:        true
)
service admin-api {
	@doc "通知消息推送流"
	@handler NotifyStream
	get /notify-messages/stream returns (StreamEvent)
}
```

**已本地实测**（goctl 1.10.2 + 本项目 `.goctl/template`，在临时工程里跑通）：

- `goctl api format`：**接受** `sse: true`；写成 `sse /path` 这种"方法关键字"会被拒（parser 只认 `get|head|post|put|patch|delete|connect|options|trace`）
- `goctl api go` 生成的 `routes.go` 带上了 **`rest.WithSSE()`**：
  `server.AddRoutes([]rest.Route{...}, rest.WithPrefix("/admin-api/v1"), rest.WithSSE())`

**（2）`rest.WithSSE()` 负责什么**（`rest/engine.go:383-402` `buildSSERoutes`）

- 清掉 `http.Server` 的写超时（`http.NewResponseController(w).SetWriteDeadline(time.Time{})`）——否则长连接会被写超时掐断
- 设三个响应头：`Content-Type: text/event-stream`、`Cache-Control: no-cache`、`Connection: keep-alive`
- **不设** `X-Accel-Buffering`（Nginx 缓冲仍需部署侧处理，或自建 handler 里补）

**（3）客户端 `Accept` 必须严格等于 `text/event-stream`** —— 这是个脆点

`rest/handler/timeouthandler.go:63-64` 的判定是**相等**而非包含：

```go
if r.Header.Get(headerUpgrade) == valueWebsocket ||
    r.Header.Get(headerAccept) == valueSSE {   // valueSSE = "text/event-stream"
```

即 `Accept: text/event-stream, */*` 之类会**匹配失败**，请求被套上超时包装 → 流被掐断。前端 `useSse.ts:213` 恰好发的就是这个精确值，**必须保持**。

**（4）生成的 handler 形状**（本项目 `.goctl/template/api/sse_handler.tpl`）

- `client := make(chan *types.<Resp>, 16)`；logic 在 `threading.GoSafeCtx` 里跑，`defer close(client)`
- 主循环 `select`：从 channel 取 → `json.Marshal` → `fmt.Fprintf(w, "data: %s\n\n", …)` → `Flush()`；`case <-r.Context().Done()` 退出（**断连清理已内建**）
- **只写 `data:`，不写 `event:`** —— 所有帧到前端都是默认事件名 `message`
- **没有心跳** —— 循环里没有 ticker

**（5）生成的 logic 形状**（`sse_logic.tpl`）

```go
func (l *NotifyStreamLogic) NotifyStream(client chan<- *types.StreamEvent) error
```

**（6）一处模板与统一出口的不一致（本次可规避）**

`sse_handler.tpl` 在 `httpx.Parse` 失败时用的是 `httpx.ErrorCtx`，**不是** `responsex.Response`（对比 `handler.tpl:18`），即请求解析错误会返回非信封响应。本次路由**无请求参数**（`HasRequest` 为假），该分支不会生成，**不影响**；但**将来若给 SSE 路由加查询参数，必须同时改模板这一行**。

## 三、决策

### D1 推「信号」，不推「内容」

事件载荷只含"**哪条消息发布/撤回了**"，**不含收件人信息**；客户端收到后自行调未读列表接口拉取。

**为什么**：通知是定向的（§2.1），推内容意味着网关必须知道每条消息的收件人——`all` 目标要展开成**全表用户 ID**，而 api/admin **没有 DB**，只能回头调 rpc。推送一条 N 万 ID 的载荷，或者让网关为每条通知做一次 RPC，都是把 rpc 的职责搬进网关。

信号模型的代价是"多一次 HTTP 往返"，换来的是：网关无状态、无连接注册表、无按人过滤、内容不经内部通道，且**天然幂等自愈**（漏掉一个信号，下一次拉取就补上）。

### D2 跨进程扇出用 **Redis Pub/Sub**

rpc 发布 → Redis channel → api/admin 订阅 → 推给本实例的 SSE 连接。

**为什么不是 MQ**：rpc 有 MQ（`mq.PublishInboxMessageEvent`），但 **api/admin 侧零消费能力**，要新建消费端与连接管理；而 Redis Pub/Sub 的**发布与订阅两侧在本仓库都有现成先例**（§2.3）。多实例网关也必须靠扇出，这一层两者都省不掉。

### D3 触发点放在 **rpc 的 publish / revoke**，不放在 MQ 消费端

- 发布：`UpdateFields` 成功后立刻发一次事件（与 MQ 投递解耦，MQ 降级路径也自然覆盖）
- 撤回：**补上**（现在是完全不对称的，§2.1）

**为什么不放在消费端**（`consume_inbox_message_logic.go`）：那是**逐收件人**的，`all` 目标一发就是 N 次；信号模型只需要"消息已发布"这**一次**。

**失败降级**：Redis 发布失败只记日志，**不影响发布/撤回主流程**——与 `mq.ErrUnavailable` 的降级同精神。

### D4 端点声明为**独立的 SSE 路由组**，组内只挂 `AdminAuth`

**首要原因：`sse: true` 是 `@server` 的组级属性**（§2.5），一旦写进某个组，**整组路由都变成 SSE 流**。所以 SSE 路由必须在 `.api` 里单独成组——这不是风格选择，是 goctl 的语法约束。

**次要原因**：不并入既有组，也就不必背它的中间件。参照 `/inbox-records` 组是 `{AdminAuth, Permission, OperationLog}` 三件套齐全（`handler/routes.go:861-863`）：

- **`OperationLog` 必须避开**：长连接会被记成一条持续数小时、跨度毫无意义的操作日志
- **`Permission` 不必挂**：这不是受 RBAC 保护的资源操作，而是"订阅自己会收到的通知"

所以组声明为 `middleware: AdminAuth`（§2.5 的 `.api` 片段）。

**与 `/ws` 的对照**：`/ws` 之所以裸注册（`routes.go:491-501`）并把鉴权下沉到 STOMP CONNECT 帧，是因为**浏览器 WebSocket 握手不能带自定义头**。SSE 走 fetch，能带任意头（`useSse.ts:209-216`），所以**不必**重复实现一套鉴权，直接用 `AdminAuth` 复用现成的 uid + 令牌校验（`adminauth_middleware.go:39-48`）。只挂 `AdminAuth` 的组在仓库里有先例：`routes.go:295-297`、`:338-339`。

### D5 与「统一响应出口」的边界：**SSE 是框架层的独立路由类型，不是漏网的例外**

SSE 路由由 `rest.WithSSE()`（`engine.go:383-402`）接管响应头与写超时，handler 由 `sse_handler.tpl` 生成、直接写 `data:` 帧——**它天然不经过 `responsex`，而这不是我们的选择，是 go-zero 的既有能力**（§2.5）。

所以 `docs/design/07-BLOG-错误码与中间件.md` 要登记的不是"给某个端点开白名单"，而是**一条边界陈述**：

> 统一响应出口约束的是 **JSON API**。SSE 路由（`.api` 中 `sse: true` 的组）是框架层的流式路由类型，其响应体是事件流而非信封；但**流建立之前的失败**（鉴权不通过、连接数超限）仍由中间件与 handler 走 `responsex` 输出信封。

边界写清楚：**鉴权失败、连接超限等错误发生在流开始之前 → 仍走 `responsex` 信封**（如 503 + `SERVICE_UNAVAILABLE`）；一旦进入 `sse_handler.tpl` 的写帧循环，就由该路由自己负责。

### D6 不做 `Last-Event-ID`，改为「连接建立即拉一次未读」

**这是对前置讨论的一次修正，必须记下**：当初选 SSE 的理由之一是"`Last-Event-ID` 内建补投语义"。但有了 D1 的信号模型，**漏掉的信号由下一次拉取自愈**——只要保证"每次连接建立成功即拉一次未读"，断线期间的通知就不会永久丢失。既然如此，维护游标（前端解析 `id:` + 重连带头 + 后端保留可回放的事件窗口）就是**多余复杂度**。

**后果**：前端的 `handleSseLine` **不用改**（它本来就不解析 `id:`），后端也不用维护事件窗口。

**诚实记录**：这一修正使 SSE 相对 STOMP 的优势重新落到两条上——① 纯 HTTP 单向流，不需要 broker 与心跳往返往返，穿代理最稳；② **天生是页面级常驻的一条流**（实例由模块持有，不随组件挂载/卸载），而 STOMP 那条在线人数的连接是**组件级**的（在 `Home.vue` 里 `onMounted` 建连、`onUnmounted` 断连）。若将来这两条不再成立，应重新评估选型。

### D7 不启用 `cachekey.InboxReadPrefix`

`infra/constants/cachekey/notification_cache.go:10` 有一个**零调用**的孤岛常量（zset，member=messageId、score=readAt），前缀还是不合群风格的 `notification:inbox:read:`。未读数建议**直接向 rpc 查**（列表接口已有），不引入第二处真相源。是否启用留作后续独立决定。

### D8 事件落点是 **store 新增 `refreshUnread()`**，不是组件内的 `fetchList()`

`stores/notification.ts` 现在只有 `unreadTotal` / `markAsRead` / `markAllAsRead`——**只减不重拉**，而重新拉取的唯一入口 `useNotice.fetchList()` 挂在 `components/NoticeDropdown/index.vue` 的 `onMounted` 上，而**那个组件全仓零引用**（§2.4）。

SSE 通道是**页面级常驻**的（实例由 `composables/sse/index.ts` 持有，不随组件挂载/卸载），不能把"收到通知后拉未读"的职责交给一个可能永远不挂载的组件。所以：

- `stores/notification.ts` 新增 `refreshUnread()`（调 `NotifyRecordAPI.queryUserInboxRecordList`，写 `unreadTotal`）
- SSE 的 `notice` / `notice-revoke` 处理器调用它
- 收件端 UI 消费 `unreadTotal`——**但"顶部入口"是启用那个死掉的下拉，还是只让 `MyNotice` 页可见，需要你定**（§八-2）

### 4.1 channel 常量

`infra/constants/cachekey/notification_cache.go` 新增，风格对齐已有的三个（`blog:<模块>x:invalidate:<实体>`）：

```go
// NotifyEventChannel 通知发布/撤回事件的 Pub/Sub channel
NotifyEventChannel = "blog:notificationx:event"
```

### 4.2 rpc 触发点（两处，对称）

| 位置 | 时机 | 载荷 |
|---|---|---|
| `publish_notify_message_logic.go` | `UpdateFields` 成功后 | `{"event":"notice","message_id":N,"title":"…","category":"…","level":"…","published_at":"RFC3339"}` |
| `revoke_notify_message_logic.go` | message 状态更新成功后 | `{"event":"notice-revoke","message_id":N}` |

字段名用 snake_case，与 HTTP 响应契约一致。RPC 层**禁止 HTTP 语义**（见 `backend.md`），此载荷是内部事件、不是 HTTP 契约，应定义在 rpc 侧的类型里。

### 4.3 端点声明与帧契约

**声明**（写进 `protocol/api/admin/notification.api`，`sse: true` 组级，见 §2.5）：

```api
@server(
	prefix:     /admin-api/v1
	group:      notify-sse
	middleware: AdminAuth
	sse:        true
)
service admin-api {
	@doc "通知消息推送流"
	@handler NotifyStream
	get /notify-messages/stream returns (StreamEvent)
}
```

路径命名对齐既有约定：通知消息 CRUD 在 `/notify-messages`，我的收件箱在 `/inbox-records`；本流推的是**消息生命周期事件**，落在 `/notify-messages/stream`。

```
请求头（AdminAuth 必需）: uid, authorization
请求头（建议同带，与 axios 口径一致）: X-Device-Id, Timestamp, X-Device-Token
   —— 不带也可通过：DeviceToken 中间件在 x-device-id 为空时放行（terminaltoken_middleware.go:31-37）
请求头（**硬约束**）: Accept: text/event-stream
   —— 必须精确等于该值，否则 go-zero 的超时包装会掐断流（§2.5(3)）

响应头: rest.WithSSE() 设置 Content-Type/Cache-Control/Connection（§2.5(2)）；
   X-Accel-Buffering: no 由 handler 首行补（WithSSE 不设该头）

帧格式: 模板只写 data:（无 event:、无 id:），事件类型放在载荷里
  data: {"event":"notice","message_id":123,"title":"…","category":"system","level":"info","published_at":"…"}
  data: {"event":"notice-revoke","message_id":123}
  : ping                          ← 心跳每 15s，handler 层写的 SSE 注释行（不触发客户端分发）
```

**四处与原稿的差异**（都因为 §2.5 的调研结论）：① 响应头不由我们写；② **没有 `event:` 字段**——所以不分事件名，前端只订默认的 `message` 事件，按载荷里的 `event` 字段分发（见 §五-7）；③ **没有内置心跳**——模板循环里没有 ticker；④ 心跳**以注释行写在 handler 层**（`beat.go`），而不是把 `{"event":"ping"}` 塞进业务通道：注释行不参与帧编解码，客户端与业务层都不必知道它的存在。

**载荷不含收件人**（D1）；客户端收到即拉未读。

### 4.4 分层：广播器在 svc、桥接在 logic、handler 补两处

生成的 handler（`sse_handler.tpl`）已经把「channel → SSE 帧」这段做完了（channel(16) + goroutine + `data:` + Flush + `ctx.Done()` 清理）。**不需要自己写帧循环，也不改模板**；handler 只手工补两处（goctl 重生成会跳过已存在的文件，改动安全）：

| 层 | 职责 |
|---|---|
| `common/sse` | **泛型广播器 `Broker[T]`**：每频道一实例，多订阅者共享事件流；注销即关通道（写锁与 Publish 的读锁互斥，不会 send on closed）、`Len()`、`Close()`。不缓存"最近一次值"——本项目的推送是信号而非快照，客户端连上后回查权威数据 |
| `svc`（`service_context.go`） | 建 `sse.NewBroker[notifyx.Event]()` 并启动 `sse.Subscriber`（Redis 订阅，照抄 `trace_enforcer.go:121-136` 的带重连循环）。`Shutdown()` 停订阅 + 关通道 |
| `common/sse` 的 `Subscriber` | Redis channel → 解析 → 投进广播器。订阅是进程级一份 |
| `logic`（生成的 `NotifyStream`） | 一行适配器：`sse.Bridge(l.ctx, l.svcCtx.NotifyBroker, client)` |
| `common/sse` 的 `Bridge` | 桥接：订阅广播器 → 转成 `types.NotifyStreamEvent` 写 `client`；发送纳入 ctx 选择，避免客户端断开后阻塞漏 goroutine |
| `handler`（生成后手工补两处） | ① 首行 `X-Accel-Buffering: no`；② 主循环加心跳分支，每 15s 写 SSE 注释行 `: ping` |

**为什么 broadcaster 必须在 svc 而不是 logic**：每个 SSE 请求是一次 handler 调用、一个独立 logic 实例，而 Redis 只有一条订阅流——订阅必须**整个进程一份**，再扇出到各个连接。放在 logic 里就是每连接一次订阅。

**为什么桥接与订阅器放在 `common/sse` 而非 logic**：logic 必须导入 `svc`，而导入 svc 会把整套 rpc client 拉进测试二进制，该仓库里 proto 重复注册会直接 panic（既有约束，`permissionx`/`tracelogx` 的测试同样避开 svc）。这条管道只依赖事件源接口与 push 帧类型，因此可测。

**连接数不设硬上限**（修正原稿的"200 + 503"）：超限若在 `logic` 里拒绝，客户端拿到的是**一个立刻关闭的空流**，而不是 503 信封——因为此时 `rest.WithSSE()` 已经接管了响应头、信封已不可能。要拿到信封只能把限制前移到**中间件**（在 handler 之前，可走 `responsex`）。admin 后台并发连接是个位数，本次不设；若日后要硬上限，按 `middlewarex.NewRateLimitMiddleware` 的模式加一个中间件，并在组里声明。

**连接管理**：Hub 内用 mutex + map 记连接；fan-out 时**非阻塞写入**每个 channel，缓冲满即丢弃（慢客户端不得拖垮服务）。

**关闭**：`ServiceContext.Shutdown()` 停订阅并关闭所有连接通道，`admin.go` 里 `defer ctx.Shutdown()`。**注意**：STOMP hub 的 `Shutdown` 在本仓库从未被调用（既有遗漏），本次只接了通知推送这条。
