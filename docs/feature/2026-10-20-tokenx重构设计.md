# tokenx 重构实现方案（v3.1）

> 日期：2026-10-21
> 范围：`blog-cloud/infra/tokenx`、`cmd/api/app`、`cmd/api/admin`
> 定位：**实现方案，设计决策不在本文重复**。v3.1 已落地，以代码为唯一真相。
> 本文取代 v2/v3。v3.1 重点修正 refresh 重放 family 解析、grace 原子性、设备标识来源、错误映射与测试边界。
>
> **实施偏移（2026-10-21）**：admin access 由 ES256 改为 HS256，移除 KeySet、`kid`、PEM 公钥加载与 ES256 codec；grace 默认开启、窗口固定为 30 秒，密钥由旧 refresh token 派生，不再需要 `GraceKey` 配置，`GraceCipher` 不对外暴露；`Audience`/`AuthMethod`/`Metadata` 已移除，`ClientID` 保留。下文涉及这些内容的描述按此偏移理解，代码为唯一真相。

## 一、已确认决策

1. **app：Web SPA 直接 Bearer，不使用 BFF**
   - access：opaque reference token，`at_` + 43 字符，共 **46**；
   - refresh：opaque reference token，`rt_` + 43 字符，共 **46**；
   - access 只存内存；refresh 只放 `HttpOnly + Secure + SameSite` Cookie；
   - 不使用 localStorage/sessionStorage 存 token；
   - `MultiPoint` 多端登录。
2. **admin：BFF + HttpOnly Cookie**
   - 浏览器只拿 BFF 会话 Cookie，BFF 服务端持有 access/refresh；
   - access：JWT **ES256**，`kid` + 公钥/JWKS，约 494 字符；
   - refresh：opaque `rt_` 46 字符；
   - `SinglePoint` 单点登录。
3. **未来原生 App**：Authorization Code + PKCE，access 内存，refresh Keychain/Keystore，Bearer；不走 Cookie。
4. **access TTL = 120 分钟**（产品选择，非 OAuth BCP 默认建议值）。
5. **refresh 生命周期**：idle 7 天、absolute 30 天、rotation grace 30 秒。
6. **refresh 重放**：grace 外重放 → 撤销整个 token family；grace 内返回缓存的轮换结果，避免并发误杀。
   - `Rotate` 必须在同一次原子操作里写 session/token/family/rotation/grace；
   - 重放时先 `LookupRotation` 拿到 family 与可选 grace，再决定返回还是撤销。
7. **存储模型**：per-session key + TTL + session/device/token/family/rotation 索引；不再使用用户 hash + expiries ZSET。
8. **token 前缀**：`at_` / `rt_`，不加 `blog` 前缀。
9. **生产 access token 只走 `Authorization: Bearer`**；不使用自定义 token 请求头；自定义头只承载 `X-Device-Id`、`X-Request-Id` 等辅助元数据。
10. **自研边界**：只自研 token 信封/claims，底层使用标准 HMAC-SHA256 / ECDSA / Ed25519；不发明密码学算法。自研封装作为可选 codec，生产默认不启用。
11. **DPoP**：暂不进生产，保留为可选/测试能力；未来 admin 高安全阶段再引入。
12. **多样性**：生产 app opaque、admin JWT ES256；可选 codec（HS256/HMAC/PASETO）由 `_test.go` 矩阵覆盖，不新增 `cmd/` 程序。
13. **设备标识来源**：`IssueRequest.DeviceID` / `RefreshRequest.DeviceID` 必须来自身份层的可信设备标识（服务端签发的设备令牌/Cookie），不直接信任客户端 `X-Device-Id` 头；该头只作辅助元数据。
14. **实现范围**：本文实现 tokenx 核心与 API 侧接入；admin BFF 与 app 前端的 token 存储/刷新/CSRF/PKCE 改造属于独立 feature 计划，不在本文伪装成已覆盖。

## 二、为什么这样设计

### 2.1 v1/v2 的问题

| 版本 | 问题 |
|---|---|
| v1 | opaque 144 字符（uid+sid+secret），形态冗长；自定义 HMAC 非标准 |
| v2 | 43 字符无前缀；admin HS256 共享密钥；refresh 滑动 TTL 可无限续期；Redis 用户 hash + expiries ZSET 清理复杂 |

### 2.2 大厂与规范对照

| 来源 | 关键做法 |
|---|---|
| Google | access 多为 opaque；ID token 才是 JWT；STS 文档给出 12288 字节上限 |
| Microsoft Entra | JWT RS256；实测 926–1354 字符 |
| Auth0 | JWT/opaque 都支持；refresh rotation + reuse detection + absolute/idle lifetime |
| Okta | JWT/opaque；refresh rotation + 30 秒 grace + family revoke |
| Keycloak | JWT 默认 RS256；refresh 可配置 revoke/max reuse；离线 session 有 idle/max |
| GitHub/Slack/Shopify | opaque token + 前缀；不依赖固定长度 |
| OAuth 2.1 / RFC 9700 | PKCE；refresh rotation + reuse detection；sender-constrained 可选 |
| RFC 9068 | JWT access token：`typ=at+jwt`、`iss`、`aud`、`exp`、`iat`、`jti` |
| RFC 8252 | 原生 App：PKCE、系统浏览器、无 client secret |
| BFF 规范 | 浏览器只拿 HttpOnly Cookie，服务端持有 token |

参考：[Auth0 Rotation](https://auth0.com/docs/secure/tokens/refresh-tokens/refresh-token-rotation)、[Auth0 Expiration](https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-expiration)、[Okta Refresh](https://developer.okta.com/docs/guides/refresh-tokens/main/)、[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700)、[RFC 9068](https://www.rfc-editor.org/rfc/rfc9068)、[RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)、[BFF Draft](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-browser-based-apps)。

## 三、目标与非目标

### 目标

- app 使用短小的 opaque reference token；admin 使用标准 ES256 JWT；
- 浏览器端不把 token 放进 localStorage；
- refresh rotation + family reuse detection + idle/absolute lifetime；
- 立即撤销、单点/多端、设备绑定；
- 存储模型简单、可自动过期、便于 Redis Cluster；
- 保持技术多样性：opaque vs ES256、BFF vs SPA、MultiPoint vs SinglePoint、可选 codec；
- 测试覆盖所有组合，不新增 `cmd/` 诊断程序。

### 非目标

- 不做纯无状态 JWT；
- 不把角色/权限塞进 token；
- 不发明密码学算法；
- 不在生产运行时随机切换 codec；
- 不允许多个会话共享同一 device；
- 当前不引入 DPoP/mTLS 到生产（保留可选/测试）。

## 六、客户端形态与 token 存储

### 6.1 app：Web SPA，不用 BFF

浏览器直接 Bearer 调用 app API；这是为了保留 SPA 架构的简单性与技术多样性，但必须满足以下条件：

- access token **只存内存**，刷新页面后通过 refresh Cookie 静默续期；
- refresh token **只放 HttpOnly + Secure + SameSite Cookie**，JS 不可读；
- 禁止 localStorage/sessionStorage/IndexedDB 存 token；
- refresh 端点：POST、校验 Origin/Referer、CSRF token（或 SameSite=Strict）；
- 严格 CSP、禁止 inline script、第三方脚本使用 SRI；
- OAuth 2.1 Authorization Code + PKCE，精确 redirect URI，state/nonce；
- access TTL 120 分钟的安全窗口依赖 CSP 与撤销；若风险不可接受，可后续降低 TTL；
- 登出删除 Cookie + 撤销 session。

**明确的风险**：无 BFF 时 access token 会暴露给 JS；XSS 可以读取 access token 并外传。HttpOnly refresh Cookie 保护 refresh token，但不能阻止 XSS 以用户身份发请求。BFF 能进一步保护 token 不被读取，但本项目选择 app 不走 BFF。

### 6.2 admin：BFF + HttpOnly Cookie

- 浏览器只拿 `__Host-bff_session` Cookie（HttpOnly、Secure、SameSite=Lax/Strict、Path=/）；
- BFF 服务端持有 access/refresh token，并负责刷新；
- BFF → admin API 使用 `Authorization: Bearer`；
- 需要 CSRF token 保护状态变更请求；
- BFF 可以是独立服务，也可以是网关内的一层；不新增测试用 `cmd/` 程序。

### 6.3 未来原生 App

- Authorization Code + PKCE；
- 系统浏览器/ASWebAuthenticationSession，不用嵌入式 WebView；
- access 内存，refresh Keychain/Keystore；
- Bearer 调用 API。

### 6.4 本文实现范围

- 本文实现 `infra/tokenx` 核心、app/admin 的 svc、鉴权中间件与刷新/登出调用点；
- admin BFF 与 app 前端的 PKCE、静默刷新、CSRF、CSP、Cookie 行为属于独立 feature 计划；
- `DeviceID` 由 app/admin 的认证中间件从**身份层可信设备标识**解析后传入 tokenx；`X-Device-Id` 仅作辅助元数据，不直接作为 `Issue`/`Refresh` 的设备来源；
- 若 BFF/前端未同步上线，app/admin 不得以“token 已支持”为由跳过安全改造。

## 七、总体架构

```
app Web SPA ── Bearer + refresh Cookie ──► app API
admin Web SPA ── HttpOnly Cookie ──► BFF ── Bearer ──► admin API

app API / admin API / BFF
        │
        ▼
tokenx.Service
        │
        ├── Codec（opaque / JWT ES256 / 可选 HS256、HMAC、PASETO）
        │
        └── SessionStore
              ├── per-session key + TTL
              ├── device / token / family 索引
              └── rotation tombstone + grace cache
```

职责边界：

- `Service`：签发、校验、刷新、撤销、会话列表；
- `Codec`：token 生成/解析/签名；
- `SessionStore`：session、token 索引、family、轮换墓碑；
- BFF：admin 浏览器侧的 token 持有与转发；
- app SPA：直接持有 access，refresh 只走 HttpOnly Cookie。

## 八、对外接口

```go
type Service interface {
    Issue(ctx context.Context, req IssueRequest) (*TokenPair, error)
    Validate(ctx context.Context, accessToken string) (*Claims, error)
    Refresh(ctx context.Context, req RefreshRequest) (*TokenPair, error)

    Revoke(ctx context.Context, userID, sessionID string) error
    RevokeDevice(ctx context.Context, userID, deviceID string) error
    RevokeAll(ctx context.Context, userID string) error

    ListSessions(ctx context.Context, userID string) ([]SessionInfo, error)
}

type IssueRequest struct {
    UserID   string
    DeviceID string
    Issuer   string
    ClientID string
}

type RefreshRequest struct {
    RefreshToken string
    UserID       string
    DeviceID     string
}

type TokenPair struct {
    UserID           string
    DeviceID         string
    AccessToken      string
    RefreshToken     string
    SessionID        string
    AccessExpiresAt  time.Time
    AccessExpiresIn  int64
    RefreshExpiresAt time.Time
    RefreshExpiresIn int64
}

type SessionInfo struct {
    ID               string
    UserID           string
    DeviceID         string
    ClientID         string
    CreatedAt        time.Time
    LastUsedAt       time.Time
    AccessExpiresAt  time.Time
    RefreshExpiresAt time.Time
    AbsoluteExpiresAt time.Time
}

type Claims struct {
    UserID    string
    DeviceID  string
    SessionID string
    Issuer    string
    TokenID   string // JWT jti；opaque 为空
    Kind      TokenKind
    IssuedAt  time.Time
    ExpiresAt time.Time
}
```

`RefreshRequest` 必须携带当前请求的 `UserID`/`DeviceID`，并与 token/session 比对。

```go
type Config struct {
    AccessCodec        Codec
    RefreshCodec       Codec
    Store              SessionStore
    LoginMode          LoginMode
    AccessTTL          time.Duration // 120m
    RefreshIdleTTL     time.Duration // 7d
    RefreshAbsoluteTTL time.Duration // 30d
    Clock              Clock
}

// KeySet 提供当前签名私钥与按 kid 取公钥的能力。
type KeySet interface {
    SigningKey(ctx context.Context) (kid string, key *ecdsa.PrivateKey, err error)
    VerificationKey(ctx context.Context, kid string) (*ecdsa.PublicKey, error)
}
```

### 8.1 错误映射

tokenx 只返回语义错误，HTTP/gRPC 映射集中在 API 层：

| tokenx 错误 | HTTP | gRPC | 说明 |
|---|---|---|---|
| `ErrTokenEmpty` / `ErrTokenInvalid` / `ErrCodecMismatch` | 401 UNAUTHENTICATED | Unauthenticated | 令牌无效 |
| `ErrTokenExpired` | 401 LOGIN_EXPIRED | Unauthenticated | access 过期 |
| `ErrSessionNotFound` | 401 UNAUTHENTICATED | Unauthenticated | 会话已撤销/不存在 |
| `ErrRefreshReused` | 401 LOGIN_EXPIRED / invalid_grant | Unauthenticated | 刷新重放或 family 已撤销 |
| 存储/加密错误 | 500 INTERNAL_ERROR | Internal | 不向客户端透出细节 |

### 8.2 密钥与 grace 加密

- **ES256 KeySet**：
  - 私钥 + 公钥 PEM 从配置/密钥文件加载，至少支持当前与上一把；
  - `kid` 写入 JWT header；未知 `kid` 直接拒绝；
  - 轮换顺序：加入新公钥 → 发布/加载 → 切换签名私钥 → 保留旧公钥至最长 access TTL 之后再移除；
  - 可选暴露 JWKS；当前至少支持本地公钥文件。
- **grace 密钥与加密**：
  - grace 默认开启，无需额外密钥配置；
  - 用旧 refresh token 经 HMAC-SHA256 派生密钥，再以 AES-GCM 加密 `TokenPair`；
  - 窗口固定为 `tokenx.GraceWindow`（30 秒）；
  - 不写日志、不进错误信息；不对外暴露 cipher 类型。
- **启动校验**：
  - admin 的 JWT 签名 secret 至少 32 字节；
  - opaque 模式不要求签名密钥。

## 九、Codec 接口

```go
type Codec interface {
    Name() string
    Encode(ctx context.Context, claims Claims) (EncodedToken, error)
    Decode(ctx context.Context, raw string) (DecodedToken, error)
}

type EncodedToken struct {
    Value      string
    LookupHash string // opaque: SHA-256(kind:value)；JWT 为空
}

type DecodedToken struct {
    LookupHash string  // opaque
    Claims     *Claims // JWT
}
```

- Opaque：生成 `at_`/`rt_` + 43 字符随机串；`LookupHash` 用于查 session；
- JWT：ES256 签名 claims；`LookupHash` 为空；`Decode` 验签；
- `Name()` 写入 session，校验时比对，防止切换 codec 后旧 session 被错误接受。

### 9.1 Opaque codec

- 32 字节 `crypto/rand` → base64url，43 字符；
- access 前缀 `at_`，refresh 前缀 `rt_`，总长 46；
- 前缀必须与 `Claims.Kind` 一致；
- 不携带 uid/sid/claims；
- 服务端存哈希索引，不存明文。

### 9.2 JWT codec

- 生产 admin 使用 **ES256**（ECDSA P-256）；
- header：`alg=ES256`、`kid`、`typ=at+jwt`；
- claims：`iss`、`sub`、`sid`、`did`、`jti`、`iat`、`exp`；
- 不使用自定义 `use` claim；
- `jti` 使用 UUIDv7；
- 强制 `exp`、限定算法、30 秒 leeway；
- 校验后仍查 session（`sid`），撤销立即生效；
- 密钥轮换：`kid` + 当前/上一把公钥；未来可暴露 JWKS；
- HS256 保留为可选/测试，不进入生产 admin。

### 9.3 可选 codec

- `hmaccodec`：自定义信封 + 标准 HMAC-SHA256；
- `pasetocodec`：PASETO v4.local；
- JWT HS256；
- 只自研信封/claims，不发明密码学算法；
- 可选 codec 放在独立子包，核心 `tokenx` 不 import 它们；生产装配也不 import；
- 由契约测试 + `matrix_test.go` 覆盖；
- 可按需装配，生产默认不启用。

## 十、SessionStore 与存储

### 10.1 接口

```go
type SessionStore interface {
    Create(ctx context.Context, session Session, mode LoginMode) error

    GetBySession(ctx context.Context, userID, sessionID string) (Session, error)
    GetByTokenHash(ctx context.Context, tokenHash string) (Session, error)

    Rotate(ctx context.Context, old Session, next Session, opts RotateOptions) error
    LookupRotation(ctx context.Context, userID, oldRefreshHash string) (Rotation, bool, error)
    RevokeFamily(ctx context.Context, userID, familyID string) error

    Delete(ctx context.Context, userID, sessionID string) error
    DeleteByDevice(ctx context.Context, userID, deviceID string) error
    DeleteByUser(ctx context.Context, userID string) error

    ListByUser(ctx context.Context, userID string) ([]Session, error)
}

type Rotation struct {
    UserID       string
    FamilyID     string
    GracePayload []byte // GraceWindow 内有效；过期后为空
}

type RotateOptions struct {
    GracePayload []byte
    RotationTTL  time.Duration // 旧 refresh 剩余有效期
    GraceTTL     time.Duration // 固定为 tokenx.GraceWindow
}
```

语义：

- `Create`：
  - `MultiPoint`：删除同 user+device 的旧 session/token/family，再创建；
  - `SinglePoint`：删除该 user 的全部 session/token/family，再创建；
  - 原子完成。
- `GetBySession`：JWT access 用 `sid` 查 session；
- `GetByTokenHash`：opaque access/refresh 用哈希索引查 session；
- `Rotate`：
  - 一次 Lua 原子完成：删除旧 session/token、创建新 session/token、更新 family；
  - 写入 `rotation:{oldRefreshHash} -> familyID`（TTL = `RotationTTL`）；
  - 写入 `rotation-grace:{oldRefreshHash} -> gracePayload`（TTL = `GraceTTL`）；
  - `gracePayload` 由 Service 内部加密，Store 只见密文；
  - 不拆成“先 Rotate 再 SaveGrace”，避免崩溃窗口与并发歧义。
- `LookupRotation`：按旧 refresh 哈希返回 userID、familyID 与可选 grace；grace 过期后 `GracePayload` 为空。Service 必须校验 `Rotation.UserID == req.UserID`。
- `RevokeFamily`：校验 family 归属后，grace 外重放时撤销整个 family 的当前 session。
- `Delete*`：清理 session、token、device、family、rotation 索引；
- `ListByUser`：过滤过期/已删除 session。

### 10.2 内部记录

```go
type Session struct {
    ID       string
    UserID   string
    DeviceID string
    FamilyID string

    ClientID string
    Issuer   string

    AccessCodec  string
    RefreshCodec string

    AccessLookupHash  string // opaque access 的查找哈希；JWT access 为空
    RefreshLookupHash string // opaque refresh 的查找哈希
    RefreshTokenHash  string // 所有方案都存

    CreatedAt         time.Time
    LastUsedAt        time.Time
    AccessExpiresAt   time.Time
    RefreshExpiresAt  time.Time
    AbsoluteExpiresAt time.Time
}
```

### 10.3 Redis 布局

```
{tokenx}:session:{sid}                 STRING JSON EX
{tokenx}:user:{uid}:sessions           SET sid EX
{tokenx}:user:{uid}:device:{did}       STRING sid EX
{tokenx}:token:{sha256}                STRING "kind\tuid\tsid" EX
{tokenx}:family:{fid}                  STRING "uid\tsid" EX
{tokenx}:rotation:{sha256}             STRING "uid\tfid" EX
{tokenx}:rotation-grace:{sha256}       STRING encrypted pair EX
```

- 每个 session 独立 TTL，不需要 expiries ZSET；
- 单点登录：读 user set，删除所有 session/token/family，再创建；
- `family` 用于重放时撤销整个登录链；
- `rotation` 与 `rotation-grace` 由 `Rotate` 在同一次 Lua 中写入；
- `rotation-grace` 只保留 30 秒，避免并发刷新误杀；
- 所有 key 使用 `{tokenx}` hash tag，保证 Lua 在同 slot 执行；热点集中但博客规模可接受；
- Redis Cluster 下仍需保持所有 key 同 slot，或将来引入 token shard。

### 10.4 内存实现

`memstore` 实现同一套语义：session、token 索引、family、grace、device；测试不依赖 Redis。

## 十一、核心流程

### 11.1 Issue

1. 校验 `UserID`，`DeviceID` 归一化为 `default`；
2. 生成 `sessionID` 与 `familyID`（UUIDv7）；
3. 构造 access/refresh claims；
4. 按配置生成 token：
   - app：opaque `at_` / `rt_`；
   - admin：JWT ES256 access + opaque `rt_` refresh；
5. 计算 `AbsoluteExpiresAt = now + 30d`，`RefreshExpiresAt = min(now + 7d, AbsoluteExpiresAt)`；
6. `store.Create(session, loginMode)`；
7. 返回 `TokenPair`。

### 11.2 Validate

1. 按 access codec 解码：
   - opaque：哈希 → `GetByTokenHash`；
   - JWT：ES256 验签 → `GetBySession`；
2. 校验 session 未过期、codec 名称匹配、token 类型为 access；
3. JWT 校验 claims 与 session 的 uid/device/sid/issuer 一致；
4. 返回 `Claims`。

### 11.3 Refresh

1. 校验 `RefreshRequest`，DeviceID 归一化；
2. 解码 refresh，计算 token 哈希：
   - opaque：`LookupHash`；
3. `GetByTokenHash(hash)`：
   - **找到** → 进入正常轮换；
   - **未找到** → `LookupRotation(userID, hash)`：
     - `Rotation.UserID != req.UserID` → `ErrTokenInvalid`，不做任何撤销；
     - `GracePayload` 非空 → 内部解密 grace payload，校验 pair 的 UserID/DeviceID 与请求一致，返回缓存 pair，不撤销 family；
     - 只有 `FamilyID` → `RevokeFamily` 撤销整个 family，返回 `ErrRefreshReused`；
     - 都没有 → 返回 `ErrRefreshReused`。
4. 正常轮换：
   - 校验 session 未过期、refresh codec 匹配、UserID/DeviceID 一致；
   - 校验 idle/absolute：`now > LastUsedAt + 7d` 或 `now > AbsoluteExpiresAt` → `ErrTokenExpired`；
   - 生成新 session/token，继承 family；更新 `LastUsedAt`、`RefreshExpiresAt = min(now+idle, AbsoluteExpiresAt)`；
   - 用旧 refresh token 派生密钥加密新 pair，得到 `gracePayload`；
   - `rotationTTL = old.RefreshExpiresAt - now`；`graceTTL = tokenx.GraceWindow`；
   - `store.Rotate(old, next, RotateOptions{GracePayload: gracePayload, RotationTTL: rotationTTL, GraceTTL: graceTTL})` 一次原子完成 session/token/family/rotation/grace；
   - 若 `Rotate` 返回 `ErrSessionNotFound`（并发竞争），走与第 3 步“未找到”相同的 `LookupRotation` 分支；
5. 返回新 pair。

### 11.4 Revoke

- `Revoke(userID, sessionID)`：删除单会话及索引；
- `RevokeDevice(userID, deviceID)`：删除该设备会话；
- `RevokeAll(userID)`：删除该用户全部会话与索引。

## 十二、登录模式与设备绑定

```go
type LoginMode int

const (
    MultiPoint LoginMode = iota
    SinglePoint
)
```

- 不变式：同一 user + device 同时只保留一个活跃会话；
- `MultiPoint`：不同设备并存；同设备重新登录替换旧会话；
- `SinglePoint`：新登录撤销该用户全部旧会话；
- **DeviceID 来源**：身份层从服务端签发的设备令牌/Cookie 解析出的可信设备标识；`X-Device-Id` 只作辅助元数据，不直接作为 `Issue`/`Refresh` 的设备来源；
- access：中间件校验 `NormalizeDeviceID(可信请求设备) == claims.DeviceID`；
- refresh：`RefreshRequest.DeviceID` 使用同一可信来源，与 session 的 device 比对；
- 设备 ID 不是秘密，设备绑定是 defense-in-depth；强约束需要 DPoP/mTLS。

## 十三、长度与传输约束

| 项 | 预算 | 说明 |
|---|---:|---|
| app access | 46（`at_` + 43） | 32 字节熵 |
| app/admin refresh | 46（`rt_` + 43） | 32 字节熵 |
| admin access | ~494（ES256） | 短 claim 名；P-256 签名 |
| HTTP header | 8KB/字段 | Nginx `large_client_header_buffers 4 8k` |
| Cookie | 4KB/name+value | RFC 6265 / 6265bis |
| DB/Redis 字段 | ≥512 字符 | 不按固定长度建表 |

传输：

- app SPA → app API：`Authorization: Bearer <at_...>`；
- admin SPA → BFF：HttpOnly Cookie；
- BFF → admin API：`Authorization: Bearer <at_...>`；
- refresh：请求体 `refresh_token` 或 HttpOnly Cookie，不走 Bearer；
- 不使用自定义 token 请求头；
- access token 不放 URL、不写日志；
- 响应 OAuth 风格：`access_token`、`token_type=Bearer`、`expires_in`、`refresh_token`、`refresh_expires_in`。

## 十七、风险与权衡

| 风险 | 说明 | 应对 |
|---|---|---|
| app 无 BFF | access token 暴露给 JS，XSS 可外传 | access 内存、refresh HttpOnly、CSP、CSRF、短 TTL（当前 120m 偏长） |
| admin BFF 复杂度 | 多一层服务/会话/CSRF | 只给 admin 上；BFF 可复用网关 |
| 120m access TTL | 比 OAuth BCP 建议长 | 有 session 立即撤销；CSP/监控；后续可降 |
| family grace 缓存 | 需要加密存储短期 token pair | 30s TTL；服务端 AES-GCM；不落日志；Rotate 原子写入 |
| family 解析 | 重放时只有旧 refresh 哈希 | `LookupRotation` 返回 familyID + grace；再决定返回或撤销 |
| ES256 密钥管理 | 需要生成/轮换/分发公钥 | `kid` + key set；未来 JWKS；旧公钥保留至最长 access TTL |
| BFF/前端未同步 | token 支持不等于客户端安全改造完成 | BFF/前端独立 feature 计划；未上线前不得跳过 CSP/CSRF/PKCE |
| Redis Cluster | 所有 key 同 slot | 使用 `{tokenx}` hash tag；热点可接受 |
| refresh 重放 | 旧 token 被重复使用 | rotation + family revoke + grace |
| 可选 codec | 非标准格式/依赖 | 默认不启用；契约/矩阵测试 |
