# api/admin 整理方案

> 日期：2026-09-11
> 范围：`protocol/api/admin` + `protocol/api/app`（同步）
> 状态：**已实施**（api/admin 当前模块结构已与 §六「改动后模块对照」一致）
> 配套：rpc 层分组于同日定案，见 `docs/design/02-BLOG-数据与接口.md` §2

## 一、判据

### 1.1 三类差异，处置不同

| 类型 | 含义 | 处置 |
|---|---|---|
| **跨层不一致** | 同一资源，api 与 rpc 分属不同模块 | **本次修正** |
| **命名分叉** | 同一模块，两层叫法不同 | **本次跟随** |
| **粒度差异** | api 聚合得更粗（如 `account` 含 auth/guest/me/user） | 保留，不改 |

依据：`docs/design/02-BLOG-数据与接口.md` §1.1 明确"两者的模块划分允许且应当不同"——但该原则说的是**划分**，不豁免**同一资源被分到不同模块**，也不构成"改名时漏掉一层"的理由。

### 1.2 一个经验事实（决定了本次改动的必要性）

api 模块名与 rpc 模块名**几乎一一对应**：

| api | rpc | 关系 |
|---|---|---|
| `content` / `discussion` / `notification` / `syslog` | 同名 | 完全相同 |
| `permission` / `resource` / `website` / `social` | 同名（rpc 于同日改名/解散） | 完全相同 |
| `account` | `user` + `auth` + `guest` | 唯一的粒度差异 |
| `common` | 无 | 无对应 |

**结论：api 层实际是跟随 rpc 的模块划分，而非按 UI 页面切。** 因此跨层不一致与命名分叉都是真问题。

## 二、改动清单

### 2.1 统计模块独立成 `stats.api`

| 项 | 值 |
|---|---|
| 现状 | `website.api` 的 `website/stats` 组，4 个 handler |
| 迁入 | 新增 `GetSystemState`（原在 `website/config`） |
| 目标 | 新建 **`stats.api`**，`group: stats/overview`，共 5 个 handler |
| URL | 全部不变（`/stats/*`、`/admin/get_system_state`） |

**理由**：
- 统计与"站点配置 / 页面"无概念关系
- `GetSystemState`（`Server{Os,Cpu,Ram,Disk}`）原挤在 `website/config` 里，与站点配置无关；它与 `GetStatsDashboard` 同属首页仪表盘的数据源

**模块名取 `stats` 而非 rpc 的 `stats`**：这是一处**有意保留的分叉**。api 侧的文件名、`group:` 前缀、URL 首段（`/stats/*`）三者据此自洽；rpc 侧仍为 `stats`。依据 02 §1.1，两层命名允许不同。

### 2.2 `social` 解散

| 资源 | 现状 | 目标 | 依据 |
|---|---|---|---|
| 友链 Friend | `social/friend`（4 handler，URL `/friend/*`） | **`site/friend`**，并入 `site.api` | rpc 定案：友链是管理员维护的站点呈现层，与 Config / Page 同生命周期 |
| 说说 Talk | `social/talk`（5 handler，URL `/talk/*`） | **`discussion/talk`**，并入 `discussion.api` | rpc 定案：与评论、留言同属"用户产出 + 需审核"的讨论内容 |

- `social.api` 删除
- URL 不变 —— `/friend/*`、`/talk/*` 本身不带模块前缀，前端无感

### 2.3 三项改名跟随 rpc

| 现名 | 目标名 | 理由 |
|---|---|---|
| `permission` | **`access`** | 该模块的 group 只有 `api` / `menu` / `role`，**没有 permission 实体**——"名实相符"在 api 层同样成立。社区调研结论：`permissions` 通常命名**资源/端点**，`access` 命名**更宽的模块**（Medusa 即模块 `access` + 资源 `permissions`） |
| `resource` | **`media`** | "资源"在 REST 语境下指代过泛；该模块只装 `album` / `photo` |
| `website` | **`site`** | 与模块名「站点」一致；友链并入后该名不再只指配置与页面 |

**注意 `permission` → `access` 的调研结论**（本轮专项）：
- 实例：Medusa 模块 `access` / 资源 `permissions`；Strapi 资源 `permissions`；Shopware 用 ACL；Shopsys、Kuadrant 用 RBAC 作伞名
- **无反例支持 `permission`** —— RuoYi 用 `system`、gin-vue-admin 不命名模块，中文后台生态没有一个用 `permission` 命名这个模块
- 备选 `rbac` 自解释但命名的是**模型**而非领域能力，且会与 rpc 分叉，未采纳

### 2.4 `account` 多块合并

| group | handler | 现分布 | 目标 |
|---|---|---|---|
| `account/auth` | 12 | **3 个 `@server` 块** | 1 块 |
| `account/guest` | 2 | **2 个 `@server` 块** | 1 块 |

其余 26 个组均为一组一块。`group:` 不变，生成目录不变，只影响 `routes.go` 注册顺序。

> **顺带需确认**：`account/guest` 的 `GetGuest` **无任何中间件**，而同资源的 `QueryGuestList` 要全套 `AdminAuth,Permission,OperationLog`。若是有意（如供第三方嵌入），建议在 `@doc` 写明；若无意，是权限缺口。

### 2.5 `website/config` 的 URL 前缀（待前端协同）

该组 5 个接口全用 `/admin/*`，而其余 26 组的 URL 首段均为**资源名**（`/page/*`、`/friend/*`、`/role/*` …）。`admin` 是服务名，不是资源名。

**这是破坏性变更** —— 这些 URL 前端在用。**单独排期，不与本次混做。**

## 三、契约质量（独立排期，不并入本次）

### 3.1 `PageResult.List` 类型化 —— 影响面最大的一项

```go
// types.api
PageResult {
    Page     int64       `json:"page"`
    PageSize int64       `json:"page_size"`
    Total    int64       `json:"total"`
    List     interface{} `json:"list"`      // ← 列表元素类型丢失
}
```

- **后果**：**所有分页接口**的列表元素类型在生成物中丢失，前端只能自行再声明一遍
- **反例**：`common.api` 的 `QueryFileListResp` 已是类型化列表（`List []*FileInfoVO`）—— 两种写法在同一个文件集里并存
- **成本**：覆盖全部分页接口，影响生成物与前端类型定义

### 3.2 `validate:` 补齐策略

全仓仅 2 处使用（`ResetUserPasswordReq.NewPassword`、`UpdateUserStatusReq.Status`），其余 130+ 个请求类型无一携带校验标签。

**先决问题**：是否需要？前端已做校验时后端仍应兜底。若需要，先定策略（写操作的必填 / 枚举 / 长度）再分批补。

### 3.3 Guest 相关类型三合一

`GuestInfoVO`（types.api）、`GuestItem`、`GetGuestResp` 三者字段几乎完全重叠。

### 3.4 `update_xxx_delete` 命名

`UpdateArticleDelete` / `UpdateAlbumDelete` / `UpdatePhotoDelete` 实为"切换软删除状态"，命名读起来像"更新删除"（审查报告 #9 已记录待议）。

## 四、`app` 侧同步

`protocol/api/app` 有对应的 `social`（friend / talk）与 `common`，且 `website` 只有 `config` / `page`（无 stats）：

| 文件 | app 侧 group |
|---|---|
| `app/social.api` | `social/friend`、`social/talk` |
| `app/website.api` | `website/config`、`website/page` |
| `app/resource.api` | `resource/album` |
| `app/permission.api` | 无（读者端不做 RBAC） |

**处置**：与 admin 同批，按同一规则改（2.2 / 2.3 项）。app 侧无 `stats` / `stats`，故 2.1 不涉及。

## 七、风险与陷阱

| # | 陷阱 | 说明 |
|---|---|---|
| 1 | **`group:` 改名会留下孤儿目录** | goctl 不改名已存在的 `handler/<module>/`，重生成会新旧并存。与 proto 侧同一问题（审查报告 §7.1 的 `notify_content` 孤儿） |
| 2 | **`generate.sh` 会先格式化 `.api`** | 脚本第一步即 `goctl api format -dir ./`，手工对齐会被覆盖 —— 期望行为，不必对抗 |
| 3 | **URL 与 `group:` 无关** | 2.1–2.3 全部**不动 URL**，前端无感；只有 2.5 动 URL |
| 4 | **`--type-group`** | 生成时类型按 group 分文件，group 变更会改变生成物布局 |
| 5 | **本方案只改 `protocol`** | 按既定范围，`blog-cloud` 的代码与生成物不动。落地后 api 契约与生成代码的脱节会**再扩大一层**（与 proto 侧同批待迁） |
| 6 | **`permission` → `access` 的权限数据** | `t_api` 表按 URL + method 记录接口，模块名不进权限判定 —— 改名**不影响已有授权数据** |
