# 通知体系重构方案

> 日期：2026-10-29
> 范围：`protocol/sql/`、`protocol/proto/`、`protocol/api/`、`blog-cloud/**`、`blog-app/**`、`blog-admin/**`
> 定位：**改造方案，日期快照**。落地后代码与 `blog.sql` 为唯一真相，本文不逐字追更。
> 依据：[《通知》](../design/33-通知.md) 的决策 D1–D10。

---

## 一、背景与目标

现有「通知」只服务运营公告：管理员写公告 → 发布 → 扇出成站内信记录。读者端没有任何通知接口，业务事件（评论回复、点赞）不产生通知，用户无法退订，同一对象被多次互动会产生多条重复。

本次按《通知》重建，不沿用旧的表结构：

- 业务事件与公告共用一条管线、一个收件箱、一套偏好。
- 按事件 / 条目 / 投递三层建模，事件表兼作扇出工作队列。
- 聚合与未读数都是读取时投影，不存折叠计数。
- 文案移入代码，服务端渲染后下发给客户端。
- 删除模板表与模板管理。
- 新增读者端收件箱、未读数、已读、删除、偏好、退订与实时信号。

**不考虑兼容旧数据**：旧表直接删除重建，不写数据迁移。

## 二、影响面

| 面 | 变化 |
|---|---|

| 前端 | blog-app 新增通知中心与偏好页；blog-admin 删除模板页与 inbox 写操作、调整公告与投递页 |

## 三、数据表

完整 DDL 落在 `protocol/sql/blog.sql`，此处只记职责与必须存在的约束。

| 表 | 职责 | 必须存在的约束 |
|---|---|---|
| `t_notification_event` | 一次通知意图；扇出工作单元（状态 + 受众总数 + 游标 + 受众） | `(status, updated_at)` 支撑兜底扫描；`(object_type, object_id)` 支撑删除清理 |
| `t_notification` | 收件箱条目，每个收件人一行，引用事件。列含场景、对象引用、`group_key`、`dedupe_key`、已读时间；**不存触发者**，它只在事件上 | 见下节 |
| `t_notification_delivery` | 每条目每渠道一行，保存最近一次尝试与回执，重试次数累加 | `(notification_id, channel)` 唯一；`(status, next_retry_at)` 支撑重试扫描；`(status, updated_at)` 支撑保留期清理 |
| `t_notification_preference` | 偏好分组 × 渠道的退订开关 | `(user_id, pref_group, channel)` 唯一 —— 列名不用 `group`，它是保留字 |
| `t_announcement` | 公告内容：草稿、编辑、定向、撤回 | 沿用现有公告表的业务约束，表名与列随新模型重建 |

**事件载荷的两种形态**：业务事件在载荷里存渲染所需的业务快照，是这批数据的唯一副本；公告事件在载荷里只存内容引用，正文以 `t_announcement` 为准，因此不复制。

**受众总数在扇出开始时物化**：`all` 取那一刻的正常用户数，`user_ids` 取列表长度，之后不再更新。没有这个分母，管理端的「扇出进度」只能显示一个裸游标，算不出百分比；运行中用户数会变，所以必须定在开始时刻。

### 3.1 条目的分组键与索引

条目在写入时物化两个键，都在插入前可算出、不需要回写：

- `group_key`：展示分组的归并键。按对象分组写 `场景 + 对象类型 + 对象标识`，不分组写 `场景 + 事件标识`。
- `dedupe_key`：幂等键。可分组场景写 `group_key + 触发者`，不可分组场景与 `group_key` 相同。

| 索引 | 支撑 |
|---|---|
| `(recipient_id, dedupe_key)` 唯一 | 扇出幂等，以及同一人对同一对象反复互动的去重 |
| `(recipient_id, scene, group_key, created_at)` | 分组合页、组大小 |
| `(recipient_id, read_at, scene, group_key)` | 未读分组数，按偏好分组分别计数时也能走索引 |
| `(scene, read_at, created_at)` | 保留期清理 —— 清理任务不知道收件人，必须有一条以场景打头的索引 |
| `(event_id)` | 事件行清理 |
| `(object_type, object_id)` | 对象删除清理 |

**按偏好分组过滤时始终展开成场景集合**（默认全部场景），分页查询总带 `scene IN (...)`，`(recipient_id, scene, group_key, created_at)` 对有无过滤都成立。不能对 `group_key` 做前缀匹配 —— 前缀匹配在组合索引上会退化成扫描。

**键长要卡住索引上限**：`dedupe_key` 由场景、对象类型、对象标识与触发者拼成，列宽按最坏情况取到 191 字符（utf8mb4 下与收件人列合起来仍在 InnoDB 单索引 3072 字节以内）。拼装时必须截断并保证唯一性不受影响 —— 对象标识与触发者都是定长数字或固定长度 ID。

**公告条目渲染要再连一次内容表**：条目只存内容引用，列表渲染时按 `t_announcement` 取正文。这是 D6「正文只存一份」的代价，查询形态里要为这一层预留关联。

**为什么必须物化组键**：不物化就得在同一句 SQL 里对「按对象分组」与「不分组」用 `CASE` 拼出两种键，索引命不中，这是本方案唯一会随数据量退化成全表扫描的读路径。

分组合页的查询形态：先按 `group_key` 聚合出 `MAX(created_at)`、`COUNT(*)` 与未读标记，`ORDER BY MAX(created_at) DESC, group_key DESC` 取一页组 —— 二级排序键保证同一时间戳下翻页不重复不漏；再按这页组键取最新触发者与事件载荷用于渲染。组数与条目数分离，组大小不受分页影响。

**不把 actor_id 冗余进条目**：渲染必须取事件载荷，事件表本来就要 join，冗余一个字段省不掉这次关联。

### 3.2 旧表处理

| 旧表 | 处理 |
|---|---|
| `t_notify_record` | 删除。站内信记录变为条目，邮件/短信记录变为投递 |
| `t_notify_message` | 删除，由 `t_announcement` 重建 |
| `t_notify_template` | 删除，文案进代码 |

旧表存在的问题不随重建带走：幂等键只有普通索引、收件人一列混存三种标识、状态取值域随渠道变化。

## 四、契约

### 4.1 gRPC 方法变更全表

**删除**

| 方法 / 类型 | 理由 |
|---|---|
| `ListNotifyTemplates`、`GetNotifyTemplate`、`CreateNotifyTemplate`、`UpdateNotifyTemplate`、`BatchDeleteNotifyTemplates` | 模板进代码 |
| `MarkRecordRead`、`BatchMarkRecordsRead`、`MarkAllRecordsRead` | 管理员不代用户改读状态 |
| `ListUserInboxRecords` | 由 `ListNotifications` 取代 |
| `NotifyRecord`、`NotifyTemplate` 消息 | 被条目、投递与代码文案取代 |

**改名并改造**

| 原 | 现 | 变化 |
|---|---|---|
| `ListNotifyMessages` 等 7 个公告方法 | `*Announcement` | 与表名、领域术语统一，响应返回公告实体 |
| `ListNotifyRecords` | `ListDeliveries` | 只含外部渠道；字段改为回执、尝试次数、重试时间；新增按 `notification_id` 反查，管理端从收件箱条目下钻看投递结果 |
| `BatchDeleteNotifyRecords` | `BatchDeleteDeliveries` | 同上 |
| `ListUndeliveredNotifyMessages` | `ListStalledEvents` | 从「公告是否有记录」改为「事件是否停滞」 |
| `RedeliverNotifyMessage` | `RedeliverEvent` | 针对事件重新扇出 |

**改造**

| 方法 | 变化 |
|---|---|
| `SendEmailCode`、`SendMobileCode` | 去掉响应中的 `id`：验证码不再产生记录 |

**新增**

| 方法 | 用途 |
|---|---|
| `ListNotifications` | 读者收件箱，**以分组分页**；收件人取自会话主体 |
| `ListUserNotifications` | 管理端按用户查看，**条目级只读**，含已读时间；投递状态经 `ListDeliveries(notification_id)` 下钻，需权限点 |
| `CountUnreadNotifications` | 未读分组数：返回总量与按偏好分组的分别计数，供角标使用 |
| `MarkNotificationsRead` | 按分组标记已读 |
| `MarkAllNotificationsRead` | 全部已读 |
| `DeleteNotifications` | 按分组删除 |
| `GetNotifyPreferences` / `UpdateNotifyPreferences` | 偏好矩阵 |
| `ListNotificationEvents` | 管理端分页查询事件与扇出进度 |
| `RedeliverDelivery` | 按投递记录重发 |
| `VerifyUnsubscribe` | 校验退订令牌，返回会退订的分组与渠道；不改变状态 |
| `Unsubscribe` | 凭令牌执行退订，不要求登录 |

**读者列表载荷**：组键、最新触发者、组大小、未读状态，以及**服务端渲染后的标题、正文与跳转**。客户端没有场景渲染逻辑，不返回渲染文本这一页就无可展示内容。投递消费者渲染同一套文本，只是额外套渠道外壳。

**仅未读视图下，组大小与最新触发者都只看未读条目**：组大小是组内未读条数，不是全部条数；最新触发者取组内最新的未读条目，否则会显示一个已经读过的触发者。

**管理端看条目、读者端看分组**：管理员排障需要单条的已读时间与原始标识，分组投影满足不了；读者只需要「谁做了什么事、共几条」。投递状态不在条目上：由 `ListDeliveries` 按 `notification_id` 反查，界面上是「点条目 → 看它的投递」的下钻。

**组键契约**：分组以服务端下发的 `group_key` 不透明键传递，客户端原样回传用于整组已读 / 整组删除，不解析、不构造。这样不分组场景与按对象分组走同一条路径，也不必把存储键的拼装规则暴露成契约。

**组视图不给可构造的寻址字段**：`NotificationGroup` 只保留 `group_key`、`scene` 与展示字段，不暴露 `object_type`、`object_id`、`notification_id`。跳转用 `link`，整组操作用 `group_key`；一旦给了组件，就是在鼓励客户端自己拼键，与「不依赖页内条目」的意图相反。管理端的条目级视图 `NotificationItem` 仍然暴露这些字段——那里是排障，需要看到原始标识。

**重投只针对失败或停滞的事件**：已完成事件重放会重新扫描受众，扇出期间新注册的用户会收到一条旧通知。契约上直接拒绝已完成事件的重投。

**渲染入口带语言参数**：当前只有一种语言，参数先留位，避免以后加语言时改一圈调用方。

**授权边界**：读者侧方法与 `ListNotifications` 一律以会话主体作为收件人条件，请求参数不得指向他人；`ListUserNotifications` 是唯一带 `user_id` 的入口，由权限点保护。标记已读与删除同样必须以收件人作为 WHERE 条件，不能只按组键更新。

**不发通知 RPC**。业务域与通知域在同一进程、共用同一个 `*gorm.DB`，跨 gRPC 调用不共享事务，会产生「业务已写入、通知事件没写」的窗口。业务域改为调用 `internal/notification` 的包内函数，见 §五。

### 4.2 管理端（`protocol/api/admin/notification.api`）

- **公告组**：路径改为 `/announcements`，响应返回公告实体。
- **投递组**：只展示外部渠道；新增按投递重发。
- **模板组**：删除。
- **inbox 组**：只保留「按用户查收件箱」，内部走 `ListUserNotifications`，供排障；删除三个标记已读接口。
- **我的通知组**：新增 `/me/notifications`（列表、未读、已读、全部已读、删除）。管理员也是用户，公告对它同样会产生条目，没有入口就成了看得见数据、看不见通知。
  - **前端入口**：管理后台顶部导航的铃铛，与公告管理平级；不是独立菜单页。
  - **不提供偏好接口**：偏好是账号级设置，与从哪个端进来无关。管理员在后台收到的只有公告与安全两类，两者都是强制分组、本就不可关闭；其余类型来自他在博客站的身份，在博客站调整即可。
  - **组视图类型与读者端各有一份**：两个网关的生成类型互不可见，无法共享定义；字段必须保持一致，改动时两处一起改。
- **事件组**：新增，分页查询事件与扇出进度、停滞事件重投。
- **SSE 流**：保留，语义收窄为「公告状态变化」。

新增的事件组需要补权限点与限流；公告组与投递组沿用现有权限点。`/me/*` 沿用 `/me/profile` 的做法，只挂 `AdminAuth`，不加权限点——读自己的东西不需要 RBAC。

### 4.3 读者端（新建 `protocol/api/app/notification.api`）

| 方法 | 路径 |
|---|---|
| 列表 | `GET /notifications`，支持 `groups`（偏好分组，可多选，缺省为全部）与 `unread_only` 过滤、按组分页 |
| 未读数 | `GET /notifications/unread-count`，同样接受 `groups` 过滤 |
| 标记已读 | `POST /notifications/read`（按分组） |
| 全部已读 | `POST /notifications/read-all` |
| 删除 | `POST /notifications/delete`（按分组） |
| 偏好查询 / 更新 | `GET` / `PUT /notifications/preferences` |
| 退订 | `GET /notifications/unsubscribe?token=...` 校验令牌并返回分组与渠道；`POST /notifications/unsubscribe` 执行；两者都免登录 |
| 实时信号 | `GET /notifications/stream`（SSE） |

**删除接口是 D9「不留墓碑」的落点**，不是可选项。

**退订必须是两步**：邮件安全扫描器会预取正文里的链接，签名令牌挡不住自动访问，把 GET 直接做成「执行退订」会被误触。GET 只校验令牌并跳转到确认页，POST 才写偏好。

**确认页放在 blog-app**：网关是 JSON API，不产出 HTML。邮件里的链接指向博客站的确认页，页面加载时调 GET 校验令牌、展示分组与渠道，用户点确认再调 POST。

**退订令牌**：`HMAC(收件人 + 偏好分组 + 渠道 + 过期时间)`，密钥来自配置；校验通过后写偏好，幂等，重复提交不报错。密钥轮换期同时接受新旧两把。

**强制分组不生成令牌**：公告与账号安全不可退订，渲染邮件时就跳过退订链接；`Unsubscribe` 校验时再拒绝一次，防止有人手工构造令牌。

**SSE 限流**：按用户与按 IP 双向限制，并处理断线回收；读者端连接数只会比管理端多，复用现有 `NotifyStreamLimit` 的思路。

| `infra/domain/cachekey/notification_cache.go` | 保留管理端公告状态频道；新增按收件人的信号频道 |
| 验证码发送 | 拆出投递编排：只复用邮件/短信客户端与渲染，不写事件、条目与投递记录 |
| `contentservice/like_article_logic.go` | 点赞包进 `GormDB.Transaction`，用 `TLikeModel.WithTx(tx)` 构造 `likes.Deps`（`Like` 签名不变），影响行数 > 0 时在同一事务上 `Emit`。同一人反复点赞由去重键吞掉，不需要额外判断 |

## 六、实施顺序

第一、二步作为一个提交，提交前必须通过 `GOWORK=off go build ./...`。

**第一步：数据与模型**
改 `blog.sql`，重新生成模型，删除三张旧表模型。

**第二步：管线**
场景目录与渲染 → `Emit` → 扇出消费者 → 投递消费者 → 公告走新管线。同步切换管理端契约、删除模板组、收窄 inbox 组、调整首页聚合，并完成 blog-admin 的相应页面改造 —— 契约与后台要一起上线，否则模板页会拿到已删除的方法。

**拓扑改名按迁移处理**，不能直接替换：

| 现在 | 之后 | 职责 |
|---|---|---|
| exchange `blog.notification` | 不变 | —— |
| routing key `notification.inbox` | `notification.event` | 扇出唤醒：初始一条，续跑每批一条 |
| queue `blog.rpc.notification.inbox` | `blog.rpc.notification.event` | 同上 |
| —— | `notification.deliver` + 队列 `blog.rpc.notification.deliver` | 投递表的唤醒信号，**每批一条**，不按条目逐条发 |
| `notification.email` / `notification.sms` | 不变 | **只承载验证码**；通知的外部投递一律走投递表与 deliver |
| exchange `blog.audit` | 不变 | —— |

**投递的唤醒与领取**：投递表本身是队列。扇出每批提交后写一条唤醒消息；消费者用 `SKIP LOCKED` 批量领取待发送记录，只捞 `next_retry_at` 已到或为空的，否则退避会被立刻绕过。不按条目逐条发消息 —— 万级广播配邮件会产生万级消息与万级 outbox 行，写放大不可接受。重试由定时扫描 `(status, next_retry_at)` 触发，不依赖消息重投。

**扇出的消息量与投递不对称，是有意的**：每次互动写一条事件、发一条唤醒，数量与互动量同阶，高峰时会有空跑（条目被去重键吞掉）。投递侧则按批评量取，因为它面向可能上万人的广播。若扇出的空跑占比明显，可以改成低频唤醒加扫描待扇出事件，与投递侧收敛到同一模型。

顺序：新建队列与绑定 → 切换生产与消费 → **停止旧消费者并丢弃旧 `inbox` 队列的剩余消息** → 删除旧队列与绑定。

旧队列里的消息是 `InboxMessageEvent{MessageId}`，引用的 `t_notify_message` 已被删除，旧消费者跑起来必然失败。本次不兼容旧数据，这些消息不迁移、不重放，直接丢弃。

**第三步：读者端**
gRPC 新增方法 → `app` 网关新增 notification 域 → 按收件人频道投递实时信号 → blog-app 通知中心与偏好页。

**第四步：业务接入**
评论回复、三类点赞、评论审核、密码与邮箱变更接入，各自在业务事务内 `Emit`。

## 七、可观测性

设计里的每条失败模式都要有对应指标，否则「需要积压告警」只是一句话。

| 指标 | 对应失败模式 |
|---|---|
| 各状态事件数量，重点看停在「扇出中」超过阈值的 | 扇出中断、兜底扫描失效 |
| 事件从创建到完成的耗时分布 | 广播投递延迟 |
| 投递表待发送记录的最老年龄 | 投递消费者停机、重试卡死 |
| 投递失败终态与死信计数 | 渠道故障、不可重试错误 |
| 读者端与管理端 SSE 在线连接数 | 连接泄漏、限流是否生效 |
| 扇出因去重被吞的条目比例 | 空跑占比，决定是否改成扫描模型 |
| 保留期清理的删除行数、耗时与失败次数 | 清理变慢、索引失效、任务卡死 |

告警阈值：停滞事件连续两个扫描周期不为 0；待发送最老年龄超过 5 分钟；死信在 10 分钟内增长；SSE 连接数逼近限流上限。

## 九、遗留与待确认

- **旧拓扑清理**：改名迁移完成后，旧 `inbox` 队列与绑定需在部署时删除，避免无人消费的堆积。
- **模板能力下线**：管理端模板页、模板 API 与相关权限点一并移除，需确认没有其他入口依赖。
- **权限与限流**：新增管理端事件组需权限点；读者端收件箱、偏好与 SSE 需登录态校验与限流。
- **退订密钥**：需要配置项与轮换流程，轮换期双密钥并行。
- **展示分组回填**：组键在写入时物化，日后调整某场景的展示分组需要对历史条目回填，或约定不可改。
- **Web Push**：作为投递渠道预留，本次不实现，接入需要 VAPID 密钥与 service worker。
- **对外广播**：公告默认只落站内信。邮件/短信广播是否开放、入口放在哪里，待运营需求确认。
- **文章与说说审核**：当前没有审核状态。若需要，是独立需求，需先定义状态机与审核入口，不在本次范围。
- **登录异常提醒**：需要判定规则（如窗口内连续失败次数），不在本次范围。
- **注销用户的通知**：其收到的条目随对象清理；其发出的通知保留还是匿名化，待定。
- **访客收不到通知**：匿名评论来自访客身份，没有收件箱与地址，被回复者是访客时直接跳过。若要让访客收到回复提醒，需要先做访客邮箱绑定，是独立需求。
- **评论审核开关是死开关**：站点配置里的 `is_comment_review` 只有字段与生成类型，服务端从未读取，评论一律先审后发。这是既有缺陷，不在本次范围。本次把触发点定义在「置为通过」这个迁移上，开关将来修好也不需要改通知逻辑；但要修复它本身属于另一项改动。
- **事件层不去重**：同一人重复点赞仍会写事件、触发一次扇出，只在条目层被去重键吞掉。高峰时空跑明显再考虑在事件层按「场景 + 对象 + 触发者」去重，它与「公告重发」的语义有交互，本期不做。
