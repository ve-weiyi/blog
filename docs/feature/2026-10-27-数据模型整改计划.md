# 数据模型整改计划

> 日期：2026-10-27
> 范围：`protocol/sql/blog.sql`、`blog-cloud/model/`、`blog-cloud/cmd/rpc/blog/**`
> 定位：**整改计划，日期快照**。落地后代码与 `blog.sql` 为唯一真相，本文不逐字追更。
> 依据：[《数据模型》](../design/13-数据模型.md) 的决策 D1–D11。

---

## 一、背景与目标

数据模型是按功能逐个长出来的，没有经过整体设计：同一语义有三种类型、联表用代理主键、计数没有明细来源、索引随意增删。

目标：按《数据模型》重整，**趁业务数据接近空的时候做**。现在改只需迁移脚本与少量代码；等有真实数据再改，成本高一个数量级。

## 二、现状快照（2026-10-27）

| 指标 | 值 |
|---|---|
| 表 | 31 |
| 外键约束 | 0 |
| 非主键索引 | 17 个唯一 + 33 个普通（A 档调整后） |

| 多数表行数 | 0 |

### 与设计决策的差距

| 决策 | 差距 |
|---|---|
| D3 会话与日志各归其位 | 会话实体已由令牌存储承载；但登出是回写「最近一条未登出的登录记录」，登出事件被塞进登录事件行 |
| D12 模板身份 | 唯一键为 `(code, channel)`，而运行时按 `(scene, channel, enabled)` 查找，同一场景可命中多条启用记录 |
| D4 列表不进主表 | `t_notify_message.target_ids`、`t_talk.images`、`t_page.carousel_covers` 为逗号分隔 |
| D5 媒体存引用 | 《媒体、站点与分发》规定只保存引用，实现上业务表存的是拼接后的完整地址 |
| D8 约束由模型表达 | `t_role.role_key` 无唯一约束，角色重名靠查询预检 |
| D9 类型按语义选 | `status` 三种类型；`cost`、`date` 存字符串；`key` 为保留字 |
| D10 派生数据有来源 | `like_count` 无明细来源；统计实现扫 `DATE(created_at)`，与《统计与报表》的快照口径不符 |
| D11 索引是查询投影 | `t_article`、`t_role_menu`、`t_photo` 有真实查询却无索引；`t_user` 有两个无查询支撑的索引 |

**已定边界不再重开**：评论/留言/说说分表、通知记录单表——这两条是既有的领域裁决，本文不作为整改项，相关替代方案进「待裁决」。

## 四、A 档明细

### 4.1 索引

| 表 | 动作 | 依据 |
|---|---|---|
| `t_article` | + `(is_delete, status, id)`、+ `(category_id, is_delete, status, id)` | 列表主路径；尾部 `id` 支持游标分页与管理端 `id desc` |
| `t_comment` | `idx_is_review` → `(is_review, created_at)`；+ `(type, topic_id, created_at)` | 首页最新评论；主题页评论（多态须带 `type`） |
| `t_role_menu`、`t_role_api` | + `(role_id)` | 鉴权热路径 |
| `t_user_role` | + `(user_id)`、+ `(role_id)` | 两个方向都查 |
| `t_operation_log` | + `(created_at)`、+ `(user_id)` | 后台按时间/用户筛选 |
| `t_photo` | + `(album_id)` | 相册详情 |
| `t_notify_template` | + `(scene, channel, enabled)` | 模板查找主路径 |
| `t_notify_record` | − `uk_channel_biz`，恢复 `idx_channel`，+ `idx_biz_id` | 幂等键仅对外发有意义，唯一约束不能覆盖站内信 |
| `t_user` | − `idx_created_at`、− `idx_deleted_at` | 无查询支撑 |

### 4.2 类型与命名

| 项 | 变更 |
|---|---|
| 状态枚举 | `t_user` / `t_comment` / `t_chat` / `t_message` / `t_login_log` 的 `status` 与 `t_comment.type` → `tinyint` |
| 数值宽度 | `t_operation_log.response_status` → `smallint`；`t_menu.rank` → `int` |
| 字符串长度 | `t_message.user_id` / `device_id`、`t_comment.reply_user_id` → `varchar(64)` |
| 定长值 | `t_upload_log.file_md5` → `char(32)` |
| 保留字列名 | `t_config.key` → `config_key`，唯一键同步改名 `uk_config_key` |
| 日期类型 | `t_daily_stats.date` → `DATE` |

### 4.3 明确排除

- `t_operation_log.cost` → 数值类型：proto 中为字符串，改类型即改 API 契约，归 C 档。
- `t_notify_record` 的索引收敛：单表模型下先按查询补索引，拆表提案见「待裁决」。
- `t_user.info` → JSON、列表列 → 子表：改 Go 类型，归 B 档。

### 4.4 已完成

- `protocol/sql/blog.sql`：4.1 与 4.2 全部落地；结构对拍确认 31 张表不变、列变更仅为上表所列。
- B/C 档的 schema 部分已一并落地：`t_notify_template` 唯一键改为 `(scene, channel)`；`t_user.info`、`t_talk.images`、`t_page.carousel_covers`、`t_notify_message.target_ids` 改为原生 JSON；新增 `t_like`；`t_operation_log.cost` 改为数值类型。

### 4.5 待完成

2. 代码适配：`FindOneByKey` → `FindOneByConfigKey`（2 处）、`model.TConfig.Key` → `ConfigKey`、`DailyStats.Date` 由 `string` 改 `time.Time`（3 处统计调用）。
3. ~~生成 `ALTER TABLE` 迁移脚本，人工执行后再对账。~~ 已完成：`protocol/sql/2026-10-27-数据模型整改.sql`，先在临时库演练，再对线上执行；结构与索引对账零差异。

## 八、执行与校验

每一档都按同一流程：

1. 改 `blog.sql`（唯一真相）。
2. 重新生成 `model/`，与 `sql` 产物逐字节对拍。
3. 适配代码，`GOWORK=off go build ./...`、`go vet`、`go test -short`。
4. 生成迁移脚本，**人工确认后**在线上执行。
5. 用 `information_schema` 与 `blog.sql` 对账，确认无漂移。
