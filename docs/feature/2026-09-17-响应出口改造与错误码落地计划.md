> 日期：2026-09-17
> 范围：`blog-cloud/infra/responsex`、`infra/biz/{bizcode,bizerr}`、`infra/limitx`、`infra/middlewarex`、198 处 handler 解析分支、`docs/design/07-BLOG-错误码与中间件.md`
> 状态：**已实施**——S1 / S2 / S3 与前后端同窗口均落地；决策偏移见文末「修订记录」
> 标准：`docs/design/07-BLOG-错误码与中间件.md`（以下简称《07》）为唯一标准，本计划是执行快照，落地后以代码为准

本文按 2026-09-17 的代码状态写成：标识计数、文件行号、调用点数均为当日实测值，不逐字追更。

## 一、目标与现状

### 1.1 目标

把响应出口收敛成《07》描述的形态：**业务侧只产出标识，状态码与响应头由出口一处派生**；并新增一条**无标识**的显式状态出口，用于《07》§2.6 允许的传输层路径。三件事同时解决：

1. **出口不再是第二个推导点**——头部按标识派生（现在按状态码派生，导致 401 只有一种 challenge）
2. **出口不再造假值**——删掉恒定的 `Retry-After: 1`
3. **出口不再误判**——请求解析失败从 500 改回 400（无 `code`）

### 1.2 现状实测

| 项 | 数字 | 位置 |
|---|---|---|
| 解析分支待替换 | **198 处** | `api/app`、`api/admin` 的 `handler/**`，形态统一为 `responsex.Response(r, w, nil, err)` |
| `responsex` 引用总数 | 412 处 | 同上 + `middlewarex` |
| 标识集 | 代码 23 个 vs 《07》§1.4 | `biz/bizcode/biz_code.go` |
| `limitx.Limiter.Take` 调用点 | 1 处 | `middlewarex/ratelimit_middleware.go:28` |
| 前端消费者 | 2 个项目 × 2 文件 | `blog-app`、`blog-admin` 的 `src/enums/api.ts` + `src/utils/request.ts` |

### 1.3 三类偏差

**甲、文档与实现互相矛盾（5 处）**

| # | 矛盾 | 实现 | 《07》 |
|---|---|---|---|
| 1 | `PARAM_MISSING` 有无产出者 | **有**：`terminaltoken_middleware.go:41,46`（带了 `x-device-id` 却缺 `timestamp`/`x-device-token` 时拒绝） | §2.3/§2.5 称该中间件"不含拒绝路径" |
| 2 | 设备令牌签名不符的处置 | **拒绝**（`terminaltoken_middleware.go:51-53`） | §2.3 表格：放行、降级为匿名 |
| 3 | `PARAM_*` 的出口状态 | **400**（`response.go:45-49`） | `422` |
| 4 | 标识集 | 仍有 `PASSWORD_INCORRECT`（产出点 `rpc/blog/internal/logic/authservice/login_by_password_logic.go:52`）；`REQUEST_TOO_FREQUENT` 无任何产出者（死条目）；缺 `PRECONDITION_FAILED`、`SERVICE_UNAVAILABLE` | §1.4 称迁移已完成 |
| 5 | 限流算法 | `limitx.PeriodLimit` 是 `INCRBY`+`EXPIRE` 的**固定窗口** | §2.4 称滑动窗口 |

**乙、实现缺陷（与文档无关）**

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 解析失败 → 500 | 客户端传坏 JSON 即产生 5xx，触发告警 |
| 2 | `defaultRetryAfter = "1"` 且无人给精确值 | 每个 `429` 都在说"1 秒后重试"，60 秒窗口下退化成重试风暴 |
| 3 | 限流 key 用 `httpx.GetRemoteAddr` | go-zero 实现（`rest/httpx/util.go:68-75`）原样返回整串 `X-Forwarded-For`，取不到"最后一跳"，客户端可伪造 IP 绕过 IP 维度限流 |
| 4 | `WithBizError` 恒发 `codes.Internal` | canonical code 不携带信息；《07》§1.10 的兜底表无法实现；标准 gRPC 中间件看到的都是 INTERNAL |
| 5 | HTTP 侧 `errors.As`、gRPC 侧裸类型断言 | `fmt.Errorf("…: %w", bizErr)` 包装过的错误：HTTP 是 401、gRPC 被压成 Internal |
| 6 | `field_violations` 无承载位置 | `BizError` 没有 details 槽，《07》§三/§1.9 的字段级契约无法表达 |
| 7 | `GetLanguage` 无调用点 | 且与 §三"服务端不做本地化"相悖 |
| 8 | `WithDetails` 的 error 被丢弃 | `error.go:22`，违反项目"必须显式检查 error"规范 |

**丙、本次核对新增的规范偏差**（已回写《07》§五）

`422` 的适用域限定在请求内容；`429` 的出处是 RFC 6585 §4；签名失败不套用 RFC 6750 的错误码；`RateLimit-*` 的字段名落后于草案现行修订。

## 二、responsex 目标形态

### 2.1 API 面：两个入口，一个方向

```go
// Response 有业务标识的路径：状态码由 §1.4 的表推导，调用方只传标识
func Response(r *http.Request, w http.ResponseWriter, resp any, err error) // 签名不变

// ResponseStatus 无标识的传输层路径（§2.6）：显式声明状态
//   2xx   → 仍写信封，code = SUCCESS（§三：除 §2.6 外所有响应都是信封）
//   非2xx → { message, data, trace_id }，不带 code，客户端走 §四 的形状判定分支
func ResponseStatus(r *http.Request, w http.ResponseWriter, status int, data any)
```

`Response` 签名不变，198 处调用点中只有解析分支需要改（见 §3.1 第 6 项）。

### 2.2 表结构

```go
type rule struct {
	status  int
	headers func(*http.Request, http.ResponseWriter) // 该标识独有的头，可为 nil
}
```

**头部由标识决定，不由状态码决定**——这是当前 401 只有一种 challenge 的根因：`StatusUnauthorized` 之下站着四种语义。表外标识兜底 500 并保留标识本身。

### 2.3 头部契约（逐标识）

| 场景 | 响应头 | 标准 |
|---|---|---|
| 令牌类 401（`UNAUTHENTICATED` / `LOGIN_EXPIRED`） | `WWW-Authenticate: Bearer realm="blog", error="invalid_token"` | RFC 9110 §15.5.2（MUST 给 challenge）+ RFC 6750 §3.1 |
| 登录凭据类 401（`CREDENTIALS_INVALID`） | `WWW-Authenticate: Bearer realm="blog"`（**不带 `error`**） | RFC 6750 §3：请求未出示令牌，不适用错误码 |
| 签名/时效 401（`REQUEST_SIGNATURE_INVALID`） | 方案自身名，如 `Signature realm="blog"` | 不套用 RFC 6750（其三个错误码描述的都是令牌） |
| `PERMISSION_DENIED` / `ROLE_MISMATCH` 403 | `WWW-Authenticate: Bearer realm="blog", error="insufficient_scope"` | RFC 6750 §3.1 |
| 所有 `429` / `503` | `Retry-After`，**给不出精确值就省略** | RFC 9110 §10.2.3；`429` 见 RFC 6585 §4 |
| 所有响应（含 `2xx`） | `RateLimit-Limit` / `-Remaining` / `-Reset`，由限流中间件先写 | §2.4（de-facto 字段名，草案仍为 Internet-Draft） |
| 所有非 `2xx` | `Cache-Control: no-store` | §三 |
| 所有响应 | `traceparent` | W3C Trace Context |

`ETag` / `If-Match`（RFC 9110 §8.8.3）、`201 + Location`（§三）为**契约已定、待首个用例落地**，本轮不实现。

### 2.4 `ResponseStatus` 白名单

| 归类 | 允许 | 依据 |
|---|---|---|
| 2xx | `200`、`201` | §三 要求创建返回 `201` + `Location`（`Location` 由调用方先写 `w`） |
| 非 2xx | `400`（请求解析失败） | §2.6 乙：有 body、**无 `code`**、`data.field_violations` 必须存在（定位不到给空数组） |

其余状态一律有标识，必须走 `Response`。白名单外传值 → 记 error 日志并按 500 写。**白名单是显式枚举，扩展需走设计评审**，以保证它不会长成"业务状态的后门"。

### 2.5 明确不做

| 不做 | 理由 |
|---|---|
| `ResponseStatus(status, code, ...)` 双显式 | 表会从"唯一真相源"降级为"参考值"，运行期必然漂移 |
| **`status → code` 反推** | 业务路径：`401`/`403`/`409`/`422`/`500` 均为 1:N，反推丢信息——`LOGIN_EXPIRED` 的"自动刷新一次"（§四）会退化成"该登出"，签名失败会被误报为 `UNAUTHENTICATED`；1:1 的格子（`200`/`404`/`412`/`429`/`502`/`503`/`504`）反推则不含任何新信息。框架路径：`404` 路由未匹配 ≠ `RESOURCE_NOT_FOUND`、框架 `503` 过载 ≠ `SERVICE_UNAVAILABLE` 依赖不可用，反推会**伪造**语义并污染归因 |
| 绕过表的 `code` 参数 | §1.1 的排他性失效，表↔`bizcode.All` 一致性测试失去保护对象 |
| `204 No Content` | 与信封契约冲突（§五 已声明为偏离） |

**方向唯一**：`标识 → 状态`（表推导）、`canonical → 标识`（§1.10 兜底，单向）。二者不可反向。

## 五、风险与回滚

| 风险 | 处置 |
|---|---|
| 198 处机械替换引入误改 | 单独成一个 commit，`git diff --stat` 复核为"行数=198、每行仅 `Response`→`ResponseStatus`"；`git revert` 整块撤销 |
