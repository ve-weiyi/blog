## 三、P0 安全

### S1 设备令牌不是签名

- **设计**：《身份模型》D4、《安全边界》标识凭据：设备令牌必须是服务端密钥签名，未声明放行、声明即校验。
- **现状**：`blog-cloud/infra/http/middlewarex/terminaltoken_middleware.go` 用 `sha256(device_id, timestamp)` 比对，没有服务端密钥；任何客户端都能自行算出。
- **影响**：令牌退化为一致性检查，无法证明请求来自某个设备；声明设备身份的请求可被伪造。
- **建议**：改为对 `device_id + timestamp` 做 HMAC，密钥只在服务端；保留时间窗口与时钟偏差容忍。
- **验收**：客户端无法在没有密钥的情况下生成可通过校验的令牌；缺少时间戳/令牌仍返回 `PARAM_MISSING`，签名不符返回 `REQUEST_SIGNATURE_INVALID`。
- **状态**：待处理

### S2 读者端令牌存放在 Web Storage

- **设计**：《认证与令牌》客户端形态与传输：access 放内存，refresh 放 HttpOnly + Secure + SameSite Cookie，禁止 localStorage。
- **现状**：`blog-app/src/utils/auth.ts` 与 `blog-app/src/stores/modules/user.ts` 将 access 与 refresh 都写入 `localStorage`。
- **影响**：任意 XSS 都能读取并外传长期 refresh，撤销前可一直换取新令牌。
- **建议**：access 只放内存；refresh 改由同源 HttpOnly Cookie 承载，刷新端点设置 Cookie 并加 CSRF 防护；清理既有 localStorage 键。
- **验收**：浏览器存储中不再出现 access/refresh；刷新在 Cookie 缺失时失败；页面刷新后通过刷新端点恢复会话。
- **状态**：待处理

### S3 CORS 与 WebSocket Origin 默认放行

- **设计**：《安全边界》D6：HTTP CORS 显式来源白名单，带凭据请求不得使用 `*`；《实时通信》连接治理：WebSocket Origin 与 HTTP 共用同一白名单，不得默认放行。
- **现状**：`blog-cloud/cmd/api/app/app.go`、`blog-cloud/cmd/api/admin/admin.go` 使用 `rest.WithCors("*")`；`stompws/server/server.go` 默认 `CheckOrigin` 返回 `true`，`blog-cloud` 未调用 `WithCheckOrigin`。
- **影响**：任意站点可发起带凭据的跨域请求或 WebSocket 连接，扩大 CSRF 与跨站 WebSocket 劫持面。
- **建议**：配置显式来源白名单；HTTP CORS 与 WebSocket Origin 共用同一份配置；带凭据请求不使用通配符。
- **验收**：非白名单来源的预检与 WebSocket 握手被拒绝；白名单来源正常。
- **状态**：待处理

## 四、P1 可靠性与一致性

### R1 通知发布没有事务性 outbox

- **设计**：《异步消息与投递可靠性》D3、《通知》发布：状态变更与 outbox 事件同事务，relay 异步发布。
- **现状**：`blog-cloud/cmd/rpc/blog/internal/logic/notificationservice/publish_notify_message_logic.go` 在状态更新事务提交后直接 `MQ.Inbox.Publish`，没有 outbox 表与 relay。
- **影响**：事务提交成功、发布失败时，库内显示已发布但投递从未发生；进程崩溃落在两步之间同样会丢事件。
- **建议**：新增 outbox 表；状态变更与事件同事务写入；relay 至少一次发布并标记已发送；消费者保持幂等。
- **验收**：模拟发布失败/进程崩溃后，outbox relay 能补发；投递记录最终生成；不产生重复记录。
- **状态**：待处理

### R2 内容读缓存与版本号未实现

- **设计**：《内容与生命周期》发布事务、《缓存与一致性》D3：写操作递增内容版本号，缓存键内嵌版本；读者端匿名内容响应可缓存。
- **现状**：`blog-cloud/infra/domain/cachekey` 没有内容版本键；内容读路径直接查询数据库，Redis 只承载点赞/浏览计数等。
- **影响**：内容读路径没有共享缓存，读多写少的性能优势未兑现；也没有可失效的响应缓存。
- **建议**：先引入内容版本号与读缓存键，再按《缓存与一致性》接入反向代理；版本号递增放在发布/更新事务提交后。
- **验收**：写操作后旧版本键不再命中；匿名内容响应不含用户字段；缓存不可用时回源。
- **状态**：待处理

### R3 全局最外层限流未接线

- **设计**：《请求管线与响应契约》请求管线：粗粒度限流在全局链最外层，路由组再按主体细限流。
- **现状**：`app.go` / `admin.go` 的全局链只有上下文、设备 Cookie、防重放、设备令牌；限流只挂在登录组与一个管理端路由组。
- **影响**：限流没有保护认证、授权等昂贵判定；新增路由组容易漏挂。
- **建议**：把粗粒度限流挂到两个网关的全局链首位；保留路由组的主体维度限流；确认计数不可得时放行的降级仍生效。
- **验收**：任意路由（含未单独配置的组）都先经过全局限流；`RateLimit-*` 与 `Retry-After` 头正确。
- **状态**：待处理

### R4 文章状态混入评论策略

- **设计**：《内容与生命周期》D2：状态只表达生命周期与可见性（草稿/私密/公开），评论策略独立。
- **现状**：`blog-cloud/infra/domain/enums/content.go` 仍有 `ArticleStatusCommentVisible = 4`，校验接受该值；查询从未使用。
- **影响**：状态机多出一条既非生命周期、也非可见性的分支；后续新增评论策略会继续堆枚举。
- **建议**：移除该枚举值与校验分支；评论策略落到独立字段或配置；确认无历史数据使用 4。
- **验收**：状态校验只接受草稿/私密/公开；查询与前端不再出现「评论可见」状态。
- **状态**：待处理

### R5 K8s 只有一个 Redis，未按角色拆分

- **设计**：《部署、可观测性与运维》部署形态、《缓存与一致性》D1：会话存储与业务缓存独立实例；前者持久化且不得淘汰，后者可清空。
- **现状**：`deploy/k8s/redis/redis.yaml` 只有一个 StatefulSet；Nacos 配置也只指向一个 Redis。
- **影响**：业务缓存的淘汰/清空会波及令牌会话；无法按角色设置持久化与淘汰策略。
- **建议**：拆分两个实例（或至少两个独立持久化与淘汰策略的部署单元）；应用配置分别指向会话存储与业务缓存。
- **验收**：清空业务缓存不影响登录态；会话存储开启持久化且不淘汰未过期键。
- **状态**：待处理

## 五、P2 功能与运维缺口

### F1 RSS / Atom / sitemap / robots 未实现

- **设计**：《媒体、站点与分发》分发：RSS 必做，Atom 可选，sitemap 只输出 `loc` + `lastmod`，robots 带绝对 `Sitemap:`。
- **现状**：`protocol/`、`blog-cloud/cmd` 中没有对应路由或生成逻辑。
- **影响**：订阅器与搜索引擎入口缺失，博客的核心分发能力不可用。
- **建议**：在 `site` 模块生成四类出口；只复用读者端可见性谓词；`lastmod` 用实质内容变更时间。
- **验收**：四个出口可访问、格式可被标准解析器解析；不包含草稿/私密内容。
- **状态**：待处理

### F2 定时任务为空，统计日快照无写入

- **设计**：《系统上下文与运行视图》S6、《统计与报表》数据流：定时发布、物化统计、回收站清理由 `blog-rpc` 的定时任务推进。
- **现状**：`blog-cloud/cmd/rpc/blog/internal/job/init.go` 的 `Init` / `Stop` 为空；`t_daily_stats` 没有写入任务。
- **影响**：历史趋势无数据；依赖定时的状态推进（发布、清理）不可用。
- **建议**：注册可靠定时任务；每项以「条件更新 + 受影响行数」保证幂等；统计快照按日期幂等 upsert。
- **验收**：任务重启不重复写；失败有日志与告警；快照可补数。
- **状态**：待处理

### F3 没有版本化数据库迁移

- **设计**：《部署、可观测性与运维》D3：迁移先于代码，expand-contract，禁止启动时 AutoMigrate。
- **现状**：`svc/service_context.go` 中 `AutoMigrate` 被注释；仓库没有迁移目录或工具。
- **影响**：schema 变更没有可回滚、可审计的执行路径；多副本启动时手工改表容易出错。
- **建议**：引入版本化迁移（如 golang-migrate），按 expand → migrate → contract 执行；迁移脚本入库。
- **验收**：空库可一键迁移到当前版本；旧代码能在新 schema 上运行；回滚窗口内兼容。
- **状态**：待处理

### F4 部分 MQ 事件缺 `event_id`

- **设计**：《异步消息与投递可靠性》事件契约：每个事件带稳定 `event_id` 与 `occurred_at`。
- **现状**：`blog-cloud/cmd/rpc/blog/internal/mq/mq.go` 中 `InboxMessageEvent` 只有 `MessageId`；`LoginEvent` / `LogoutEvent` 没有 `EventId`。
- **影响**：消费者无法按事件 ID 去重；重投只能依赖业务键，登录/登出日志可能重复。
- **建议**：为所有可重投事件补 `event_id` 与 `occurred_at`；消费者按 ID 幂等。
- **验收**：重复投递同一事件不产生第二条记录。
- **状态**：待处理

### F5 点赞与浏览计数键没有 TTL

- **设计**：《缓存与一致性》D5：所有业务缓存与可重置热状态的键必须带 TTL。
- **现状**：`blog-cloud/infra/domain/cachekey/like_cache.go` 的集合与 ZSET、`visit_cache.go` 的浏览计数 ZSET 写入时没有设置过期。
- **影响**：键随用户与文章数无限增长；冷数据长期占用内存。
- **建议**：为点赞集合与计数 ZSET 设置合理 TTL；按业务需要定期校正；确认过期不会让聚合计数不可恢复。
- **验收**：所有键都有 TTL；长期无访问的键会被回收；计数仍可由数据库校正。
- **状态**：待处理

### F6 媒体物理销毁不清理对象存储

- **设计**：《媒体、站点与分发》1.4：数据库删除不等待对象存储；对象清理异步、按引用扫描、幂等。
- **现状**：`mediaservice/batch_destroy_albums_logic.go`、`batch_destroy_photos_logic.go` 只删除数据库行，没有对象删除或孤儿清理任务。
- **影响**：对象存储留下永久孤儿；删除相册后图片仍可被直链访问。
- **建议**：先删/标记数据库行，再异步清理未被任何文章、头像、站点配置、页面轮播引用的对象；清理任务幂等并可重试。
- **验收**：销毁后对象最终被删除；仍被引用的对象不被删除；任务重复执行无副作用。
- **状态**：待处理

### F7 聊天内容治理未实现

- **设计**：《实时通信》3.4：长度与频率限制、本地关键词规则（可选）、作者撤回/编辑、管理员处置、身份级封禁。
- **现状**：`cmd/api/app/internal/stomphook/chatroom.go` 有长度上限与编辑/撤回入口，但没有频率限制、关键词规则、管理员处置与封禁。
- **影响**：刷屏与滥用只能靠人工观察；违规用户无法临时阻断。
- **建议**：接入按主体/IP 的频率限制；管理端提供撤回/删除；封禁在 CONNECT 与 SEND 两处校验。
- **验收**：超频被拒绝；管理员可处置任意消息；封禁用户在重连与发送时都被拒绝。
- **状态**：待处理

### F8 STOMP 失败延迟与按 IP 限制未实现

- **设计**：《实时通信》连接治理：认证失败延迟约 1 秒、按来源 IP 的连接与失败频次限制、可信代理 IP 口径。
- **现状**：`stompws/server/server.go` 只有全局 `maxConnections`（默认 10000）；没有失败延迟与按 IP 计数；`blog-cloud` 未配置可信代理 IP。
- **影响**：暴力猜测与单 IP 连接洪泛缺少约束；延迟抗爆破只停留在设计。
- **建议**：异步实施失败延迟；按 IP 统计连接与失败次数；明确 `X-Forwarded-For` 的可信跳。
- **验收**：单 IP 超限被拒；失败连接不阻塞处理线程；直连与代理场景 IP 取值正确。
- **状态**：待处理

### F9 文章缺少恢复与物理销毁

- **设计**：《内容与生命周期》D4：软删除可恢复；物理销毁独立权限、独立端点、不可逆。
- **现状**：`protocol/api/admin/content.api` 只有文章删除与更新，没有 restore / destroy / batch-destroy；相册与接口资源已有对应端点。
- **影响**：文章误删只能改库恢复；物理销毁没有受控入口。
- **建议**：补恢复与销毁端点；恢复默认回到草稿；销毁校验权限并提示不可逆。
- **验收**：恢复后文章回到草稿且不自动公开；销毁需要独立权限；两类操作都有审计。
- **状态**：待处理

### F10 站点配置没有版本号与缓存失效

- **设计**：《媒体、站点与分发》站点：站点配置读多写少，写入后递增站点版本号，缓存整体失效。
- **现状**：`blog-cloud/cmd/rpc/blog/internal/logic/siteservice/get_config_logic.go` 直接查库，没有缓存或版本号。
- **影响**：配置读取每次都打数据库；也没有可失效的缓存键。
- **建议**：引入站点版本号与读缓存；写操作递增版本；缓存不可用时回源。
- **验收**：写配置后旧版本缓存不再命中；读路径在缓存命中时不查库。
- **状态**：待处理

### F11 读者端没有改密入口

- **设计**：《认证与令牌》账号生命周期：已登录 + 旧密码可修改密码，并撤销其他会话。
- **现状**：`protocol/api/app/account.api` 只有密码重置，没有修改密码；管理端 `PUT /admin-api/v1/me/password` 存在，并在 API 层 `RevokeAll`。
- **影响**：读者只能走「忘记密码」流程改密，无法在已知旧密码时主动更换。
- **建议**：读者端补改密端点，复用 rpc 的改密逻辑；改密成功后撤销其他会话。
- **验收**：旧密码错误被拒；改密后其他设备失效；当前会话按产品策略保留或重新登录。
- **状态**：待处理

| 站点在线与管理端在线 | 设计《系统上下文与运行视图》《实时通信》已改为独立 Redis 集合，与实现一致 |

| 通知撤回不需要 outbox | 设计《通知》《异步消息与投递可靠性》已对齐：状态与未读记录同事务，广播只做加速 |
| 解绑最后一个登录方式 | 实现已在 rpc 层检查密码、邮箱、手机与其余第三方绑定，至少保留一种；无需改动 |

## 七、验证方式

修复后至少执行：

```bash
# 单模块构建与测试（blog-cloud / vkit / stompws）
GOWORK=off go build ./...
go test -short ./...
go test -race -short ./infra/...   # blog-cloud
```

针对性检查：

```bash
grep -R 'WithCors("\*")' blog-cloud/cmd
grep -R 'WithCheckOrigin' blog-cloud
grep -R 'Sha256v' blog-cloud/infra/http/middlewarex
grep -R 'localStorage' blog-app/src/utils/auth.ts
grep -R 'AutoMigrate' blog-cloud/cmd
```

部署侧核对：

- `deploy/k8s/redis/redis.yaml` 是否为两个独立实例；
- Nacos 配置是否分别指向会话存储与业务缓存；
- `deploy/k8s/` 应用清单与端口是否仍与设计一致。
