## 二、总体评价

整体方向与设计文档一致，几处模型收口做得比预期好：

- **写入管线是事务性的**：`Emit` 在业务事务内同时写事件与发件箱；点赞、审核、改密都与业务写入同事务；
- **扇出可重入**：事件行锁 + 游标 + 状态机；`Entry.External` 让「站内信不进投递表」从约束变成了类型；
- **投递表即队列**：`SKIP LOCKED` + 租约 + 独立重试计数，不依赖 MQ 重投；
- **审核时序正确**：通知在「审核通过」这个状态迁移上产生，复核驳回会先回收已发条目；
- **退订令牌**：签发与校验两端都拒绝强制分组，`hmac.Equal` 常量时间比较。

问题集中在五处：

1. **投递终态判断写错**，导致已发布公告/审核结果的邮件实际发不出去；
2. **app 端 SSE 桥接会在客户端断开时泄漏 goroutine 与 Redis 订阅**；
3. **评论回复的收件人仍采信客户端传入的 `reply_user_id`**，可被用来给任意用户发通知；
4. **几处「有接口无数据」的功能缺口**：管理端公告 SSE 没有发布端、邮件退订链接没有签发端、邮箱变更告警发到了新邮箱；
5. **清理与编辑的一致性缺口**：复核驳回/文章删除/用户注销的条目清理不完整，公告编辑会覆盖发布状态。

## 三、Must Fix

### 3.1 投递 worker 把 `done` 当成终止，邮件实际发不出去

- `cmd/rpc/blog/internal/notification/delivery_worker.go:118-120`

```go
if IsTerminal(ev.Status) {
    return w.finish(ctx, d, DeliveryCancelled, "事件已终止")
}
```

`IsTerminal` 对 `done / failed / terminated` 都返回真（`notification/service.go`），而扇出完成后事件状态正是 `done`。因此**已完成扇出的所有投递都会被置为 `cancelled`**。这不是「部分投递失效」，而是**外部渠道整体不可用**：本轮只有「内容审核结果」与「账号安全」两个场景会产生外部投递（公告默认只落站内信，不走投递表），所以这两类通知的邮件送达率为 0；只有事件仍处于 `fanning` 的短暂窗口里可能漏出去几条。

应只拒绝 `terminated`（必要时加 `failed`），`done` 是正常可投递状态。建议抽一个 `undeliverableStatus` 判据，避免再次与 `IsTerminal` 混用。

**测试缺口**：`DeliveryWorker.process` 没有测试。补一条「事件 `done` + pending 投递 → 结果为 `sent`」即可锁住。

### 3.2 app 端 SSE 桥接在客户端断开时泄漏

- `cmd/api/app/internal/sse/bridge.go:27-33`

```go
for range sub.Channel() {
    select {
    case <-ctx.Done():
        return nil
    case client <- &types.NotificationStreamEvent{...}:
    }
}
```

外层 `for range` 阻塞在下一个 Redis 消息上；`ctx.Done()` 只有在消息到达后才被检查。客户端断开且恰好没有新信号时，桥接 goroutine 永久阻塞，defer 的 `sub.Close()` 不执行，Redis 订阅一并泄漏。读者端连接数远高于管理端，这类泄漏会随断线累积。

应与 admin 侧的 `sse/bridge.go:24-38` 一致：在同一个 `select` 里同时监听 `ctx.Done()` 与 `sub.Channel()`，并在 `client <-` 时也纳入 ctx 选择。

### 3.3 评论回复的收件人仍采信客户端 `reply_user_id`

- `cmd/rpc/blog/internal/logic/discussionservice/create_comment_logic.go:36`
- 受影响：`cmd/rpc/blog/internal/logic/discussionservice/review_notify.go:101-113`

`CreateComment` 直接落库请求体里的 `ReplyUserId`；`repliedUserID` 又在它非空时优先采用。审核通过后，构造请求的客户端可以让**任意用户**收到「XXX 回复了你的评论」。通知虽然要经过审核，但审核只判断评论内容，不校验收件关系。

方案 §五 已明确要求「收件人必须由服务端按被回复评论反查作者」。应在 `CreateComment` 里按 `ReplyId`（缺省 `ParentId`）反查作者并覆盖该字段；反向用例（伪造值不应生效）应进测试。

## 四、Should Fix

### 4.1 批量审核缺少原状态守卫，与单条路径并发语义不一致

- `cmd/rpc/blog/internal/logic/discussionservice/batch_review_comments_logic.go:51-52`

批量路径用 `WHERE id IN ?` 无条件更新，通知却按事务外预读的 `comments` 快照判断；单条路径（`review_comment_logic.go:53-61`）用 `WHERE id = ? AND is_review <> ?` 加影响行数裁决。并发审核时两条路径可能给出不同结论，也会出现「状态没变但发了通知 / 状态变了没发通知」。

建议：批量更新同样带 `is_review <> ?`，或先 `SELECT ... FOR UPDATE` 锁住再逐条按影响行数判断。（规则 3.3 / 5.2）

### 4.2 邮箱变更告警发到了新邮箱

- `cmd/rpc/blog/internal/logic/userservice/bind_me_email_logic.go:64-80`

安全通知在改邮箱的同一事务里发出，但投递地址是**扇出时**从 `t_user.email` 解析的，也就是**新邮箱**。会话被盗后改邮箱的典型场景里，受害者旧邮箱收不到任何告警，通知全发给了攻击者的地址；站内通知也只有攻击者的在线会话能看到。

建议在更新前捕获旧邮箱，通过一条独立的同步发送（或事件载荷里的显式收件地址）送达旧邮箱；站内条目仍按用户 id 落库。（规则 4.5）

### 4.3 管理端公告 SSE 没有发布端

- `infra/messaging/notifyx/event.go:19-22`（`EventAnnouncementPublished` / `EventAnnouncementRevoked` 零引用）
- `cmd/api/admin/internal/logic/notification/announcement/publish_announcement_logic.go:28-35`、`revoke_announcement_logic.go:28-35`

管理端 `sse/subscriber.go` 仍在订阅 `NotifyEventChannel`，但全仓没有任何 `notifyx.Publish(...)` 调用。方案 §4.2「SSE 收窄为公告状态变化」目前是断的：发布/撤回不会推送，多管理员协作的列表刷新失效。

建议二选一：rpc 的 `PublishAnnouncement`/`RevokeAnnouncement` 在提交后发布（需要给 `Notifier` 补一个公告维度的方法）；或 admin 网关在 RPC 成功后发布。（规则 2.1）

### 4.4 邮件退订链接没有签发端

- `infra/domain/notify/token.go:34`（`SignUnsubscribe` 零调用）
- `cmd/rpc/blog/internal/notification/delivery_worker.go:260-269`（`emailShell` 不含链接）

`VerifyUnsubscribe` / `Unsubscribe` 两个端点、令牌签发与校验都写好了，但没有任何地方签发令牌，邮件正文也没有退订链接。功能上等价于「退订页面存在但用户走不到」。

建议在投递渲染时对可退订分组（`GroupInfo.Mandatory == false`）签发带过期时间的令牌并拼进 `emailShell`。（规则 1.5）

### 4.5 `RedeliverDelivery` 没有复位尝试次数

- `cmd/rpc/blog/internal/notification/announcements.go:167-171`

手动重发只复位 `status` / `error_msg` / `next_retry_at`，`attempts` 仍停在终态时的 5（或更高）。worker 领取时 `attempts+1`，第一次发送失败即被 `retryLater` 判定 `>= deliveryMaxAttempts` 直接置失败——手动重发没有重试预算。

建议同时写入 `"attempts": 0`。复位后 worker 领取会先 `attempts+1`，第一次失败记为 1，实际余量是 4 次重试（第 5 次领取失败才进终态），不是 5 次。（规则 4.7）

### 4.6 投递 worker 逐条查条目与事件

- `cmd/rpc/blog/internal/notification/delivery_worker.go:104-151`

`process` 对每条投递各查一次条目与事件，一批 50 条约 100 次查询。后台任务不阻塞请求，但与 `read.go` 的批量取数风格不一致，也随积压线性放大。

建议在 `drain` 里按 `notification_id` / `event_id` 批量预取，`process` 只做内存查找与发送。（规则 1.4）

### 4.7 更新公告会覆盖 `status` / `published_at` / `published_by`

- `cmd/rpc/blog/internal/logic/notificationservice/update_announcement_logic.go:39-52`
- 相关：`model/base.go:127-129` 的 `Update` 实现是 `Omit("id","created_at","updated_at").Select("*").Updates(&in)`，即**整行写入**

逻辑先 `FindById` 取实体，再改可编辑字段，然后 `TAnnouncementModel.Update(l.ctx, entity)`。注释写的是「状态与发布人由发布/撤回流程维护，不能在这里被覆盖」，但 `Update` 会把这些列一起写回**读取时**的旧值：另一个管理员在这期间发布/撤回，编辑提交后状态会被悄悄改回。发布后编辑可能把 `published` 改回 `draft`（条目还在、内容却是草稿），撤回后编辑可能把 `revoked` 改回 `published`（内容说已发布、条目已被删）。

建议改用 `UpdateFields` 只写可编辑列（`title`/`content`/`category`/`level`/`target_type`/`target_ids`），并按 `id` 定位；读取实体只为回显。（规则 3.3 / 4.1）

### 4.8 复核驳回只清理了「评论被回复」，没清理「内容收到评论」

- `cmd/rpc/blog/internal/logic/discussionservice/review_notify.go:71-97`（`emitRejected`）
- 相关：`review_notify.go:54-68`（`SceneContentCommented` 的 `ObjectType` 是文章/说说，不是评论）

审核通过时会发两条通知：`SceneCommentReplied`（对象是**评论**）和 `SceneContentCommented`（对象是**文章/说说**）。复核驳回时 `TerminateObject(ObjectComment, [comment.Id])` 只按评论对象清理，前者被删掉，后者（内容作者的「你的文章有新评论」）保留下来——但那条评论已经不可见。

这更像**设计没想清楚**，而不是清理代码漏了一行：`content.commented` 的对象是文章/说说，按「评论」终止天然清不到它，所以应先改 33 号文档再落代码。两种取向里，「载荷里带上评论 id、驳回时一并清理」更贴合文案——「你的文章有新评论」指向的是当前状态，评论已不可见时它就是在说假话；但要注意载荷是 JSON，按它清理需要可索引的引用（或给条目/事件加一列评论引用），不能靠扫 JSON。另一种取向是承认它是历史事实，那就必须改文案，避免让用户点进去找不到评论。（规则 4.5 / 5.2）

### 4.9 删除文章不会清理其评论的通知

- `cmd/rpc/blog/internal/logic/contentservice/batch_delete_articles_logic.go:32-51`

`BatchDeleteArticles` 只删 `t_article_tag`、`t_like`、`t_article`，**不级联删除文章的评论**；随后 `TerminateObject(ObjectArticle, ids)` 只清理对象是文章的通知。「评论被点赞」「评论被回复」的条目对象是评论，因此保留下来，而它们的 `link` 指向 `/article/{id}`——文章已删，点开即 404。

这是通知对象与跳转目标分离导致的：清理按「分组对象」走，死链按「跳转目标」判断。**评论是否随文章删除应由讨论域裁决，不该由通知需求驱动**，所以不建议把「级联删评论」作为通知侧的解法。更合适的是按跳转目标清理：删文章时额外清理 `topic` 指向它的评论类条目。同样要注意可索引性——条目只存了评论对象，`topic` 目前在事件载荷里，要么加一列，要么接受一次按场景 + 载荷的扫描（删除是低频操作，可接受）。（规则 4.5）

### 4.10 用户注销的条目清理没有接线

- `cmd/rpc/blog/internal/logic/userservice/deactivate_account_logic.go:60-70`
- 相关：`TerminateObject` 的调用点只有文章、说说、评论（`grep` 全仓确认没有 `ObjectUser`）

实现者确认这是**刻意不做**：当前的「注销」是带 30 天冷静期、可复活的停用，清空收件箱会破坏复活体验。所以它不是「代码缺一根线」，而是**方案措辞与实现语义不一致**：应把方案里的「用户注销时清理」改成「硬删除用户时清理」，并说明可复活的停用不清理。（规则 1.5 / 4.5）

### 4.11 读者端 SSE 没有心跳，与客户端 45 秒静默判定叠加

- `cmd/api/app/internal/handler/notification/notify_stream/notification_stream_handler.go`（无心跳）
- `blog-app/src/composables/useNotificationStream.ts:16-17`（`StaleTimeout = 45000`，注释写明「服务端心跳 15s，取 3 倍」）
- 对照：`cmd/api/admin/internal/handler/notification/notify_stream/beat.go:15`（`HeartbeatInterval = 15s`）

客户端按「服务端每 15 秒一条心跳」设计静默上限 45 秒，但读者端 handler 根本不发心跳。于是即便连接完全正常、只是没有新通知，客户端也会在 45 秒后判定链路已死、主动 abort 并重连。单看两端都自洽，合起来是持续的行为缺陷。

更严重的是它与 §3.2 叠加：每次 45 秒重连都会取消请求 context，而桥接 goroutine 不观察取消，`sub.Close()` 不执行——**每个在线用户每 45 秒泄漏一个 goroutine 与一条 Redis 订阅**。修 §3.2 能让重连只浪费流量，补心跳才能消掉 45 秒一次的重连本身；两条应一起做。（规则 3.5 / 5.2）

## 七、优化建议（按优先级）

## 八、值得肯定

- **投递表即队列**：`claimDeliveries` 的 `SKIP LOCKED` + 租约 + 独立尝试计数，进程崩溃后租约到期自动回队，设计干净。
- **`Entry.External` + `writeDeliveries` 拆分**：站内信不可能再进入投递表，上一轮的 inbox 投递 bug 从模型上消失。
- **`review_notify.go`**：通过/驳回两条路径分开，复核驳回先回收再发结果，时序与设计一致。
- **`token.go`**：签发与校验两端都拒绝强制分组，签名用 `hmac.Equal` 常量时间比较。
- **`job.Runner` + `blog.go` 启动顺序**：先声明消费拓扑再启动 outbox relay，关闭时先停后台任务再释放资源。

## 九、结论

改动整体是「设计落地」而不是「功能堆叠」，写入管线、扇出可重入、投递队列、审核时序都站得住。合并前必须处理 §3 的三条；其中 §3.1 会让邮件投递整体失效，§3.2 会在读者端断线时累积泄漏，§3.3 是可被利用的通知注入。其余 Should Fix 建议在前后端联调前收掉。
