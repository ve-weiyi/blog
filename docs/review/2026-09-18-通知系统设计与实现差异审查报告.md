## 二、结论概览

| 类别 | 内容 |
|---|---|
| **一致** | 权威状态在库；推送只做信号；发布与撤回共用事件管道；先落库后广播；推送失败不影响发布结果；未读数由查询派生而非增量维护；服务端有建连限流；前端有兜底对账 |
| **代码做了、文档说不要** | 广播写扩散；逐行已读标记 |
| **文档要求、代码没有** | outbox；事件版本号与 LWW；撤回时间窗 |
| **文档说不要、代码做了且做得对** | 内容的草稿态 |
| **文档与代码均未覆盖的问题** | `MarkRecordRead` 缺归属校验；`biz_id` 定义未接线；消费者不校验消息状态（§7.4，**已修**）；`publish` 状态判断非原子（§7.5，**已修**）；撤回的跨表不一致（§7.1，**已修**）；死代码（**已删**） |

**总体判断**：实现质量不低——注释解释了关键取舍（为何先落库后广播、为何事件不带收件人），有中间件测试，前端有兜底对账。主要问题不是"实现有 bug"，而是**文档在最近一轮按行业实践重构后，与既有实现走向了两条不同路线**（读扩散 + 水位线 vs 写扩散 + 逐行标记），且实现侧少了几个可靠性环节。

**修复进展**：截至 2026-09-18 第二轮，本报告列出的高优先级问题多数已修复（逐条见 §十一）；文档侧的对齐已完成（见 §十）。**剩余项与终端用户读者端相关度最高**，建议与其一起做。

## 三、模型层

### 3.1 广播是写扩散，文档要求读扩散 —— **方向性分歧**

**文档** §3.2：广播「投递记录**不按用户写行**」。
**代码**：`consume_inbox_message_logic.go:113` 与 `publish_notify_message_logic.go:118` 对 `target_type = "all"` 的处理：

```go
users, err := l.svcCtx.TUserModel.FindALL(ctx, "status = ?", 1)  // 全量拉用户
for _, u := range users { ids = append(ids, u.UserId) }
```

随后为**每个用户插入一条 `t_notify_record`**。

**影响**：一条全员公告的写入量、存储量与接收者数线性相关。当前用户规模下无碍，但这是文档 §八「何时重新审视」的第一条触发条件。

**两条路线各自自洽**：写扩散 + 逐行已读，或读扩散 + 水位线。**当前状态是文档已改为后者、代码仍是前者**——不是谁错，是没对齐。

### 3.2 已读是逐行标记，文档要求水位线 —— **成本差异最大的一处**

**代码**：`t_notify_record.status = unread | read` + `read_at`，配合三个接口。

`mark_all_records_read_logic.go:33` 的全部已读：

```go
UpdateFields({"status": "read", "read_at": now},
  "channel = ? AND recipient = ? AND status = ?", "inbox", userId, "unread")
```

**写入量 = 该用户全部未读行数**。文档 §3.3 的水位线是 O(1) 单次写入。

### 3.3 未读计数由 COUNT 派生 —— **代码符合文档要求**

`list_user_inbox_records_logic.go:102`：

```go
unreadTotal, err = TNotifyRecordModel.FindCount(ctx,
  "channel = ? AND recipient = ? AND status = ?", "inbox", in.UserId, "unread")
```

文档 §3.3 要求"未读计数是派生量、不做增量维护"——**代码完全符合**，天然可重算、不会漂移。

**注**：文档推水位线是更省的方案，但**不能说当前实现有正确性问题**，只是每次查询多一次 COUNT 扫描。

### 3.4 撤回把两个正交维度压进一列

`revoke_notify_message_logic.go:49-52`：

```go
UpdateFields({"status": "revoked"},
  "message_id = ? AND channel = ? AND status = ?", in.Id, "inbox", "unread")
```

`status` 一个字段同时承载**已读状态**（unread/read）与**可见性**（revoked）。文档 §3.4 明确要求「撤回只改变**可见性口径**，不改变其存在」——实现将两者合并。

**直接后果**：撤回后无法再区分"从未读过"与"被撤回时未读"，而文档 §3.2 恰恰需要这个区分来算「仅未读者」。

**已排除的一条疑似缺陷**：撤回后调用 `MarkRecordRead` 不会让记录复活——该接口的 WHERE 是 `status = ? AND id = ?`（`mark_record_read_logic.go`，参数 `"unread"`），revoked 记录不匹配。`MarkAllRecordsRead` 同样带 `status = 'unread'` 条件。**两条路径均安全。**

### 3.5 内容的草稿态：**代码是对的，文档该改**

| | 内容 |
|---|---|
| 文档 §六 | 「**明确不引入**内容的草稿态。内容状态机只含**已发布 / 已撤回**两态，创建即发布」 |
| 代码 | `t_notify_message_model.go:47` status 枚举含 `draft`，默认值即 draft；`publish_notify_message_logic.go:40` 要求 `status == "draft"`；`update_notify_message_logic.go:39` 只允许编辑 draft |

**判断**：**代码的实现更合理**。没有 draft 就无法"先写后发"，而管理端发布是人工动作，草稿是刚需；且当前实现顺带保证了"已发布内容不可编辑"，这是正确的约束。**建议修改文档，而非删除 draft。**

## 四、投递链路

### 4.1 没有 outbox —— **可靠性缺口，优先级最高**

`publish_notify_message_logic.go:50-57`：

```go
_, err = TNotifyMessageModel.UpdateFields(ctx, fields, "id = ?", in.Id)   // ① 状态改为 published
if err != nil { return nil, err }

event := &mq.InboxMessageEvent{MessageId: msg.Id}
err = mq.PublishInboxMessageEvent(ctx, event)                              // ② 发出投递事件
```

**①② 不在同一事务，中间没有任何补偿。**

- 进程在 ①② 之间崩溃 → 消息状态已是 published，投递事件从未发出，**永远不会被投递**
- 没有任何机制能发现这条消息（无 outbox 表、无对账任务）

文档 §4.1 要求的是「事务内落库 + outbox 事件」，实现在这一点上没有对齐。

**现成的改造基础**：项目已有"DB 写后发消息"的机制——`infra/dbnotify/callback.go` 注册了 GORM 回调，在 `t_api` / `t_role` / `t_role_api` 写操作后发布 Redis 失效消息。**把通知表加进其映射即可获得同事务发消息的能力**，比新造一套 outbox 便宜。

### 4.2 `biz_id` 定义了却全程未接线

`t_notify_record.biz_id` 注释为"业务幂等键"，proto 中亦有该字段，但**两条插入路径都没有填**：

- `consume_inbox_message_logic.go:66-73`
- `publish_notify_message_logic.go:67-74`

（`template_code` 同样未填。）

于是幂等只能退化为 `consume_inbox_message_logic.go:48` 的做法：

```go
existing, _ := TNotifyRecordModel.FindALL(ctx, "message_id = ? AND channel = ?", event.MessageId, "inbox")
// 再在内存中建 set 去重
```

**把该消息的全部投递记录拉进内存**。接收者为 N 时，每次消息重投都要 SELECT N 行。

### 4.3 两条投递路径不一致

| 路径 | 批量方式 | 执行位置 |
|---|---|---|
| MQ 消费者（`consume_inbox_message_logic.go:81`） | `InsertBatch` | 异步 |
| MQ 不可用时的降级路径（`publish_notify_message_logic.go:75`） | **逐条 `Insert`** | **发布请求的同步链路内** |

降级路径在同步链路里跑完整用户列表的展开与逐条插入。MQ 故障本身就是高负载场景，此路径会进一步放大。

### 4.4 先落库后广播的时序处理 —— **实现正确**

两条路径都遵守"投递记录落库后再广播"，且注释写明了原因（信号早于记录写入会导致该次回查查不到）。文档 §4.3 的一致性说明在此得到落实。

## 七、文档未覆盖、实现侧发现的问题

### 7.1 撤回的跨表不一致（静默）

`revoke_notify_message_logic.go:43-55`：message 状态更新与 record 状态更新**不在同一事务**，且 record 那步失败只记日志不返回：

```go
_, err = TNotifyRecordModel.UpdateFields(ctx, {"status": "revoked"}, "...")
if err != nil {
    l.Errorf("RevokeNotifyMessage UpdateFields error: %v", err)   // 错误被吞
}
```

**可能的终态**：message 已是 revoked + 事件已广播 + record 仍是 unread。

此时客户端回查列表，过滤条件是 `status != 'revoked'`（`list_user_inbox_records_logic.go:39`），而该 record 的 status 是 `unread` —— **那条已被撤回的通知仍然可见**。且调用方拿到的是 `Success: true`。

### 7.2 `MarkRecordRead` 缺归属校验

```go
UpdateFields({...}, "id = ? AND status = ?", in.Id, "unread")
```

**不校验 `recipient` 是否为调用者**。任何通过 AdminAuth 的调用方均可按 ID 标记他人的记录为已读。

在 admin 网关下或许可接受，但这与文档"读者端标记自己的已读"的设计语义不符。**需明确是否有意为之。**

另：该接口固定返回 `Success: true`，行数为 0（记录不存在 / 已读 / 非 unread）时无区分。

### 7.3 死代码

`blog-cloud/api/admin/internal/handler/notification/notify_content/` 下 6 个 handler 文件（**已于 2026-09-18 删除**）：

- `routes.go` 无任何引用
- 无对应的 logic 目录（实际在用的一套是 `notify_message/`）

成因已记录在 `docs/feature/2026-09-11-api-admin整理方案.md:191`：`group:` 改名后 goctl 不会重命名已存在的 `handler/<module>/`，旧目录被留下。

### 7.4 消费者不校验消息状态（撤回后可被"复活"）

**原文未覆盖，且属于正确性缺陷。**

`consume_inbox_message_logic.go` 的 `Consume` 读到消息后**不检查 `msg.Status`**，直接展开收件人并插入 `unread` 记录。而撤回路径只回收"当时已存在"的未读记录。于是：

```
t1  发布：status=published，提交，投递事件入队
t2  撤回：status=revoked，把已存在的 unread 记录标记为 revoked（此刻可能一条都还没有）
t3  消费者拿到队列里那个事件 → 为一条「已撤回」的消息插入 N 条 unread 记录
```

**结果：撤回的公告对所有人可见且是未读状态。** 窗口是 MQ 投递延迟，用户量大时消费者展开本身也要时间，"发布后马上撤回"是现实场景。

**已于 2026-09-18 修复**（§十一 #3），与文档 §3.4「未投递 → 不再投递」一致。

### 7.5 `publish` 的状态判断不是原子的

`publish_notify_message_logic.go` 是"先 `FindById` 判 `status == draft`，再按 `id` 更新"。两次并发发布会同时通过判断，各自入队一条投递事件。同一形态在 `revoke` 中也存在（已随 §7.1 一并修复）。

**已于 2026-09-18 修复**：WHERE 带上原状态，由影响行数裁决（§十一 #2）。

## 八、优化建议（按优先级）

> 状态截至 2026-09-18 第二轮修复，逐条对应见 §十一。

### P0 · 先定方向，再改代码

1. ✅ **扩散模型已定**：以**写扩散**为准（保持代码现状）。文档 §二决策 3、§3.2、§3.3、§八 已改回并写明理由。
2. ⚠️ **补 outbox**（§4.1）—— **部分完成**。未做自动重投，但已补上**排查入口**：新增"查询已发布但未投递的消息"与"重新投递"两个接口（见 §十一 #5）。能否发现到能否自愈，是两件事，先解决前者。

### P1 · 已有字段未接线，成本低

4. ⬜ **`biz_id` 接线**：插入时填（建议 `{message_id}:{recipient}`），加唯一索引，重投改为 `INSERT IGNORE` / `ON DUPLICATE KEY UPDATE`。可一并去掉"全量 SELECT 去重"。
5. ✅ **撤回的 record 更新已纳入事务**（§十一 #1），失败不再被吞；并补了并发裁决。
6. ⬜ **拆开 `status` 的两个语义**：保留 unread/read，可见性另立一列（或由 message 状态 JOIN 得出）。这是 §3.4 的前置条件，也是「仅未读者」可计算的前提。

### P2 · 清理

7. ✅ 已删除 `notify_content` 孤儿目录（6 个文件）。
8. ✅ **两条投递路径已统一**——降级路径改为**复用消费者逻辑**，比"改用 InsertBatch"更彻底：扇出规则只剩一份实现（§十一 #4）。
9. ⬜ 明确 `MarkRecordRead` 是否需要归属校验。**注意**：现有 `/admin-api/v1/inbox-records/*` 是**管理员跨用户操作**（请求显式带 `user_id`），加归属校验会破坏它——该保证应由**终端用户读者端**结构性地提供，见 §九 #1。
