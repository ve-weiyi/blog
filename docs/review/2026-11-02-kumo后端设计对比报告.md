# kumo 后端设计对比报告

日期：2026-11-02
对比对象：`yocto/kumo`（Go + go-zero + PostgreSQL + RabbitMQ）与 `blog`（Go + go-zero + MySQL + RabbitMQ）
对比范围：kumo 的 `kit/`、`app/`、`admin/`、`user/`、`kcore/`、`botm/`、`log/`、`test/e2e/`、`docs/standards/`、CI 与 `.claude/rules/`
方式：初轮只读阅读与逐项核对；后续按报告结论实施，落地记录见第七节。
路径约定：kumo 路径相对 kumo 仓库根；blog 路径相对 blog 仓库根（后端在 `blog-cloud/`）。

---

## 一、结论

两仓的后端基础设施**高度同源**。`blog-cloud/infra` 与 `vkit` 已经覆盖了 kumo `kit/infra`、`kit/adapter` 的绝大部分：tokenx 轮换、bizerr/responsex、mqx（EventSpec、订阅、死信、重试）、transactional outbox、jobx 式任务 runner、limitx 滑动窗口、storagex 多 provider、redactx、httpx，都能一一对上；`jobx.Runner`、`modelx` 等包的结构与注释也基本一致。

因此，"再从 kumo 搬一个包"的收益很低。真正值得借鉴的是 kumo **已经落地、blog 还停在设计或注释里**的运行期闭环，集中在三件事：

1. 通知扇出的自动对账（崩溃恢复）；
2. 日志与通知的保留期清理；
3. 后台循环的 panic 隔离。

此外，kumo 的端到端契约测试骨架、outbox 的 trace 上下文持久化、对象存储对账等，属于条件性借鉴。

**实施进度（2026-11-03）**：前三项、outbox trace、`initialize/` 拆分、每日统计聚合已完成；E2E 骨架完成，真实链路按决定暂不执行；对象存储对账按决定不做；窄消费接口、SSE 模板主动留后。状态标记见第二节，落地位置见第七节。

## 三、逐项说明

### P0-1 通知扇出的崩溃恢复（✅ 已完成）

**kumo 的做法**

`kcore/internal/job/resident.go:297` 的 `pendingCatchup` 是崩溃恢复兜底：

- 查询创建超过 1 分钟、仍停在 `pending` 的文件，避免与上传后的正常消费竞态；
- 每轮最多 100 条；
- 重发走**同一条 outbox 事件**（`file.submitted`，带 `reason=catchup`），不另开修复分支；
- 依赖未就绪的项（dataset 尚未置备）直接跳过，等下一轮；
- 逐项记录日志，单条失败不影响整轮。

它挂在每分钟一次的 `parsing` cron 上，和正常轮询共用调度。

**blog 的现状**

`cmd/rpc/blog/internal/notification/fanout.go:42` 与 `:101` 两处注释都写着"丢了由兜底扫描补上""只能等兜底扫描"，`docs/design/33-通知.md` 第八节也把"兜底扫描"当作进程内既有的能力。但 `cmd/rpc/blog/blog.go:114-119` 实际只注册了两个任务：

- `outbox-relay`
- `notify-delivery`

没有扫描 `pending`/`fanning` 事件的任务。唤醒消息一旦丢失、或进程在批次之间崩溃，事件会永远停在 `fanning`，该批之后的收件人收不到通知，也不会有告警。目前只能靠管理端 `ListStalledEvents` 发现、`RedeliverEvent` 手工重跑。

**建议形态**

- 查询条件直接复用 `cmd/rpc/blog/internal/logic/notificationservice/list_stalled_events_logic.go:53` 的 `status IN ('pending','fanning') AND updated_at < ?`；
- 阈值取大于一批扇出耗时的值（如 5 分钟），避开正常唤醒的竞态；
- 经 outbox 重发 `FanoutMessage`。`Fanout` 内部已有事件行锁、状态复查、游标与 `(recipient_id, dedupe_key)` 去重，重发是安全的；
- 每轮限量（如 100 条），逐项失败只记日志。

**为什么排在第一位**：改动面小、不改表结构、直接补上设计 33 已写明但代码缺失的部分，且失效时用户无感。

### P0-2 保留期清理（✅ 已完成：通知 + 日志）

**kumo 的做法**

`log/internal/job/retention.go`：

- cron 每日 03:00 执行，`SkipIfStillRunning` + `Recover`；
- 逐表处理，超过上限（每表 300 万行）才删；
- 每次删 5000 行，循环直到删够；
- 每张表写一条 task log，失败时记录"已删 N/M"，而不是只打一行错误；
- 删除条件按 `created_at ASC`，保留最新数据。

**blog 的现状**

`infra/domain/notify/scene.go:72-74` 已为每个场景声明 `ReadTTL` / `UnreadTTL`（互动类 90/180 天，公告 180/365 天），并有测试保证"未读不短于已读"；`docs/design/33-通知.md` §3.7 也写清了"未读也要过期""条目与投递同批删""按场景索引分批"。

但没有任何任务消费这些 TTL。四张日志表（`t_login_log`、`t_operation_log`、`t_upload_log`、`t_visit_log`）也没有清理任务。结果就是表只增不减。

**建议形态**

- 通知：按场景分别删已读/未读，条目与其投递在同一批、同一事务内删除；事件行只回收"已终止且无引用条目"的；
- 日志：按时间窗（如 90/180 天）分批删除，行数上限作为兜底；
- 每批独立事务、按 id 游标推进，避免深 offset 与大事务锁；
- 每天低峰执行，并记录每轮删除量。

### P1-1 后台循环的 panic 隔离（✅ 已完成）

`cmd/rpc/blog/internal/notification/delivery_worker.go:60-80` 与 `cmd/rpc/blog/internal/mq/outbox/relay.go:136-150` 都是裸 goroutine + ticker。ticker 本身不会重入（缓冲为 1，慢批次会丢 tick），这一点没有问题；缺的是**一轮处理内部 panic 会把整个 rpc 进程带走**。

kumo 在 cron 层统一挂 `Recover`，把单轮失败限制在单轮。blog 不一定要引入 `robfig/cron`，在两个循环各包一层 `defer recover() + Errorw` 即可。

### P1-2 端到端契约测试（⏭ 骨架完成，真实链路暂不执行）

kumo 的 `test/e2e/` 约 2.6k 行 Python，真正值得借鉴的是四条性质：

1. **endpoint 清单从 `.api` 机器生成**（`spec/endpoints.json`，125 条），用例只绑定 operation，不写死路径；
2. **`spec/safety.json` 给每个操作分级**（normal / heavy / destructive / unimplemented），未登记的操作不允许执行；
3. **数据隔离与清理**：`e2e-<run_id>-` 前缀、逆序清理、run lock、只从 `{{ctx.created.*}}` 取 id；
4. **退出码区分**：0 通过 / 1 断言失败 / 2 环境失败 / 3 覆盖率或契约漂移 / 4 清理残留。

blog 有 21 个 `.api` 文件，goctlx 已能解析契约，生成清单成本不高。建议只做一条 smoke 链：

注册 → 登录 → 发文章 → 评论 → 通知读取 → 退订。

先证明"上线前契约没破"，再逐步扩套件；不要一开始铺全量。

### P2 其余项

- ✅ **outbox trace 上下文**：`cmd/rpc/blog/internal/mq/outbox/model.go` 有 `Headers` 字段，但 `store.go` 的 `Enqueue` 只序列化调用方传入的 headers。vkit 的 mqx 在**发布时**注入 trace；outbox 是延迟发布，发布时的 ctx 已是 relay 的，原始请求的 trace 断链。kumo 在 `kit/infra/outbox/capture.go` 里于写入时捕获 trace 并持久化。blog 已把当时的 `trace_id` 写进 headers。
- ⏭ **对象存储对账**：kumo 有只读的 `reconcileStorage` 与上传失败补偿。blog 的上传（网关直接写对象存储）与建记录（rpc）是两跳，第二步失败会留孤儿文件。**不做**：URL 长期可访问，按当前决定不做对账；前提是 CDN/域名与 provider 配置不变。
- ⏸ **窄消费接口**：kumo 用 `storagex.ImageStore` 只暴露消费者需要的方法；blog 的 `svcCtx.StorageProvider` 是全集。消费者应按需依赖窄接口。**留后**：三个方法各有消费者，拆分无行为收益。
- ⏸ **SSE 模板**：kumo 把 SSE handler/logic/route 固化进 goctl 模板（flush、`data:` 帧、channel、禁缓冲）。blog 的 goctlx 没有 SSE 模板，`cmd/api/app/internal/sse` 是手写的；再出现第二个 SSE 端点时容易漂移。**留后**：goctlx 从 Swagger 生成，Swagger 没有 `sse` 语义。
- ✅ **初始化拆分**：kumo 是 `internal/initialize/{gorm,redis}.go` + 108 行 svc；blog 已把连接与适配器装配拆成 `cmd/rpc/blog/internal/svc/` 下的 `gorm.go`、`redis.go`、`email.go`、`sms.go`、`oauth.go`、`migrate.go`，`service_context.go` 只保留容器与业务装配。

## 四、不建议借鉴

- **拆成六服务、每服务一库**：kumo 的 app/admin/user/kcore/botm/log 拆分是规模与团队边界驱动的。博客规模下，跨服务事务、调试与部署成本远大于隔离收益；单 rpc + 两网关是合适的。
- **k8s / bot 编排、RAGFlow / Seafile、MCP、GPU 调度**：领域不相关。
- **PostgreSQL 专属 DDL**（部分唯一索引、`ANY(array)` 权限 SQL）：blog 是 MySQL，语义不同。
- **kumo 的无锁 cron**：kumo 自身就是单副本假设，多副本会重复执行。blog 扩副本时，清理与扫描必须先加单活约束（`GET_LOCK` 或 SKIP LOCKED 租约），不要照抄。
- **kumo 文档里的"5 级 RBAC"**：代码里已不成立（实际是 tier + team role）；blog 的 role-api 模型更完整，不应回退。
- **再复制一份 `x/`、`mqx`、`storagex`**：vkit 已有，第二份只会漂移。

## 五、建议落地顺序（执行状态）

按以下顺序执行：

1. ✅ **通知扇出对账**：复用 `ListStalledEvents` 的查询与 `FanoutMessage`，新增一个后台任务；

3. ✅ **后台循环 recover**：由 `job.Guard` / `job.Periodic` 统一处理。

前三项都不改表结构，都能复用现有索引与查询，且正好补上 `docs/design/33-通知.md` 已经写明、代码尚未实现的部分。
