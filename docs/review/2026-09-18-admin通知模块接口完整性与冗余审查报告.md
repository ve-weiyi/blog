# admin 通知模块：接口完整性与冗余审查报告

日期：2026-09-18
对照文档：`docs/design/09-BLOG-消息通知系统设计.md`
审查范围：admin 网关的 21 条通知路由、其下游 RPC 与模型、以及前端的实际消费面

## 一、审查范围与口径

### 1.1 与既有报告的分工

同日已有一份《2026-09-18-通知系统设计与实现差异审查报告》，覆盖的是**语义层**——递散模型（写扩散 / 读扩散）、outbox、事件版本号与 LWW、撤回时间窗、跨表一致性、死代码等。

**本报告不重复那份的条目**，只做**接口面**的审查：受众边界、契约形状、端点冗余、以及"设计要求有某类端点而实现里没有"这类**结构性缺失**。两份报告在少数条目上视角不同（同一事实，一份按语义记、一份按接口记），§八 给出了逐条对照。

### 1.2 判"完整"的尺子

以 doc 09 中**可判定为"有 / 没有"的硬性要求**为准：

| 出处 | 要求 |
|---|---|
| §六 契约表 | 管理端三类动作 + **读者端两类契约** |
| §3.3 | 标记已读**必须校验记录归属**；已读只进不退；"全部已读"是服务端一次批量迁移 |
| §3.4 | **可见性与已读状态必须是两个正交的维度**；**投递记录一律保留**，撤回只改可见性口径、不改其存在 |
| §七 | **不物理删除**——撤回一律为状态流转，墓碑在保留期内不得回收 |
| §五 | 撤回时间窗 24h；频次控制；断线补偿必须给出降级信号、**禁止静默截断**；多端已读同步 |
| §4.4 | 连接注册表**必须外置且每条带 TTL**；注册表批量续租 |
| §4.3 | 推送**只发信号不发内容** |

### 1.3 未覆盖

`blog-app` 侧、邮件/短信通道适配器内部、验证码链路、SSE 帧格式与前端 `sseEvents.ts` 的一致性（归既有报告）。

## 二、结论概览

| 类别 | 内容 |
|---|---|
| **主干完整** | 发布 → 撤回 → 台账 → 人工重发，四段齐全；草稿态、幂等已读、派生未读数、快照可见性口径均正确 |
| **契约级缺失** | **读者端契约组整组缺失**（§六）；**标记已读不校验归属**（§3.3）；**投递记录批删无归属校验且物理删除**（§七，危害最高） |
| **参数级缺失** | 撤回时间窗、频次控制、补发降级信号、多端已读同步（§五）；连接注册表与按人定向（§4.4）；inbox 通道无"失败终态" |
| **模型级缺失** | `status` 单列混合可见性与已读（§3.4）；**消息批删无状态守卫，留下孤儿投递记录**；`biz_id` 未接线；无组合索引 |
| **推送越界** | 事件携带 `Title` 且**全局单频道广播**，与 §4.3「只发信号不发内容」相反 |
| **真冗余** | 2 条可删的零调用端点（另 1 条亦零调用，判为未接线，见 §5.2）、4 次写完回查（可优化，非多余）、两种成功响应形态、1 处异形分页、**3** 处不检查影响行数 |
| **不是冗余、易误删** | `batch-mark-read`（未接线，非冗余）、`undelivered`/`redeliver`（唯一兜底）、`inbox-records` 与 `notify-records` 并存（两个受众） |

**总体判断**：这 21 条路由的**结构问题只有一个根因**——记录域的两组端点（`/inbox-records`、`/notify-records`）被**两个受众共用**：管理控制台的跨用户查询，与终端用户自己的收件箱。doc 09 §六 要求的读者端因此无处安放，§3.3 的归属校验也因此加不上，销毁类操作（批删）同样被普通用户触达。其余缺漏都是这一条的下游影响，或是 §五/§4.4 未实现的工程参数。

主干无结构性错误。

### 4.2 P0 —— 契约级缺失

#### 4.2.1 读者端契约组整组缺失

**doc 09 §六**：*"两类读者：后台管理员与终端用户……差别只在挂载点与鉴权——管理端走管理前缀 + 管理员鉴权，读者端走普通用户前缀 + 用户态鉴权"*，并要求读者端提供「状态快照（**只返回属于调用者自己的记录**）」与「标记已读（单条 / 批量 / 全部）」。

**实现**：读者端不存在。`protocol/api/app/` 下无任何通知契约，`blog-cloud/api/app/` 无通知 logic。终端用户界面全部骑在 admin 端点上：

| 消费方 | 文件:行 | 调用的 admin 端点 | 状态 |
|---|---|---|---|
| 未读轮询（SSE 事件触发 + 5 分钟对账） | `blog-admin/src/stores/notification.ts:43` | `GET /admin-api/v1/inbox-records` | **活** |
| 用户"我的通知"页 | `blog-admin/src/views/profile/notice/index.vue:148` | 同上；另 `:181` 调 `POST /notify-records/batch-delete` | **活** |
| ~~顶栏铃铛~~ | `components/NoticeDropdown/useNotice.ts:27` | 同上 | **死代码**——全仓零引用，项目自己的 TODO 已标注：`composables/sse/index.ts:23` "*顶部入口 `components/NoticeDropdown/` 是零引用死代码*" |

即**活跃消费方只有 2 个**（未读轮询、个人页）。铃铛未接线，故未读数的 UI 出口只有「我的通知」页——这一点削弱了"影响面广"的直觉，但不改变结论：读者端缺失仍成立，因为个人页本身就是普通用户在使用。

#### 4.2.2 标记已读不校验归属

**doc 09 §3.3**：*"标记已读必须校验归属。接口只允许操作属于调用者自己的记录——否则任何人都能按 ID 抹掉他人的未读角标。"*

**实现**：三个已读接口全部只有 `id`，无 `recipient` 约束。

| 接口 | 文件:行 | WHERE 子句 |
|---|---|---|
| `MarkRecordRead` | `mark_record_read_logic.go:34-36` | `id = ? AND status = ?` |
| `BatchMarkRecordsRead` | `batch_mark_records_read_logic.go:45-46` | `status = ? AND id IN (...)` |
| `MarkAllRecordsRead` | `mark_all_records_read_logic.go:33` | `channel = ? AND recipient = ? AND status = ?`——但 `recipient` 取自 `in.UserId`，即**调用方自报** |

三者都无 `recipient` 约束。（`BatchMarkRecordsRead` 连 `channel` 也不限，与另两个不一致；因 `unread` 仅存在于 inbox 通道，当前无实际影响。）

#### 4.2.3 身份的可用性与实际来源不一致（根因）

**服务端本来就有可信身份**：`adminauth_middleware.go:35` 已从 header 取到 `uid` 并用 `tokenx` 以 `uid + deviceId + token` 三要素验签。

**但通知模块把它丢弃了**，改用请求体里的 `user_id`：

```
admin: query_user_inbox_record_list_logic.go:31   UserId: req.UserId
       mark_all_records_read_logic.go:30          UserId: req.UserId
rpc:   list_user_inbox_records_logic.go:38        WHERE recipient = in.UserId
       mark_all_records_read_logic.go:33          WHERE recipient = in.UserId
```

从 HTTP 入参到 SQL `WHERE`，**没有任何一层从 token 派生身份**。

**而取身份的手段是现成的、且在同一网关里已被使用**：`metax.GetApiUserIdFromCtx(l.ctx)` 从 outgoing gRPC metadata 里读 `bizheader.HeaderUid`（`infra/metax/meta_api.go:13-26`），该 metadata 由拦截器按白名单从 HTTP header 透传而来。admin 网关内已有 **8 处**调用（如 `logic/account/auth/logout_logic.go:30`、`logic/common/upload/upload_file_logic.go:53`），`metax` 包本身也导出了该函数。

即：这**不是"缺少管道"，而是"管道现成却不用"**。同一条链路上，`adminauth_middleware.go:35`、`permission_middleware.go:29`、`operationlog_middleware.go:114` 三处都从 header 读到了 uid（最后一处还把它写进了操作日志），通知模块是唯一的例外。

**是否可被越权**取决于 `Permission` 中间件对该路径的放行面——仓库内无 `t_api` 种子数据（`protocol/sql/blog-data.sql` 无 INSERT），**无法从仓库判定**。但有一条**使未注册路径天然放行**的机制必须指出，它正是决定 §4.2.2 严重性的那一环：

- `permissionx/rbac_enforcer.go:220-223`：当 `METHOD:PATH` 未被任何角色引用（不在 `allPerms`）时**直接 `return true, nil`**（日志 `unregistered, allowed`）；
- `permissionx/rbac_enforcer.go:201-205`：`root` 角色全放行。

即 `/admin-api/v1/inbox-records` 只要未被登记，`Permission` 对它就是**空操作**，§4.2.2 的缺失归属校验便从"设计缺陷"变成"可利用"。

#### 4.2.5 初稿理由更正：加归属约束**不会**破坏现有调用方

初稿此处写的是"不能给现有端点加 `recipient` 约束，会废掉管理控制台的跨用户查询"。**这个理由不成立，特此更正**——它会让修复被高估成"必须新增一整组端点"。

| 事实 | 证据 |
|---|---|
| `/inbox-records` 的**活跃**调用方只有 2 个 | `stores/notification.ts:38`（`AuthStorage.getUid()`）、`views/profile/notice/index.vue:144`（`userStore.userInfo.user_id`） |
| 二者传的**都是调用者自己的 uid** | 同上。第三个调用方 `NoticeDropdown/useNotice.ts:27` 是死代码（§4.2.1） |
| 管理端台账走的是**另一组**端点 | `record/config/content.ts:25` → `queryNotifyRecordList` → `/notify-records`；其 `recipient` 搜索在 `record/config/search.ts:45` |

也就是说，`/inbox-records` 的"跨用户查询能力"是**设计出来的、但当前无任何消费者**。加一条由令牌派生的 `recipient` 约束**不会破坏任何现有调用方**。

这改变的是**修复的路径**，不改变**结论**：读者端仍应新增（doc 09 §六 明确要求按受众分挂载点与鉴权），但可以先做一条成本极低的过渡措施，无需等读者端建好（见 §七）。

#### 4.2.4 投递记录的批删：无归属校验 + 物理删除

**这一条的危害高于 4.2.2 的三条，初稿遗漏。**

| 环节 | 内容 |
|---|---|
| 契约 | `notification.api:154` `DeleteNotifyRecordReq { Ids []int64 }`——**入参里没有身份字段** |
| admin logic | `api/admin/internal/logic/notification/notify_record/batch_delete_notify_record_logic.go:28-31`，只透传 `Ids` |
| rpc logic | `rpc/blog/internal/logic/notificationservice/batch_delete_notify_records_logic.go:28-34`，逐 id `TNotifyRecordModel.Delete(l.ctx, id)` |
| 调用方 | `blog-admin/src/views/profile/notice/index.vue:181`——**普通用户的"我的通知"页** |

**两个问题叠加**：

1. **无归属校验** —— 与 4.2.2 同源，但这条是**销毁**（凭 id 删掉他人的投递记录），而非抹掉未读角标。
2. **物理删除** —— `t_notify_record` 无 `deleted_at` 列，`Delete` 是真删除，直接违反 doc 09 §七「**不物理删除**——撤回一律为状态流转；墓碑在保留期内不得回收」与 §3.4「投递记录一律保留」。

**初稿为何漏掉**：§1.2 的「尺子」表未收录 §七，物理删除类缺陷因此在判定标准之外。尺子已补，缺陷随之纳入。

### 4.3 P1 —— §五 参数表的约定基本未实现

| # | §五 约定 | 现状 | 证据 |
|---|---|---|---|
| 1 | **撤回时间窗 24h**，超出即拒绝 | ❌ 无 | `revoke_notify_message_logic.go:36` 只判 `status != "published"` |
| 2 | **频次控制**：每用户每日上限 + 两条之间最小间隔，超限丢弃不排队 | ❌ 无 | 发布链路 `publish_notify_message_logic.go` 无任何限流 |
| 3 | **补发响应必须携带"是否连续"的标志**、**禁止静默截断** | ❌ 无该字段、无该端点；且 `sse/broker.go:73` 缓冲满时**静默丢帧** | `SubscriberBuffer = 64`（`broker.go:18`），`Publish` 的 `default:` 分支直接丢弃 |
| 4 | **多端**：一端的已读需作为事件同步到其他端 | ❌ 无此类事件 | `notifyx` 只有 `EventNotice` / `EventNoticeRevoke` 两个类型（`event.go:18-23`） |

第 3 条的丢帧语义值得单独说明：`broker.go:17` 的注释称*"丢帧由客户端重连时的回查补齐"*，而 §五 点名禁止的正是这种"客户端无法区分'没有新数据'与'数据被丢了'"的形态（该节以 Twitter `since_id` 为反面案例）。因丢的是**信号**而非数据，危害从"永久丢消息"降为"未读数停留在旧值直到下一个事件或对账轮询"。**该前提已核实成立**：`blog-admin/src/composables/sse/index.ts:13,44` 有 `ReconcileIntervalMs = 5 * 60 * 1000` 的 `setInterval(() => refreshUnread(), ...)`。故此处是**形态违反**（静默截断），而非实际丢数据——评级据此下调，但 §五 的"必须给出降级信号"仍未实现。

### 4.4 P2 —— §4.4 多副本投递路由的前置件缺失

| # | §4.4 要求 | 现状 | 后果 |
|---|---|---|---|

#### 4.4.1 由此产生的隐私越界

`notifyx.Event` **携带内容元数据**：

```go
// blog-cloud/infra/notifyx/event.go:29-36
Title       string `json:"title,omitempty"`
Category    string `json:"category,omitempty"`
Level       string `json:"level,omitempty"`
```

**是"确实填了值"，不是"定义了没填"**（这一点单独查过）：发布侧实填于 `mq/mqlogic/consume_inbox_message_logic.go:103-110`，值取自 DB 行；三者在 admin 创建契约里是**必填**（`types/notification_notify_message.go:7-10` 无 `,optional`）。**撤回事件不带**——`revoke_notify_message_logic.go:71-74` 只填 `Type + MessageId`，故本问题**仅对发布事件成立**。

而该事件经**全局单频道**推给**所有在线连接**：`sse.Bridge(l.ctx, l.svcCtx.NotifyBroker, client)` 不带 userId（`notify_stream_logic.go:34`），且 handler / logic / bridge / broker / subscriber **五层均无按人过滤**（`sse/` 与 `notifyx/` 两目录下 grep `recipient|userId|uid|target|filter` 零命中）。

**受众比"管理员"宽得多——初稿低估了**：

| 环节 | 事实 |
|---|---|
| SSE 路由中间件 | `notification.api:291` / `routes.go:920` = `AdminAuth, NotifyStreamLimit`，**无 `Permission`** |
| `AdminAuth` 的强度 | 只验令牌、**不验角色**（`adminauth_middleware.go:49`） |
| 登录侧 | `rpc/blog/internal/logic/authservice/login_by_password_logic.go:67` 只判 `UserStatusDisabled`，**无角色门槛** |

三者叠加：**任何已启用的登录用户**都能连上这条流，收到每条发布事件的标题——包括 `target_type=user_ids` 的点对点通知。

**与 §4.3 的关系**：doc 09 §4.3 的隐私理由讲的是**推送网关**（Matrix `event_id_only`、FCM collapsible，防的是 APNs/FCM 这类第三方中间人读到内容），而实现的问题是**同侪连接之间互见标题**——比文档的动机更直接。**注意**：既有报告已就"事件带字段"作过决议（改文档措辞为"不带正文"）；本节的实质新增是**广播范围**，冲突点见 §8.3。

两点澄清（不影响结论）：① 官方前端只读 `frame.event`（`composables/sse/index.ts:35-39`），标题是**线缆级泄露**而非界面级渲染；② 慢消费者缓冲满会丢帧（`broker.go:73`），"所有连接"是尽力而为。

## 六、根因

### 6.1 根因一：记录域的端点被两个受众共用

4.2.1–4.2.4 四条是**同源症状**：

```
                   /admin-api/v1/inbox-records        /admin-api/v1/notify-records
                    ├── 管理控制台：查任意用户收件箱      ├── 管理控制台：投递台账
                    └── 终端用户：我的收件箱              └── 终端用户「我的通知」页：批删（:181）
                              ↑                                    ↑
                     同一组端点，两个受众，两套应有的鉴权语义
```

| 症状 | 因果强度（初稿有误，此处更正） |
|---|---|
| 4.2.1 读者端无处安放 | **描述性成立**。严格说"无处安放"是叙事——没有任何机制阻止新增一组契约，缺的是**决策**而非位置 |
| 4.2.2 归属校验缺失 | **因果方向相反**。初稿称"加了会废掉控制台"，实为**无任何消费者**（§4.2.5）。真正的因果是：**因为读者端没建，归属校验才没处落** |
| 4.2.3 身份取自客户端 | **并列症状，非下游**。共用使 `user_id` 入参成为自然的输入形状，但共用**不强制**丢弃 ctx 身份——`metax` 取一次即可，同服务内别处就在用 |
| 4.2.4 批删被普通用户触达 | **成立**。终端用户页确实在调管理端销毁接口 |

**更准确的表述**：这是一组**互相强化的并列症状**——共用端点使"读者端该不该建"被长期搁置；读者端缺席又使归属校验无处落；身份链条因此从未被要求补全。**不宜简化为单一因果链。**

### 6.2 根因二：通知 SSE 通道是全局单频道（独立于 6.1）

4.4.1 的推送越界**与端点如何切分无关**——`notifyx` 不带收件人、`broker` 无频道键是**独立且刻意的设计**（`notifyx/event.go:3-4` 包注释明写*"不携带收件人…避免网关为此展开全量收件人列表"*）。

**即使按 §七 第一优先拆出读者端，4.4.1 依然原样存在。**

初稿把 4.4.1 列在 6.1 因果链的末端，又在 §七 把它列为独立的"第二优先"，**两处自相矛盾**，此处更正。

### 6.3 与根因无关的项

§4.3 的其余条目与 §4.5 全部条目，均属 §五 / §4.4 / §3.4 的工程参数未实现，可独立推进。

## 七、修复建议

按"是否阻塞其他项"排序，不按工作量。

### 第一优先：拆出读者端（解根因）

新增读者端契约组，走普通用户前缀 + 用户态鉴权，身份从 token 派生、**不收 `user_id` 入参**：

| 契约 | 语义 |
|---|---|
| 状态快照：当前可见通知列表 + 未读数 | 只返回 `recipient = <token 派生>` 的记录 |
| 标记已读（单条 / 批量 / 全部） | 幂等、只进不退、**归属由服务端强制** |

管理端 `/admin-api/v1/inbox-records` 保留为管理能力（**注意：当前无消费者**，见 §4.2.5）。活跃消费点只有 2 个需改接：`stores/notification.ts`、`views/profile/notice/index.vue`（`NoticeDropdown/useNotice.ts` 是死代码，可一并删除）。

**不必等读者端建好才有安全收益——可分两步走**：

| 步骤 | 内容 | 代价 |
|---|---|---|
| **过渡（可立即做）** | 三个已读接口 + 收件箱列表，在 rpc 层把 `recipient` 从入参改为**由令牌派生**（`metax.GetApiUserIdFromCtx`）。因无消费者传他人 uid，**不破坏任何调用方**（§4.2.5） | 小，但**必须动契约**：`MarkRecordReadRequest` / `BatchMarkRecordsReadRequest`（`notification.proto:273-284`）**连身份字段都没有**，rpc 侧无鉴权拦截器、且**没有按 id 查单条记录的 RPC**，故仍需改 proto + `.api` + 跑 `generate.sh` |
| **终态** | 新增读者端契约组（普通用户前缀 + 用户态鉴权），消费点改接 | 中 |

读者端仍应建——这是 doc 09 §六 的明确要求；但过渡步骤能先把"任何登录用户可改/删他人记录"堵住。

**这一步同时消解 4.2.1 / 4.2.2 / 4.2.3 的归属问题。** 4.2.4 的**归属**部分同被消解，但它的**物理删除**部分需要独立决策：

| 选项 | 后果 |
|---|---|
| 读者端不提供删除 | 最简，但用户无法清理自己的列表 |
| 改为可见性流转（新增 `deleted`，`Delete` 改 `UpdateFields`） | 满足 §七「不物理删除」；需与 §4.5 #1 的 `status` 拆列一并做，否则又是一列混三个维度 |
| 维持物理删除、只在文档记为例外 | 与 §七 直接冲突，需先改文档并说明理由 |

**顺手要一并处理的**：`BatchDeleteNotifyMessages` 的 `status = 'draft'` 守卫（§4.5 #7）——两条批删实现口径不一致，同为 `Delete*`，一条有守卫一条没有。

### 第二优先：§4.3 推送越界（改动小、性质重）

二选一：

- **事件不带正文**（对齐 §4.3 原文）——从 `notifyx.Event` 移除 `Title/Category/Level`。**注意需三处同步**：`notifyx/event.go`、`notification.api` 的 `NotifyStreamEvent`、前端 `sseEvents.ts`

| 项 | 出处 | 规模 |
