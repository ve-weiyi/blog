旧实现从 `blog-cloud` 的 `HEAD^`（`737fc05`）取回后逐服务移植——该提交是 `protocol` 大规模改名前的最后一个状态。

## 四、发现并修复的契约缺陷

### `MenuMeta.type` 契约与存储层不一致

移植 `accessservice` 时撞上：`int64` 与 `string` 两边对不上，无法编译。

```
HEAD~3  menu.api        Type string
HEAD~2  permission.api  Type string
HEAD~1  access.api      Type int64   ← 改动发生在这次
```

而下游四层全部是字符串：

| 层 | 类型 | 证据 |
|---|---|---|
| DB 列 | `varchar(64)` | `../../protocol/sql/blog.sql` |
| model | `string` | `TMenu.Type` |
| 前端 | 字符串枚举 | `MenuTypeEnum.CATALOG = "CATALOG"` / `MENU` / `BUTTON` |
| 存量数据 | 空串 `''` | `../../protocol/sql/blog-data.sql` |

当初协议评审给 `MenuMeta` 用 `int64` 的理由是「对应 DB 列」，与事实不符——DB 列本就是 `varchar`。

**处置**：改回 `string`，同时修正注释（实际取值是 `CATALOG`/`MENU`/`BUTTON`，不是 `0/1/2/3`）。

```diff
-		Type       int64             `json:"type"` // 菜单类型（0代表目录、1代表菜单、2代表按钮、3代表外链）
+		Type       string            `json:"type"` // 菜单类型（CATALOG目录、MENU菜单、BUTTON按钮）
-  int64 type = 1;                 // 菜单类型 0目录 1菜单 2按钮 3外链
+  string type = 1;                // 菜单类型 CATALOG目录 MENU菜单 BUTTON按钮
```

## 五、发现并修复的旧代码缺陷

### `service/app/rpc` 坏 import + `notificationrpc2` 别名

旧 `notificationservice` 的绝大多数文件带一个指向**别的项目布局**的 import：

```go
"github.com/ve-weiyi/blog-cloud/service/app/rpc/internal/pb/notificationrpc"   // 该路径不存在
notificationrpc2 "github.com/ve-weiyi/blog-cloud/rpc/blog/internal/pb/notificationrpc"
```

同一文件把同一个包 import 两次（一次用假路径、一次用别名），`go build` 无法通过。受影响文件 22 个、共 41 处，已统一规整为对真实路径的单次普通 import。

`socialservice`（→ `siteservice` / `discussionservice`）带同样的问题，11 个文件已在移植时一并修正。

### `UpdateLoginLog` 被契约削减

新 `syslog.proto` 的 12 个 RPC 中不含 `UpdateLoginLog`（旧契约有，作用是把 `logout_at` 回填到登录日志）。已核实削减安全：

- api 层无任何调用点；
- 登出流程由 `mqlogic/logout_consumer_logic.go` **直接经 model** 更新 `LogoutAt`，不经过该 RPC。

## 六、按新契约调整的行为

| 项 | 变化 | 说明 |

| `RegionStat` | `name`/`value` → `region`/`count` | 旧字段名与语义不符（`name` 存的是地区名） |

## 七、遗留待办

> 三项均已处置，见 §十。以下保留原始记录。

### 1. `t_menu.type` 列类型与语义不符

契约与 model 现在都是 `string`，与 DB 列一致，编译与运行都正确。但 DB 列的默认值是 `DEFAULT '0'`——一个**数字形态的默认值**，而实际取值是 `CATALOG`/`MENU`/`BUTTON`。存量数据里该列全是空串。

建议：把默认值改为 `''`，并清洗存量空串。属于数据层整理，不影响当前代码。

### 2. `ListArticlePreviewsRequest` 与 `ListArticlesRequest` 字段完全重复

两个消息字段逐一相同，分开定义是为满足「每个 RPC 持有独立请求类型」的约束。字段重复导致 `contentservice` 需要一个适配器：

```go
// toArticleQuery 把预览查询请求适配成文章查询请求
```

**未做成接口**：helper 用 `!= nil` 判断 optional 字段，其中 `is_delete = 0` 是**有效筛选值**，改用取值方法（零值判断）会让该筛选失真。若将来在此处去重，需先确认这一语义。

### 3. `api` 层整体待重构

`blog-cloud/api` 有 29 个包、109 个文件引用 6 个已消失的 client 包（`articleservice` / `configservice` / `permissionservice` / `resourceservice` / `socialservice` / `userauthservice`）。这是服务改名的必然结果，属后续工作。

另：api 层已生成的 `types.go` 中 `MenuMeta.Type` 仍是 `int64`，api 重新生成后会自动变为 `string`。
