# blog 博客系统 — 消息通知系统设计

初稿：2026-09-18　·　最近更新：2026-09-18

## 一、定位与范围

本文定义**管理员发布通知 → 用户接收 → 撤回**这条链路上，通知域的**模型、投递语义与撤回语义**。

**归本文**：广播与点对点的建模差异、发布与投递的解耦方式、事件模型、拉取与推送的语义分工、已读与未读的口径、去重与聚合、撤回的作用范围与边界。

**不归本文**（已有归属，不重复定义）：

| 内容 | 归属 |
|---|---|
| 模块与数据所有权 | 见模块设计 |
| 模板 / 内容 / 投递记录三层模型 | 见通知域模型定义 |
| 投递通道（站内信 / 邮件 / 短信）与通道适配器 | 见通道设计 |
| 验证码 | 见验证码设计 |
| 实时通道选型、身份校验、连接层限流、状态外置 | 见实时通道设计 |
| 异步消息的重试 / 幂等 / 不作保证 | 见异步消息约定 |

**部署前提：多副本。** 本文只讨论多副本部署——实时连接分散在多个实例上，**触发投递的实例未必持有目标连接**。这一条决定了 §四 的投递路由与 §五 的补偿语义。单副本场景不在讨论范围内：在那里进程内即可维护连接与状态，本文的外置注册表与跨实例路由都不成立。

## 二、核心决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **权威状态在库，实时通道只做加速** | 推送通道不可靠——断网、切后台、多端登录、重连、进程重启都发生在通道侧。未读列表与已读状态的唯一真相源是 MySQL；通道收到什么不影响"用户究竟有哪些通知"。通道类型（STOMP）与本决策无关 |
| 2 | **发布与投递解耦** | 发布动作在事务内只完成落库，投递异步进行。沿用既有的异步消息约定，不让投递耗时进入发布者的请求链路 |
| 3 | **广播与点对点共用投递记录模型，差别只在目标解析** | 二者都是"一条内容 / N 条投递记录"，差别是 N 由"全部用户"还是"指定列表"解析而来。**读时求值不可行**——定向列表是一个集合，读路径无法索引；且一旦广播支持分段定向，标量水位线就不成立 |
| 4 | **发布与撤回共用同一事件管道** | 二者只是同一事件的两个 `type`。合并后撤回免费获得发布已有的可靠性与补偿机制；若为撤回单开一条链路，它会成为后续所有一致性问题的来源 |
| 5 | **拉取返回状态快照，推送返回事件** | 两者语义不同，**不可混用同一套数据**。见 §四.3 |
| 6 | **撤回是状态流转，不物理删除** | 物理删除会使审计断链，且离线客户端无法区分"被撤回"与"不存在"。墓碑（tombstone）是行业一致做法：Matrix 的 redaction 明文"不可撤销"且事件仍留在时间线中，Kafka 用带 key 的空值消息表达删除 |
| 7 | **已读是投递记录的属性，未读数由它派生** | 已读状态是唯一真相；**不做独立的计数维护**——增量计数必然漂移，而由已读状态重算永远是对的。见 §3.3 |
| 8 | **连接状态外置，且必须租约化** | 多副本下连接分散在各实例，变更方未必持有目标连接。注册表**必须存于共享存储**（即实时通道的在线列表），**且每条记录必须带 TTL**——否则实例崩溃后残留的死连接永远不会被清理 |
| 9 | **推送的到达性不作保证，且补发失败必须可被客户端识别** | 跨实例转发是尽力而为。**"补发不上"不能是静默的**——客户端必须能从响应中区分"没有新数据"与"补发失败、需重新全量拉取"。见 §五 |
| 10 | **每个实例的投递记录 ID 即幂等键，去重窗口必须声明** | 至少一次投递下，重复投递不得产生第二条记录。**幂等保证的强度等于接收方记住该键的时间窗**——窗口到期后迟到的重试会二次生效 |

## 三、模型

### 3.1 在三层模型上的补充

模板 / 内容 / 投递记录三层模型已由通知域模型定义。本文补充两点：

- **内容层承载撤回状态**——撤回作用于一次发布（内容），而非单条投递。内容关注"是否已发出、是否已撤回"。
- **投递记录层承载已读状态**——已读是投递记录的属性，不是内容的属性；本文沿用。

### 3.2 两类通知的存储形态

| | 广播（全员公告） | 点对点（业务通知） |
|---|---|---|
| 内容 | 一条 | 一条 |
| 投递记录 | **每接收者一行** | **每接收者一行** |
| 差别 | 接收者 = 全部有效用户 | 接收者 = 指定列表 |
| 已读 | 投递记录的属性（§3.3） | 投递记录的属性 |
| 撤回粒度 | 可精确到「仅未读者」 | 可精确到「仅未读者」 |

两类**共用同一套模型**，差别只在发布时的目标解析。因此撤回、已读、幂等的语义对两者完全一致——不需要为广播单独设计一套。

**已评估、当前不采纳：广播不写逐行记录（读扩散）。** 做法是只存内容，读时按人组装（Facebook News Feed 的聚合层即此路线），写入与存储量与接收者数无关。**不采纳的理由是三条代码层面可证的约束：**

- **定向无法在读时求值**。定向目标是一个集合，读路径要回答"这条通知是否包含我"。集合成员判定走不了索引，且随定向规则复杂化持续变贵。写扩散把目标解析**一次性完成在发布时刻**，读路径退化为一条带索引的等值查询。
- **标量水位线无法表达分段定向**。读扩散通常配一条"已读到第 N 条"的水位线，但它只能表达"全部广播"。一旦广播从"全员"细化为"某类用户"，水位线就要按定向维度分裂。
- **读路径必须唯一**。读扩散会让广播与点对点走两条不同的读路径与撤回路径，复杂度翻倍，而收益只在高基数接收者下才显现。

**触发条件**：接收者规模增长到逐行写入不可行时（§八），重新评估。

**由此确定的模型约束**：投递记录是**唯一**的投递事实来源，广播与点对点都落在同一张表；未读、已读、撤回都只在这张表上表达。

### 3.3 已读建模

**已读是投递记录的属性**，每条记录一个已读状态；**未读数由已读状态派生**。

**未读数不得独立维护。** 这是行业反复踩出来的结论——"未读数被陈旧快照覆盖""已读事件被跨语义复用导致误清零""异步推进已读状态后无人刷新派生计数"都是公开出现过的缺陷形态。**任何"在投递记录上 +1/-1 维护计数"的写法都会漂移**；正确做法是：已读状态是唯一真相，计数由它计算，且任何时候都能重算。

三条约束：

- **已读只能前进**。已读不可回到未读；重复标记已读必须幂等。
- **标记已读必须校验归属**。接口只允许操作属于调用者自己的记录——否则任何人都能按 ID 抹掉他人的未读角标。
- **"全部已读"是一次批量状态迁移**，不是客户端逐条调用。它的代价与该用户的未读条数成正比，应由服务端一次完成。

**已评估、当前不采纳：每用户一条已读水位线。** 行业主流用的是它——Matrix 的 `m.read` / `m.fully_read`、Slack 的 read cursor、Mattermost 的 `last_viewed_at`，语义都是"标记某条已读代表该条及其之前全部已读"，优势是"全部已读"与"未读数"都变成 O(1)。**不采纳的理由**：水位线是一个标量，无法表达分段定向的广播（§3.2）；**触发条件**同 §3.2——接收者规模增长到逐行写入不可行时重新评估。

### 3.4 撤回的作用范围

**撤回作用于「未投递 + 已投递未读」两段，且是单向、不可逆的状态迁移。**

| 投递记录状态 | 撤回后 |
|---|---|
| 未投递 | 不再投递 |
| 已投递、**未读** | 从客户端可见集合中移除；记录保留 |
| 已投递、**已读** | **保留，不追回**——已经抵达用户的内容无法真正收回 |

**投递记录一律保留**，撤回只改变其**可见性口径**，不改变其存在。这是 §二 #6 的直接后果，也是审计与幂等重放的前提。

**可见性与已读状态必须是两个正交的维度。** 撤回改变的是**可见性**，已读记录的是**阅读状态**——把两者塞进同一个字段（例如用一个 `status` 同时表达 `unread / read / revoked`）会丢掉"该条被撤回时是否已读"这一事实，而 §3.2 恰恰需要它来界定「仅未读者」的撤回范围。

**"已读不追回"不是本项目的保守选择，而是行业一致结论。** 行业在这一点上措辞比预期更直白：

- WhatsApp 官方 FAQ：*"Recipients may see your message before it's deleted or if deletion was not successful."*
- 微信官方（公众号"微信派"）解释撤回无法无痕的原因之一是**手机通知栏**——*"即使微信能无痕撤回，手机通知栏的提醒微信也爱莫能助"*
- Matrix 规范：redaction **"cannot be undone"**，且被撤回的事件**仍留在时间线中**
- Outlook 经典撤回的前提就是"收件人尚未打开该邮件"，且官方单列了"邮件被移出收件箱则撤回失败"

**因此撤回的准确定义是「收回副本 + 留下墓碑」，不是「消除」。** 本文的措辞与实现都应以这个定义为准。

**不可追回的副作用必须显式列出**：已推送的通知栏、已被客户端渲染的内容、已发出的读回执。**撤回作用于记录，不作用于这些已产生的副本。**

### 3.5 去重与聚合

**去重**：投递记录 ID 即幂等键，重复消费同一 ID 不得产生第二条记录。**去重窗口必须显式声明，并且长于上游的最长重试窗口**——窗口一旦短于重试窗口，迟到的重试会在键被清理后静默地二次生效。行业参照：Stripe 的幂等键保留 **24 小时**；SQS FIFO 的去重窗口是 **5 分钟**。**本文的去重窗口取投递记录的保留期**（§五），二者共用一个参数。

**聚合**：把多条同类通知合并为一条展示。**聚合发生在写入侧 / 消费侧，不在读取侧**——LinkedIn 的通知平台在流处理侧做 batch 与 aggregate（例如把短时间内的多条连接邀请卷成一封邮件），而不是让读取端合并。读取侧聚合是 Feed 场景的选择，不是通知的。

**本项目的取舍**：管理端公告由人工发布，**不需要聚合**。但**频次控制是必需的**——同一用户短时间内收到大量点对点通知会构成刷屏。行业两条公开防线：LinkedIn 对上游应用做限流，"防止它们意外刷屏"；Uber 在推送侧用"每日上限 + 两条之间的最小间隔 + 发送窗口"排期，**超过上限时丢弃而非排队**。本文采用后者的形态（§五）。

## 四、数据流

### 4.1 发布

```
管理端发布 ──▶ 通知域【事务】内容落库（已发布）
                      └─ outbox 事件（PUBLISHED）
                            └──▶ 异步投递：生成投递记录 → 经实时通道推送
                                        └─ 离线用户：不推送，由拉取兜住
```

**事务边界内只做落库**。投递失败不回滚发布——内容已发布是事实，投递由既有的异步消息重试与兜底约定处理。

### 4.2 撤回

```
管理端撤回 ──▶ 通知域【事务】内容状态（已撤回，版本 +1）
                      └─ outbox 事件（RECALLED）
                            ├──▶ 在线连接：推送 recall 事件
                            ├──▶ 未读投递记录：不再投递 / 从可见集合移除
                            └──▶ 未读计数：由已读状态重算，不做增量递减
```

撤回与发布走**同一条管道**（§二 #4），仅事件 `type` 与状态迁移方向不同。

**注意最后一步的写法**：未读数**不递增递减**，而是"可见集合变小 → 计数重算"。增量维护计数是 §3.3 已排除的写法。

### 4.3 拉取与推送的分工

| 通道 | 语义 | 内容 |
|---|---|---|
| 拉取（HTTP） | **当前状态快照** | 当前可见的通知列表、未读数 |
| 推送（实时通道） | **事件** | 「某通知已发布 / 已撤回」 |

**为什么不统一**：离线用户在撤回前拉到了通知但尚未渲染，撤回后重连——若拉取接口返回的是"事件流"，他会看到一条本应消失的通知。**返回状态快照的接口天然正确**，因为它读的是当前状态。这是 §二 #5 的完整理由。

**"推送只发信号不发内容"是行业标准形态，且除了正确性之外还有第二个理由——隐私。** Matrix 的推送网关有专门的 `event_id_only` 格式（只带 `event_id`、`room_id`、`counts`），其引入目的就是不让推送网关读到敏感内容；Firebase 的折叠消息（collapsible）官方用法也是"发一个不带内容的信号让 App 去同步"。

### 4.4 多副本下的投递路由

事件由任一实例消费，但它未必持有目标连接。投递因此分两步：

```
事件 ──▶ 投递网关（任一实例）
            ├── 本实例持有目标连接 ──▶ 直接推送
            └── 其他实例持有       ──▶ 经广播通道转发 ──▶ 持有实例推送
```

**四个约束**：

| 项 | 要求 | 理由 |
|---|---|---|
| 连接注册表 | **必须外置**（共享存储），**且每条记录带 TTL** | 否则实例无从知道目标连接在哪个实例上（决策 8）；没有 TTL，实例崩溃后的死连接永不清理 |
| 注册表续租 | **批量续租**，不要每次心跳都写 | 心跳是秒级的，逐次写会把注册表变成热点 |
| 跨实例转发 | 经广播通道（Pub/Sub 或 MQ） | 多副本下没有进程内捷径 |
| 转发失败 | 按**错误分类**处置，不是一刀切重试 | 见下 |

**关于"转发失败不重试"**：方向正确，但**必须按错误分类**，并且要有止损线。行业在这点上有明确得多的实践：

- **不可重试**：APNs 官方列出 `BadDeviceToken` / `DeviceTokenNotForTopic` / `Forbidden` / `ExpiredToken` / `Unregistered` / `PayloadTooLarge` 不得重试，且把 `410 Unregistered` 定性为**终止性错误**，正确动作是**删除该 token**；FCM 同样规定 `400/401/403/404` 直接放弃，只有 `429/500/503` 才重试。
- **重试的代价是真实的**：FCM 官方警告，不加退避与抖动的重试会造成**重试放大**、加剧拥塞，**问题发送方有被拉黑的风险**。
- **止损线**：FCM 给出的口径是"退避重试超过 60 分钟仍失败，说明该请求被错误分类，或服务本身故障"。

**这与 §二 #1 是同一件事的两面**：正因为推送可能丢，才必须让拉取承担正确性。**推送链路上不存在"必须送达"的环节**——出现这种环节即为设计错误。

## 五、投递语义（改动需重新走设计评审）

| 项 | 约定 | 理由 |
|---|---|---|
| **至少一次** | 沿用既有的异步消息约定——消费者按投递记录 ID 去重 | 重复投递不得产生第二条记录 |
| **去重窗口** | **= 投递记录保留期**，且必须长于上游最长重试窗口 | 窗口短于重试窗口，迟到的重试会静默二次生效（§3.5） |
| **顺序** | **不引入顺序保证**。发布与撤回的竞争由**事件版本号 + 客户端 LWW** 消解 | 见下方专述 |
| **断线补偿** | 沿用实时通道的会话游标补发，**必须设条数上限**（默认 **200**），**且必须返回"补发是否成功"的显式信号** | 见下方专述 |
| **心跳** | 间隔 **15 秒**；连续 2 次无响应即判死连接并清理注册表 | 见下方专述 |
| **重连风暴** | 客户端重连**指数退避 + full jitter**：基数 **500 ms**、上限 **20 秒**；服务端对建连限流 | 任一实例重启会让其承载的连接同时重连。多副本下实例数越多，风暴越集中，且与投递转发叠加 |
| **注册表 TTL** | **90 秒**（> 心跳间隔 × 3），离线判定不早于 TTL 到期 | 心跳漏掉一两次不应误判为离线 |
| **多端** | 同一用户的多个连接**都要**收到事件；一端的已读需作为事件同步到其他端 | 权威状态在库，但各端界面需自行收敛 |
| **未读计数** | **由已读状态派生，不做增量增减**（§3.3） | 增量维护必然漂移，且撤回时最容易漏 |
| **撤回时间窗** | 发布后 **24 小时**内可撤回，超出即拒绝 | 时限越久，已读比例越高、撤回收益越低。行业参照：企业微信内部消息 24 小时、对外 2 分钟；微信会话消息 2 分钟、文件 3 小时——**同一产品内部与对外可差三个数量级**，说明该值应按场景定而非按惯例定 |
| **频次控制** | 每用户每日推送上限 + 两条之间最小间隔；**超限丢弃，不排队** | 防止自动触发的点对点通知刷屏（§3.5） |
| **不作保证** | 沿用既有的异步消息约定——不承诺不丢失 | 丢失由「失败终态 + 管理端重发」与拉取接口兜住 |

### 关于"顺序" —— 与既有异步约定的关系

既有的异步消息约定明确「**不引入任何需要顺序保证的设计**」。撤回的加入**没有推翻这一条**，理由如下：

发布与撤回对同一条通知构成竞争，若乱序到达（撤回先到、发布后到），客户端会先移除、再加入，**界面上留下一条本应消失的通知**。若靠"保证同一通知的事件有序"来解决，就引入了顺序依赖——与既有约定冲突。

**消解方式**：每个事件携带该通知的**单调版本号**，客户端只应用版本号更大的事件，重复、过期、乱序的事件一律丢弃（last-write-wins）。

- 该方案**不要求任何顺序**——乱序是安全的，因为版本号自会裁决
- 重连补发、多端并发、消息重投导致的乱序**同时被覆盖**，无需为它们分别设防
- 代价是客户端需维护每个通知已应用的版本号，属于可接受的实现成本

**另一条更弱的消解路径**：客户端收到任何事件后**回查状态快照**（§4.3），而不是增量地应用事件。快照读的是当前状态，本身就不会被乱序污染。**当客户端统一走回查时，版本号比对是可选加强而非必需**——两条路径选哪条取决于客户端是否做增量渲染，属于实现取舍，不影响本节的设计要求（乱序必须被消解）。

行业对照：LinkedIn 对消息重放的处置是"**丢弃已处理过的请求，但允许它们轻微乱序**"——与本文的处置一致。

### 关于"心跳" —— 间隔由链路上最小的空闲超时倒推

**心跳间隔不是可随意取的整数，它由链路上最短的那个空闲超时决定。** 常见默认值：

| 链路环节 | 空闲超时 |
|---|---|
| 蜂窝网络 NAT | 约 **30 秒** |
| AWS ALB / nginx / ingress-nginx | **60 秒** |
| Azure 负载均衡 | **4 分钟** |
| Envoy `stream_idle_timeout` | **5 分钟** |
| AWS NLB | **350 秒** |

取 **15 秒**，即链路最小超时（蜂窝 NAT 约 30 秒）的一半，留出两次重试余量，也低于行业常见取值（Socket.IO 的 `pingInterval` 为 25 秒、Centrifugo 为 25 秒）——**更保守是有意为之**。

**该值与客户端判定耦合**：前端以它的 3 倍作为静默超时（超时即认定链路已死）。**调整心跳间隔必须同步调整客户端阈值**，只改服务端会让正常连接被误判为断开。

**两条必须写进设计的边界：**

- **TCP 层的 keepalive 不能替代应用层心跳。** RFC 1122 要求 TCP keepalive 默认关闭且间隔不小于 **2 小时**，Linux 默认配置下发现死对端需要约 **2 小时 11 分**——比链路上 60 秒的空闲超时大两个数量级。更关键的是：**它的应答由对端内核代劳，因此探不到进程挂死**（死锁、长 GC、事件循环阻塞时 TCP 层依然健康）。RFC 6455 把 Ping 定义为"验证远端**端点**是否仍有响应"，检查的正是应用端点。
- **RFC 6455 不规定任何心跳间隔**，只定义 Ping/Pong 的语义与应答义务。**心跳间隔是本设计自己的选择**，必须由链路超时推导，不能写成"按 RFC 建议"。

**不做心跳的后果已在 §五 表中写明**：客户端断电、断网时 TCP 半开，服务端收不到断开事件，注册表持续残留死连接，推送落进黑洞——表现为"用户在线但收不到通知"，且随运行时长恶化。

**另有一个容易被忽略的坑**：把"在线状态"直接绑在连接生命周期上，会在**发布 / 实例重启**时批量产生假的离线再上线。注册表的离线判定应以 **TTL 到期**为准，而不是以连接断开事件为准。

### 关于"断线补偿" —— 必须给出降级信号

补发条数上限解决了"一次重连拉起全量历史"，但**没有解决"补发失败时客户端怎么知道"**。行业在这一点上有三种可抄的形态：

| 范式 | 做法 |
|---|---|
| **布尔信号** | 补发响应带一个 `recovered` 标志，`false` 即"连续性已断，请重新拉全量快照"（Centrifugo 的做法，官方明确"**绝不返回部分补发**"） |
| **游标失效** | 游标本身是有生命周期的资源，失效时返回一个可识别的错误，客户端丢弃位置、重新全量拉取（Matrix 用 `M_UNKNOWN_POS`，Kafka 用 `offset.reset`） |
| **静默截断**（反面） | 服务端悄悄把游标回退到最旧可用位置，**客户端无法区分"没有新数据"与"数据被丢了"**（Twitter 的 `since_id` 即此形态，会导致永久性丢消息） |

**本文采用前两种的组合**：拉取接口返回**当前可见列表 + 未读数**（本身即快照语义），并在补发路径上返回显式的成功 / 失败标志。**禁止静默截断。**

## 六、接口契约

按既有的接口通则：动作作为独立路径段、管理端与读者端分前缀、分页用偏移分页、错误码不进契约。

**两类读者**：后台管理员与终端用户。二者**共用同一套投递模型与语义**（§3.2），差别只在**挂载点与鉴权**——管理端走管理前缀 + 管理员鉴权，读者端走普通用户前缀 + 用户态鉴权。**不按受众分模型、不分表。**

| 端 | 契约 | 语义 |
|---|---|---|
| 管理端 | 创建通知内容 | 落为**草稿** |
| 管理端 | 发布 / 撤回 | 状态流转，触发异步投递与事件广播 |
| 管理端 | 查询投递记录 | 运维与排障视角，可见全部接收者 |
| 读者端 | **状态快照**：当前可见的通知列表 + 未读数 | **只返回属于调用者自己的记录** |
| 读者端 | 标记已读（单条 / 批量 / 全部） | 必须幂等、只进不退；**必须校验记录归属**（§3.3） |

**实时事件**（与发布、撤回共用）：事件只描述"发生了什么"，**不带正文**——客户端据 `id` 自行收敛。

| 事件 | 客户端动作 |
|---|---|
| 已发布 | 按 `id` 回查；重算未读数 |
| 已撤回 | 移除该通知的可见性；重算未读数 |
| 补发响应 | 携带**补发是否连续**的标志；不连续时客户端**丢弃本地状态、重新全量拉取** |

**内容状态机含三态：草稿 / 已发布 / 已撤回。** 创建即草稿，**仅草稿可编辑**，发布后内容不可再改——已发布的公告被编辑会让"谁在什么时候看到了什么"不可考，而通知是要留痕的。

**已评估、明确不引入：内容聚合**。理由见 §3.5——人工发布的公告没有聚合收益。

## 七、边界

- **不做已读内容的召回**——技术上不可行（§3.4），产品上应降级为"补发更正通知"。行业同样如此：Outlook 官方对撤回失败的建议就是补发一封更正邮件
- **不保证跨通知的全局顺序**——同一通知内的事件乱序必须被消解，但消解手段不限定为版本号比对（§五）
- **不物理删除**——撤回一律为状态流转；墓碑在保留期内不得回收
- **不引入数据库层监听**（触发器 / CDC）——发布与撤回**均由本系统发起**，走应用层 outbox 即可。数据库层监听是为"外部写入者"准备的，当前不存在该角色。若出现外部系统直接写通知表，需重新走设计评审
- **不保证实时到达**——实时通道是加速手段，权威路径是拉取
- **不承诺"撤回后对方看不到"**——只承诺"收回副本 + 留下墓碑"（§3.4）。**界面上仍显示该通知不构成缺陷**
- **不做读取侧聚合**——聚合在写入 / 消费侧（§3.5）
- **不讨论单副本场景**——本文的连接外置、跨实例路由、重连风暴均以多副本为前提（见 §一 部署前提）

## 八、何时重新审视

- 接收者规模增长到**广播按用户写行不可行**（如全员公告到达万级）
- **撤回需覆盖已读内容**——这意味着产品的召回诉求超出了技术能力边界
- 出现**外部系统直接写通知表**——§七的 outbox 结论失效，需评估数据库层监听
- 广播的接收者规模增长到**逐行写入不可行**，或**定向规则复杂到读路径需要求值**——此时重新评估读扩散与水位线（§3.2、§3.3）
- **单用户的通知量级增长到需要聚合**——§3.5 的"不聚合"结论失效
- **客户端离线时长开始超过去重窗口**——补发路径的语义需重新论证（§五）
- 实时通道从 STOMP 切换
