# blog 博客系统 — 用户与游客身份标识

初稿：2026-10-20　·　最近更新：2026-10-20

## 一、设计目标

系统中有两类身份主体：注册用户与游客。两者都会以裸 ID 的形式进入日志、消息与在线名册，设计需要满足：

- **仅凭 ID 字符串即可判断主体类型**，不依赖数据库反查，也不依赖调用方上下文。
- **不引入类型前缀**，不改变公共接口，不为判定新增存储。
- 用户 ID 全局唯一、永不变更，不携带权限、租户或角色语义。
- 游客 ID 由服务端签发并跨会话稳定；不承诺清除站点数据后仍识别同一客户端。
- 既有身份标识继续可用，不做数据迁移。

## 二、身份形态

| 主体 | 形态 | 长度 | 字符集 | 生成时机 |
|---|---|---|---|---|
| 注册用户 | UUIDv7 | 36 | 小写十六进制 + 4 个 `-`（8-4-4-4-12） | 注册或首次自动注册时 |
| 游客 | 随机 hex | 32 | 小写十六进制 | 服务端签发，客户端持久化 |
| 其他 | — | — | — | 不满足上述形态的标识一律视为未知 |

示例：

```
用户：0190f3a1-7c2e-7c3a-9f4e-1a2b3c4d5e6f
游客：d41d8cd98f00b204e9800998ecf8427e
```

UUIDv7 按 RFC 9562 定义：48 位毫秒时间戳 + 74 位随机数，另含 version 与 variant 位。标准文本形式为 36 位小写十六进制、8-4-4-4-12 分组；按字符串排序近似按创建时间排序，同一毫秒内由随机位决定先后。

选择 UUIDv7 而不是 ULID 的原因：两者同为时间有序的 128 位标识，但 UUIDv7 是 RFC 标准文本形式，现有 UUID 工具与生态可以直接解析；代价是文本比 ULID 长 10 位。本项目生成、存储、比较与展示一律使用标准小写形式。

## 三、判定规则

判定只依据字符串本身，按顺序执行：

1. 长度为 36、可解析为 UUID、version 为 7，且重新编码后与输入完全一致 → **注册用户**；
2. 长度为 32 且全部为小写十六进制 → **游客**；
3. 其余 → **未知**。

补充约定：

- **只接受规范小写 UUIDv7**。大写、省略横线的 32 位裸 hex、`urn:uuid:` 前缀等形式一律视为未知，不做静默归一；否则同一个 ID 会出现多种文本，破坏字符串相等、缓存键与唯一索引的一致性。
- 类型由形态区分：36 位带横线的 UUID 与 32 位裸 hex 不会互相误判。version = 7 是对用户 ID 的附加校验，不参与与游客的区分。
- 不使用类型前缀，不以数据库反查作为判定的组成部分。
- 生成与判定规则集中在一处，其他模块不得自行复制这套约定。

## 四、不变量

1. 用户 ID 只能是 36 位规范小写 UUIDv7，任何情况下都不得生成 32 位小写 hex 的用户 ID。
2. 游客 ID 只能是 32 位小写 hex，任何情况下都不得生成 UUID 形态的游客 ID。
3. **类型判定是提示，不是保证**：
   - 不满足两种形态的标识（例如初始化数据中的既有标识）判为未知；
   - 32 位小写 hex 在理论上既可能是游客，也可能是未按本设计生成的用户标识；
   - 消费方在“按类型查无结果”时必须回查另一类，不能据此丢弃记录。
4. 游客 ID 只用于展示与聚合，**不作为鉴权主体**，也不作为权限归属依据。
5. 用户 ID 一旦生成永不变更；用户名、邮箱、手机号、第三方绑定都不得充当 ID。

## 五、消费方语义

| 场景 | 是否判定类型 | 说明 |
|---|---|---|
| 在线名册 | 是 | 唯一混存命名空间；按类型分流查询，未命中的 ID 合并后回查另一张表 |
| 聊天消息 | 否 | 消息同时携带用户字段与设备字段，按字段取值 |
| 访问/登录/操作/上传日志 | 否 | 用户字段与设备字段分列；游客只有设备字段 |
| 通知投递 | 否 | 收件人按渠道与标识分别存储 |
| 其他新消费方 | 优先结构化字段 | 确需从裸 ID 判定时，必须实现回查兜底 |

## 六、生命周期

- **注册用户**：ID 在注册或手机/OAuth 首次登录自动注册时生成，随账号永久存在；停用、注销、改绑都不改变 ID。
- **游客**：ID 由服务端签发，保存在 Cookie 与 localStorage 中；同一客户端跨会话稳定，换网络或换 IP 不改变 ID。清除站点数据、无痕模式、换浏览器或换设备会得到新的游客 ID。
- **其他标识**：不重写、不迁移，通过回查兜底保持可见。

## 七、设备标识的签发与持久化

游客 DeviceID 由服务端签发，代表同一个浏览器配置文件或 App 安装。它不随 IP、UA、系统版本变化；清除站点数据、无痕模式、换浏览器或换设备视为新客户端。

### 7.1 形态与生成

- 32 位小写十六进制，128 位随机数，服务端生成。
- 与用户 36 位 UUIDv7 的形态区分保持不变。
- 不再从 IP、OS、浏览器推导；三者只作为游客档案属性，仅在变化时更新。

### 7.2 存储与读取优先级

| 存储 | 作用 | 生命周期 |
|---|---|---|
| HttpOnly Cookie `blog_device_id` | 服务端权威值，HTTP 请求自动携带 | 400 天 |
| localStorage | 前端镜像，用于请求头与 WebSocket 会话标识 | 随站点数据清除 |

读取顺序：中间件优先读 Cookie；Cookie 缺失时由 `/guest` 读取请求头 `X-Device-Id`；两者都没有则生成新值。

只清 localStorage 或只清 Cookie 时可由另一处恢复；清除站点数据、无痕模式、换浏览器或设备视为新客户端。

### 7.3 Cookie 约定

- 名称 `blog_device_id`，`Path=/`，`Max-Age` 400 天，`HttpOnly`，HTTPS 下带 `Secure`，`SameSite=Lax`。
- 只作为第一方 Cookie，不用于跨站追踪。
- 当前前后端同源部署；若改为独立子域，需要同步调整 `Domain`、`SameSite` 与 CORS 凭据配置。

### 7.4 签发与恢复流程

调用频率：

- `/guest` 只在客户端没有本地标识，或本标签页会话尚未引导时调用；
- 已有本地标识时后台补一次，不阻塞导航；
- Cookie 只由 `/guest` 下发；中间件不根据请求头补发。

流程：

1. 中间件解析 Cookie，存在时覆盖请求头；Cookie 缺失时由 `/guest` 读取请求头候选值；
2. `/guest` 读取最终候选值；
3. 档案存在 → 仅在 IP、OS、浏览器或地区变化时更新；
4. 档案不存在 → 以候选值创建，恢复部分清空后的身份；
5. 候选缺失或非法 → 生成新值并创建；
6. 插入撞唯一键 → 回查并复用已有行；
7. 响应体返回 DeviceID；前端写入 localStorage。

### 7.5 生命周期

- 游客档案长期保留，不设自动清理；记录数量与独立客户端数量同阶。
- 已存在游客只在环境属性变化时更新，避免读路径写放大。
- 不再使用指纹，因此无需为“找回”维护额外索引。

### 7.6 与用户、鉴权的关系

- 不复用 UserID，也不把游客数据并入用户账号。
- DeviceID 不作为鉴权主体，不参与权限判断。
- 需要可信设备语义时，另行设计签名或账号绑定，不在本设计范围内。

## 八、设计边界

1. 不承诺清除站点数据、无痕模式或换设备后仍识别同一客户端；这些情况视为新游客。
2. 不重发、不迁移既有用户标识。
3. 不重写初始化数据中的既有身份标识。
4. 不做游客与注册用户的身份合并；游客历史仍按 DeviceID 查询。
5. 不把游客 ID 提升为可信凭证。

## 九、备选方案与取舍

| 方案 | 结论 | 原因 |
|---|---|---|
| 类型前缀（`usr_` / `gst_`） | 未采用 | 类型信息污染 ID 文本 |
| ULID（26 位） | 未采用 | 更短且同样时间有序，但不是 RFC 标准的 UUID 文本形式 |
| UUIDv7 Base64URL（22 位） | 备选 | 更短，但大小写敏感、含 `-`/`_`、工具支持少；“可还原为 UUID”当前没有收益 |
| Snowflake（≤19 位数字） | 未采用 | 需要 worker id 与时钟回拨处理，对当前规模过度设计 |
| 64 位随机（约 11 位） | 未采用 | 牺牲唯一性保证 |
| 双方统一 UUID、以 version 位区分 | 未采用 | 游客保持 32 位 hex，才能仅凭形态与用户区分 |
| 指纹回退（IP + UA） | 未采用 | 只在全量清空后尝试找回，NAT 会合并、换 IP 会失效，且涉及隐私
| 不区分形态、只做双查 | 保留为兜底 | 无需格式约定，但每次都要多一次批量查询 |

## 十、后续演进

- 若对 ID 文本长度敏感：可切换 ULID 或 Base64URL(UUIDv7) 编码，判定规则同步更新。
- 若需要清除站点数据后仍识别同一客户端：只能引入账号绑定或指纹回退；后者不可靠且涉及隐私，不作为默认方案。
- 若游客身份需要可信：增加服务端签名或绑定令牌；届时重新评估“游客 ID 不是鉴权主体”的边界。
- 若在线名册出现更多消费方：优先为名册增加显式类型字段，而不是继续扩展字符串约定。
