# stompws 实时通信服务设计

日期：2026-10-15
实现：`stompws/`（独立模块，主仓 submodule）
相关：`docs/feature/2026-10-15-stompws中继串行化改造.md`（改造方案与实施）、`docs/review/2026-10-15-stompws全模块审计报告.md`（审计）

> 本文只写**决策层**：目标与约束、模块边界与所有权、通信方式、对外语义、权衡。函数签名、文件清单、

## 一、定位与边界

**是什么**：WebSocket 之上的 STOMP 1.0/1.1/1.2 服务端。提供两种中继 —— topic（广播）与 queue（点对点、
带 ack 与重入队），并负责连接生命周期（握手/心跳/断开清理）。

**不是什么**：不是消息中间件。**无持久化、无集群、无跨节点路由**；身份校验策略、业务路由、在线用户存储
都由消费方通过 `Authenticator` / `EventHook` / `OnlineTracker` 三个接口注入，本服务只提供默认实现。

**与上游的关系**：移植自 `go-stomp/stomp/v3` 的 `server` 与 `server/client`（基线 v3.2.0）。移植约定是
「对应文件尽量与上游一致，便于日后照搬上游 diff」—— 实际 `server/queue`、`server/topic` 的 9 个源文件里
7 个与上游逐字一致，`queue/queue.go` 做过接口替换，`queue/subscription.go` 与 `queue/subscription_list.go`
是本仓的 shim（上游直接复用 `client` 包的同名类型）。

## 二、模块与所有权

**所有权是本服务的核心架构事实**：每块可变状态只有一个写者，因此大部分结构不需要锁。

| 角色 | 拥有什么 | 说明 |
|---|---|---|
| `StompHubServer` | 连接登记表、在线列表、配置项；`OnlineTracker` 的**生命周期** | 不再持有中继状态 |
| `requestProcessor`（**单 goroutine**） | `topic.Manager` 与 `queue.Manager`，以及目的地上限的登记表 | 所有中继操作的唯一执行者；上游是同一角色，但它是 fire-and-forget |
| `Conn`（每连接） | 该连接的三条 goroutine、会话身份、订阅表、待确认表、投递缓冲 | 三条 goroutine 分别是 **readLoop**（解析帧）/ **writeLoop**（独占写出）/ **processLoop**（处理帧与生命周期） |
| 消费方实现 | `Authenticator` / `EventHook` / `OnlineTracker` | 回调只在**该连接的 processLoop** 上被调用，因此实现里可以做同步 I/O，但不该做无界阻塞 |

**投递缓冲**：每连接两个 —— `subChannel`（队列投递，携订阅）与 `writeChannel`（topic 投递与协议帧）。
两者都是「满了即判慢消费者」的投递边界，见 §四。

## 三、通信方式

**请求通道**：连接协程与外部调用方（如消费方的在线广播）都只能经 `chan Request` 与中继交互。
订阅类请求（SUBSCRIBE/UNSUBSCRIBE）**带回执通道**，其余 fire-and-forget。

**三条必须守住的不变量**（改这块代码时的检查表）：

1. **中继状态只有 processor 一个写者** —— queue/topic 的 map 与 list 因此不需要锁，任何绕过请求通道的
   直接调用都会破坏这条（`requeueDirect` 是唯一例外，且它只允许在 processor 协程上调用）。
2. **processor 永不往自己的请求通道发送** —— 否则会在通道满时自锁（唯一消费者给唯一通道发送）。
3. **投递与回执均非阻塞** —— 投递（送进连接的缓冲）与请求回执都不能阻塞，否则慢客户端/放弃等待的调用方
   会把共用的中继拖停。

**为什么单 goroutine 而不是加锁**：加锁方案把正确性交给「人守纪律」（六个文件里任一处在持锁时碰 channel
即死锁），而单写者把它交给结构（状态只有唯一写者，锁这个概念不存在）。代价见 §六。

## 四、对外语义契约

这些是对客户端（与消费方）的**承诺**，改动即破坏兼容：

| 契约 | 内容 |
|---|---|
| **RECEIPT 时序** | SUBSCRIBE 带 `receipt` 时，RECEIPT 一定在**订阅真正挂上之后**才发出（上游服务端不回应 SUBSCRIBE 的 RECEIPT，本实现补上了这条，`SubscribeOpt.Receipt` 依赖它）。SEND 的回执在帧被受理后发出；事务内的帧在入事务时回执一次，提交重放**不再重复回执** |
| **心跳** | 按 STOMP 规范发**数据帧心跳**（一个 `"\n"` 文本帧），间隔 = CONNECT 协商出的 `heart-beat`（下限 30s）。**不发 WebSocket 控制帧 ping 充数** —— 主流客户端只用数据帧刷新「服务端活跃时间」 |
| **队列投递语义** | `/queue/` 是**至少一次**：正常投递 + ack 确认；连接异常断开或 ack:auto 的帧未写出时，帧退回队首。可能重复，不会静默丢失 |
| **topic 投递语义** | fire-and-forget：多订阅者各拿一份（最后一个复用原帧，其余克隆）；投不出去不退回 |
| **慢消费者** | 投递缓冲（`subChannel`/`writeChannel`，默认各 256）满即断开该连接，队列消息退回队首。**不改回阻塞式投递** —— 那会把影响面从一条连接扩大到全体 |
| **上限** | 目的地数量（默认 4096）、同时连接数（默认 10000）、未发 CONNECT 的空连接（默认 10s）都有上限：目的地与连接都由客户端发起，不设限就是远程可触发的资源增长 |
| **帧边界** | STOMP 帧的边界与 WebSocket 消息边界**无关**：一个消息可含多帧、一帧可跨多个消息（客户端分片）。畸形帧回 ERROR 后断开（流式读无法重新对齐） |
| **CONNECT 校验** | CONNECT/STOMP 帧本身也过验证器（必需 `host`/`accept-version`、`receipt` 不允许、`heart-beat` 格式与上限） |
| **关停顺序** | `Shutdown`：先停 HTTP（不再接新连接）→ 通知各连接收尾 → **等 writeLoop 也退出**（它退出时才把未写出的帧退回队首）→ 再停中继 → 关闭 `OnlineTracker`。顺序反过来会丢帧 |

## 五、配置的顶层结构

- **`ServerOption`（构造时注入、公开 API）**：认证器、事件钩子、日志、队列存储（`queue.Storage` 扩展点）、
  在线追踪器、WebSocket 握手检查。语义是「注入依赖」，不是「调参」。
- **包级可调项（未做成 Option）**：心跳下限、目的地/连接上限、空连接超时、在线同步间隔。做成 Option 会
  扩大公开 API，暂以包级变量承载（测试也靠它们压到毫秒级）。
- **`queue.Storage` 是持久化的唯一扩展点**。注意实现契约：`Dequeue` 返回的是存储内部那个帧指针（不 clone）、
  上游注释里「Enqueue 会设 message-id」这句话在当前实现里并不成立（真正分配在写出侧）。

## 六、权衡与已知代价

| 决定 | 代价 |
|---|---|
| 中继单 goroutine 串行化 | 吞吐上限 = 单核。真要扩容按目的地分片（仍不需要锁，只是多个 processor 各持一部分） |
| 投递非阻塞、满即断 | 瞬时突发可能误伤健康客户端（已把缓冲放宽到 256 缓解）；对订阅者是「断开重连」而不是「静默漏消息」 |
| `/queue/` 至少一次 | 可能重复投递（消费方需幂等） |
| 请求通道饱和取背压（阻塞提交） | 提交方会等 —— 但提交方几乎总是产生负载的那个连接的 processLoop，等于把背压施加在源头 |
| 目的地/连接上限 | 到上限后拒绝新建目的地、拒绝新连接；值是可调常量，不是精细的容量规划 |
| 心跳下限 30s | 客户端请求更短间隔会被抬到 30s（避免被压到不实用的量级） |
| 「中继永不阻塞」的前提 | 依赖 `websocket.Conn.Close()` 不取写锁（gorilla v1.5.3 成立）与 `queue.Storage` 不阻塞 —— **更换/降级 websocket 库或注入慢 storage 时必须重验** |

## 七、边界之外

以下刻意不做，若要做属新设计而非增量：

- 消息持久化与重启恢复（`Storage` 接口留了位置，但本服务不保证投递语义跨进程）
- 集群与跨节点路由（topic 广播只在单实例内）
- 背压之外的流控（限速、配额、按用户限流）
- 协议扩展（STOMP over TCP、消息压缩、认证之外的授权模型）
