# blog 博客系统 — 权限变更生效机制

初稿：2026-09-18　·　最近更新：2026-09-18

## 一、问题定义

### 1.1 核心矛盾与本文的解法

权限变更"立即生效"的本质冲突在于：

- 权限判定发生在**每一次请求**上（高频、要求低延迟）——逼着系统缓存
- 权限变更要求**立刻可见**（低频、要求强一致）——逼着系统不缓存

**本文不试图消除这个矛盾，而是把"新鲜度"从"每请求向权威源求证"改为"本地持有一份不会过期的版本视图"。**

具体地说，三个动作分开：

| 动作 | 承担者 | 频次 |
|---|---|---|
| 判定 | 进程内缓存，键含版本号 | 每请求，**零远程调用** |
| 刷新版本视图 | 推送（加速）+ 轮询（兜底） | 按刷新周期，与请求量无关 |
| 校验权威 | 只在刷新时向权威源读取 | 与刷新周期同频 |

这样判定路径上没有任何远程依赖，**陈旧上界由刷新周期静态给出**——这才是"可证明"的由来。要求每条请求都向权威源求证新鲜度，是把刷新成本乘以请求量，且会让权威源成为全站单点。

### 1.2 目标的正确表述

**目标不是"绝对立即"，而是"有界且可证明的陈旧"。** 这不是折中，是行业基线：

| 系统 | 官方公开的生效时效 |
|---|---|
| Google Cloud IAM | allow / deny 策略**通常 2 分钟，可能 7 分钟或更久**；组成员变更**数分钟至数小时** |
| Azure RBAC | 角色分配**最多 10 分钟**；托管标识的组成员变更**数小时** |
| AWS IAM | **不承诺任何上界**，只承认最终一致，并建议不要把 IAM 变更放进关键高可用路径 |
| Microsoft Entra CAE | 关键事件传播**最长 15 分钟** |
| SpiceDB | 默认陈旧上界 ≈ **5 秒**（修订量化）再叠加最多 10% |
| OPA | bundle 轮询 **60–120 秒** |
| Cerbos ePDP | 轮询 **60 秒**（最小值 10 秒） |
| Kubernetes 授权 webhook | 决策缓存 **10 秒** |

**一个不给上界承诺的系统，等于把"多久生效"交给运气。** 因此本文的承诺必须是数字：

| 档 | 陈旧上界（默认值，可配） | 由什么保证 |
|---|---|---|
| 吊销 | **毫秒级** | 主体 / 全局纪元 + 本地极短最大年龄 |
| 强 | **≤ 2 秒** | 推送；轮询周期 1–2 秒兜底 |
| 中 | **≤ 10 秒** | 推送；轮询周期 5–10 秒兜底 |
| 弱 | **≤ 120 秒** | 轮询 / 前端事件 |

**承诺写不出数字，就说明设计没做完**——这是本文与"变更会生效"式表述的分界。

### 1.3 部署前提

**本文只讨论多副本（微服务）部署。** 单副本不在范围内——在那里，进程内缓存与内存中的版本号即可满足全部要求，本文的跨实例传播、强一致读、不一致窗口都不成立。

多副本带来四个新问题，本文的机制全部由它们驱动：

| 问题 | 后果 |
|---|---|
| 判定缓存不再天然一致 | 实例 A 改了权限，实例 B 仍持旧值——**§4.3 的推送 + 轮询由此而来** |
| 版本视图分散在各实例 | 各实例对"新鲜度"的判断不一致——**§4.5 的硬性最大年龄由此而来** |
| 变更在不同实例的到达时刻不同 | 传播窗口内同一请求可能判出不同结果——**§4.8 的过渡期语义由此而来** |
| 长连接分散在多个实例上 | 变更方未必持有目标连接——**§4.4 的长连接层由此而来** |

## 二、时效分档

不同场景对"立即"的严格程度差别极大，**混为一谈是设计跑偏的首要原因**。

**分界依据是安全后果，不是技术难度。** 而后果决定**走哪条通道**——这是本文与"三档只是一组参数"的关键差别：

| 档 | 场景 | 后果 | 通道 | 时效 |
|---|---|---|---|---|
| **吊销** | 账号停用 / 封禁、离职、泄密响应、强制下线 | 安全事件 | **身份通道**：主体 / 全局纪元 | 毫秒级 |
| **强** | 用户角色降级、角色定义收紧 | 越权访问 | **判定通道**：版本号 + 有界陈旧 | ≤ 2 秒 |
| **中** | 数据行级权限、租户 / 档位变更 | 数据或商业越权 | 判定通道 | ≤ 10 秒 |
| **弱** | 菜单、按钮可见性 | 体验问题 | 前端事件刷新 | 最终一致 |

**为什么要分成两条通道，而不是一条通道调不同参数：**

- 身份通道操作的是**主体级 / 全局级的单个键**（单调纪元）。单键意味着传播面极小、可被所有实例以极短周期拉到、且**不需要参与低基数判定缓存**——因此它可以做到毫秒级。
- 判定通道操作的是**低基数维度上的版本号**（角色、资源类型、租户）。扇出大、粒度细，只能做到有界陈旧。
- 行业在紧急档上一致地选择"钝而小的键"：AWS 的撤销会话是往角色上挂一条时间条件 deny（时间戳前推约 30 秒），Keycloak 的 `notBefore` 是 realm / client / user 三级时间戳，Microsoft Entra CAE 用 claims challenge 让资源方主动拒绝已签发令牌。**没有人用细粒度权限传播做安全响应**——因为来不及。

**推论：强档的"用户角色降级"不进身份通道。** 它是权限变更而非吊销，按决策 4 不得触发下线；它走判定通道，承诺是"秒级"而非"立即"。

## 三、核心决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | **权限明细不进入令牌**；若进入，必须配套版本号 | 令牌是自包含快照，签发即定。Auth0 官方文档直言 "Once issued, an access token cannot be revoked"，其默认寿命是 24 小时；Okta 的登出同样不撤销已签发令牌 |
| 2 | **新鲜度由"版本号 + 硬性最大年龄"保证，不由每请求权威读保证** | 每请求求证会把刷新成本乘以请求量、并把权威源变成全站单点。判定路径应只做一次本地比对（§4.3） |
| 3 | **执行点分散、决策点集中、变更入口唯一** | 失效不可靠的根因几乎总是**变更入口不唯一**——有多处能改权限，就有多处在漏失效。Cerbos 不做可嵌入库的官方理由之一即 "slightly divergent authorization rules between services become a security issue" |
| 4 | **令牌吊销与权限变更是两个维度** | 前者是"身份不能用了"，后者是"身份还能用但权力变了"。**权限变更不得触发下线**；但身份类事件（封禁 / 泄密响应）走身份通道，这是两条不同的路 |
| 5 | **长连接必须显式处理** | 长连接建立后权限被冻结，HTTP 侧的机制覆盖不到它（§4.4） |
| 6 | **推送是加速，轮询是正确性来源** | 事件会丢、消费者会挂、新实例可能错过订阅。**只有轮询能给出静态可证明的上界**（§4.3） |
| 7 | **陈旧必须有界：版本号可以陈旧，但不得超过硬性最大年龄** | 缓存陈旧只导致一次旧判定；**版本视图无界陈旧会让实例误判自己仍然新鲜**，从而静默地长期使用旧权限——多副本下最难排查的失效形态 |
| 8 | **缓存键必须覆盖全部影响判定的维度** | 键不完整 = 越权。OpenFGA 在 v1.13.1 / v1.14.1 / v1.16.0 连续修了三个"两个不同请求产生相同 cache key → 复用旧结果"的授权绕过漏洞，SpiceDB 有同类漏洞——**全部发生在引入属性参与判定之后** |

**决策 7 与决策 2 是一体的**：允许缓存陈旧，前提是陈旧有上界；而有上界的前提是刷新周期已知且被强制执行。任何一条缺失，整个机制就是漏的。

## 四、机制分层

### 4.1 令牌形态决定撤销能力

| 形态 | 撤销能力 | 行业代表 |
|---|---|---|
| 自包含（JWT） | **差**——签发即定 | 被广泛误用 |
| 参考令牌（不透明串） | 好——每次校验回源 | OAuth2 Token Introspection |
| 自包含 + 吊销列表 | 中——需存储全部被吊销者 | OAuth2 Token Revocation |
| **自包含 + 版本号** | **好——O(1) 比对** | 通用最佳实践 |

**行业共识：自包含令牌不是会话。** 需要即时撤销时，必须在它外面挂一层可撤销状态，或改用参考令牌。

**这段取舍的标准出处是 RFC 7009 的 Implementation Note**：自包含、句柄回源、短寿命三选一，且 "which approach of token revocation is chosen will depend on the overall system design and on the application service provider's risk analysis"。本文选"自包含 + 版本号"。

### 4.2 判定架构

业界的经典划分（XACML 术语体系，ABAC 指南亦沿用）：

| 角色 | 职责 |
|---|---|
| **PEP**（策略执行点） | 业务侧拦截请求，向决策点索取判定 |
| **PDP**（策略决策点） | 执行判定 |
| **PIP**（策略信息点） | 供给判定所需属性 |
| **PAP**（策略管理点） | 变更入口——**失效可靠性的前提是入口唯一** |

集中式决策点的标杆是 **Google Zanzibar**，其核心贡献是**一致性令牌（zookie）**：写操作返回一枚令牌，读请求携带它，服务端保证"**至少**看到该写入之后的状态"。

**注意它的语义边界**：zookie 是**下界 / 单调性**语义——论文原话是 "at-least-as-fresh semantics, which allow Zanzibar to choose any timestamp fresher than the one encoded in a zookie"。它保证"不早于我上次写入"，**不保证"足够新"**。因此它解决的是"读己之写"，不是全局新鲜度。全局新鲜度在任一系统中都不由令牌提供，而由**刷新周期**提供（本文 §4.3）。

集中式决策点解决的是"权限模型复杂到单机缓存装不下"与"多系统需共享同一份授权真相"，**与时效无关**。

### 4.3 变更传播与缓存

**落地时最容易做错的一层。** 两件事必须分开看：**传播**（新版本如何到达各实例）与**缓存**（判定结果如何复用）。

**传播方式：**

| 方式 | 角色 | 说明 |
|---|---|---|
| **定期轮询（pull）** | **正确性来源** | 上界 = 轮询间隔，**静态可证明**。必须带抖动 |
| 变更推送（push） | **加速** | 把"最坏窗口"压成"常见情况"。会丢，不得作为正确性来源 |
| 事件广播（跨系统） | 加速 | 同上，见 §4.5 |

**轮询间隔必须抖动。** 固定周期会让全部实例在同一时刻醒来、同时打权威源——OPA 的轮询就是 `min_delay` / `max_delay` 构成的**随机区间**而非固定值，官方正是为避免这种同步惊群。

**缓存方式：**

| 方式 | 可靠性 | 说明 |
|---|---|---|
| **版本号进缓存键** | **高** | 变更时只递增版本号，旧键自然失效、由 TTL 回收 |
| 删除缓存条目 | **低** | 存在经典竞态：删除与并发读回填交错时，旧值被写回且**不再被任何失效动作触及** |
| 短 TTL | 中 | 仅用于**回收内存**，不作为陈旧上界 |
| 广播清本地缓存 | 中 | 存在进程内缓存（多级缓存）时必需 |

**版本号进缓存键是唯一没有失效竞态的**——因为它根本不需要"删除"这个动作。Zanzibar 正是这么做的：把快照时间戳编码进缓存键，避免复用来自不同快照的结果。

**三条必须同时满足的约束：**

**① 缓存键必须覆盖全部影响判定的维度。** 键不完整就是越权漏洞。OpenFGA 的三个漏洞（v1.13.1 / v1.14.1 / v1.16.0，官方定名 "cache-key delimiter injection … enables intra-store authorization-decision poisoning"）与 SpiceDB 的同类漏洞，根因全一致：**两个不同的判定请求产生了相同缓存键**。三者**都发生在属性（condition / caveat）参与判定之后**——即"低基数维度进键、高基数输入不进键"这个优化手法失手的典型形态。若采用该手法，必须能证明"被排除的输入不会改变判定结果"，并为此保留针对性回归测试。

**② 放行与拒绝的 TTL 应当不对称。** 拒绝需要更快地"重新尝试"。Kubernetes 授权 webhook 把两者分开配置，源码注释直言 "You generally want more responsive, 'deny, try again' flows"。对本文而言，这条**直接压缩 §5.5 中"推送丢失"的安全暴露面**：放行结果的 TTL 越短，陈旧放行的窗口越小。

**③ 并发同键请求必须合并。** 一次角色定义变更会让该角色的全部持有者同时失效（§5.1），这是天然的惊群。Zanzibar 用 lock table 让同键并发只有一个执行、其余阻塞；Facebook 的 memcache lease 用同一思路把峰值数据库查询从 17K/s 压到 1.3K/s。落地上就是单飞（single-flight）语义。

**陈旧上界的计算式：**

```
陈旧上界 = 轮询最大间隔 + 抖动上限
硬性最大年龄 = 陈旧上界（超过即视为不可信，见 §4.5）
```

推送成功时实际延迟远小于此值；**上界描述的是最坏情况，而它必须是可计算的**。

### 4.4 长连接

长连接（WebSocket / SSE / gRPC stream）建立后权限是冻结的，**这是最常被漏掉的一环**：很多系统 HTTP 侧做得扎实，长连接上却长期持有旧权限。

| 方式 | 适用 |
|---|---|
| 连接注册表 + 变更时主动断开 | 最常用。需外部存储维护「主体 → 活跃连接」 |
| **每条消息重新判定** | 订阅关系本身可变时**必须**采用（聊天室成员、协作文档权限） |
| 周期重校验 | 开销敏感且时效要求不高的折中 |

**反例是现成的**：SurrealDB 的 `LIVE SELECT` 在订阅注册时记录授权状态且永不刷新，用户被撤销或登出后仍以陈旧主体继续接收推送，官方公告的措辞是持续到 "the originating connection is closed"。**"机制已覆盖长连接"在没有显式处置时是假象。**

### 4.5 跨系统传播

权限变更以事件形式广播给各系统。但**事件只用于加速，不作为正确性来源**——事件会丢、消费者会挂、新系统可能错过订阅。正确性由各系统自身读路径的版本校验兜底。

### 4.6 中间件参与点

机制落到管道上，参与方与次序固定如下：

| 组件 | 位置 | 职责 |
|---|---|---|
| 限流中间件（粗粒度） | 最外层 | 界定"判定不可用"时的整体负载上限（此时身份未知，只能按 IP / 连接） |
| **认证中间件** | 管道第 1 层 | 校验令牌 + **比对身份纪元**（吊销维度） |
| **授权中间件（PEP）** | 管道第 2 层 | **比对本地版本视图 + 查缓存 + 回源**（新鲜度维度）——决策 2 的落点 |
| 限流中间件（身份粒度） | 认证之后 | 按主体 / 租户限流；此时身份已知 |
| 审计中间件 | 管道最内层 | 记录实际进入业务的请求——**授权失败另走安全审计通道** |

**装配次序：限流 → 认证 → 授权 →（身份限流）→ 审计。** 理由：

- **粗粒度限流最外层**——它要保护后面所有环节的计算成本，包括认证的密码学开销
- **认证在授权前**——授权需要主体标识；反序会出现"对匿名请求做权限判定"
- **身份粒度限流在认证后**——按主体限流需要先知道主体
- **审计在授权之后**——被拒绝的请求不产生**操作**审计

**审计必须分两条，否则会丢掉安全信号：** 操作审计（授权通过后，全量记录业务动作）与**安全审计**（认证 / 授权失败，独立通道 + 采样）是两件事。越权尝试是核心安全信号，把它当作"刷满存储的噪音"过滤掉是错的。Cerbos 的默认行为可作对照：审计默认记录**全部决策含拒绝**，只有显式配置才过滤。

**两处必须分开，合并必然出错：**

| 必须分开 | 理由 |
|---|---|
| 认证 vs 授权 | 失败语义不同——"我不知道你是谁"与"我知道你是谁，但你不能做这个"。合并后客户端无法区分"该去登录"还是"该去申请权限" |
| 身份纪元 vs 维度版本号 | 这是**两枚不同的版本号，存在于两个不同的键上**。做成同一枚，就会出现"改个权限把所有人踢下线"——即决策 4 明令禁止的过度反应 |

**降级方向：**

| 组件不可用 | 降级 | 理由 |
|---|---|---|
| 判定缓存 | 回源查询 | 缓存可重建，回源慢但正确 |
| 推送刷新 | 回退到轮询 | 推送本就只是加速（决策 6） |
| **推送与轮询都失败，但本地版本未超硬性最大年龄** | **继续用本地版本判定 + 告警** | 陈旧仍在承诺的上界内。此时拒绝服务是**白送的可用性损失**——与 §1.2"有界陈旧可接受"的前提直接矛盾 |
| 本地版本**超过**硬性最大年龄 | **fail-closed** | 此时已无法证明不陈旧 |
| 令牌 / 会话 / 纪元存储 | **fail-closed** | 放行等于吊销机制失效 |

**规则：能重建的（缓存）可降级回源；只是暂时变旧的（版本视图在年龄内）**继续服务并告警**；已无法证明的（超龄版本、纪元、会话）一律 fail-closed。**

行业对照：OPA 在 bundle 激活失败时"继续沿用旧 bundle 并通过 status API 上报失败"，Cerbos 官方明确 "update failures are silent by default, the client continues using the previously loaded bundle"。**"拿不到新策略"与"判定不出来"是两件事，前者应保持旧值 + 上报，后者才 fail-closed。**

**长连接是独立的另一层**——接入层的身份校验在语义上等价于认证中间件，但**只在连接建立时跑一次**。不在消息处理链上补判定，就必须在变更时主动断开（§4.4）。

**微服务下多出一个决策：判定在哪做。**

| 模式 | 形态 | 代价 |
|---|---|---|
| **本地判定 + 数据同步** | 授权服务把权限数据 / 版本号同步给各服务，各服务本地判定 | 延迟最低，需做数据同步——**行业主流** |
| 远程 PDP 调用 | 每个服务 RPC 调授权服务判定 | 口径唯一，但决策点进入每条请求的关键路径 |

Cerbos 官方对两种部署都有明确立场：中心 PDP 在集群内的网络跳转"typically sub-millisecond"，但它同时强调**单一一致的策略源**是安全要求。**微服务下 PEP 必然分散**，这一点没有选择余地。

### 4.7 服务清单与放置

多副本部署下，机制依赖以下组件：

| 组件 | 角色 | 关键要求 |
|---|---|---|
| **关系数据库** | 授权数据**与版本号的唯一权威源**，事务边界所在 | 变更必须在**同一事务**内完成"写权限数据 + 递增版本号 + 写 outbox"。数据库层要挡住旁路写入——任何绕过应用层的直接改库，都会让全部失效机制失效 |
| **进程内版本视图** | 每个实例持有「维度 → 版本号」的本地副本 | **必须带硬性最大年龄**（决策 7）。这是判定路径上唯一的版本来源 |
| **判定缓存** | 判定结果缓存，键含版本号 | 可随时清空；清空不产生正确性影响 |
| **纪元存储** | 身份通道的单调计数器 | 与会话 / 令牌状态同源。读取失败即 fail-closed |
| **广播通道** | 跨实例失效通知、长连接断开指令 | Pub/Sub 即可（决策 6：丢失由轮询兜底）。**仅当实例间不共享该通道时**才需要消息队列 |

**版本号放在关系库、与变更同事务，而不是放在内存存储。** 这一点决定了三件事：

- "递增版本号"与"写权限数据"是原子的，outbox 的语义成立
- 版本号天然与判定缓存隔离，**不存在"某次运维动作把版本号一起清掉"的风险**
- 版本号的读取必须走主库（不做读写分离）——但**它只在刷新时读，不在每请求读**，因此主库压力与请求量无关

**版本号用单调计数器，不得用时间戳。** 多实例时钟偏移会让"新版本"判成"旧版本"，表现为变更不生效且极难排查。行业里用时间戳的方案（Keycloak 的 `notBefore`）必须为此内置时钟偏移容忍（官方实现是 10 秒，上限 60 秒），并已出现多级值互相屏蔽的语义漏洞——**它们是这条约束的反证，不是替代方案。**

**消息队列不是必需项**：它只在"跨系统分发权限变更事件"时引入，而事件按 §4.5 只加速、不担正确性——**可以先不做，且不影响机制成立**。

**一个容易混淆的因果**：外置存储与跨实例传播的必要性来自**多副本**，不来自"立即生效"；集中式决策点的必要性来自**权限模型复杂度**（行级 / 关系型），不来自时效要求——在时效上它不比"版本号 + 本地判定"更强。

### 4.8 过渡期语义

多副本下有一个比"陈旧"更隐蔽的问题：**变更在各实例的到达时刻不同。**

推送逐实例送达，轮询逐实例唤醒——两者都不承诺原子切换。Istio 官方对此的表述是 "Istio can't guarantee that all workloads receive the new policy at the same time"；Casbin 用词是 "all enforcers eventually see the same policy"，并明确 dispatcher "only sync changes after init. They do not fix existing divergence"。

**后果**：传播窗口内，实例 A 已用新版本、实例 B 仍用旧版本，**同一个用户在两个实例上会被判出不同结果**。这是**不一致**，而不是陈旧——陈旧是全站一致地旧，至少语义统一；不一致则连"当前生效的是哪一版"都不可知。

**处置规则：**

- **窗口不得大于 §1.2 承诺的陈旧上界。** 传播机制不允许引入自己的、更长的窗口
- **降权类变更必须走窗口最短的通道**。窗口越短，"用户在 A 被拒、在 B 被放行"的概率越低。因此角色定义收紧（影响面大、扇出广）不应被放进紧急档——它的窗口天然更长
- **身份类事件走纪元通道**。纪元是**单个键**，传播面最小、可被所有实例以极短周期拉到，窗口最短。这是行业在紧急档一致选择"钝而小的键"的原因
- **禁止"新旧并存但语义未定义"**。如果某个场景既无法接受窗口、又无法走纪元通道，那么它需要的是重新审视权限模型（§8），而不是更快的缓存

**已知的取舍**：窗口不可能为零。本文不承诺原子切换——**行业里也没有先例**。

## 五、变更时序

§四 讲的是机制由什么构成，本节讲它们按什么顺序串起来——一次变更从提交到生效的完整视图。

### 5.1 两类变更必须先分叉

"更改用户的权限"在实现上是**两件不同的事**，传播路径与成本完全不同：

| | 场景 A | 场景 B |
|---|---|---|
| 动作 | 改**用户的角色**（给某人加/减一个角色） | 改**角色所含的权限**（给某角色加一个接口资源） |
| 影响面 | **一个用户** | **该角色的全部持有者** |
| 缓存维度 | 用户维度 | 角色维度（低基数） |

**"按低基数维度缓存"的价值全部体现在场景 B**——改一次角色定义只失效一条缓存，却覆盖全部持有者。若按用户缓存，改角色定义需遍历失效所有持有者，规模不可控。

**但场景 B 也是惊群的来源**：一次变更让该角色的全部持有者同时失效。因此 §4.3 的单飞（single-flight）不是可选项。

### 5.2 端到端时序（场景 B）

| 阶段 | 内容 |
|---|---|
| **1 · 落库** | 授权服务作为唯一变更入口（决策 3），在**同一事务**内完成：写关联表 → **递增该角色的版本号** → 写 outbox 事件 → 提交。此步之后**新权限已是真相**。注意是**递增版本号，而不是删除缓存**——没有删除动作，就没有删除竞态与删除失败 |
| **2 · 加速传播** | 向全体实例广播"角色 R 的版本已变"。各实例收到后，从**主库**读到新版本号，更新**本地版本视图**——**广播的语义是"通知版本变了"，不是"去删缓存"**，因此天然幂等、与到达顺序无关 |
| **3 · 兜底传播** | 广播丢失的实例，在下一个**抖动轮询**周期自行拉到新版本号。**这是陈旧上界的来源**（决策 6） |
| **4 · 长连接处置** | 持有该角色的用户，其已建立连接上仍是旧权限（§4.6 的独立层）。按目标连接是否承载需判定的动作决定：不动它 / 主动断开 / 每条消息重新判定。跨实例寻址依赖外置的连接注册表 |
| **5 · 下一次请求** | 认证放行（纪元未变）→ 授权按新的本地版本号拼键 → miss → 回源 → 新权限 → 判定。**"立即生效"的准确含义是"下一次请求生效"，且上界由阶段 3 保证** |
| **6 · 其他系统** | 事件广播给各系统，**只加速、不担正确性**（§4.5）——它们各自也要在读路径做版本校验 |

**阶段 2 与阶段 3 的关系是本文的要点**：推送决定"常见情况多快"，轮询决定"最坏情况多慢"。**只有后者是承诺**。

### 5.3 场景 A 的差异

改的是"用户 → 角色"绑定，影响面只有一个用户：

| 情况 | 后果 |
|---|---|
| 该映射**不缓存** | **零失效动作**——本就每次查，改完下次请求即是新值 |
| 该映射**缓存了** | 需要**用户维度**的版本号（与角色版本号是两个不同的键，决策 4） |

两种都常见。**若采用"全维度缓存 + 每维度各自版本号"，两个场景走同一套逻辑**，仅版本号粒度不同——这是最统一的做法。

**前提是各维度的优先级必须显式定义。** 多级版本号并存时"以哪一级为准"不能留给实现自由发挥：Keycloak 的 `notBefore` 在 realm / client / user 三级并存时曾出现 realm 级被 client 级屏蔽、导致撤销失效的漏洞。**规则应统一取"更严者"（即更新 / 更受约束的那一级）。**

### 5.4 不会发生的事

| 不会发生 | 依据 |
|---|---|
| **不会吊销令牌**、不会踢下线 | 决策 4（身份类事件除外，那走身份通道） |
| 不会打断正在处理的请求 | 判定发生在请求进入时，之后不再复查 |
| 不会刷新已建立的长连接 | 除非显式断开（阶段 4） |
| 不会刷新前端菜单 | 弱档；且**前端隐藏从来不是安全边界** |
| 不会原子切换 | §4.8：传播窗口客观存在 |

最后一条需强调：权限被撤销后**界面上可能仍显示那个按钮**，但点下去必然失败——服务端独立判定。**"界面还显示着"不是漏洞。** Slack 的官方架构与此一致：动作判定永远走权限服务做权威判定，客户端展示走边缘缓存里的**非权威副本**，官方明确承认展示层 "can't be authoritative due to the cache's temporal nature"。

**关于"在途请求"**：判定发生在请求进入时，之后不再复查。对中低档这是合理取舍；对**身份类事件（封禁、泄密响应）**，在途请求仍会带着旧身份跑完——**这是残余风险，需要在强档场景下对高危动作（批量删除、导出、改密）在提交点做一次复核。**

### 5.5 失败模式与可观测性

| 阶段 | 失败 | 表现 | 兜底 |
|---|---|---|---|
| 1 落库 | 旁路写入（绕过应用直接改库） | **永不生效** | 决策 3：变更入口收口 |
| 2 加速传播 | 广播丢失 | 陈旧一个轮询窗口 | **轮询兜底**（决策 6） |
| 2/3 传播 | 版本号发生时钟偏移 | **永不生效，无报错** | 用单调计数器，不用时间戳（§4.7） |
| 2/3 传播 | 版本号读自从库 | **永不生效，无报错** | 刷新时读主库（§4.7） |
| 2/3 传播 | 刷新持续失败且本地版本超龄 | 该维度不可信 | **硬性最大年龄 + fail-closed**（决策 7） |
| 3 长连接 | 未处理 | 该连接上权限长期有效 | 断开，或每条消息重新判定 |
| 缓存 | 缓存键遗漏判定维度 | **越权，且表现为"偶发"** | 决策 8：键完整性 + 回归测试 |

**其中三类仍是"永不生效且无报错"——这套机制坏掉时是静默的。** 决策 7 的硬性最大年龄把其中"刷新失败"一类从静默转为显式，但**旁路写入与键不完整仍然静默**。因此可观测性不是可选项：

| 观测项 | 要求 |
|---|---|
| 变更留痕 | 每次变更记录：变更人、时间、受影响的角色 / 主体、递增后的版本号 |
| **当前生效版本** | 每个实例此刻使用的各维度版本号——**这是"我生效到哪一版"的直接答案** |
| **上次成功同步时间** | 每个实例上次成功刷新版本视图的时刻——**超龄判定与告警的依据**。行业标准做法：OPA 的 status API 就上报 `active_revision` / `last_successful_download` / `last_successful_activation` / 失败原因，并可被健康探针查询 |
| **生效可验证** | 提供以指定主体复算权限的接口，供变更后自检与排障——**否则只能靠用户报障发现** |
| 缓存命中率 | 突变（持续 miss）意味着版本号在抖动；**长期高命中而在变更后不降，则意味着推送没到** |
| 拒绝率 | 放行 / 拒绝 TTL 不对称（§4.3）后，拒绝率是观察"是否在过度 fail-closed"的信号 |

**最后一项中的"长期高命中而在变更后不降"是这套机制少有的现成信号**——缓存命中率能反映"失效是否真的传播到了"。但它只是间接信号；**"上次成功同步时间"才是直接信号**，应当优先。

**历史审计不可缺**：授权变更记录必须**先归档再删除**。曾有真实公告（hexpm 的私有包越权漏洞）在修复时无法确认或排除历史越权，原因正是记录令牌签发行为的数据库行被日常清理任务删除、而访问日志不记录账号——**漏洞修完了，影响面却永远查不清。**

## 六、分档组合

同一套传播设施，按 §二 的三档取不同参数：

| 档 | 通道 | 组合 |
|---|---|---|
| **吊销** | 身份通道 | 主体 / 全局纪元 + 本地极短最大年龄（1–2 秒） |
| **强** | 判定通道 | 版本号进缓存键 + 推送 + 抖动轮询（1–2 秒）+ 长连接主动断开 + 变更入口唯一 |
| **中**（主流） | 判定通道 | 权限不进令牌 + 按低基数维度缓存 + 版本号进缓存键 + 推送 + 抖动轮询（5–10 秒） |
| **弱** | — | 短 TTL（60–120 秒）+ 前端事件刷新 |

**档位只决定参数，不决定组件集合**（吊销档多一枚纪元计数器，它是同一套设施里的一个键）。为不同档位各造一套组件是过度设计。

**规模再上一档**才需要集中式决策点——它解决的是"权限模型复杂到单机缓存装不下"与"多系统需共享同一份授权真相"，**而不是"立即生效"本身**。

## 七、边界

- **不为菜单 / 按钮可见性做强一致**——它是体验问题，前端隐藏从来不是安全边界，服务端必须独立判定
- **不用"踢下线"解决权限变更**——那是身份吊销的手段，二者维度不同（决策 4）
- **不依赖事件到达**保证正确性——推送只是加速（决策 6）
- **不追求绝对立即**——目标是可证明的陈旧上界（§1.2）
- **不在判定路径上做远程权威读**——那会把刷新成本乘以请求量（决策 2）
- **不承诺原子切换**——传播窗口客观存在，只承诺窗口有界（§4.8）
- **不引入集中式决策点**——当前规模未到；引入的触发条件见 §八
- **不讨论单副本场景**——在那里进程内缓存与内存版本号即可满足全部要求（§1.3）

## 八、何时重新审视

- 权限模型演化到**数据行级 / 关系型（ReBAC）**，单机缓存装不下
- 出现**多个系统需共享同一份授权真相**——各自实现的判定必然产生分歧
- **长连接开始承载需要判定的业务动作**，而非只有连接建立时校验一次
- 变更入口**不再唯一**（出现旁路写授权数据），决策 3 的前提瓦解
- **过渡期窗口被证明不可接受**——即 §4.8 的"窗口内不一致"造成了实际越权，此时需要的不是更短的轮询周期，而是重新审视权限模型
- 陈旧上界被证明**不可接受**（如合规要求给出明确的生效时延上界，且该上界小于当前档位）
