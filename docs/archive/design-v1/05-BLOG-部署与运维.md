# blog 博客系统 — 部署与运维

初稿：2026-09-11　·　最近更新：2026-09-16

## 一、部署形态

### 1.1 环境划分

| 环境 | 用途 | 编排方式 |
|---|---|---|
| 本地开发 | 单人调试 | Docker Compose 拉起依赖，服务本机进程运行 |
| 生产 | 对外提供服务 | 单机容器化 + Nginx 反向代理 |

依赖服务（MySQL / Redis / RabbitMQ / Nacos / MinIO 对象存储）在两种环境中**同构部署**，仅配置不同——避免"本地能跑、线上不行"。

**Redis 按角色拆分实例**：业务缓存与会话存储**不得混用**（见《02》§4.2）。本地与生产遵循同一拆分方式——本地可用同一实例的不同逻辑库近似，生产必须是**独立实例**且会话存储开启持久化，避免本地与线上在"这个库能不能清"这件事上行为不一致。

### 1.2 本地编排

Compose 编排**只负责依赖服务**（数据库、缓存、消息队列、注册中心），业务服务以本机进程运行，便于断点调试与热重启。

### 1.3 生产部署

五个服务容器 + 宿主机 Nginx：

| 类别 | 服务 | 说明 |
|---|---|---|
| 前端 | 管理后台、博客前台 | 容器内 Nginx 托管静态资源 |
| 网关 | 两个 HTTP 网关 | 对外接口入口 |
| 服务 | 核心 gRPC 服务 | 业务与数据 |

宿主机 Nginx 承担**域名分流、HTTPS 终止与接口转发**：`/api` 直接转发到读者端网关、`/admin-api` 转发到管理端网关，其余路径才导向前端容器。

**反向代理以宿主机 Nginx 为唯一真相源**。前端容器内**不配置**反代规则——接口与站点既然同机部署，容器内反代没有可转发的目标，只会成为与宿主机规则重叠、需要同步维护的死配置。若将来改为分机部署，再在前端容器内补规则，并同步下线宿主机侧的对应规则，**不允许两处并存**。

**内容缓存的落地细则**——这一层是《01》§2.6 读路径的第 ② 层，三条约定：

- **缓存键必须显式声明，不能沿用默认值。** 默认键包含完整查询串，`?utm_source=`、`?_t=` 这类跟踪参数会让同一份内容各占一份缓存，命中率被稀释；需按归一化后的参数生成键。**登录态请求整体不进内容缓存**，键中也不含 Cookie——否则缓存会按会话碎片化
- **微缓存兜底**：反代层用**独立的短 TTL（10 秒量级）**，**不服从上游的 `Cache-Control`**，并开启同键请求合并。10 秒的陈旧度已被《01》§1.1 的一致性目标允许，却能吸收绝大多数突发流量；若服从上游的 `s-maxage`，微缓存将形同虚设（见《01》§2.6）
- **禁止清空缓存目录**——整体清空会让全部请求瞬时回源，把后端打爆，且丧失单条清理能力。失效由《01》§2.6 的**内容版本号**承担，不靠删目录

**暴露缓存命中状态供排查**，仅在非生产或内网可见。

### 1.4 Kubernetes

提供完整的 K8s 清单作为**备选部署形态**，覆盖应用、数据库、缓存、消息队列、注册中心与日志收集。适用于需要多副本与自愈的场景；单机形态为默认。

**Redis 的按角色拆分在两种形态下都必须成立**（见 §1.1）——K8s 清单需分别声明业务缓存与会话存储，**不得共用同一实例**；后者另需持久卷，理由同 §1.1。

## 二、镜像与配置

### 2.1 镜像构建

**一个 Dockerfile 构建多个服务，通过构建参数区分**：

- 后端：构建参数指定**服务所在目录**，同一构建流程产出不同服务镜像
- 前端：构建参数指定**产物目录与后端地址**，同一构建流程产出两个前端镜像

**收益**：构建逻辑单点维护。新增服务只需增加一个条目，不改 Dockerfile。

**镜像命名统一前缀**，使一批服务在镜像仓库中自然聚拢，便于清理策略按前缀生效。

### 2.2 配置注入

**配置不打进镜像**，运行时经挂载卷注入：

| 挂载点 | 内容 | 变更频率 |
|---|---|---|
| 运行时目录 | 日志、缓存文件 | 高频写 |
| 配置目录 | 服务配置、证书 | 低频改 |

**收益**：换环境不必重新构建镜像；改配置重启容器即可生效。

**敏感配置**（数据库口令、注册中心凭据、第三方密钥）**只经运行时注入**，不进入代码仓库与镜像层。

### 2.3 配置分层

| 层 | 内容 | 存放位置 |
|---|---|---|
| 框架级 | 端口、日志、健康检查路径 | 服务配置文件 |
| 依赖级 | 数据源、缓存、消息队列地址 | 服务配置文件 |
| 运行时级 | 注册中心地址与凭据 | 容器启动参数 |

**注册中心地址走启动参数而非配置文件**——它决定了服务能否被发现，是"服务如何加入集群"的信息，与"服务内部怎么跑"分离。

## 三、发布流程

### 3.1 触发方式

**手动触发**，可选择构建哪些服务、部署哪些服务，二者独立：

- 支持只构建不部署（验证构建产物）
- 支持只部署指定服务（灰度或修复单个服务）
- 构建与部署**可分离**，因为镜像与部署目标不是一对一关系

### 3.2 构建

流水线按服务并行构建，每个服务独立推送镜像，**任一服务失败不影响其余服务**。

**门禁口径**（详见《[06 测试方案](06-BLOG-测试方案.md)》§三）：待推送镜像的服务**必须先通过该服务的编译与测试**。上面这句「不影响其余服务」指的是**并行构建中其他服务不被阻塞**，不是「测试失败仍可推送镜像」——两者是不同的断言，不要混读。

镜像标签采用**分支 + 提交 + 最新**三重策略，兼顾可追溯与"取最新"的便利。

### 3.3 部署

部署经 SSH 在目标主机执行：

```
拉取新镜像 → 停止并移除旧容器 → 以新镜像启动 → 健康验证 → 清理旧镜像
```

**关键决策**：

- **单机形态下一个服务一个容器**，容器名与服务名对应，重启即替换。**容器名由编排层分配，不写死为服务名**——否则同机无法运行第二份副本（见《01》§1.4 的扩容口径）
- **部署后健康验证**，失败则流水线失败——不让"启动了但没起来"的容器蒙混过关
- **自动清理旧镜像**，避免磁盘被历史镜像占满

**多副本时的停机问题**：上述流程是「停旧 → 起新」，**存在停机窗口**，且会同时作用于该服务的全部副本。当前单机单副本形态下该窗口即一次重启，可接受；**一旦某服务开始按副本扩容，此流程必须先改为逐副本替换（滚动），否则扩容反而放大停机影响**。

### 3.4 数据库迁移（硬约束）

**代码可回滚，schema 不可回滚**。这一不对称是回滚能否成立的前提，因此对迁移作出硬约束：**只允许向前兼容的变更**。

| 允许 | 禁止 |
|---|---|
| 新增表、新增可空列或带默认值的列 | 重命名 / 删除列或表 |
| 新增索引、放宽约束（如增大长度） | 新增非空且无默认值的列 |
| 在枚举末尾追加取值 | 修改列类型、收紧约束、调整枚举取值顺序或语义、复用已废弃取值 |

**理由**：单机形态无编排器托管版本历史，回滚 = 重新部署上一版本镜像。只要 schema 对**新旧两个版本同时兼容**，代码回滚就不必触动数据库；反之若迁移是破坏性的，回滚必然失败或丢数据。**该约束优先于任何单次变更的便利**——确需破坏性变更时，走「新增列 → 双写 → 迁移历史数据 → 下线旧列」的多版本流程，不一次性改掉。

### 3.5 回滚

回滚**不依赖流水线的自动回滚**，而是**重新部署上一版本镜像**：

- 镜像带提交标识，可精确定位历史版本
- 配置外置，回滚代码不影响配置
- schema 因 §3.4 的约束保持双向兼容，回滚不涉及数据库
- **回滚是运维动作而非流水线能力**——这是单机容器化形态下的合理取舍（无编排器托管版本历史）

## 四、可观测性

### 4.1 健康与指标

每个服务暴露**健康检查端点**与**指标端点**，供探针与监控采集，不占用业务端口。

### 4.2 日志

- **服务日志落文件**，写入运行时目录（挂载于宿主机），容器重建不丢日志
- **访问与操作日志入数据库**，供管理端查询与审计（见《03》§三）
- **K8s 形态下接入日志收集栈**，集中检索

三类日志**用途不同、去向不同**：服务日志排障、操作日志合规、访问日志分析。

### 4.3 告警

指标端点只有被**主动查询**才有意义，故障需要**主动推送**。告警规则按「用户可感知」筛选，不追求覆盖全部指标：

| 类别 | 触发口径（示例） |
|---|---|
| 依赖 | **§1.1 列出的全部依赖**（MySQL / Redis / RabbitMQ / Nacos / MinIO）不可达——**最高优先级**；会话存储不可达时服务按 fail-closed 拒绝全部请求（降级方向见《08》§四） |
| 可用性 | 健康检查连续失败、服务进程退出 |
| 错误率 | 5xx 占比超阈值 |
| 资源 | 容器内存 / 磁盘使用率超阈值、连接池耗尽 |
| 业务 | 关键路径（登录、发布）失败率异常 |

**告警必须有接收方**——未配置接收方的告警等于没有告警。

### 4.4 备份与恢复

生产为单机部署，**§1.1 列出的全部依赖与业务容器同机**——宿主机故障即全部数据同时不可用。备份不是可选的例行事项，而是这套部署形态的必要组成：

| 对象 | 内容 | 说明 |
|---|---|---|
| MySQL | 定期全量 + binlog | 业务实体的唯一权威源，**恢复优先级最高** |
| Redis 会话存储 | 快照 / 持久化文件 | **权威数据**（见《02》§4.2），丢失会使已吊销令牌复活。业务缓存**不在备份范围** |
| MinIO | 上传的二进制 | 对象存储，量大，按需全量 |
| 配置与证书 | 挂载卷内容 | 体积小，随版本管理 |

**必须定期做恢复演练**——未被验证可恢复的备份不构成备份。演练周期与责任人属运维规程。

### 4.5 数据清理

- 容器镜像按前缀定期清理（见 §3.3）
- 运行日志需轮转，避免无限增长
- 历史上传文件与过期数据需独立的清理策略——**属运维例行事项，但须明确：清理不得触及 §4.4 的备份对象，也不得清空 Redis 的会话存储**（见《02》§4.2）
