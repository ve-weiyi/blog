# 错误码设计规范

本文整理**错误码设计的行业通用做法与取舍依据**，供选型与设计评审参考。

外部依据：[RFC 9457 Problem Details for HTTP APIs](https://www.rfc-editor.org/rfc/rfc9457.html) · [Google AIP-193 Errors](https://google.aip.dev/193) · [Microsoft REST API Guidelines — Error condition responses](https://github.com/microsoft/api-guidelines/blob/vNext/graph/articles/errorResponses.md)

---

## 一、错误响应的分层

主流规范对此分工一致：**HTTP 状态码承载粗粒度类别，响应体里给一个细粒度、机器可读的错误标识**。

| | HTTP 状态码 | 机器可读的错误标识 |
|---|---|---|
| 回答 | 这个请求**能否被处理** | 处理**结果是什么** |
| 载体 | 状态行 | 响应体字段 |
| 取值 | 标准 HTTP 语义 | 由各规范自行定义 |

三种规范给这个标识起了不同的名字与形式：

| 规范 | 字段 | 形式 |
|---|---|---|
| RFC 9457 | `type` | URI |
| Google AIP-193 | `details[].ErrorInfo.reason`（**必填**） | `UPPER_SNAKE_CASE` 字符串 |
| Microsoft REST API Guidelines | 根级 `code`；具体原因放 `innererror.code` | camelCase 字符串 |

**为什么不能只有一层**：状态码是*类别*，同一状态下有客户端反应不同的多个原因。RFC 9457 因此要求客户端在 `type` 上分支；AIP-193 因此把 `reason` 定为必填，并明确写明**多个错误会共享同一个状态码**，控制流应依赖 `reason` 而非状态码。

**两条共同的硬约定**：

- 机器可读标识是**契约**——客户端依赖它做分支，因此必须稳定、可枚举、可文档化
- `message` 是**不稳定的**——面向开发者，用于调试。RFC 9457 明确写出客户端**不得**解析自然语言（`if (message.includes(...))`）来判断原因

## 二、标识取什么形式

三种主流形式，各有代价：

| 形式 | 采用方 | 优点 | 代价 |
|---|---|---|---|
| `UPPER_SNAKE_CASE` 字符串 | Google AIP-193、gRPC、AWS | 自描述、可检索、无需对照表 | 无结构化分类，分组需另行承载 |
| 数字 | Twilio、Cloudflare、国内多数框架 | 紧凑、可按区间归类 | **必须查表**；易与 HTTP 状态码撞值 |
| URI | RFC 9457 的 `type` | 机器可读 + 可直接指向文档 | 需要维护对外文档站 |

Microsoft 的做法把两者叠起来：根级 `code` 取 HTTP 状态描述的 camelCase（即冗余于状态行），具体原因放 `innererror.code`。该嵌套的动机是**规避"新增根级码即破坏性变更"**——它用层级换向后兼容空间。

**选择判据**：

- 有公开的错误文档站 → URI，或「数字 + 逐码文档 URL」
- 内部服务、或链路中存在 gRPC → 字符串（与 `ErrorInfo.reason` 同形）
- 仅当确实需要按区间归类时才用数字

**数字的两个隐性代价**，选型时容易被低估：

- **必须查表**——日志、看板、告警都要 join 一张对照表才能读出语义
- **代价会外溢**——数字派普遍要额外配一份逐码文档 URL 来补偿；而实际调用方往往还会退化成匹配错误文本判断原因（Cloudflare 的公开 Go 客户端即以 `strings.Contains(err.Error(), "81053")` 判错），这恰好是 RFC 9457 与 AIP-193 都点名禁止的反模式

## 三、业务错误挂哪个 HTTP 状态

业务失败用哪个状态码，有两种实践：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A** | 业务错误恒返回 HTTP 200，靠 body 的标识区分 | 调用方只需判别标识；监控不因"正常业务失败"误报 | 与 HTTP 语义不一致；网关 / 代理无法据状态码区分业务失败 |
| **B** | 业务错误返回对应状态码（资源不存在 → 404、无权限 → 403…） | 符合 HTTP 语义；网关、CDN、监控可直接利用 | 同一状态承载多义，监控侧需按标识二次过滤，否则把正常业务结果当故障告警 |

**选择依据是「有没有 CDN / 网关 / 代理依赖状态码做差异化处理」**：有则 B，无则 A。项目内必须全局统一，不得混用。

## 四、分类维度：按场景，不按模块

**按错误场景分类，而非按业务模块分类。** 同一标识可跨模块复用——"资源不存在"对用户、文章、评论一视同仁。

**分类依据是"客户端该如何反应"**，而非"服务端哪个模块抛出的"：

| 类别 | 场景 | 客户端应有的反应 |
|---|---|---|
| 成功 | 请求已正常处理 | 正常处理 |
| 流控 / 安全 | 请求过快、签名或时效不符 | 降速、重新签名、重新验证 |
| 请求参数 | 请求不合法 | 修正请求 |
| 身份认证 | 身份缺失或无效 | 补身份、重新登录 |
| 权限授权 | 有身份但无权限 | 引导用户 |
| 业务规则 | 请求合法，但业务上不成立 | 引导用户 |
| 服务端 | 服务端问题 | 重试或上报 |

**判据是「客户端该做什么」，而非「谁的责任」**——限流可明确归因于客户端，但客户端该做的是降速而非改请求，故归流控类。

**为什么不按模块分段**：

- 客户端拿到标识之后要的是"我该怎么反应"，**模块信息对客户端没有意义**
- 模块分段会逼出**大量语义重复的标识**：每个模块都要各备一套"不存在 / 已存在 / 状态不允许"，客户端的处理分支随之膨胀
- **模块划分会变，标识不能变**——一旦模块重组，模块分段就成了必须背下去的历史包袱

模块维度的区分应放在**细分标识**上：通用标识为 `RESOURCE_NOT_FOUND`，确需区分时再增 `ARTICLE_NOT_FOUND` / `ALBUM_NOT_FOUND`。这样分类骨架稳定，模块细分可按需增加。

数字方案的常见做法是把这一层做成**分段编号**（如 `A-BB-C`：1 位大类 + 2 位场景 + 1 位细分），使区间本身携带分类信息；改写为字符串时，分类改由文档分组承载。

## 五、码表示例

> 以下均为**示例**，用于说明组织方式与粒度，不是任何具体系统应采用的取值。

### 5.1 HTTP 状态码

常用子集与适用场景（完整定义见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)）：

| 状态码 | 语义 | 适用场景 |
|---|---|---|
| `200` | OK | 请求被正确处理 |
| `201` | Created | POST 创建资源成功，通常带 `Location` 头 |
| `204` | No Content | 操作成功且无响应体（如 DELETE） |
| `400` | Bad Request | 请求本身不合法：JSON 无法解析、参数类型不符、必填缺失 |
| `401` | Unauthorized | **未认证**——凭据缺失、无效或已过期。响应应带 `WWW-Authenticate` |
| `403` | Forbidden | **已认证但无权限**——身份有效，但无权访问该资源 |
| `404` | Not Found | 路径不存在，或目标资源不存在 |
| `409` | Conflict | 与资源当前状态冲突：已存在、状态不允许该操作 |
| `413` | Payload Too Large | 请求体超过服务端限制 |
| `422` | Unprocessable Content | 请求格式正确但语义不合法，典型是字段校验失败 |
| `429` | Too Many Requests | 触发限流，宜带 `Retry-After` |
| `500` | Internal Server Error | 未预期的服务端错误 |
| `502` | Bad Gateway | 上游返回无效响应 |
| `503` | Service Unavailable | 过载、维护中、熔断打开 |
| `504` | Gateway Timeout | 上游未在时限内响应 |

**三处常见分歧**：

- **`400` 与 `422`**——前者用于"请求根本读不懂"（语法层），后者用于"读懂了但不接受"（语义层）。只用 `400` 也完全可行，关键是在项目内统一
- **`401` 与 `403`**——判据是**身份是否已确认**，而不是"权限问题给哪个"。"令牌已过期"属 `401`（凭据无效）；"身份有效但无权"才是 `403`
- **`404` 与 `410`**——`410 Gone` 表示资源曾存在且明确不会回来。用它区分"已删除"与"从未存在"会泄漏信息（可被探测），多数系统只用 `404`

### 5.2 业务错误码：数字分段形式

以 `A-BB-C`（1 位大类 + 2 位场景 + 1 位细分）为例，区间本身携带分类信息：

| 码值 | 含义 | 说明 |
|---|---|---|
| `2000` | 成功 | `2xxx` 成功段 |
| `3000` | 请求过于频繁 | `3xxx` 流控与安全段 |
| `3010` | 请求被限流 | |
| `3030` | 请求签名无效 | |
| `4000` | 参数错误 | `4xxx` 客户端错误段 |
| `4010` | 参数缺失 | |
| `4020` | 参数格式错误 | |
| `4100` | 未登录 | `BB` 位细分场景：`41xx` 身份认证 |
| `4110` | 登录已过期 | |
| `4200` | 无操作权限 | `42xx` 权限授权 |
| `4300` | 资源不存在 | `43xx` 业务规则 |
| `4310` | 资源已存在 | |
| `5000` | 服务器内部错误 | `5xxx` 服务端错误段 |

**要点**：`C` 位为 `0` 表示该场景的**通用码**；确需客户端区分具体原因时才占用 `1–9`。大类段与「客户端应有的反应」（§四）对应，使客户端既可**按区间粗处理**、也可**按具体码细处理**。

**该形式的固有代价**（见 §二）：必须查表；且需额外规定"业务码不得与 HTTP 状态码同值"——`4100` 与 `410` 并列时，只看数字容易读错所属层级。

### 5.3 业务错误码：字符串形式

与 Google AIP-193 的 `ErrorInfo.reason` 同形：

| 标识 | 含义 | 类别 |
|---|---|---|
| `UNAUTHENTICATED` | 未登录 | 身份认证 |
| `LOGIN_EXPIRED` | 登录已过期 | 身份认证 |
| `PERMISSION_DENIED` | 无操作权限 | 权限授权 |
| `PARAM_INVALID` | 参数错误 | 请求参数 |
| `RESOURCE_NOT_FOUND` | 资源不存在 | 业务规则 |
| `RESOURCE_ALREADY_EXISTS` | 资源已存在 | 业务规则 |
| `RATE_LIMIT_EXCEEDED` | 请求被限流 | 流控 |
| `INTERNAL_ERROR` | 服务器内部错误 | 服务端 |

**要点**：标识自描述，**类别不编码进标识**——类别由文档分组承载，或交由 `ErrorInfo.domain` 一类的字段承载。命名取 `UPPER_SNAKE_CASE`、字母开头、上限 63 字符。

## 六、通用约定

- 客户端**只判断机器可读标识，不判断 `message`**——规范明确禁止解析 prose
- **HTTP 状态码仍是权威**，响应体不替代它：`401` 仍需 `WWW-Authenticate`，`429` 可带 `Retry-After`
- 错误响应**不透出内部细节**（堆栈、SQL、内部主机名、账号是否存在）；完整信息记服务端日志，并以 `trace_id` 一类字段关联返回
- 标识**只增不改**——已发布的不得改变含义、不得回收复用；含义变更等于新增标识
- 同一语义**不得有两个标识**；同一标识**可以**跨模块复用
